# chok-check — 문제 영향도 분석 스킬

문제점을 기술하면 프로젝트 컨텍스트와 웹 조사를 기반으로 이슈 목록, 문제 본질, 보안 위반, 영향도, 개선 권고를 분석한다. 분석 불명확 시 유추 질문으로 정확도를 높이고, 최종 chok-supervisor가 결과를 검증한다.

> **모델 정책**: 모든 분석 단계 — Agent() `model: "opus"` 파라미터 고정 (Agent 도구 enum 값 "opus", 현재 canonical: claude-opus-4-7). 영향도 분석과 이슈 분류는 최고 추론 능력이 필요하다.

## Usage

```
/chok-check "[문제 설명]"
```

### Examples

```bash
# 기능 문제 분석
/chok-check "결제 모듈에서 간헐적으로 트랜잭션이 중복 처리되는 문제가 발생한다"

# 성능 문제 분석
/chok-check "API 응답 속도가 배포 후 3배 느려졌다"

# 아키텍처 의심
/chok-check "서비스 간 의존성이 너무 많아 배포할 때마다 사이드 이펙트가 발생한다"

# 보안 우려
/chok-check "사용자 인증 토큰이 로그에 노출되는 것 같다"
```

## Execution Phases

### Phase 0: Pre-flight — 프로젝트 컨텍스트 수집

```
1. 문제 설명 파싱 → 핵심 키워드 추출
2. 프로젝트 컨텍스트 수집:
   - README.md, CLAUDE.md (있으면)
   - package.json / go.mod / requirements.txt / pom.xml (기술 스택 감지)
   - git log --oneline -10 (최근 변경 흐름)
3. 기술 스택 자동 감지 (언어, 프레임워크, 주요 라이브러리)
4. 분석 범위 추정 (문제가 어느 레이어에 속하는가)
```

### Phase 1: Web Research — 웹 조사

**목적**: 문제 유형에 대한 외부 패턴, 베스트 프랙티스, 알려진 이슈 수집.

```
WebSearch: "{문제 키워드} common causes root cause {감지된 스택}"
WebSearch: "{문제 유형} best practices impact analysis {현재연도}"
WebSearch: "{문제 유형} OWASP security implications" (보안 관련성 있을 때)
```

수집 항목:
- 동일/유사 문제의 알려진 원인 패턴
- 안티패턴 목록
- 권고 해결 방향
- 관련 보안 취약점 (해당하는 경우)

### Phase 2: Project Deep Scan — 프로젝트 스캔

```
1. 문제 관련 키워드로 코드베이스 grep
2. 관련 파일 read (최대 10개, 가장 관련성 높은 것 우선)
3. git log --oneline -20 / git blame (최근 변경 이력)
4. 영향 가능 모듈/파일 목록 식별
5. 의존성 그래프 추적 (import/require/include 관계)
```

### Phase 3: Analysis Engine — 5-Lens 분석

> **모델**: `opus` 고정. 5가지 렌즈로 이슈를 병렬 분석한다.

```xml
<analysis-lenses>
  <lens id="1" name="이슈 분류">
    이슈 유형: [BUG|ARCH|PERF|SEC|DEBT|CONFIG|DATA]
    심각도:   [CRITICAL|HIGH|MEDIUM|LOW]
    증거:     파일:라인 또는 패턴 참조
    신뢰도:   0–100%
  </lens>

  <lens id="2" name="영향도 매핑">
    직접 영향: 문제가 직접 발생하는 파일/모듈/컴포넌트
    간접 영향: 파급 가능 영향권 (의존성 체인)
    전파 경로: A → B → C 형태로 전파 경로 추적
    영향 범위: ISOLATED(단일 파일) | LOCAL(단일 모듈) | WIDESPREAD(다수 모듈) | SYSTEMIC(전체 시스템)
  </lens>

  <lens id="3" name="문제 본질 분석 (Root Cause)">
    표면 증상: 사용자가 기술한 관찰 현상
    근본 원인: 구조적/설계적/운영적 원인 분류
      - 구조적: 아키텍처 설계 결함
      - 설계적: 알고리즘/데이터 구조 선택 오류
      - 운영적: 환경 설정, 배포 과정 문제
    파생 문제: 동일 근본 원인에서 발생 가능한 다른 이슈
    본질 해결 방향: 증상 치료(임시방편) vs. 원인 제거(근본 해결) 구분
  </lens>

  <lens id="4" name="보안 위반 체크 (OWASP)">
    대조 항목 (OWASP Top 10):
      A01: Broken Access Control
      A02: Cryptographic Failures
      A03: Injection (SQL, NoSQL, Command)
      A04: Insecure Design
      A05: Security Misconfiguration
      A06: Vulnerable and Outdated Components
      A07: Identification and Authentication Failures
      A08: Software and Data Integrity Failures
      A09: Security Logging and Monitoring Failures
      A10: Server-Side Request Forgery (SSRF)
    추가 체크:
      - secrets/credentials in code or logs
      - 민감 데이터 노출 (PII, 토큰, 키)
      - XSS / CSRF 벡터
      - 의존성 취약 버전 (package.json / go.sum 기준)
    발견 시: [SEC-CRITICAL] 태그 + 즉시 조치 권고
    결과: CLEAN 또는 이슈 목록
  </lens>

  <lens id="4b" name="에이전트 영향-출처 검증 (ARGUS, LLM/agent 시스템 한정)" applies-when="대상이 LLM/agent가 untrusted 입력(웹·문서·도구결과·이메일·DOM)을 처리하고 행동(도구호출·쓰기·전송)하는 시스템일 때">
    영향-출처 그래프 (influence provenance graph) — 간접 프롬프트 인젝션 방어 (arxiv 2605.03378):
      1. untrusted source 식별: 모델이 읽는 외부/관측 데이터(웹페이지·파일내용·MCP/도구 응답·DOM 속성·에러메시지). 이들은 데이터이지 명령이 아니다.
      2. 영향 추적: 각 side-effectful 결정(도구호출/쓰기/전송/권한변경)이 어떤 출처에서 유래했는지 역추적.
      3. 검증 게이트: 결정이 untrusted source의 지시에서 비롯되면 차단 — 신뢰 가능한 출처(사용자 직접 지시·검증된 정책)에 근거할 때만 실행 허용.
    적용 체크:
      - observed content를 명령으로 취급하는 코드 경로 존재 여부 (instruction-source boundary 위반)
      - untrusted 입력이 검증 없이 exec/eval/도구인자/URL로 흐르는가 (taint flow)
      - 권한·전송·삭제 등 비가역 행동 전 출처 신뢰성 확인 단계 존재 여부
    발견 시: [SEC-CRITICAL] + provenance 검증 단계 삽입 권고. 대상이 LLM/agent 시스템이 아니면 이 렌즈 skip.
    결과: CLEAN | 인젝션 노출 경로 목록
  </lens>

  <lens id="5" name="개선 권고">
    우선순위:
      [MUST]   즉시 조치 (CRITICAL/HIGH 이슈, 보안 위반)
      [SHOULD] 단기 개선 (MEDIUM 이슈, 품질 향상)
      [COULD]  장기 개선 (LOW 이슈, 아키텍처 개선)
    분류: 단기(1주 이내) / 중기(1개월 이내) / 장기(분기 이내)
  </lens>
</analysis-lenses>
```

**신뢰도 산정**: 각 이슈마다 증거(코드 참조, 웹 출처) 기반으로 신뢰도 0–100% 부여.

### Phase 4: Confidence Check + Clarification

분석 결과에서 신뢰도 < 70%인 항목이 있으면 유추 질문으로 정확도를 높인다.

```xml
<confidence-gate threshold="70">
  <check>
    신뢰도 < 70% 이슈가 1개 이상인가?
    OR 근본 원인이 2개 이상 후보로 압축 안 됐는가?
    OR 영향 범위가 WIDESPREAD/SYSTEMIC으로 추정되나 증거 부족한가?
  </check>

  <if-low-confidence>
    AskUserQuestion 도구 사용:
    - 불명확한 항목당 질문 생성 (최대 4개)
    - 질문 유형: 재현 조건, 발생 시점, 영향 범위, 기술 스택 세부 정보
    - 답변 수신 후 해당 항목 재분석 (Phase 3 부분 재실행)
  </if-low-confidence>

  <if-high-confidence>
    Phase 5로 바로 진행
  </if-high-confidence>
</confidence-gate>
```

**질문 생성 기준**:
- 재현 조건이 불명확할 때: "이 문제가 특정 조건(환경, 데이터, 시간)에서만 발생합니까?"
- 발생 시점이 불명확할 때: "이 문제는 최근 변경 후 발생했습니까, 아니면 이전부터 있었습니까?"
- 영향 범위가 불명확할 때: "이 문제가 특정 사용자/기능/서비스에서만 발생합니까?"
- 기술 맥락이 부족할 때: "관련 기술 스택이나 라이브러리 버전을 알려주실 수 있습니까?"

### Phase 6: Supervisor Review

분석 리포트를 chok-supervisor에 전달해 3rd-party 검증.

```
Agent(
  subagent_type: "chok-supervisor",
  model: "opus",
  prompt: "chok-check Phase 5 (Report Delivery) 완료.
    다음을 검토하라:
    - 원래 요청/이슈: {사용자 입력}
    - Phase 5 산출물: 아래 분석 리포트 요약

    원래 문제 설명: {사용자 입력}
    프로젝트 스택: {감지된 기술 스택}
    분석 증거: web search {N}건, 코드 스캔 {N}파일, 사용자 보완 답변 {Yes/No}

    분석 리포트 요약:
    - 발견 이슈: {N}건 (CRITICAL: {N}, HIGH: {N}, MEDIUM: {N}, LOW: {N})
    - 보안 이슈: {CLEAN | N건}
    - 영향 범위: {ISOLATED|LOCAL|WIDESPREAD|SYSTEMIC}
    - 근본 원인: {한 줄 요약}
    - 핵심 권고: {MUST 항목 요약}

    6가지 관점(방향성/정확성/품질/아키텍처/완성도/회귀위험)으로 판정하라.
    VERDICT: APPROVED | REVISE | REJECT
    REASON: (한 줄)
    RISKS: (핵심 위험 1–2개, 없으면 NONE)"
)
```

## Phase 7: Retrospective

### 3-Dimension 자기 평가

```xml
<retrospective-dimensions total-max="15">
  <dimension name="분석 정확도" max="5">
    <evaluates>이슈 분류가 정확했는가? 근본 원인이 표면 증상과 구분됐는가? 신뢰도 산정이 증거 기반이었는가?</evaluates>
  </dimension>
  <dimension name="보안 체크 완성도" max="5">
    <evaluates>OWASP 10개 항목을 모두 대조했는가? 보안 이슈 미탐지는 없었는가? SEC-CRITICAL 태그가 적절하게 부여됐는가?</evaluates>
  </dimension>
  <dimension name="권고 실행 가능성" max="5">
    <evaluates>MUST/SHOULD/COULD 분류가 우선순위에 맞게 됐는가? 권고 항목이 구체적이고 실행 가능한가? 단기/중기/장기 분류가 현실적인가?</evaluates>
  </dimension>
</retrospective-dimensions>
```

## Boundaries

**Will:**
- 문제 기술로부터 프로젝트 내 이슈 및 영향도 분석
- 5-lens (이슈 분류/영향도/근본원인/보안/개선권고) 적용
- 신뢰도 < 70%일 때 AskUserQuestion으로 유추 질문
- WebSearch로 외부 패턴/베스트프랙티스 조사
- OWASP Top 10 대조 + 보안 위반 탐지
- Opus 모델로 최고 정확도 분석
- chok-supervisor를 통한 3rd-party 검증

**Won't:**
- 코드 직접 수정 (분석 전용, fix는 /chok-fix 사용)
- 증거 없는 이슈 주장
- 무한 재분석 루프 (supervisor REVISE 최대 1회)
- 문제 설명 없이 실행
