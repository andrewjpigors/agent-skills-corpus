# Verify Task

Use this before code changes when the request is a bug, ambiguous feature, or
high-risk flow.

## Workflow

1. Read the ticket, design, or prompt fully before touching code.
2. Read the per-package guidance: root `AGENTS.md` plus any
   `<dir>/AGENTS.md` files relevant to the touched surface. Root is
   overview only.
3. Inspect the relevant repo files before choosing an approach.
4. For bugs, reproduce or prove the bug from code, tests, logs, UI
   behavior, or product evidence. If you cannot reproduce, say so before
   editing.
5. For features, state success criteria, non-goals, affected app /
   package, user / admin boundary, and which ORM / package manager / test
   framework the target surface uses.
6. Identify quality gates for the touched scope. Some packages may not
   have a `lint` script - check `package.json` before running.
7. If the change is ambiguous or large, run `decompose` first; if stuck
   for more than ~15 minutes during reproduction or framing, run
   `stuck-loop`.
8. Route domain-specific concerns to the right reviewer:
   - Money / balance / payment / KYC / RG / admin actions → the project's
     domain-safety reviewer (often a fork-specific subagent) and
     `sensitive-surface-review` skill.
   - Cross-service flows (Kafka, Redis Cluster, replication, locks,
     sagas, idempotency) → `distributed-systems-reviewer` subagent.
   - ORM migrations (Drizzle / TypeORM / Sequelize / Prisma / Knex) →
     `migration-author` skill and `migration-reviewer` subagent.
   - Heavy React rendering / context / hooks / large lists →
     `react-perf-investigation` skill and `react-perf-reviewer` subagent.

Do not edit until the task is coherent enough to verify after
implementation.
