# Bugfix

You're in maximum-rigor mode. Your job isn't to make symptoms go away. It's
to (a) understand the causal discrepancy between desired and observed
behaviour, (b) fix the root cause at the layer it originated, (c) prove the
fix with a reproducer that initially failed for the right reason and now
passes, (d) update any documentation the discrepancy revealed to be wrong
or absent, and (e) survive a hostile adversarial review.

You won't declare success until every gate below is PASS with cited
evidence. Premature victory is this skill's cardinal failure mode.

**Argument hint:** `[bug summary, issue ref, or "investigate <symptom>"]`

## Quick Start

Two invocation paths. Pick based on what the user gave you.

**Path A — Specific direction.** User says something like "fix this auth
bug, here's the stack trace" or "investigate the timeout regression in
worker-3" or "check the logs in /var/log/svc-auth/ for the 500s." You:

1. Skip Phase 0. Go straight to Phase 1.
2. Emit a `## Bug statement` block (expected, observed, environment,
   smallest triggering input, regressed signal) from the user's input.
3. Run Phases 2 through 9 normally.

**Path B — General invocation.** User says something open like "run a
bugfix pass" or just invokes the skill with no specific target. You:

1. Run Phase 0 — Bug Discovery. Proactively scan logs, code, docs, recent
   git history, and the issue tracker. Build a prioritised candidate list.
2. Pick the highest-priority candidate (security / correctness > drift >
   code quality). Don't ask the user "what should I fix?" — that's lazy
   and the whole point of this path is autonomous discovery.
3. Emit the Bug statement for the chosen candidate. Proceed to Phase 2.
4. **Only ask the user when:** discovery surfaced multiple roughly-equal
   candidates AND the priorities can't be objectively ranked, OR no
   candidates were found at all (in which case report `## No bugs found`
   with evidence of what you searched).

In both paths, if you catch yourself reaching for "should work" or
"looks right," you haven't collected the evidence the gates require. Go
back, find the citation, then state what the evidence actually shows.

## When to Use This Skill

Trigger on any of these — even when the user hasn't asked for rigour
explicitly:

- A defect, regression, or "this is broken" report (any phrasing).
- "User reports," "logs show," a stack trace, a Sentry / Linear / GitLab
  issue reference.
- "The spec says X but the code does Y" — drift between artefacts.
- A partial or unfinished feature where acceptance criteria aren't met.
- Anything touching auth, crypto, supply chain (SLSA / SBOM / provenance),
  concurrency, persistence, or a trust boundary — these always warrant
  the full gate sequence.
- A failing test, even one labelled "flaky" — flakiness is itself a bug.
- A general invocation like "run a bugfix pass," "find me something to
  fix," "check this project for bugs," or the skill being invoked with no
  specific target. In these cases, Phase 0 runs autonomous discovery.

## The fixed reasoning structure

```
0. Discovery          — (general invocation only) scan logs/code/docs/git
                        for candidates; pick highest priority
1. Intake             — restate bug; expected vs actual; environment
2. Context gathering  — code, logs, docs; AskUserQuestion only if needed
3. Reproducer first   — failing test that fails for the right reason
4. Causal analysis    — three-way diff; >=3 hypotheses; falsify each
5. Structural fix     — minimal change at the originating layer
6. Verification       — all test layers green; mutation-test the fix
7. Documentation      — delegate ADR / spec / threat-model / story updates
8. Adversarial review — hostile reviewer; cold-context re-derivation
9. Definition of Done — literal checklist with cited evidence
```

Phase 0 runs only when the user invoked the skill without a specific
target. With user-given specifics, jump straight to Phase 1.

After every phase, emit:
`GATE <n> (<name>): PASS | FAIL | PENDING — evidence: <citation>`

A skipped or unjustified gate counts as FAIL.

## Phase 0 — Bug Discovery (general invocation only)

Skip this phase if the user gave you a specific bug, issue reference, log
file, or class of bugs to look at. Otherwise: run discovery before
anything else. Asking the user "what should I look at?" is forbidden in
this phase — that's the failure mode this phase exists to prevent.

Run these scans in order. Each one contributes candidates to a shared
list. The full pattern catalogue (commands, regex examples, prioritisation
heuristics) lives in
[references/bug-discovery.md](references/bug-discovery.md).

### 0a. Recent activity scan

- `git log --since="2 weeks ago" --grep="fix\|revert\|hotfix\|broken\|regression"`
  — recent bug-shaped commits often surface adjacent unfixed cases.
- `git log --since="2 weeks ago" -- '**/*.lock' '**/Cargo.toml' '**/package.json'`
  — recent dependency bumps (potential SLSA regressions or breaking changes).
- `git log --diff-filter=D --since="2 weeks ago" -- '**/tests/**'`
  — recently deleted tests. Suspicious unless paired with a replacement.

### 0b. Log and issue tracker scan

- Project-local logs: `find . -name '*.log' -mtime -7`, then `grep -E
  'ERROR|FATAL|panic|SIGSEGV|unhandled'` and look for repeating patterns.
- Issue tracker: `gh issue list --label bug --state open --limit 20` (or
  `glab issue list --label bug --state opened`).
- Sentry / Linear references mentioned in `TODO`/`FIXME` comments.

### 0c. Code smell scan

- `rg -n 'TODO|FIXME|XXX|HACK' --type-add 'src:*.{rs,py,c,h,go,ts,js}' -tsrc`
  — comments flag known-bad code.
- `rg -n '\.unwrap\(\)|\.expect\(' --type rust`
  — unwraps without `// SAFETY:` or contextual justification.
- `rg -n 'except Exception:|except:\s*pass' --type py`
  — exception swallowing in Python.
- `rg -n 'TODO: security|FIXME: auth|HACK: skip' -ti`
  — security / auth / authz comments are top-priority candidates.

### 0d. Drift scan

- For each ADR in `docs/adr/` or `docs/decisions/`, check the referenced
  code still exists and matches the decision. ADR-described behaviour
  that the code no longer implements is a drift bug.
- For each spec in `specs/` or `docs/specs/`, check that referenced test
  files exist and pass.
- For each `THREATMODEL.md` mitigation, check that the cited control's
  still in the codebase.

### 0e. Test-suite health scan

- Run `cargo nextest run` / `pytest -x --tb=no -q` and capture any
  flakes, ignored tests, or slow tests.
- `rg '#\[ignore\]|@pytest.mark.skip|xfail' --type rust --type py`
  — skipped tests that may hide live defects.
- **Mutation-survivor scan** — first check `.test-effectiveness/baseline.json`
  and the latest `iter-NNN/delta.json`; when the runtime harness (built via `harness-builder`)
  produced them, every surviving mutant is already enumerated and
  Haiku-triaged. When absent, run `cargo mutants --in-diff <(git diff
  HEAD~10) --json` (or `mutmut`/Stryker/go-mutesting/mull for non-Rust).
  Surviving mutants on recently-changed code are latent defects: the
  test suite can't tell whether the line is correct. Treat each
  surviving mutant as a candidate — they're bugs that haven't
  manifested yet but will. The harness's `triage-verdict.json` may
  already classify a surviving mutant as `stub-implementation` or
  `dead-code`; respect that classification when scoping the fix (see
  [references/reproducer-and-mutation.md § Part 4b](references/reproducer-and-mutation.md)).
- **CRAP-score scan** — same precedence: read
  `.test-effectiveness/baseline.json` first. When absent, run
  `cargo llvm-cov --lcov --output-path lcov.info && cargo crap --lcov
  lcov.info` (Rust, cargo-crap pinned to v0.2.0 with hand-computed
  fallback); equivalent flow for other languages
  (`.claude/rules/static-analysis.md`). Anything above 30 is dangerous
  undertested complexity — score the file as a candidate even without
  an active error report, because a future change to it is likely to
  introduce a real bug.

### 0f. Candidate prioritisation

Score each candidate on:

1. **Security impact**: touches auth / crypto / supply chain / trust
   boundary / PII? → **P0**.
2. **Correctness impact**: causes wrong output, data loss, or silent
   failure? → **P0**.
3. **Drift / spec gap**: documented behaviour that code doesn't honour →
   **P1**.
4. **Quality / known-bad code**: `TODO` / `FIXME` / unwrap / swallowed
   except → **P2**.
5. **Test hygiene**: skipped / flaky / slow tests → **P2**.

Emit a `## Discovery candidates` block listing the top 6-8 candidates with
scores, sources (file:line, log line, issue ID), and a one-sentence reason.
Pick the top-scored candidate as the target.

### 0g. Tie-breaking

If two or more candidates tie at P0 with no objective priority between
them, AND running both in sequence would take more than a single bugfix
session, THIS is the one time you may call `AskUserQuestion` with the
candidates as multiple-choice options. Otherwise pick the one with the
most concrete reproducer signal (a stack trace beats a `TODO` comment).

### 0h. No candidates found

If discovery returns nothing after all five scans, emit:

```
## No bugs found

Scans performed:
- git log --since="2 weeks ago" --grep="..." → 0 matches
- find . -name '*.log' --mtime -7 → 0 files
- gh issue list --label bug → 0 issues
- rg TODO/FIXME/XXX/HACK → 0 matches
- ADR / spec / threat-model drift check → 0 drift
- Test suite → all green

This is either a remarkably clean codebase or the scans missed something.
Ask the user whether to widen scope (older history, broader patterns)
or stand down.
```

Don't fabricate a candidate to fill the gap.

`GATE 0: PASS` (when run) requires: at least four of the five scans
executed with results captured, prioritised candidate list emitted,
target candidate named with rationale.

## Phase 1 — Intake

Output a `## Bug statement` block with exactly:

- **Expected**: one sentence, in domain language.
- **Observed**: one sentence, with the exact error or symptom signature.
- **Environment**: OS, toolchain version, relevant feature flags,
  branch / commit.
- **Smallest known triggering input**: literal value or steps.
- **Regressed signal**: per Google SRE — Latency / Errors / Traffic /
  Saturation, or USE on a resource.

If any field's unknown:

- **In Path A (user-given specifics)**: try Phase 2's context-gathering
  ladder first (read the code, logs, docs). Only fall back to
  `AskUserQuestion` when at least one of Phase 2's escalation criteria's
  met — see below.
- **In Path B (Phase 0 discovery)**: derive the field from the discovery
  evidence. The candidate's source (log line, file:line, issue ID)
  provides Observed; the ADR / spec / docstring provides Expected. Don't
  ask the user — your job is to surface what you found, not pass the
  question back.

`GATE 1: PENDING` only persists if Phase 2 also can't resolve the gap.

## Phase 2 — Context gathering

Follow this ladder in order. Escalate only when the prior rung's exhausted
with a documented negative result.

1. **Code**: Grep / Glob for the symptom's call site; Read the file and
   each callee on the failing path. Stop when you can narrate the path
   line-by-line.
2. **Logs / traces**: Find log lines or spans matching the symptom. For
   distributed systems, follow `trace_id` across services through the
   transport's `traceparent` header. See
   [references/observability-debug.md](references/observability-debug.md)
   for the log→trace→reproducer pipeline.
3. **Docs**: Locate (a) the user story or acceptance criteria, (b) ADRs in
   `docs/adr/` or `docs/decisions/`, (c) `THREATMODEL.md` or
   `docs/security/`, (d) inline docstrings on the touched modules, and (e)
   `CLAUDE.md` for repo conventions. Summarise each as "states X" or
   "silent on this."
4. **User clarification (AskUserQuestion)**: invoke only when at least one
   of these holds:
   - Two or more plausible interpretations of *Desired* behaviour survive
     after doc review.
   - Spec contradicts itself or contradicts an ADR.
   - The fix would touch a trust boundary, auth path, persistence schema,
     or inter-process protocol — confirm the intended invariant.
   - Reproducer attempts have repeatedly produced the wrong failure mode.
   - The bug report's a single sentence with no example input.

   `AskUserQuestion` must offer concrete multiple-choice options. Example
   for ambiguous-desired: `(a) Treat empty list as success`, `(b) Treat
   empty list as error`, `(c) New configurable behaviour, default error`.

**Context-sufficiency self-check** (emit literally):

```
CONTEXT CHECK:
- Code path read end-to-end?   yes / no — files: <list>
- Relevant logs / traces seen? yes / no — sources: <list>
- Spec / ADR / TM / AC located? yes / no — paths: <list>
- Desired behaviour unambiguous? yes / no
```

Any `no` blocks Phase 3.

## Phase 3 — Reproducer first

Write a test that reproduces the bug **before** any production-code fix.
The test must:

1. **Initially fail** on the current (broken) tree. Run it, capture the
   verbatim output.
2. **Fail for the right reason** — pin the specific error type, message
   substring, and post-state. Never `assert is_err()` alone, never bare
   `pytest.raises(Exception)`.
3. **Catch the bug class**, not just the literal input. If the defect's
   parameterised (range of inputs, set of states), add parametrise or
   table tests OR a property-based test. One example isn't enough.
4. **Sit at the right pyramid layer** (unit / component / workflow /
   property). See [references/test-pyramid.md](references/test-pyramid.md)
   for the decision tree plus templates in Rust and Python.

The full reproducer-quality protocol — pinning failure modes, the
revert-and-rerun check, flaky-reproducer handling, anti-pattern table — is
in [references/reproducer-and-mutation.md](references/reproducer-and-mutation.md).

Emit a `## Reproducer` block citing the file, test name, exact invocation
command, and verbatim failing output.

`GATE 3: PASS` requires: red-on-broken-code confirmed; expected error
signature matched; pyramid layer justified in one sentence.

## Phase 4 — Causal analysis

### 4a. Three-way diff

```
Desired:     <one sentence; cite spec / AC, or USER if from chat>
Documented:  <one sentence; cite ADR-NNNN / docs/...:line / "silent">
Implemented: <one sentence; cite file:line>
Classification: [code-defect | doc-defect | spec-gap | ADR-gap |
                 threat-model-gap | drift]
Authoritative source: [code | AC | ADR-NNNN | threat-model | user-decision]
```

Decision matrix:

- Doc = Desired, Impl differs → code defect; patch the code.
- Doc = Impl, Desired differs and there's a clear authority → stale doc;
  update doc, code may not change.
- Doc = Impl, Desired differs and authority's unclear → spec / UX defect or
  new requirement. **Stop. Negotiate via AskUserQuestion before any code
  change.**
- All three differ → drift; surface and require human alignment.
- Doc silent → spec gap; write the failing executable example, get
  sign-off, then implement.
- Doc contradicts itself → resolve the doc first.

### 4b. Hypothesis enumeration (≥3)

For each hypothesis, emit:

- **Mechanism**: one sentence of causal claim.
- **Confirming evidence sought**: what you looked for AND whether you found it.
- **Disconfirming evidence sought**: what would *falsify* this AND whether
  it appeared.
- **Verdict**: surviving / falsified / inconclusive.

The chosen root cause must explain ALL observed symptoms, not just the
loudest. If only one hypothesis survives, search harder before committing —
a lone survivor often reflects confirmation bias, not truth.

### 4c. Rubber-duck trace

Before proposing a fix, narrate the suspect code line-by-line with the
expected value at each step. State the precise line where reality diverges
from expectation. Mandatory even when the bug "looks obvious" —
overconfident pattern-match is the top source of cosmetic fixes.

`GATE 4: PASS` requires: filled three-way diff, ≥3 hypotheses with
falsification searches logged, surviving hypothesis explains every symptom,
line-by-line trace identifies the divergence line.

## Phase 5 — Structural fix

### 5a. Layer check

Does your fix change code at the layer the bug originated? A fix in the
caller for a callee's bug is symptomatic. Name the originating layer and
the patched layer; if they differ, justify or relocate.

### 5b. Structural-vs-cosmetic audit (Ousterhout heuristics)

Score each yes / no with citation:

1. Does the diff change a function signature, type, trait / interface, or
   message contract?
2. Does the diff DELETE code that handled cases the new invariant makes
   impossible?
3. Does the new code add `try/except`, broad catch, `.unwrap_or_default()`,
   `.ok()`, or wrap a call in `if err.kind() == ...`? [Y → cosmetic flag]
4. Could a small perturbation of the failing input still trigger the
   symptom? [Y → cosmetic flag]
5. Does the fix make the previously-bad state unrepresentable in the type
   system (Option→T, newtype, narrowed enum, NonEmptyVec, sum types)?
6. Is the fix accompanied by an L4 property test, not just an example?
7. Does the commit message name the violated invariant and where it's now
   upheld?
8. Does the fix add a special-case `if x == <reported-value>` branch?
   [Y → cosmetic flag]

Four or more structural Yes → proceed. Mostly cosmetic flags → return to
Phase 4 and search for the underlying invariant.

### 5b.1. Cache, concurrency, and process-identity anti-patterns

When the fix touches caching, concurrency, or process liveness, run
this short checklist on top of the Ousterhout audit. Each item names
a bug pattern that's burned us before:

- **Sentinel-default conflates unrelated states.** If your "no data"
  path returns a literal string / int / well-known value the caller
  can mistake for real data, two distinct no-data scenarios collide
  into a single key/hash/decision. Type-level alternative: return
  `Option<T>`, `Result<T, E>`, or a sum type (`Cacheable(_) |
  Uncacheable(_)`) the caller MUST destructure. Worked example:
  SPEC-004 C-001 — `code_fingerprint` returned `"no-head"` for every
  non-git workdir; the composite sha256 then collapsed across
  unrelated projects. Fix swapped the return type to
  `Option<String>` and the caller to `CacheKey::{Cacheable,
  Uncacheable}`. PR/commit `add7a8d`.

- **PID-keyed liveness without an identity pin.** Process IDs are
  recycled by the kernel. `kill(pid, 0).is_ok()` is true both for the
  original holder AND for any unrelated process that's inherited that
  PID later. Reliable POSIX liveness requires recording a per-process
  identity that survives PID reuse — `/proc/{pid}/stat` field 22
  (start time in clock ticks since boot) is the standard pin on
  Linux. Worked example: SPEC-004 C-003 + commit `40ee09d`.

- **EPERM is not "dead".** `kill(pid, 0)` returns `Err(EPERM)` when
  the process exists but is unsignalable from your uid (cross-uid
  containers, hardened LSM policy, etc.). Code that maps EPERM →
  dead reaps live holders. Liveness checks MUST distinguish ESRCH
  (truly gone) from EPERM (alive but unsignalable). Worked example:
  SPEC-004 C-004 + commit `40ee09d`.

- **Defensive-fallback direction depends on what you're protecting.**
  `match result { Err(_) => true }` embeds an assumption that "true"
  is the safe direction. It isn't always — for a capacity bound,
  "keep slot on error" is the UNSAFE direction (ghost-holds
  capacity). For availability, "drop request on error" is the unsafe
  direction. Pick the direction that protects the invariant you
  named in 5b question 7; don't default to the path of least
  resistance. Worked example: SPEC-004 C-005 + commit `40ee09d`.

- **Specs that promise universal canonicalization across multiple
  tool grammars.** "Sort flags alphabetically", "normalize paths",
  "canonicalize URL forms" — these claims usually look universal but
  depend on per-tool argv/syntax grammars the spec doesn't ship.
  Implementation then either silently drops the claim (drift) or
  implements something unsafe. Specs MUST name the grammar boundary
  the canonicalization assumes, OR scope the claim to the specific
  tools where it's safe. Worked example: SPEC-004 C-002 — spec
  promised flag sorting that would have corrupted `cargo test --
  --nocapture` and `pytest -k "expr"`; amended spec to match
  verbatim-with-trim behaviour. Commit `40ee09d`.

### 5c. Scope discipline (blast-radius rule)

The diff must stay within the discrepancy's blast radius. New unrelated
refactors, dependency bumps, formatting churn, opportunistic cleanups —
forbidden in this commit. If you find an adjacent issue, record it under
`## Out of scope` and continue.

### 5d. Sibling-case sweep

Before committing, grep for structurally similar call sites of the changed
function or symbol, plus any pattern that resembles the failing input.
Enumerate each sibling and decide explicitly: same fix needed, or not, with
a one-sentence reason. This catches the SWE-bench failure mode of fixing
only the literal case in the issue.

`GATE 5: PASS` requires: layer check named, structural audit ≥4 Yes,
blast-radius respected, sibling sweep documented.

## Phase 6 — Verification

### 6a. Reproducer revert-and-rerun

Apply the fix → reproducer goes green. Revert ONLY the fix → reproducer
goes red with the same predicted error. Re-apply. Emit both outputs
verbatim. A test that doesn't go red on revert is exercising the wrong
code path; return to Phase 3.

### 6b. Pyramid run

Run every applicable layer, citing the command and pass / fail counts. See
[references/test-pyramid.md](references/test-pyramid.md) for the standard
commands per language. Any failure outside the reproducer = regression.
Investigate. Don't touch the failing test to make it pass.

### 6c. Mutation testing on changed lines

Every mutant on the fix must be **caught** by some test. Surviving mutants
on patched lines mean the suite doesn't actually exercise the fix. Add a
test that kills each survivor, or return to Phase 3. The full runbook
(`cargo-mutants`, `mutmut`, scope, timeout handling, output reading) is in
[references/reproducer-and-mutation.md](references/reproducer-and-mutation.md).

### 6d. Lint / format / type gates

Run the project's lints, formatters, and type checkers as strict gates on
touched modules. Warnings count as errors on the lines you changed.

### 6e. Verification through `noelle-harness verify run`

WHERE `noelle-harness` is on PATH, every verification command in this
phase — reproducer runs, pyramid layers, mutation scans, lints, type
checkers, formatters — MUST be invoked through `noelle-harness verify
run --profile <lang> -- <command>`. Direct invocation of `cargo`,
`go`, `pytest`, `tsc`, etc. for verification work is a **`verify-
bypass` finding** and causes the adversarial reviewer in Phase 8 to
reject the fix outright. There is no `--allow-bypass` escape hatch
(SPEC-004 NFR-HARN-006).

Why: parallel bugfix subagents in `bug-burndown` share a tiered slot
semaphore that bounds heavy compile/test concurrency by RAM. They
also share a verify-result cache so identical commands at the same
worktree HEAD sha don't repeat work. Both mechanisms only fire when
verification goes through `verify run`.

Language-to-profile mapping:

| Language     | `--profile`  | Common tiers |
|--------------|--------------|---------------|
| Rust         | `rust`       | check/clippy/fmt → cheap, build -p → medium, test/nextest → heavy |
| Go           | `go`         | vet/staticcheck → cheap, build pkg → medium, build/test ./... → heavy |
| C / C++      | `c`          | cppcheck/clang-tidy → cheap, make obj → medium, make check/ctest → heavy |
| Python       | `python`     | ruff/mypy/pyright → cheap, (no medium), pytest/tox → heavy |
| TypeScript   | `typescript` | eslint/tsc --noEmit → cheap, vite/tsc build → medium, vitest/jest → heavy |
| anything else| `<name>`     | falls back to all-heavy classification (FR-HARN-008.1) |

The profile auto-classifies the command into a tier. Pass `--tier
<cheap|medium|heavy>` only when you need to override (rare). For
narrow reproducer runs that name a specific test, pass `--tier cheap`
or `--tier medium` if you're confident the work fits — the reviewer
won't flag an explicit downgrade, only a bypass.

**Narrow verification first.** If a log line pinpoints
`noelle-graph::tests::vuln_query::handles_empty_set` as the failing
test, your verify run is:

```bash
noelle-harness verify run --profile rust --tier heavy --holder bugfix:BUG-001 -- \
    cargo test -p noelle-graph --test vuln_query handles_empty_set
```

Not `cargo test --workspace`. The verify cache keys on the exact
command, so a narrow run that later widens to the suite picks up the
narrow cache hit and only pays for the delta. Running the suite when
the log already names the test is a verification-budget violation
even though it passes `verify run` (no bypass) — the adversarial
reviewer warns on broad scope when narrow was sufficient.

**Opt-in nextest sharding.** For projects that use `cargo nextest`
and have many tests, the heavy tier can be sharded:

```bash
noelle-harness verify run --profile rust --shard 4 --holder bugfix:BUG-001 -- \
    cargo nextest run -p noelle-graph
```

Each of the 4 shards acquires its own `medium` slot and runs
`--partition hash:i/4`. Cached shards skip re-execution
(FR-HARN-010.1).

**Fallback when noelle-harness isn't on PATH.** Skip this section
and call the underlying command directly. The bug-burndown
dispatcher caps parallelism at 2 in this case (see bug-burndown
references/dispatcher.md § "Slot semaphore unavailable"), so the
RAM-pressure risk is bounded.

`GATE 6: PASS` requires: reproducer red-on-revert AND green-on-fix, every
applicable pyramid layer green, mutation survivors = 0 on changed lines,
lint clean, AND every verification command above issued through
`noelle-harness verify run` when that binary is on PATH.

## Phase 7 — Documentation deltas (delegated)

This skill doesn't author ADRs, specs, threat models, or user stories.
Those live in dedicated companion skills you MUST invoke for the
corresponding work. Your job here is to (a) detect which artefact classes
the fix implicates, (b) hand off with the right context, and (c) cite the
returned artefact path in DoD.

**Companion skills:**

| Artefact class       | Create               | Review               |
|----------------------|----------------------|----------------------|
| ADRs                 | `/adr-create`        | `/adr-review`        |
| Specs                | `/spec-create`       | `/spec-review`       |
| User stories / ACs   | `/story-creator`     | `/story-reviewer`    |
| Threat models        | `/threat-model-create` | `/threat-model-review` |

**Delegation contract.** When handing off:

- Provide the full Phase 4 Causal-discrepancy block.
- Provide the Phase 5 structural-fix summary (layer, signature changes,
  invariant restored, blast radius).
- Provide Phase 3 / 6 test names so the artefact can cite executable
  confirmation.
- Receive back: a path / ID / link. That's the evidence you cite in DoD.

Don't inline-author. If a companion skill's unavailable, surface
`GATE 7: FAIL — companion skill X not loaded` and ask the user before any
manual fallback.

### 7a. ADR triggers (≥2 Y → `/adr-create`; existing ADR touched → `/adr-review`)

- [ ] Module boundary touched / new import edge.
- [ ] Function / API / message / error contract changed.
- [ ] Concurrency, locking, ordering, transaction, or idempotency model
      changed.
- [ ] New external dependency (lib, service, env var, feature flag).
- [ ] Data model: schema, index, constraint, retention, PII classification.
- [ ] Trust boundary / auth / authz / credential path.
- [ ] Same fix needed in more than one location (hidden invariant).

### 7b. Spec / acceptance-criteria triggers

- [ ] User-observable behaviour changed.
- [ ] New error condition surfaced to a user or operator.
- [ ] Bug was a doc-defect, spec-gap, or drift in the Phase 4
      classification.
- [ ] API contract surfaced to external callers changed.

Action: `/spec-create` for gaps, `/spec-review` for amendments. Use the
Phase 3 reproducer as the executable example.

### 7c. Threat-model triggers

- [ ] New attack surface (endpoint, port, listener, deserialisation).
- [ ] Changed trust boundary or principal.
- [ ] New external input.
- [ ] Changed auth / authz path or session / token handling.
- [ ] Changed data flow, especially PII.
- [ ] New or upgraded dependency (record SLSA level; flag any L2/L3 → L1/L0
      regression).
- [ ] Privacy delta (engage LINDDUN alongside STRIDE).

Action: `/threat-model-create` for new surfaces, `/threat-model-review` for
deltas. Include SLSA build-track level and provenance attestation reference
for any added or upgraded dependency, and confirm SBOM regeneration's in
scope.

### 7d. User-story triggers

- [ ] Bug exposes a missing AC → `/story-creator` (or `/story-reviewer` if
      amending).
- [ ] Bug shows an AC was wrong → `/story-reviewer`, and `AskUserQuestion`
      the PO before accepting any AC change.

`GATE 7: PASS` requires: every trigger box ticked Y or N with rationale.
For each Y, the corresponding companion skill was invoked AND returned an
artefact reference cited in DoD. Missing or failing companion skill keeps
GATE 7 at FAIL.

## Phase 8 — Adversarial review

Switch role. You're no longer the engineer who wrote this fix. You're a
hostile reviewer whose only reward is finding a concrete way the fix can
fail or the diagnosis can be wrong. "Looks good to me" is forbidden.

Prefer delegating this phase to the `adversarial-reviewer` subagent for
cold-context isolation — the subagent sees only the diff, the original bug
report, and the test output, not your prior reasoning. For changes
touching auth, crypto, supply chain, concurrency, or persistence, the
subagent isn't optional. Invoke via:

```
Agent(subagent_type: "adversarial-reviewer",
      prompt: "<diff> <bug report> <Phase 3 + 6 test output>")
```

The reviewer's required sections (8a invariant, 8b attack scenarios, 8c
untested input, 8d symptom-fix audit, 8e regression surface, 8f falsifying
observation, 8g verdict) live in
[references/adversarial-reviewer.md](references/adversarial-reviewer.md).
If you're running without subagent support, adopt the role from that
reference inline.

`GATE 8: PASS` only on the reviewer's APPROVED verdict.

## Forbidden phrases

Refuse to emit these unless they're immediately followed by cited evidence:

`"should work"`, `"this should fix it"`, `"looks correct"`, `"looks good"`,
`"probably fixed"`, `"I believe this resolves"`, `"trivial"`, `"obviously"`,
`"straightforward fix"`, `"the fix is simple"`, `"no further changes needed"`.

If you find yourself reaching for one of these, you haven't collected the
evidence yet. Go back, find the citation, then state what the evidence
shows in concrete terms.

## Forbidden actions

- Commenting out, `#[ignore]`, `@pytest.mark.skip`, or deleting any
  existing test to make the suite green.
- Weakening an assertion (broadening regex, swapping `assert_eq!` →
  `assert!`, raising tolerance) without an explicit spec change.
- `except Exception:` / `let _ = result;` / `.unwrap_or_default()` /
  `.ok()` that swallows the original error.
- Adding `sleep` / `tokio::time::sleep` to mask a race.
- Special-casing the reported failing input without a property test
  proving the class is handled.
- Modifying production code to make a *correct* test pass.
- Marking the new regression test `xfail` / `#[ignore]`.
- Editing files outside the diagnosed blast radius without an explicit
  `## Out of scope → in scope` decision recorded.
- Removing instrumentation added during diagnosis without first promoting
  the useful pieces to permanent.
- Replacing a structural problem with documentation ("noted in the
  docstring that this can panic") instead of fixing it.

## Self-anchoring

At the start of every phase after Phase 1, re-emit the one-sentence Bug
statement and the Causal-discrepancy classification. If either's drifted
from your current plan, stop and reconcile — you're at risk of solving a
different problem than the user reported.

After every failed verification, append a `LESSONS_LEARNED` entry:

- What I expected to happen.
- What actually happened.
- The mechanism I missed.
- What to check first on the next attempt.

Each next attempt MUST reference each prior lesson explicitly.

## Circuit breaker

Stop and report inability when ALL of these hold:

- Five or more hypotheses tried and falsified.
- Every context-ladder rung exhausted (code, logs, docs, user).
- Reproducer either can't be made deterministic OR fails for the wrong
  reason after three attempts.
- Your mental model of the failure still doesn't match observed behaviour.

Emit a `## Blocked` report naming the simplest experiment that'd break the
impasse and the specific info / tool / access you'd need. Don't thrash
further.

## Tool-use discipline

- Prefer `Grep` / `Glob` over speculative `Read` for localisation.
- After every `Edit`, re-`Read` the touched region to verify post-state.
- Run targeted test invocations during the inner loop; full-suite only at
  Phase 6.
- Delegate full-suite runs and the adversarial review to subagents when
  available — they return a summary, keeping your context clean.
- Avoid rewriting more than ~50 lines in one Edit; prefer a sequence of
  focused edits with re-reads.

## Optional: Definition-of-Done hook

The skill ships a `PreToolUse` hook at `scripts/require-dod.sh` that blocks
`Edit` / `Write` / `MultiEdit` calls if the DoD checklist file's missing or
has unchecked boxes during Phase 9. It's a no-op outside bugfix sessions.
To enable it, add to `~/.claude/settings.json`:

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Edit|Write|MultiEdit",
        "hooks": [{"type": "command", "command": "bash $HOME/.claude/skills/bugfix/scripts/require-dod.sh"}]
      }
    ]
  }
}
```

State lives in `.bugfix/` (top-level dotfile directory, auto-gitignored)
rather than `.claude/state/` — this keeps writes outside Claude Code's
project-state directory and avoids per-write permission prompts during
long autonomous sessions. At Phase 1, the skill should ensure
`.bugfix/` is in `.gitignore`, then write a marker file at
`.bugfix/active-$CLAUDE_SESSION_ID`, keep the DoD checklist at
`.bugfix/dod-$CLAUDE_SESSION_ID.md`, and a phase counter at
`.bugfix/phase-$CLAUDE_SESSION_ID`:

```bash
ensure_gitignored() {
    local entry="$1" gi=".gitignore"
    [ -f "$gi" ] || touch "$gi"
    grep -qxF "$entry" "$gi" || { echo "$entry" >> "$gi"; echo "Added '$entry' to .gitignore"; }
}
ensure_gitignored ".bugfix/"
mkdir -p .bugfix
```

The persistent bugfix log used by `bug-burndown` for recurrence detection
lives at `.bugfix/log/` (same dotfile directory, shared across sessions).
Leave the hook unregistered if you'd rather keep DoD enforcement purely
conversational.

## Writing Style

Apply [`natural-writing-style`](../natural-writing-style/SKILL.md) to every
prose block this skill emits — Bug statement, Causal discrepancy,
hypothesis log, structural audit, DoD evidence, adversarial verdict.
Specifically:

- Be concrete and evidence-cited. Don't claim a gate "passes" without
  quoting the actual test output or `file:line` proving it.
- Avoid unsubstantiated readiness or completeness claims. State what you
  verified and what remains. See `natural-writing-style` for the full
  banned-phrase list.
- No effort or duration estimates. Describe scope and risk in objective
  terms (number of files, dependencies, risk factors) instead.
- Use contractions naturally. The skill's authority comes from rigor, not
  formality.
