# 技能创建器

一个用于创建新技能并迭代改进它们的技能。

从高层次来看，创建技能的过程如下：

- 确定你希望技能做什么，以及大致如何做
- 编写技能的草稿
- 创建几个测试提示词，并对它们运行附带该技能的 claude
- 帮助用户从定性和定量两个角度评估结果
  - 在运行在后台进行的同时，如果没有定量评估的话，起草一些定量评估（如果已经有了一些，你可以直接使用或在你觉得需要修改时进行修改）。然后向用户解释这些评估（或者如果它们已存在，解释已经存在的那些）
  - 使用 `eval-viewer/generate_review.py` 脚本向用户展示结果供他们查看，并让他们查看定量指标
- 根据用户对结果的评估反馈（以及如果从定量基准中显现出任何明显的缺陷）来重写技能
- 重复直到你满意为止
- 扩展测试集并在更大规模上再次尝试

你在使用这个技能时的任务是弄清楚用户在这个流程中的哪个位置，然后参与进来，帮助他们推进这些阶段。因此，例如，也许他们说"我想为 X 做一个技能"。你可以帮助明确他们的意思，写一个草稿，编写测试用例，弄清楚他们想如何评估，运行所有的提示词，然后重复。

另一方面，也许他们已经有一个技能的草稿。在这种情况下，你可以直接进入评估/迭代循环部分。

当然，你应当始终灵活应变，如果用户说"我不需要运行一堆评估，跟我凭感觉来就行"，你也可以那样做。

然后，在技能完成后（但同样，顺序是灵活的），你也可以运行技能描述优化器——我们为此单独设了一个脚本——来优化技能的触发。

酷吧？酷。

- 对于"JSON"和"断言"，在未经解释就使用之前，你需要看到用户确实了解这些概念的明确线索

如果你有疑虑，简要解释术语是可以的；如果你不确定用户是否明白某个术语，请随意用简短的定义来澄清。

## 创建技能

### 捕获意图

首先理解用户的意图。当前对话可能已经包含了用户想要捕捉的工作流（例如，他们说"把这个变成一个技能"）。如果是这样，先从对话历史中提取答案——使用的工具、步骤顺序、用户所做的修正、观察到的输入/输出格式。用户可能需要填补空白，并且在进入下一步之前应该确认。

1. 这个技能应让 Claude 能够做什么？
2. 这个技能应在何时触发？（什么用户短语/上下文）
3. 预期的输出格式是什么？
4. 我们是否应该设置测试用例来验证技能是否有效？具有客观可验证输出的技能（文件转换、数据提取、代码生成、固定工作流步骤）受益于测试用例。具有主观输出的技能（写作风格、艺术）通常不需要。根据技能类型建议适当的默认方案，但让用户决定。

### 访谈与研究

主动询问有关边缘情况、输入/输出格式、示例文件、成功标准和依赖项的问题。在将这部分弄清楚之前，不要急着编写测试提示词。

检查可用的 MCP——如果对研究有用（搜索文档、查找类似技能、查询最佳实践），通过子代理（如果可用）并行研究，否则内联进行。带着上下文准备，以减轻用户的负担。

### 编写 SKILL.md

根据用户访谈，填写以下组成部分：

- **name**：技能标识符
- **description**：何时触发，做什么。这是主要的触发机制——既包括技能做什么，也包括何时使用它的具体上下文。所有"何时使用"的信息都放在这里，而不是正文中。注意：目前 Claude 有"触发不足"的倾向——在技能有用时却不使用它们。为了应对这个问题，请让技能描述稍微"主动"一些。例如，不要写"如何构建一个简单的快速仪表板来显示 Anthropic 内部数据"，你可以写"如何构建一个简单的快速仪表板来显示 Anthropic 内部数据。确保在用户提到仪表板、数据可视化、内部指标，或想要显示任何类型的公司数据时使用此技能，即使他们没有明确要求'仪表板'。"
- **compatibility**：所需工具、依赖项（可选，很少需要）
- **技能的其余部分 :)**

### 技能编写指南

#### 技能剖析

```
skill-name/
├── SKILL.md (必需)
│   ├── YAML 前置元数据（name, description 必需）
│   └── Markdown 指令
└── 捆绑资源（可选）
    ├── scripts/    - 用于确定性/重复性任务的可执行代码
    ├── references/ - 按需加载到上下文中的文档
    └── assets/     - 输出中使用的文件（模板、图标、字体）
```

#### 渐进式披露

技能使用三级加载系统：

1. **元数据**（name + description）- 始终在上下文中（约 100 词）
2. **SKILL.md 正文** - 当技能触发时在上下文中（理想情况 < 500 行）
3. **捆绑资源** - 按需加载（无限制，脚本无需加载即可执行）

这些字数统计是近似值，如果需要，你可以自由地写得更长。

**关键模式：**

- 将 SKILL.md 保持在 500 行以下；如果接近这个限制，请添加额外的层级结构以及清晰的指引，告诉模型接下来应该去哪里跟进。
- 从 SKILL.md 中清晰地引用文件，并指导何时阅读它们
- 对于大型参考文件（> 300 行），包含目录

**领域组织**：当技能支持多个领域/框架时，按变体组织：

```
cloud-deploy/
├── SKILL.md（工作流 + 选择）
└── references/
    ├── aws.md
    ├── gcp.md
    └── azure.md
```

Claude 仅读取相关的参考文件。

#### 无意外原则

不言而喻，技能不得包含恶意软件、漏洞利用代码或任何可能危及系统安全的内容。技能的内容在其所描述的意图上不应让用户感到意外。不要配合创建误导性技能或旨在促进未经授权访问、数据泄露或其他恶意活动的请求。诸如"角色扮演为某某"之类的东西是可以的。

#### 编写模式

在指令中优先使用祈使语气。

**定义输出格式** - 你可以这样做：

```markdown
## 报告结构
始终使用此精确模板：
# [标题]
## 执行摘要
## 关键发现
## 建议
```

**示例模式** - 包含示例很有用。你可以像这样格式化它们（但如果示例中包含"输入"和"输出"，你可能需要稍微偏离这个格式）：

```markdown
## 提交消息格式
**示例 1：**
输入：Added user authentication with JWT tokens
输出：feat(auth): implement JWT-based authentication
```

### 写作风格

尽量向模型解释为什么某些事情很重要，而不是使用生硬的强制性"必须"。运用心理理论，尽量让技能具有通用性，而不是局限于具体的例子。先写一份草稿，然后用新的眼光审视它并加以改进。

### 测试用例

在编写技能草稿后，想出 2-3 个现实的测试提示词——就是真实用户实际会说的那种。与用户分享它们：[你不必使用这种确切的语言]"这里有几个我想尝试的测试用例。这些看起来对吗，还是你想添加更多？"然后运行它们。

将测试用例保存到 `evals/evals.json`。现在不要写断言——只写提示词。你将在下一步骤中当运行在进行时起草断言。

```json
{
  "skill_name": "example-skill",
  "evals": [
    {
      "id": 1,
      "prompt": "用户的任务提示词",
      "expected_output": "预期结果的描述",
      "files": []
    }
  ]
}
```

参见 `references/schemas.md` 获取完整模式（包括你稍后将添加的 `assertions` 字段）。

## 运行和评估测试用例

本节是一个连续序列——不要中途停止。不要使用 `/skill-test` 或任何其他测试技能。

将结果放入 `<skill-name>-workspace/` 中，作为技能目录的同级目录。在工作区内，按迭代组织结果（`iteration-1/`、`iteration-2/` 等），在其中，每个测试用例获得一个目录（`eval-0/`、`eval-1/` 等）。不要预先创建所有这些——只需随着进行创建目录。

### 第 1 步：在同一轮中派生所有运行（带技能和基线）

对于每个测试用例，在同一轮中派生两个子代理——一个带技能，一个不带。这很重要：不要先派生带技能的运行，然后再回来做基线。同时启动所有运行，以便它们大致同时完成。

**带技能运行：**

```
执行此任务：
- 技能路径：<path-to-skill>
- 任务：<eval prompt>
- 输入文件：<eval files if any, or "none">
- 将输出保存到：<workspace>/iteration-<N>/eval-<ID>/with_skill/outputs/
- 要保存的输出：<用户关心的内容——例如"the .docx file"、"the final CSV">
```

**基线运行**（相同的提示词，但基线取决于上下文）：

- **创建新技能**：完全不用技能。相同的提示词，无技能路径，保存到 `without_skill/outputs/`。
- **改进现有技能**：旧版本。在编辑之前，对技能进行快照（`cp -r <skill-path> <workspace>/skill-snapshot/`），然后将基线子代理指向该快照。保存到 `old_skill/outputs/`。

为每个测试用例编写 `eval_metadata.json`（断言目前可以为空）。根据测试内容为每个评估起一个描述性名称——不仅仅是"eval-0"。也使用此名称作为目录名。如果此迭代使用新的或修改过的评估提示词，为每个新的评估目录创建这些文件——不要假设它们会从之前的迭代中延续下来。

```json
{
  "eval_id": 0,
  "eval_name": "descriptive-name-here",
  "prompt": "用户的任务提示词",
  "assertions": []
}
```

### 第 2 步：当运行在进行中时，起草断言

不要只是等待运行完成——你可以利用这段时间高效地工作。为每个测试用例起草定量断言，并向用户解释它们。如果 `evals/evals.json` 中已经存在断言，审查它们并解释它们检查什么。

好的断言是客观可验证的，并且有描述性的名称——它们应该在基准查看器中读起来清晰明了，这样浏览结果的人一眼就能理解每个断言检查什么。主观技能（写作风格、设计质量）更适合定性评估——不要将断言强加于需要人类判断的事情上。

一旦起草完断言，用这些断言更新 `eval_metadata.json` 文件和 `evals/evals.json`。同时向用户解释他们在查看器中会看到什么——定性输出和定量基准。

### 第 3 步：当运行完成时，捕获时间数据

当每个子代理任务完成时，你会收到一个包含 `total_tokens` 和 `duration_ms` 的通知。立即将这些数据保存到运行目录中的 `timing.json`：

```json
{
  "total_tokens": 84852,
  "duration_ms": 23332,
  "total_duration_seconds": 23.3
}
```

这是捕获这些数据的唯一机会——它通过任务通知传递，不会在其他地方持久化。在每个通知到达时处理它，而不是试图批量处理。

### 第 4 步：评分、聚合并启动查看器

一旦所有运行完成：

1. **对每次运行进行评分**——派生一个评分子代理（或内联评分），读取 `agents/grader.md` 并根据输出评估每个断言。将结果保存到每个运行目录中的 `grading.json`。grading.json 的 expectations 数组必须使用字段 `text`、`passed` 和 `evidence`（而不是 `name`/`met`/`details` 或其他变体）——查看器依赖这些确切的字段名称。对于可以程序化检查的断言，编写并运行脚本而不是用眼睛看——脚本更快、更可靠，并且可以跨迭代重复使用。
2. **聚合到基准中**——从 skill-creator 目录运行聚合脚本：

   ```bash
   python -m scripts.aggregate_benchmark <workspace>/iteration-N --skill-name <name>
   ```

   这会生成 `benchmark.json` 和 `benchmark.md`，包含每个配置的 pass_rate、时间和 tokens，带有均值 ± 标准差和增量。如果手动生成 benchmark.json，请参见 `references/schemas.md` 获取查看器期望的确切模式。
   把每个带技能的版本放在其基线对应项之前。
3. **进行分析**——读取基准数据并揭示聚合统计数据可能隐藏的模式。参见 `agents/analyzer.md`（"分析基准结果"部分）了解要寻找什么——诸如无论如何都始终通过的断言（无区分力）、高方差评估（可能不稳定）以及时间/token 权衡等。
4. **启动查看器**，包含定性输出和定量数据：

   ```bash
   nohup python <skill-creator-path>/eval-viewer/generate_review.py \
     <workspace>/iteration-N \
     --skill-name "my-skill" \
     --benchmark <workspace>/iteration-N/benchmark.json \
     > /dev/null 2>&1 &
   VIEWER_PID=$!
   ```

   对于第 2 次及以后的迭代，还需要传递 `--previous-workspace <workspace>/iteration-<N-1>`。

   **Cowork / 无头环境：** 如果 `webbrowser.open()` 不可用或环境没有显示器，使用 `--static <output_path>` 来写入一个独立的 HTML 文件而不是启动服务器。当用户点击"提交所有评审"时，反馈将作为 `feedback.json` 文件下载。下载后，将 `feedback.json` 复制到工作区目录中，以便下一次迭代使用。

注意：请使用 generate_review.py 来创建查看器；无需编写自定义 HTML。

5. **告诉用户**类似这样的话："我已经在你的浏览器中打开了结果。有两个选项卡——'输出'让你点击查看每个测试用例并留下反馈，'基准'显示定量比较。完成后，回到这里告诉我。"

### 用户在查看器中看到什么

"输出"选项卡一次显示一个测试用例：

- **提示词**：给出的任务
- **输出**：技能生成的文件，尽可能内联渲染
- **上一次输出**（第 2 次迭代及以后）：显示上次迭代输出的折叠部分
- **正式评分**（如果已运行评分）：显示断言通过/失败的折叠部分
- **反馈**：在输入时自动保存的文本框
- **上一次反馈**（第 2 次迭代及以后）：他们上次的评论，显示在文本框下方

"基准"选项卡显示统计数据摘要：每个配置的通过率、时间和 token 使用情况，包含每个评估的细分和分析观察。

导航通过上一个/下一个按钮或箭头键。完成后，他们点击"提交所有评审"，这将所有反馈保存到 `feedback.json`。

### 第 5 步：读取反馈

当用户告诉你他们完成了，读取 `feedback.json`：

```json
{
  "reviews": [
    {"run_id": "eval-0-with_skill", "feedback": "图表缺少轴标签", "timestamp": "..."},
    {"run_id": "eval-1-with_skill", "feedback": "", "timestamp": "..."},
    {"run_id": "eval-2-with_skill", "feedback": "完美，很喜欢这个", "timestamp": "..."}
  ],
  "status": "complete"
}
```

空反馈意味着用户认为可以。将改进重点放在用户有具体抱怨的测试用例上。

完成后，杀掉查看器服务器：

```bash
kill $VIEWER_PID 2>/dev/null
```

## 改进技能

这是循环的核心。你已经运行了测试用例，用户已经审查了结果，现在你需要根据他们的反馈来让技能变得更好。

### 如何思考改进

1. **从反馈中归纳。** 这里发生的大局是，我们试图创建可以被使用一百万次（也许字面上，甚至更多，谁知道呢）跨越许多不同提示词的技能。在这里，你和用户只反复迭代几个示例，因为这有助于更快地推进。用户对这些示例了如指掌，他们能快速评估新的输出。但如果你们共同开发的技能只对这些示例有效，那就是无用的。不要进行琐碎、过度拟合的修改，或是压迫性地使用限制性"必须"，如果存在某些顽固的问题，你可以尝试采用不同的隐喻，或者推荐不同的工作模式。尝试的成本相对较低，也许你们会找到很棒的东西。
2. **保持提示词精简。** 移除那些不起作用的部分。一定要阅读转录记录，而不仅仅是最终的输出——如果看起来技能让模型浪费大量时间做无意义的事情，你可以尝试去掉技能中导致它那样做的部分，然后看看会发生什么。
3. **解释为什么。** 尽量解释你要求模型做的每件事背后的**为什么**。当今的 LLM 是*聪明的*。它们有良好的心理理论，当被给予一个好的框架时，可以超越死记硬背的指令，真正地把事情做成。即使来自用户的反馈是简短或沮丧的，也要试着真正理解任务以及用户为什么写他们写的东西，以及他们实际写了什么，然后将这种理解传递到指令中。如果你发现自己用全大写写 ALWAYS 或 NEVER，或者使用超级僵化的结构，那是一个黄色警告标志——如果可能，请重新构思并解释推理，让模型明白你所要求的为什么重要。这是一种更人性化、更强大、更有效的方法。
4. **查找跨测试用例的重复工作。** 阅读测试运行的转录记录，注意子代理是否都独立编写了类似的辅助脚本或对某些事情采取了相同的多步骤方法。如果所有 3 个测试用例都导致子代理编写一个 `create_docx.py` 或 `build_chart.py`，这是一个强烈的信号，表明技能应该捆绑那个脚本。一次编写，放入 `scripts/`，并告诉技能使用它。这样每次将来调用时就不需要重新发明轮子了。

这项任务相当重要（我们试图每年创造数十亿美元的经济价值！），而你的思考时间不是瓶颈；慢慢来，真正仔细考虑。我建议先写一份修订草稿，然后用新的视角重新审视它并加以改进。真正尽力去理解用户的头脑，理解他们想要什么和需要什么。

### 迭代循环

在改进技能之后：

1. 将你的改进应用到技能上
2. 将所有测试用例重新运行到一个新的 `iteration-<N+1>/` 目录，包括基线运行。如果你正在创建一个新技能，基线始终是 `without_skill`（无技能）——这在迭代中保持不变。如果你正在改进一个现有技能，运用你的判断力来决定什么作为基线是合理的：用户带来的原始版本，还是前一次迭代。
3. 使用 `--previous-workspace` 指向前一次迭代来启动评审器
4. 等待用户评审并告诉你他们完成了
5. 读取新的反馈，再次改进，重复

一直持续直到：

- 用户表示满意
- 反馈全是空的（一切看起来都很好）
- 你没有取得有意义的进展

## 高级：盲比

对于你想要更严格比较两个技能版本的情况（例如，用户问"新版本真的更好吗？"），有一个盲比系统。阅读 `agents/comparator.md` 和 `agents/analyzer.md` 了解详情。基本思想是：将两个输出交给一个独立的代理，但不告诉它哪个是哪个，让它评判质量。然后分析为什么获胜者胜出。

这是可选的，需要子代理，大多数用户不需要它。人工评审循环通常就足够了。

## 描述优化

SKILL.md 前置元数据中的 description 字段是决定 Claude 是否调用某个技能的主要机制。在创建或改进技能后，提供优化描述以获得更好触发准确率的选项。

### 第 1 步：生成触发评估查询

创建 20 个评估查询——混合了应该触发和不应该触发的。保存为 JSON：

```json
[
  {"query": "the user prompt", "should_trigger": true},
  {"query": "another prompt", "should_trigger": false}
]
```

查询必须是现实的，是 Claude Code 或 Claude.ai 用户实际会输入的内容。不是抽象的请求，而是具体、有足够细节的请求。例如，文件路径、关于用户工作或情况的个人背景、列名和值、公司名称、URL。一点背景故事。有些可能是小写的或包含缩写、拼写错误或随意的讲话。使用不同长度的混合，并专注于边缘情况，而不是让它们泾渭分明（用户将有机会确认它们）。

坏的：`"Format this data"`、`"Extract text from PDF"`、`"Create a chart"`

好的：`"ok so my boss just sent me this xlsx file (its in my downloads, called something like 'Q4 sales final FINAL v2.xlsx') and she wants me to add a column that shows the profit margin as a percentage. The revenue is in column C and costs are in column D i think"`

对于**应该触发的**查询（8-10 个），思考覆盖率。你想要同一意图的不同表述——一些正式的，一些随意的。包括用户没有明确命名技能或文件类型但显然需要它的情况。加入一些不常见的用例以及此技能与另一个技能竞争但应胜出的情况。

对于**不应该触发的**查询（8-10 个），最有价值的是那些近似的——与技能共享关键词或概念但实际上需要不同东西的查询。想想相邻领域、模糊的措辞，天真的关键词匹配会触发但不应该触发，以及查询触及技能所做的某些事情但在另一个工具更合适的上下文中。

要避免的关键事情：不要让不应该触发的查询明显不相关。对于一个 PDF 技能，用"写一个斐波那契函数"作为否定测试太容易了——它测试不了任何东西。否定案例应该是真正有难度的。

### 第 2 步：与用户一起评审

使用 HTML 模板向用户展示评估集以供评审：

1. 从 `assets/eval_review.html` 读取模板
2. 替换占位符：
   - `__EVAL_DATA_PLACEHOLDER__` → 评估项的 JSON 数组（不要引号——它是一个 JS 变量赋值）
   - `__SKILL_NAME_PLACEHOLDER__` → 技能名称
   - `__SKILL_DESCRIPTION_PLACEHOLDER__` → 技能当前的描述
3. 写入一个临时文件（例如 `/tmp/eval_review_<skill-name>.html`）并打开它：`open /tmp/eval_review_<skill-name>.html`
4. 用户可以编辑查询、切换 should-trigger、添加/删除条目，然后点击"导出评估集"
5. 文件下载到 `~/Downloads/eval_set.json`——如果有多个版本（例如 `eval_set (1).json`），检查 Downloads 文件夹中的最新版本

这一步很重要——差的评估查询会导致差的描述。

### 第 3 步：运行优化循环

告诉用户："这需要一些时间——我会在后台运行优化循环，并定期检查它。"

将评估集保存到工作区，然后在后台运行：

```bash
python -m scripts.run_loop \
  --eval-set <path-to-trigger-eval.json> \
  --skill-path <path-to-skill> \
  --model <model-id-powering-this-session> \
  --max-iterations 5 \
  --verbose
```

使用你系统提示中提供当前会话能力的模型 ID，以便触发测试与用户实际体验的相符。

在它运行时，定期查看输出，向用户更新它在哪个迭代以及分数看起来如何。

这会自动处理完整的优化循环。它将评估集分成 60% 训练集和 40% 保留测试集，评估当前描述（每个查询运行 3 次以获得可靠的触发率），然后调用 Claude 根据失败的情况提出改进建议。它会在训练集和测试集上重新评估每个新描述，最多迭代 5 次。完成后，它会在浏览器中打开一个 HTML 报告，显示每个迭代的结果，并返回带有 `best_description` 的 JSON——根据测试分数而非训练分数选择，以避免过拟合。

### 技能触发的工作原理

理解触发机制有助于设计更好的评估查询。技能以其名称 + 描述出现在 Claude 的 `available_skills` 列表中，Claude 根据该描述决定是否查阅某个技能。要知道的重要事情是，Claude 仅会为它自己不易处理的任务查阅技能——像"阅读这个 PDF"这样简单的单步查询可能不会触发技能，即使描述完美匹配，因为 Claude 可以直接用基本工具处理。复杂的、多步骤的或专门的查询在描述匹配时会可靠地触发技能。

这意味着你的评估查询应该足够实质性，使 Claude 真正从查阅技能中获益。"阅读文件 X"这样的简单查询是差的测试用例——它们不会触发技能，无论描述质量如何。

### 第 4 步：应用结果

从 JSON 输出中取出 `best_description` 并更新技能 SKILL.md 的前置元数据。向用户展示前后对比并报告分数。

### 打包并呈现（仅当 `present_files` 工具可用时）

检查你是否有权访问 `present_files` 工具。如果没有，跳过此步骤。如果有，打包技能并将 .skill 文件呈现给用户：

```bash
python -m scripts.package_skill <path/to/skill-folder>
```

打包后，引导用户到生成的 `.skill` 文件路径，以便他们可以安装它。

## Claude.ai 特定说明

在 Claude.ai 中，核心工作流是相同的（草稿 → 测试 → 评审 → 改进 → 重复），但由于 Claude.ai 没有子代理，一些机制会改变。以下是需要适应的内容：

**运行测试用例**：没有子代理意味着没有并行执行。对于每个测试用例，阅读技能的 SKILL.md，然后遵循其指令自己完成测试提示词。一个一个地做。这不如独立的子代理严格（你编写了技能，你也在运行它，所以你拥有完整的上下文），但这是一个有用的合理性检查——而人工评审步骤弥补了不足。跳过基线运行——只需使用技能按要求完成任务。

**评审结果**：如果你无法打开浏览器（例如，Claude.ai 的虚拟机没有显示器，或者你在远程服务器上），完全跳过浏览器评审器。相反，直接在对话中呈现结果。对于每个测试用例，显示提示词和输出。如果输出是用户需要查看的文件（如 .docx 或 .xlsx），将其保存到文件系统并告诉他们文件在哪，以便他们可以下载并检查。以内联方式请求反馈："这个看起来怎么样？你想改变什么吗？"

**基准测试**：跳过定量基准测试——它依赖于基线比较，这在没有子代理的情况下没有意义。专注于来自用户的定性反馈。

**迭代循环**：和之前一样——改进技能，重新运行测试用例，请求反馈——只是在中间没有浏览器评审器。如果你有文件系统，你仍然可以将结果组织到迭代目录中。

**描述优化**：此部分需要 `claude` CLI 工具（具体是 `claude -p`），这仅在 Claude Code 中可用。如果你在 Claude.ai 上，跳过它。

**盲比**：需要子代理。跳过它。

**打包**：`package_skill.py` 脚本在任何有 Python 和文件系统的地方都能运行。在 Claude.ai 上，你可以运行它，用户可以下载生成的 `.skill` 文件。

**更新现有技能**：用户可能要求你更新现有技能，而不是创建新技能。在这种情况下：

- **保留原始名称。** 注意技能的目录名称和 `name` 前置元数据字段——不加更改地使用它们。例如，如果安装的技能是 `research-helper`，输出 `research-helper.skill`（而不是 `research-helper-v2`）。
- **在编辑前复制到可写位置。** 安装的技能路径可能是只读的。复制到 `/tmp/skill-name/`，在那里编辑，然后从副本打包。
- **如果手动打包，首先在 `/tmp/` 中暂存**，然后复制到输出目录——由于权限问题，直接写入可能会失败。

## Cowork 特定说明

如果你在 Cowork 中，需要了解的主要事项是：

- 你有子代理，所以主要工作流（并行派生测试用例、运行基线、评分等）都能工作。（然而，如果你遇到严重的超时问题，可以按顺序而不是并行运行测试提示词。）
- 你没有浏览器或显示器，所以在生成评估查看器时，使用 `--static <output_path>` 来写入一个独立的 HTML 文件，而不是启动服务器。然后提供一个用户可以点击以在他们的浏览器中打开该 HTML 的链接。
- 不知出于什么原因，Cowork 设置似乎让 Claude 在运行测试后不愿意生成评估查看器，所以只是为了重申：无论你是在 Cowork 中还是在 Claude Code 中，在运行测试后，你都应该**始终**生成评估查看器，让人在你自己修改技能并试图做出修正之前查看示例，使用 `generate_review.py`（而不是编写你自己的定制 HTML 代码）。抱歉提前说，但我要在这里全大写：在你自己评估输入**之前**，生成评估查看器。你想尽快把它们呈现在人的眼前！
- 反馈的工作方式不同：由于没有运行服务器，查看器的"提交所有评审"按钮将以 `feedback.json` 文件的形式下载反馈。然后你可以从那里读取它（你可能需要先请求访问权限）。
- 打包有效——`package_skill.py` 只需要 Python 和文件系统。
- 描述优化（`run_loop.py` / `run_eval.py`）应该在 Cowork 中正常工作，因为它通过子进程使用 `claude -p`，而不是浏览器，但请等到你完全完成技能并且用户同意它状况良好后再进行。
- **更新现有技能**：用户可能要求你更新现有技能，而不是创建新技能。遵循上面 claude.ai 部分中的更新指导。
