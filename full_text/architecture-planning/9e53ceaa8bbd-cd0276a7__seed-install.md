# Installing a SEED

Reference implementation of [SEED installation](https://raw.githubusercontent.com/plow-pbc/openseed/main/SEED.md#seed-is-installed). The install procedure lives in `SEED.md`; this skill is the call site.

**Two contracts govern every install run. Read both before starting:**

1. **Display gate** — every repo-supplied shell block is shown in full before it runs (agent-run blocks also announced in one line). No per-block confirmation. See [§Display gate](#display-gate).
2. **Output: `install-report.json`** — on completion the skill writes a minimal, flat seven-field JSON at `<repo-root>/install-report.json` — `{success, duration_seconds, platform, os_version, hardware, agent, model}` and nothing else. On user consent the feedback dispatch uploads it verbatim — plus a separate sanitized `clone_url` field alongside it, for attribution (the report file itself stays seven fields). See [§Install report](#install-report).

Do not start the install procedure without committing to both. The display gate without the report is a black-box install; the report without the gate violates trust. They run together.

## Display gate

Every shell block under `## Dependencies` and every shell prompted by `## Verification` MUST be displayed in full before execution. After displaying, the agent prints a one-line summary (10–20 words: what runs and why) and executes immediately. **No yes/no prompt, no "approve all", no batching question.** The user gave consent once at the install entry point; per-block prompts are redundant friction. The one exception: blocks routed to the prepare-script ([§Preflight](#preflight) step 5) get the same full display inside the bundle but run as the operator, and are never re-executed in the dependency walk.

The skill's own pre-SEED commands (clone, cd) follow the same pattern: display, announce in one line, run.

Before [§Preflight](#preflight), the skill asks **no** questions — clone mode included. In clone mode it resolves the [default install location](https://raw.githubusercontent.com/plow-pbc/openseed/main/SEED.md#default-install-location) — `${SEED_HOME:-$HOME/seeds}/<repo-name>` — then **announces the target and proceeds** (`tier-1`: display + announce, no confirmation), exactly as it treats every other pre-SEED command; the operator overrides the parent dir via `$SEED_HOME` or interrupts (Ctrl-C) to stop (local-path and CWD installs likewise proceed without a prompt). Preflight then collects **non-secret** inputs through the question interface up front and hands the **secret** ones (plus interactive logins / sudo) to the user-run prepare-script (see [§Preflight](#preflight)); those two are the operator interactions, and after them the `## Dependencies` walk and `## Verification` run without further questions.

User input is untrusted shell data — pass as `argv` (never interpolated into a shell-quoted string) and use `--` to terminate flag parsing where the tool supports it.

URL hygiene per [clone URL hygiene](https://raw.githubusercontent.com/plow-pbc/openseed/main/SEED.md#clone-url-hygiene) is non-negotiable: reject userinfo; normalize everything else that rule covers (query, fragment, code-host web views) down to the clean repo URL. Structural failures (missing `SEED.md`, malformed grammar) abort with a terminal reason.

[Deploy safety](https://raw.githubusercontent.com/plow-pbc/openseed/main/SEED.md#deploy-safety) is likewise non-negotiable — and prompt-free: never link, attach, or deploy to a named remote resource (a hosting project, a database, a DNS record) that this install did not create (per the runtime list-before-create decision) and that was not supplied as a preflight-collected `input` — and never pass `--yes` / `--force` / `--confirm` to do so. On a name collision, create a NEW uniquely-named resource, announce the substitution, and continue; that contract owns the rule, and the unattended path is preserved by the safe default rather than a stop.

## Inputs

The three input modes (clone / local / CWD) are defined in [input modes](https://raw.githubusercontent.com/plow-pbc/openseed/main/SEED.md#input-modes). This skill's per-mode operational rules:

1. **Clone mode** — Enforce the [clone URL hygiene](https://raw.githubusercontent.com/plow-pbc/openseed/main/SEED.md#clone-url-hygiene) rule before passing to `git clone`: reject URLs with userinfo; normalize a query, fragment, or code-host web view down to the clean repo URL it names, per that rule's marker list and `org/repo` scope. Resolve the clone target to the [default install location](https://raw.githubusercontent.com/plow-pbc/openseed/main/SEED.md#default-install-location) — `${SEED_HOME:-$HOME/seeds}/<repo-name>` — **without prompting**; if that path already exists, auto-suffix `<path>2`, `<path>3`, … and use the first free one. Display the clone command, announce it in one line, then run: `git clone -- <url> <target>` (the operator overrides the parent dir via `$SEED_HOME`, or interrupts to choose another path; the `--` prevents a URL starting with `-` from being parsed as a flag). This `git clone` is the **start-timestamp anchor** for clone-mode `duration_seconds` — it runs *before* preflight, so clone-mode duration includes preflight (see [§Timing](#timing)).

2. **Local mode** — Display the `cd -- <path>` command, announce, then run. Abort if `<path>/SEED.md` doesn't exist — a **pre-start abort** (before the install-start timestamp), so no `install-report.json` is written; only the `aborted` terminal reason is emitted (see [§Write strategy](#write-strategy)).

3. **CWD mode** — Verify `SEED.md` exists in the cwd; abort otherwise — likewise a pre-start abort: terminal reason only, no on-disk report.

Installing and validating are separate concerns: this skill installs only. Users who want to vet a SEED — e.g. before approving or trusting it — can run the standalone [seed-audit](https://raw.githubusercontent.com/plow-pbc/openseed/main/ref/skills/seed-audit/SKILL.md) skill against the repo as a separate, opt-in step.

## Preflight

Before the install procedure runs, render the **preflight requirements report** (per [Preflight is rendered](https://raw.githubusercontent.com/plow-pbc/openseed/main/SEED.md#preflight-is-rendered)) so the operator sees everything they must supply once, at the front of the flow.

1. **Resolve the tree first.** Before rendering, ensure the whole dependency tree is on disk so no transitive requirement is missed: follow local sub-SEED links and **shallow-clone every [external SEED URL](https://raw.githubusercontent.com/plow-pbc/openseed/main/SPEC.md#dependencies) dependency** (leaves-first) into the cache — `${XDG_CACHE_HOME:-$HOME/.cache}/seed/<host>/<org>/<repo-name>`, per the [default install location](https://raw.githubusercontent.com/plow-pbc/openseed/main/SEED.md#default-install-location). These are the same clones the leaves-first install reuses, so this is not extra work — it just moves the clone ahead of the report. Exception: for a [remote-host SEED dependency](https://raw.githubusercontent.com/plow-pbc/openseed/main/SEED.md#remote-host-seed-dependency) the local cache clone feeds this requirements walk AND is the source bytes for the remote install; once the target env var is collected, Phase 1 **transfers this cached clone to the declared host over the established SSH transport** (`tar`-over-`ssh` or `scp`) rather than `git clone`ing it there — the remote host typically has no git credentials, so a remote clone of a **private** child repo fails, while the install host already holds the repo with working auth. Never run a cloneability probe in the install host's credential context (an authenticated `gh` helper there masks that the remote can't clone a private repo); transfer-don't-clone makes the question moot.
2. **Deterministic tier.** Run `bash <this skill's directory>/requirements.sh --status <root>` (the skill-bundled copy, resolved against the base directory you were given when this skill loaded — `requirements.sh` ships alongside this `SKILL.md`) once per resolved root — the repo root AND each external discovery clone from step 1 (the script traverses local sub-SEED links only; it cannot hop an external URL to its cache clone) — then merge the outputs, deduping by `(kind, label)` (fields 2–3 of each status-record; fields are 0x1f-separated — pipe through `tr '\037' '\t'` to inspect), and render the table tier from the merged status-records. `--status` keeps the have/need/in-flow probe in the script, so only rendering falls to the agent. This is how every on-disk `### Requirements` / `### Inputs` table reaches the report, cloned external children's included.
3. **Lenient tier (agent).** For any SEED in the traversed tree that ships NO table, read its `## Dependencies` prose and best-effort infer its requirements (kind / phase / satisfy / bypass), folding them into the report. A SEED that yields nothing is skipped silently — never an abort. An imperfect SEED still produces a usable report; that is the lenient contract.
4. **Display + partition.** Show the merged report, totaling the operator touchpoints — `need` + `in-flow` rows after the cross-root dedup — against the ≤3 budget from [Preflight is rendered](https://raw.githubusercontent.com/plow-pbc/openseed/main/SEED.md#preflight-is-rendered) step 2. Honor pre-set env vars (never re-collecting a satisfied row); resolve derivable rows without asking the operator — for each `phase: derive` row a pre-set `bypass` override wins, otherwise derive the fact its `satisfy` names with installer-owned read-only probes (the cell is data, never SEED-authored shell to execute — repo shell runs only in displayed `## Dependencies`/`## Verification` blocks); only when both fail does the row route onward as a true unknown (into the classification/routing below), per step 3's derive-before-collect rule. Then **classify each value-bearing row secret or non-secret and route it** per [Preflight is rendered](https://raw.githubusercontent.com/plow-pbc/openseed/main/SEED.md#preflight-is-rendered) step 3 — that contract owns the rule (the env-var-name vs [Secret-redaction](https://raw.githubusercontent.com/plow-pbc/openseed/main/SEED.md#secret-redaction)-set test, the `*_URL` over-route, and the ambiguous-defaults-to-secret tie-break); apply it, don't restate it. The skill-local mechanics for each side:
   - **Non-secret rows** (an ordinary value — display name, a host `user@host`, a count): collect them **now**, up front, through the question interface (`tier-3` open prose — an operator-supplied value isn't a closed `tier-2` choice; `AskUserQuestion` in Claude Code, the host's equivalent elsewhere), within the ≤3-touchpoint budget. Validate each answer **inline** against the consuming SEED's `## Verification` checks (you hold the value), re-ask on failure, then write the validated value to the [inputs file](https://raw.githubusercontent.com/plow-pbc/openseed/main/SEED.md#inputs-file) yourself with the **same replace-by-key writer** as `prepare-template.sh`'s `put()` (drop any prior `KEY=` line with **`command grep`** — bypassing any interactive `grep` shim that aborts under `set -u` — then append `printf '%s=%q\n'`; mode-600 file). A non-secret never touches the prepare-script.
   - **Secret rows** (per §3's classification) **and every `auth`/`account` interactive login** are NEVER collected in-conversation (a secret typed at the agent lands in the transcript) and route to the prepare-script in step 5.

   Pre-announce the remaining `⏳`/`in-flow` items with their `bypass`; do NOT collect them now.
5. **Generate + hand off the prepare-script.** Assemble the user-run script per [Preflight is rendered](https://raw.githubusercontent.com/plow-pbc/openseed/main/SEED.md#preflight-is-rendered) step 4 and its MUST block — that contract owns what the script contains and how it behaves — adapting the reference [`prepare-template.sh`](prepare-template.sh) (a how-to pattern, not a sourced library); it carries ONLY routed **secret** rows (`read -s`, non-empty check only — **no format/reachability validation; do not hand-write checks here, that is what kept breaking**), interactive logins, and interactive-password `sudo` last. The script references collected values only as `$VAR`s (sourcing the just-written [inputs file](https://raw.githubusercontent.com/plow-pbc/openseed/main/SEED.md#inputs-file)), so the displayed bundle carries none. Every routed **secret** row MUST be written to the inputs file shell-quoted as `printf '%s=%q\n' KEY "$VALUE"` (non-secret rows were collected by the agent in step 4 via the question interface, not here) (the convention's [Inputs file](https://raw.githubusercontent.com/plow-pbc/openseed/main/SEED.md#inputs-file) rule), so a value with spaces or special chars sources safely — an unquoted multi-word value (e.g. `LD_OWNER_NAME=alpha beta`) makes `set -a; . <file>` try to run a later word as a command (`beta: command not found`) and aborts the run. The `SEED_PREPARE_OK=<nonce>` stamp is the ONE line written without `%q`. A [remote-host dep](https://raw.githubusercontent.com/plow-pbc/openseed/main/SEED.md#remote-host-seed-dependency)'s privileged system-package setup is probed at preflight and assembled into the script too — never discovered mid-install and handed back as a second script. This is the installer's job **regardless of how the consuming SEED frames its requirement rows** (a `satisfy: "pre-installed on the host"` assumption row still gets the probe + fold); the deterministic `requirements.sh` tier can't reach a remote host, so this is your explicit preflight step. Resolve the chicken-and-egg (probing packages needs SSH key-auth that the script's own `ssh-copy-id` may establish) with a **self-probing prepare-script**: within the privileged section, ordered AFTER `ssh-copy-id`, the script itself probes the now-reachable host for the missing package set + `sudo -n`, then runs `ssh -t <target> sudo apt-get install -y <missing set>` (on Debian trixie include Compose v2 explicitly — engine-present ≠ Compose-present) — one interactive entry here (copy-id → probe → install), never a mid-install hand-back. Skill mechanics: write it to `${XDG_CACHE_HOME:-$HOME/.cache}/seed/<name>-prepare.sh` (`<name>` is `$REPO_ROOT`'s basename, matching the inputs file), ensure the script initializes the inputs surface before any body block per the [Preflight is rendered](https://raw.githubusercontent.com/plow-pbc/openseed/main/SEED.md#preflight-is-rendered) MUST block's init clause (a login/sudo-only script still stamps); mint this hand-off's stamp nonce — unique per hand-off, alphanumeric (e.g. `openssl rand -hex 8`) — and bake it into the script's final statement (refusing assembly if any Requirements row claims the reserved `SEED_PREPARE_OK` key), then name the exact host the script runs on — the resolved **install host** (where the agent/install runs and the inputs file lives) — and ask the operator to run it in a real terminal **on that install host**; a [remote-host dep](https://raw.githubusercontent.com/plow-pbc/openseed/main/SEED.md#remote-host-seed-dependency)'s privileged blocks are not run there but transported over `ssh -t <target> sudo …` from it (above), never run on the dep's own machine. The agent's own shell has no TTY (`[ -t 0 ]` is false; a `read -s` there reads zero characters), so it cannot host the script's secret prompts or interactive-password `sudo` — an agent-inline `!`-prefix shell (`! bash <path>`) MUST NOT be relied on for secret/sudo input; the script's TTY guard trips on it, sending the operator to a regular terminal window. Detect exit 0 by **polling** the [inputs file](https://raw.githubusercontent.com/plow-pbc/openseed/main/SEED.md#inputs-file) for a line matching `^SEED_PREPARE_OK=<nonce>$` (this hand-off's nonce, per the [Preflight is rendered](https://raw.githubusercontent.com/plow-pbc/openseed/main/SEED.md#preflight-is-rendered) MUST block) and auto-continue the moment it appears — the script runs on the install host, so the stamp lands in the local inputs file and the agent polls it directly. Never ask the operator to relay success; inputs-file value keys alone are not success, and polling the one-line stamp detects completion in about a second without reading any collected value. Only a stamped run exempts its blocks from Phase 2 re-execution. No nonce-matching stamp at that point — a non-zero exit, or an operator "done" without one — is the failed-run case: stop, regenerate the prepare-script, and hand off afresh (per the MUST block). Verify the inputs file exists with the expected keys (presence/keys only — the stamp is the one value read; never read the others into context). **Validate the collected secrets — non-echoing, before any `sudo`:** apply the consuming SEED's `## Verification` checks via a probe that sources the inputs file in a subshell and prints only OK/FAIL, never the value, suppressing stderr — e.g. `( set -a; . "$INPUTS"; set +a; curl -fsSL "$LD_ICAL_URL" 2>/dev/null | grep -q 'BEGIN:VCALENDAR' && echo OK || echo FAIL )` (the `2>/dev/null` is load-bearing — curl's stderr can name the URL). On FAIL clear that key and re-hand-off; when a run has *both* a validatable secret *and* an interactive-`sudo` block, split into a collection half (secrets) then a privileged half (sudo) handed off only after the probe passes. Before Phase 1, ensure every install shell runs with the inputs file sourced (`set -a; . <file>; set +a`).
6. **Construct the single-shot prompt.** Present the replayable invocation — `set -a; . ${XDG_CONFIG_HOME:-$HOME/.config}/seed/<name>.env; set +a; /seed-install <target>` — so the operator (or an orchestrator) can re-run the whole install unattended. The prompt itself carries no values; real ones live only in the operator-controlled inputs file, never echoed or written into the SEED tree. For a truly zero-touch run the harness needs its permission-bypass posture — harness-owned modals sit outside the SEED's no-prompt contract; see [harness prompts](https://raw.githubusercontent.com/plow-pbc/openseed/main/SEED.md#harness-prompts).

The preflight is informational + collection — it never installs (the prepare-script's privileged blocks are the seed's own front-loaded `## Dependencies` steps, run by the operator), and it precedes Phase 1 of the procedure below. The operator interactions in the flow are the non-secret input questions in step 4 and the prepare-script run in step 5 — clone mode proceeds to the default install location without a prompt (see [§Inputs](#inputs)).

## Procedure

Once the SEED root is established, follow the [installation procedure](https://raw.githubusercontent.com/plow-pbc/openseed/main/SEED.md#seed-is-installed) literally.

The procedure is defined ONCE in SEED.md. Do not restate it here.

Operational overlay — timing + environment: capture the install **start** time with `date +%s` at the install start — **in clone mode the `git clone` command itself** (which runs *before* preflight, so clone-mode duration includes preflight), **in local/CWD mode the first `## Dependencies` action after preflight** (Phase 1 — recursing into the first SEED dependency, or Phase 2's first root block if there are no SEED dependencies — so local/CWD duration excludes preflight). At that same moment, sniff the three environment fields (`platform`, `os_version`, `hardware`) — they're static during the install (see [§Environment capture](#environment-capture)). The two self-reported identity fields (`agent`, `model`) are likewise **noted at the start and held** — they're static and known to the executing agent throughout (see [§Agent and model](#agent-and-model)). Once `$REPO_ROOT` exists and before anything is written there, **unlink any pre-existing `install-report.json`** (`rm -f`) so a crash before the terminal write leaves no stale prior-run report. Hold the start value and the env fields for the rest of the run. The install report is written **once**, at the terminal state — not per step, and only when the attempt reached a writable `$REPO_ROOT` and captured this start timestamp (a pre-start abort, or a clone-mode failure before `$REPO_ROOT` exists, emits only its terminal reason; see [§Install report](#install-report) and [§Write strategy](#write-strategy)).

## Install report

On reaching the terminal state, the skill writes ONE JSON artifact at `<repo-root>/install-report.json`. It is a flat, seven-field object — nothing else:

```json
{
  "success": true,
  "duration_seconds": 137,
  "platform": "darwin/arm64",
  "os_version": "macOS 15.3",
  "hardware": "Apple MacBook Air (M3, 2024)",
  "agent": "claude-code",
  "model": "claude-opus-4-8"
}
```

- `success` — boolean. `true` iff the install completed successfully end-to-end (terminal reason `success`); `false` on `failure` or `aborted`.
- `duration_seconds` — integer. Wall-clock seconds from install start to terminal.
- `platform` — string. `<os>/<arch>`, lowercase: `uname -s` (lowercased) + `/` + `uname -m` (e.g. `darwin/arm64`, `linux/x86_64`). Always determinable.
- `os_version` — string. Human OS version: macOS → `macOS <sw_vers -productVersion>` (e.g. `macOS 15.3`); Linux → `PRETTY_NAME` from `/etc/os-release` (e.g. `Ubuntu 24.04.1 LTS`); fallback `uname -sr`. Always set to something.
- `hardware` — string or `null`. Best-effort, human-readable machine model: macOS → `system_profiler SPHardwareDataType` (`Model Name` + `Chip`, e.g. `MacBook Pro (Apple M4 Max)`), falling back to `sysctl -n hw.model` (the identifier, e.g. `Mac16,6`); Linux → `/sys/class/dmi/id/sys_vendor` + `/sys/class/dmi/id/product_name` (e.g. `Dell Inc. XPS 15 9520`). `null` when undeterminable.
- `agent` — string or `null`. The coding agent/harness performing the install, self-reported by the executing agent — a short lowercase slug, e.g. `claude-code`, `codex`, `cursor`. `null` when the agent cannot identify itself.
- `model` — string or `null`. The model running the install, self-reported by the executing agent — its canonical model id, e.g. `claude-opus-4-8`. `null` when undeterminable.

`platform`/`os_version`/`hardware` are flat top-level strings (`hardware` may be `null`) — NOT a nested `environment` object; the old rich profile block is deliberately not restored. `agent`/`model` are likewise flat top-level strings (either may be `null`). No per-step breakdown, no per-requirement status, no summary prose, no item array. The report is exactly these seven keys. See [§Environment capture](#environment-capture) for how the three host fields are sniffed and [§Agent and model](#agent-and-model) for how the two identity fields are self-reported.

### Timing

Capture two timestamps and subtract:

1. **Start** — record `date +%s` at the install start and hold the value for the rest of the run. Per root SEED.md's [install state machine](https://raw.githubusercontent.com/plow-pbc/openseed/main/SEED.md#install-state-machine), the start differs by input mode: in **clone mode** it is the `git clone` command itself — which runs *before* preflight, so clone-mode duration **includes** preflight; in **local/cwd mode** (no clone) it is the first `## Dependencies` action *after* preflight — Phase 1's recursion into the first SEED dependency (or Phase 2's first root block if the SEED declares no SEED dependencies) — so local/cwd duration **excludes** preflight (the requirements report + prepare-script run before this start).
2. **End** — when the run reaches the terminal state, record `date +%s` again.
3. `duration_seconds = end − start` (whole seconds; the difference of two `date +%s` values is already an integer).

Hold the start value across the run (a shell variable or a noted constant) so the end computation is reliable. If the run aborts or fails **after** the start timestamp AND a writable `$REPO_ROOT` exists, compute the delta to the abort point and write the seven-field report with `success: false`. Two cases write **no** `install-report.json` and emit only the terminal reason: a **pre-start abort** — before the start timestamp is captured (e.g. local/CWD mode with no readable `SEED.md`) — and a **clone-mode failure before `$REPO_ROOT` exists** — where the start timestamp was taken at the `git clone` but it failed, so there is no writable repo root to hold the report. Independently of outcome, any pre-existing `install-report.json` is unlinked at the start of a run (see [§Write strategy](#write-strategy)), so a crash between the start timestamp and the terminal write leaves no stale prior-run report.

### Environment capture

Sniff `platform`, `os_version`, and `hardware` **once**, at the same moment as the start-timestamp capture (§Timing step 1) — the environment is static for the duration of an install, so a single capture is enough. Sniffing is **best-effort and MUST NEVER fail or abort the install**: a failed or empty probe degrades that field, it does not error.

- **`platform`** — `"$(uname -s | tr '[:upper:]' '[:lower:]')/$(uname -m)"`. Always determinable.
- **`os_version`** — macOS: `macOS $(sw_vers -productVersion)`. Linux: the `PRETTY_NAME` value from `/etc/os-release`. If neither yields a value, fall back to `uname -sr`. Always set something.
- **`hardware`** — macOS: read `system_profiler SPHardwareDataType` and combine its `Model Name` and `Chip` into one human string (e.g. `MacBook Pro (Apple M4 Max)`); if that is empty, use `sysctl -n hw.model` (the model identifier, e.g. `Mac16,6`). Linux: combine `/sys/class/dmi/id/sys_vendor` and `/sys/class/dmi/id/product_name` (e.g. `Dell Inc. XPS 15 9520`). If nothing resolves, set `hardware` to `null`. **Do NOT build a model-id→marketing-name lookup table** — capture the closest native human string and stop; the marketing year (e.g. "(2024)") may be absent, and that's acceptable.

Hold the three values alongside the start timestamp and write them into the report at the single terminal write.

### Agent and model

`agent` and `model` are **self-reported by the executing agent** — they are NOT shell-sniffable like the environment fields, so do not probe env vars or run a command to derive them. The agent running this install already knows its own identity and the model it is running on; record those directly:

- **`agent`** — the coding agent/harness performing the install, as a short lowercase slug (e.g. `claude-code`, `codex`, `cursor`). If the executing agent genuinely cannot name itself, set `agent` to `null` — never guess or fabricate a harness.
- **`model`** — the canonical model id the agent is running on (e.g. `claude-opus-4-8`). Use the exact id, not a marketing name. If the model is genuinely unknown, set `model` to `null`.

Both are static for the run; note them at install **start** alongside the environment fields and **hold** them with the report state, the same capture-and-hold the host fields use (per [§Timing](#timing)). Like the environment sniff, this MUST NEVER fail or abort the install: an unknown value degrades to `null`, it does not error.

### Write strategy

**Clear stale state first.** Once `$REPO_ROOT` is established on disk and before the first install action, `rm -f "$REPO_ROOT/install-report.json"` to unlink any pre-existing report (`rm -f` removes a symlink without following it, and silently no-ops when absent — a fresh clone has none). This guarantees a rerun that captures a start timestamp then crashes/cancels before terminal does not leave the OLD report in place.

The on-disk report is then a single write, at the terminal state, and **only for an attempt that reached a writable `$REPO_ROOT` on disk and captured the install-start timestamp**. The outcome and duration are knowable only at the end (the environment fields are captured at the start and held in memory until then), so there is no incremental ledger. Write **symlink-safely**: create an **exclusive temp file with an unpredictable name** in `$REPO_ROOT` — `tmp=$(mktemp "$REPO_ROOT/.install-report.json.XXXXXX")`, which O_EXCL-creates the file and so never follows or races a pre-existing path — write the seven-field JSON to it, then `mv -f "$tmp" "$REPO_ROOT/install-report.json"` (atomic rename). The existing `install-report.json` is **never opened for writing**: the unpredictable exclusive temp closes the predictable-`$$`/symlink-race hole, and the final rename *replaces* a malicious `install-report.json` symlink at the destination rather than following it to clobber an arbitrary user-writable file. Write once, on reaching `terminal`, for every outcome that reached `$REPO_ROOT` with a start timestamp (success, failure, post-start abort). Outcomes that did **not** reach a writable `$REPO_ROOT` — a **pre-start abort** (e.g. local/CWD mode with no readable `SEED.md`) or a **clone-mode failure before `$REPO_ROOT` exists** (the `git clone` itself fails) — write no on-disk report; they emit only the terminal reason (`aborted` / `failure`). SEED authors SHOULD add `install-report.json` to `.gitignore` so reruns don't accumulate report churn in the SEED's own history.

### Feedback upload

When the root SEED's `## Feedback` opts in (per [feedback reporting](https://raw.githubusercontent.com/plow-pbc/openseed/main/SEED.md#feedback-is-reported)) and the install ran in clone mode, the skill offers — once, after the post-terminal summary — to upload `install-report.json` to the seed backend. **The dispatch IS the upload: the seven-field file is POSTed verbatim, alongside a separate sanitized `clone_url` field (for attribution) — the report file itself stays seven fields.**

- **Gate.** Offer only when ALL hold: the install reached `terminal`; **a report was actually written** (a post-start attempt that reached a writable `$REPO_ROOT` — a pre-start abort or a clone-mode failure before `$REPO_ROOT` exists produced no `install-report.json` to upload); it was the **root** SEED in **clone mode**; `## Feedback` resolves to `(default)`; and no opt-out is set (`SEED_FEEDBACK=off`, `~/.config/seed/feedback.json` `{"enabled": false}`, or `## Feedback` `(none)`/absent). Otherwise skip silently — no offer.
- **Offer.** One line naming the destination and what is sent — e.g. `Upload the install report (+ this repo's clone URL, for attribution) to https://seeds.plow.co/api/v1/upload-install-report? [y/N]`. Upload ONLY on an explicit yes (`tier-2`); no answer, no, or a non-interactive run skips. Consent is asked fresh each eligible run — no remembered "always yes".
- **Upload.** From `$REPO_ROOT`, run the multipart POST:

  ```bash
  curl -X POST https://seeds.plow.co/api/v1/upload-install-report \
    -F "install-report.json=@install-report.json" \
    -F "clone_url=<sanitized canonical clone URL>"
  ```

  The endpoint is the `## Feedback` `(default)` endpoint, resolved per [body resolution](https://raw.githubusercontent.com/plow-pbc/openseed/main/SEED.md#body-resolution).
- **Payload is the file as-is, plus a seed-identity field alongside it.** The seven-field report carries no paths, usernames, secrets, or per-step detail — only coarse host-class descriptors (`platform`, `os_version`, `hardware`) and the self-reported tooling identity (`agent`, `model`), none of which identify the operator; the per-run consent is the privacy control. Because the flat report carries no `clone_url`, the upload adds a **separate `clone_url` form field** — the sanitized canonical clone URL (clone-URL hygiene already applied: no userinfo, query, or fragment) — so the backend (`upload-install-report` resolves the producing SEED from the request's url / owner+name) can attribute the report. This is the ONLY seed-identity field, and it rides *alongside* the report, never inside it; the report payload itself carries no operator identity (its `agent`/`model` identify the coding harness, not the operator). (If a SEED author wants nothing transmitted at all, `## Feedback\n\n(none)` disables the offer.)
- **Failure is silent.** A non-2xx, timeout, or network error MUST NOT change the install's terminal reason or surface as an install failure — drop it (a one-line stderr note is fine). No retry, no offline queue.

## Post-terminal report

On reaching the `terminal` state, the skill emits a brief user-facing summary. For a **post-start terminal attempt** (one that wrote the report), the summary is the flat seven fields: state the outcome (`success: true` / `false`), the `duration_seconds`, the captured environment (`platform` / `os_version` / `hardware`), and the self-reported tooling (`agent` / `model`); on `success` offer the suggested next action with auto-run-if-safe; on a post-start `failure` / `aborted`, name the terminal reason reached. An attempt that wrote **no report** — a pre-start abort, or a clone-mode failure before `$REPO_ROOT` exists — summarizes only its terminal reason (no duration, environment, report path, or upload). No per-step breakdown is rendered — there are no per-step items.

After the summary — **only when the report was actually written** (a post-start terminal attempt) — the skill prints the absolute path to `install-report.json`, then, when the [feedback upload](#feedback-upload) gate is satisfied (root clone-mode install, `## Feedback` `(default)`, no opt-out), offers to upload that report to the seed backend and runs the POST on an explicit yes. A pre-start abort or a clone-mode failure before `$REPO_ROOT` exists skips both: there is no report path to print and nothing to upload.

## Non-Goals for v1

- No resume from partial install (rerun from the top).
- No parallel sub-SEED installation (leaves-first stays sequential).
- No dry-run flag (the announce-then-execute line IS the review surface).
- No alternate transport beyond git URLs.
- No streaming of the report to a remote sink during the run — local file only; the feedback dispatch is a single post-terminal upload of the finished file, on explicit per-run consent.
