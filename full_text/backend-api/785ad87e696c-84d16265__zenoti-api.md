Zenoti supports two auth methods. Both are sent via the `Authorization` header.

### API Key Auth (server-side)
```
Authorization: apikey <api_key>
```
- Valid for **1 year**; does not auto-expire
- Scope: global master data access, no per-user restrictions
- Best for: server-side integrations, data pipelines
- Rotate via Zenoti Admin UI; old key stays valid **1 week** after rotation

### Bearer Token Auth (user-scoped)
```
Authorization: bearer <access_token>
```
- Access token valid for **24 hours**
- Refresh token valid for **90 days**
- Scoped to employee/guest permissions and security roles
- Best for: client-side apps, guest-facing flows

### Token Flow

**Generate token:**
```
POST https://api.zenoti.com/v1/tokens
Content-Type: application/json

{
  "account_name": "yourorg",        // from yourorg.zenoti.com
  "user_name": "employee_username",
  "password": "employee_password",
  "grant_type": "password",
  "app_id": "<GUID>",               // from backend app setup
  "app_secret": "<secret>",         // from backend app setup
  "device_id": "<GUID>"             // unique per device
}
```
Response returns: `access_token`, `access_token_expiry`, `refresh_token`, `refresh_token_expiry`, `token_type` ("bearer"), `token_id`, `app_id`, `user_type` ("Guest" or "Employee").

**Refresh token:**
```
POST https://api.zenoti.com/v1/tokens
Content-Type: application/json

{
  "refresh_token": "<refresh_token>",
  "grant_type": "refresh_token"
}
```
- Deactivates ALL existing access tokens and issues new ones
- Refresh token is **single-use** -- a new one is issued each time
- Only refresh when the access token has expired or is about to expire

**Revoke all tokens:**
```
DELETE https://api.zenoti.com/v1/tokens/sessions/revoke
```
Immediately revokes all active access tokens.

### API Key Setup

1. Zenoti Admin > Organization > Configuration > Apps (under Integrations)
2. Create a backend app: Name, URI, Description, Login User Type (Guest/Employee), Source App type
3. Source App types: `External CMA` (mobile), `External Webstore` (web), `Client App`, `Bot`
4. After creation: copy Application ID, Secret, and generated API Key before navigating away

## 3. Authorization (API Groups)

> **Deep-dive file:** `guides/zenoti-api-groups-1.md` — JWT groups, API key groups, permission model

Two permission layers must both allow access:
1. **Security role permission** -- the user's role in the org (configured in Admin > Security Roles)
2. **Backend app group permissions** -- JWT Groups (token auth) or APIKEY Groups (API key auth)

If the user has app group permission but NOT the security role permission, the API returns an error.

Required role permissions for API management:
- Admin > Organization > Security Roles > Administrator > API
- Check: `Manage API Keys`, `Manage Apps`, `Manage Automation`

## 4. Pagination

> **Deep-dive file:** `guides/pagination.md` — full examples, error handling

| Parameter | Type | Default | Max | Description |
|-----------|------|---------|-----|-------------|
| `page` | int | 1 | -- | Page number |
| `size` | int | 10 | 100 | Records per page |

Response includes:
```json
"page_info": {
  "total": 27,
  "page": 1,
  "size": 10
}
```

Requesting `size` > 100 returns HTTP `422`: `"You cannot request more than 100 items."`

**Note:** Some endpoints use `page_num`/`num_records` instead (e.g., loyalty points history, opportunities use `page_num`/`records`).

## 5. Rate Limits

> **Deep-dive file:** `guides/api-rate-limits-1.md` — token bucket details, retry strategies, queue recommendations

| Item | Value |
|------|-------|
| Default limit | **60 calls per minute** |
| Bucket type | Token bucket -- 60 tokens added every 60 seconds, max bucket size 60 |
| Exceeded response | HTTP `429` |
| Retry header | `Retry-After` (seconds to wait) |

Response headers on every call:
- `Organization-RateLimit-Limit`: `60;w=60;b=60` (rate;window;bucket_max)
- `RateLimit-Remaining`: calls remaining
- `RateLimit-Reset`: seconds until bucket refills

Contact Zenoti account manager for higher limits.

## 6. Error Codes

> **Deep-dive file:** `guides/response-and-error-codes.md` — full error table with examples

| Code | Meaning |
|------|---------|
| `200` | Success (`"error": null` in body) |
| `4XX` | Client-side error |
| `422` | Pagination limit exceeded (>100 records) |
| `429` | Rate limit exceeded |
| `5XX` | Server-side error -- contact `apisupport@zenoti.com` |
| `503` | Traffic spike -- usually resolves within 5 minutes |

All error responses include: `"error": { "code": ..., "message": ... }`

| Timeout | 10 seconds per request |

| Auto-deactivation | After 20 consecutive failures; must re-enable manually |
| Requirement | Zenoti API package subscription |

### Event Envelope

Every webhook payload wraps event-specific `data` in:
```json
{
  "id": "webhook_call_id",
  "event_id": "event_type_id",
  "event_schema": "v1",
  "event_resource": "Guest",
  "event_type": "Guest.Created",
  "event_timestamp": "2024-01-15T10:30:00Z",
  "data": { ... }
}
```

**Note:** Some events omit the envelope wrapper in practice. Always route on `event_type`, not `event_resource` (which can be null).

## 10. Common Transaction Workflows

### Service Booking Flow

> **Full walkthrough:** `guides/service-booking-apis.md` + `guides/step-1-create-a-booking.md` through `guides/step-4-collect-payment-for-the-invoice.md`

1. `GET /v1/guests/search` -- find guest
2. `GET /v1/Centers/{center_id}/services` -- browse services
3. `POST /v1/bookings` -- create booking -> get `booking_id`
4. `GET /v1/bookings/{booking_id}/slots` -- get available times
5. `POST /v1/bookings/{booking_id}/slots/reserve` -- lock a slot
6. `POST /v1/bookings/{booking_id}/slots/confirm` -- confirm -> get `invoice_id`
7. `GET /v1/invoices/{invoice_id}` -- verify invoice
8. `POST /v1/invoices/{invoice_id}/online_payments` -- collect payment
9. `PUT /v1/invoices/{invoice_id}/close` -- close invoice

### Product Sale Flow

> **Full walkthrough:** `guides/product-sale-apis.md` + `guides/step-1-choose-a-product.md` through `guides/step-3-collect-payment-for-the-invoice.md`

1. `GET /v1/centers/{center_id}/products` -- browse products
2. `GET /v1/guests/search` -- find guest
3. `POST /v1/invoices/products` -- create invoice -> get `invoice_id`
4. Collect payment + close invoice (same as steps 7-9 above)

### Membership Sale Flow

> **Full walkthrough:** `guides/membership-sale-apis.md` + `guides/step-1-select-a-membership.md` through `guides/step-4-close-the-invoice-and-send-a-confirmation-email-to-the-guest.md`

1. `GET /v1/centers/{center_id}/memberships` -- browse memberships
2. `GET /v1/guests/search` -- find guest
3. `POST /v1/invoices/memberships` -- create invoice -> get `invoice_id`
4. Collect payment
5. `PUT /v1/invoices/{invoice_id}/close` -- close invoice
6. `PUT /v1/invoices/{invoice_id}/email` -- send confirmation

### Gift Card Sale Flow

> **Full walkthrough:** `guides/gift-card-sale-apis.md` + `guides/step-1-select-a-gift-card-template.md` through `guides/step-4-send-the-gift-card-sale-email-to-the-guest.md`

## 11. Data Extraction Tips

- **Pagination ceiling:** Max 100 records per page. Loop with `page` incrementing until `page * size >= page_info.total`.
- **Date range limits:** Appointments list max 7 days. Employee schedules max 30 days. Room blockouts max 10 days. Break large ranges into batches.
- **`expand` parameter:** Many endpoints support `expand` to include nested objects. Always use it to reduce call count (e.g., `expand=InvoiceItems,Appointments,Transactions` on invoices).
- **Deprecated reports:** `collections_report` and `salesreport` have 7-day max ranges and are deprecated. Use `flat_file` report endpoints instead.
- **Guest search behavior:** Depends on org-level `SearchAcrossCenter` setting. Use `search_across_zone=true` to search across all centers.
- **Membership status codes:** -1=all, 1=active, 2=inactive, 3=frozen, 4=cancelled, 5=expired.
- **Rate limiting:** At 60 calls/min, a full sync of a large org requires careful pacing. Cache static data (services, therapists, memberships) and only poll transactional data (appointments, invoices) frequently.
