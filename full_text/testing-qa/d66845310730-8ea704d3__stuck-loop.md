# Stuck Loop

When you've been stuck for more than ~15 minutes - same file open,
same error, no new information - you are not making progress. Stop
guessing. Run this skill.

## Definition of "stuck"

- Same error message for 3+ attempts.
- Same file open for >15 minutes with no edit committed.
- Reading the same paragraph of the same doc twice.
- Compiling the same code with the same outcome.
- Re-running the same test expecting it to pass this time.

If any of these are true, you are stuck. Move to the prescriptions
below; do NOT keep guessing.

## Prescriptions (run in order, stop when one breaks the stuck-ness)

### 1. Restate

Write the problem in your own words. Treat this as rubber-ducking;
saying it out loud (or to the user) is the whole point.

### 2. Reduce

Strip a constraint and solve the reduced version. Then re-introduce
the constraint and see exactly where it breaks. This converts "stuck
on a big thing" into "stuck on a small thing I can name."

### 3. Divide

Block out the piece you are stuck on; proceed with another piece. The
new piece often informs the stuck piece. This is also how the manager
session keeps shipping while a subagent is stuck.

### 4. Look for an analogy

Search the codebase for a similar shape. Concrete prompts:

- A similar HMAC-validated webhook somewhere in the repo.
- A similar idempotent Kafka consumer somewhere in the repo.
- A similar ORM migration with the same shape (numeric-prefixed for
  Drizzle, timestamp-prefixed for TypeORM / Sequelize / Knex).
- A similar React state machine on the client side.

Compare your stuck piece to the working pattern. The diff is usually
the bug.

### 5. Experiment in isolation

Build the smallest possible repro: a single file with the function in
question, hand-written input, expected output. Run it. The result
either confirms your model (and you're stuck somewhere else) or
disproves your model (and you've found the bug).

### 6. Verify pointer / identity / type

When two things "should be the same" or "should be different,"
prove it. Log the actual values. Check the actual types at the actual
boundary. Type assertions in TypeScript hide this class of bug.

### 7. Walk away

When the above fail, stop. Run a separate task for 10-20 minutes -
review a different MR, write a different test, take a literal walk.
The book is explicit: "do something else, something that keeps your
blood flowing but doesn't make your brain hurt." Background processing
usually finishes the problem.

### 8. Ask, precisely

If the above have not worked, ask the user (or a colleague) with a
help request shaped like:

- "Here is the code: ..."
- "Here is what it does: ..."
- "Here is what I expected: ..."
- "Here is what I have ruled out: ..."
- "Here is exactly where I am stuck."

A precise help request is itself half a debug session.

## Anti-patterns

- Trying the same change with different syntax.
- Reading the same error and "thinking harder."
- Adding `console.log` everywhere without a hypothesis.
- Restarting the dev server / IDE / machine without first restating
  the bug.
- Asking for help with "it doesn't work."

## When to surface to the user

After ALL eight prescriptions, if still stuck on a correctness issue
(ledger drift, double-claim, signature mismatch, broken migration),
STOP. Surface to the user with the precise help request from step 8.
Don't keep looping silently.
