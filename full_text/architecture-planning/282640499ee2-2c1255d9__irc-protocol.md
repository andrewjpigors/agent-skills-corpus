# IRC Protocol

This skill is a **protocol concept teacher**.

It teaches the student what the IRC protocol looks like at the conceptual level — message structure, connection lifecycle, registration, commands, channels, operators, modes, and numeric replies — but only the subset required by the mandatory ft_irc subject.

It behaves like a senior engineer explaining protocol concepts to a junior 42 student who has never seen IRC before: patient, precise, grounded in the subject, and focused on building understanding before implementation.

- A teacher of IRC protocol concepts.

- The bridge between "I read the subject" and "I understand what IRC messages look like."

## Protocol Concepts

### 1. What IRC Is

**Why it exists:** IRC (Internet Relay Chat) is a text-based communication protocol created in 1988. It defines how clients and servers exchange messages in real time. The ft_irc project requires building an IRC server (MR-12) — understanding what IRC is at the protocol level is the foundation.

**Relation to the subject:** The subject says to build "an IRC server" (MR-12). It does not say "a chat server" or "a custom protocol server." The protocol is IRC, which means messages must follow IRC conventions so that a real IRC client (MR-24, MR-25, MR-26) can connect and work.

**Related MR IDs:** MR-12, MR-24, MR-25, MR-26

**Key points:**

- IRC is a client-server protocol. Clients connect to a server.
- The server you are building is the server side only (MR-12). You do not build a client (MR-13).
- No server-to-server communication (MR-14). Your server stands alone.
- Communication happens over TCP/IP (MR-18).

**Common mistakes:**

- Building a custom protocol instead of following IRC message format. The reference client expects IRC — not a homebrew format.
- Trying to implement server-to-server linking (S2S). The subject explicitly forbids this.
- Confusing "IRC server" with "chat application." IRC has a specific message format and registration flow.

---

### 2. Client ↔ Server Communication Model

**Why it exists:** IRC separates concerns between client and server. The client sends commands; the server processes them and sends responses. This asymmetry defines the entire interaction model.

**Relation to the subject:** The subject requires building the server side (MR-12), forbids building a client (MR-13), forbids server-to-server (MR-14), and requires TCP/IP communication (MR-18). The only valid data flow is: client → server → client(s).

**Related MR IDs:** MR-12, MR-13, MR-14, MR-18, MR-19

**Key points:**

- Clients send **commands** to the server (e.g., authentication, joining a channel, sending a message).
- The server sends **replies** back to clients (e.g., confirmation, error, forwarded message).
- The server may send messages to **multiple clients** simultaneously (MR-32 — channel message forwarding).
- Multiple clients connect simultaneously (MR-19). The server serves them all.

**Common mistakes:**

- Treating the server as a relay between two specific clients. The server manages all connections and routes messages based on IRC rules.
- Forgetting that the server also initiates messages to clients (e.g., forwarding channel messages, sending numeric replies).

---

### 3. IRC Message Structure

**Why it exists:** Every single interaction between client and server is an IRC message. Understanding the message format is essential because every command, every reply, every forwarded message follows the same structure.

**Relation to the subject:** The subject requires handling partial data (MR-43), which means the server must understand where one message ends and the next begins. The reference client (MR-25, MR-26) expects standard IRC message format.

**Related MR IDs:** MR-43, MR-25, MR-26

**Key points:**

An IRC message has this general structure:

```
[:<prefix>] <command> [<params>] [:<trailing>]\r\n
```

- **Prefix** (optional): Indicates the source of the message. Servers add a prefix to messages they relay. Clients typically do not send a prefix.
- **Command**: The verb — either a named command (like `NICK`, `JOIN`, `PRIVMSG`) or a three-digit numeric code (like `001`, `433`).
- **Parameters**: Space-separated arguments to the command. The number and meaning depend on the command.
- **Trailing parameter**: The last parameter, introduced by a colon (`:`). It can contain spaces. Used for message text, topic text, etc.
- **CRLF**: Every message is terminated by `\r\n` (carriage return + line feed).

**Examples of real IRC messages (conceptual):**

| Direction | Message | Meaning |
| --- | --- | --- |
| Client → Server | `NICK alice\r\n` | Client wants nickname "alice" |
| Client → Server | `USER alice 0 * :Alice Smith\r\n` | Client sets username and real name |
| Client → Server | `JOIN #general\r\n` | Client joins channel #general |
| Client → Server | `PRIVMSG #general :Hello everyone\r\n` | Client sends a message to #general |
| Server → Client | `:server 001 alice :Welcome\r\n` | Server sends welcome reply (numeric 001) |
| Server → Clients | `:alice PRIVMSG #general :Hello everyone\r\n` | Server forwards the message to all other channel members |

**Common mistakes:**

- Forgetting the `\r\n` terminator. IRC uses CRLF, not just `\n`. The subject's `nc -C` test uses CRLF.
- Confusing the prefix with a parameter. The prefix starts with `:` at the very beginning of the message — the trailing parameter starts with `:` after the command and earlier parameters.
- Assuming messages arrive complete. The subject explicitly requires handling partial data (MR-43) — a message may arrive in fragments across multiple `recv` calls.

### 4. CRLF Termination

**Why it exists:** IRC uses `\r\n` (CRLF) to mark the end of each message. This is how the server knows where one command ends and the next begins.

**Relation to the subject:** MR-43 requires the server to aggregate partial data and rebuild complete commands. The CRLF delimiter is what defines "complete." The subject's `nc -C` test example sends data with CRLF endings.

**Related MR IDs:** MR-43, MR-25, MR-26

**Key points:**

- Every IRC message ends with `\r\n`.
- The server must not process a command until the full CRLF-terminated message has been received.
- Data may arrive in fragments — the server must buffer until `\r\n` is found.
- Multiple complete messages may arrive in a single `recv` — the server must handle this too.

**Common mistakes:**

- Splitting only on `\n` and ignoring `\r`. Some clients send only `\n`, but the protocol standard is `\r\n`. A robust server should handle both, but the protocol expectation is CRLF.
- Processing data before a complete CRLF-terminated message is assembled.
- Not handling multiple messages in a single buffer read.

### 5. Connection Lifecycle

**Why it exists:** IRC defines a specific sequence for how a client connects, registers, interacts, and eventually disconnects. Understanding this lifecycle is essential because the server must track each client's state.

**Relation to the subject:** The subject requires authentication (MR-27), nickname (MR-28), username (MR-29), and then interaction (MR-30, MR-31). This is the connection lifecycle.

**Related MR IDs:** MR-19, MR-25, MR-27, MR-28, MR-29

**Key points:**

The lifecycle has distinct stages:

1. **TCP connection** — The client opens a TCP connection to the server's port (MR-03, MR-18).
2. **Registration** — The client sends password, nickname, and username commands. Until registration completes, the client cannot use most server features.
3. **Active session** — The registered client can join channels, send messages, use operator commands, etc.
4. **Disconnection** — The client disconnects (voluntarily or due to error). The server cleans up the client's state.

**Common mistakes:**

- Allowing unregistered clients to join channels or send messages. Registration must complete first.
- Not tracking which stage each client is in. The server must know whether a client has completed registration.
- Crashing when a client disconnects unexpectedly (MR-15, MR-16).

### 6. Registration Sequence

**Why it exists:** Before a client can do anything meaningful, it must identify itself to the server. The registration sequence establishes the client's password, nickname, and username.

**Relation to the subject:** The subject requires authentication (MR-27), setting a nickname (MR-28), and setting a username (MR-29). The connection password (MR-04) must be validated. The reference client (MR-25) will send these commands as part of its connection flow.

**Related MR IDs:** MR-04, MR-27, MR-28, MR-29, MR-25

**Key points:**

The typical IRC registration flow involves three commands:

- **PASS** — Sends the connection password. Must match the server's password (MR-04).
- **NICK** — Sets the client's nickname (MR-28).
- **USER** — Sets the client's username and real name (MR-29).

Registration is considered complete when all three have been successfully processed. The server then typically sends a welcome numeric reply (e.g., 001).

> **Ambiguity A1:** The subject requires authentication and a connection password but does not name `PASS`, `NICK`, or `USER` explicitly. The reference client determines the exact commands. In practice, all standard IRC clients send these three commands.

**Common mistakes:**

- Not requiring the password before allowing registration to complete. The subject says every connecting client must authenticate (MR-27) using the server's password (MR-04).
- Accepting `NICK` or `USER` before `PASS`. The typical flow is PASS first, then NICK and USER (in either order).
- Not handling the case where a nickname is already taken.
- Allowing interaction before registration is complete.

### 7. Nickname

**Why it exists:** The nickname is the primary identity of a user on the IRC network. Every other user sees and uses the nickname to communicate.

**Relation to the subject:** MR-28 requires the ability to set a nickname. Nicknames are used in message routing, channel membership, and operator commands.

**Related MR IDs:** MR-28

**Key points:**

- The nickname is set via the NICK command during registration.
- Nicknames must be unique — two clients cannot have the same nickname simultaneously.
- A client can change their nickname after registration.
- Nicknames appear in message prefixes when the server relays messages.

**Common mistakes:**

- Allowing duplicate nicknames.
- Not updating references (channel membership, etc.) when a nickname changes.
- Confusing nickname with username — they are different (see below).

---

### 8. Username

**Why it exists:** The username is metadata about the user, set during registration. It is distinct from the nickname and is part of the user's full identity.

**Relation to the subject:** MR-29 requires the ability to set a username. The username is sent via the USER command during registration.

**Related MR IDs:** MR-29

**Key points:**

- The username is set once during registration and typically does not change.
- The USER command also includes a "real name" parameter (the trailing parameter).
- The username appears in the user's full hostmask (e.g., `nick!user@host`) which the server uses in message prefixes.

**Common mistakes:**

- Confusing username with nickname. The nickname is the visible display name; the username is metadata.
- Ignoring the real name parameter in the USER command.
- Allowing the username to be changed after registration (it typically cannot be).

---

### 9. Message Prefix

**Why it exists:** When the server forwards a message from one client to another, it needs to identify who sent it. The prefix provides this source identification.

**Relation to the subject:** The reference client (MR-25, MR-26) expects properly formatted messages with prefixes. Without correct prefixes, the reference client cannot display who sent a message.

**Related MR IDs:** MR-25, MR-26, MR-32

**Key points:**

- The prefix starts with `:` at the very beginning of a message.
- The server adds the prefix when relaying messages. The client does not typically send a prefix.
- The prefix usually contains the sender's full hostmask: `nick!user@host`.
- For server-generated messages (like numeric replies), the prefix is the server name.

**Examples:**

| Message | Prefix | Meaning |
| --- | --- | --- |
| `:alice!alice@localhost PRIVMSG #general :Hello\r\n` | `alice!alice@localhost` | Message from user alice |
| `:server 001 alice :Welcome\r\n` | `server` | Reply from the server |

**Common mistakes:**

- Not adding a prefix when relaying messages. The receiving client needs to know who sent the message.
- Sending malformed prefixes that break the reference client's display.
- Confusing prefix format with the trailing parameter (both use `:`).

### 10. Command

**Why it exists:** The command is the verb of an IRC message. It tells the server what action the client wants to perform, or tells the client what kind of response the server is sending.

**Relation to the subject:** The subject explicitly names four commands (MR-34–MR-37: KICK, INVITE, TOPIC, MODE) and implies five more through required behaviors (MR-27–MR-31: authentication, nickname, username, join, private messages).

**Related MR IDs:** MR-27–MR-31, MR-34–MR-37

**Key points:**

- Commands are uppercase words (e.g., `NICK`, `JOIN`, `PRIVMSG`, `KICK`, `MODE`).
- Some commands are sent by clients (e.g., `NICK`, `JOIN`).
- Numeric reply codes are also commands — three-digit numbers sent by the server (e.g., `001`, `433`).
- Each command has its own parameter format and semantics.

**Subject-required commands (explicitly named):**

| Command | Subject Description | MR ID |
| --- | --- | --- |
| KICK | Eject a client from the channel | MR-34 |
| INVITE | Invite a client to a channel | MR-35 |
| TOPIC | Change or view the channel topic | MR-36 |
| MODE | Change the channel's mode | MR-37 |

**Subject-implied commands (from required behaviors):**

| Behavior | Typical Command | MR ID | Ambiguity |
| --- | --- | --- | --- |
| Authenticate | PASS | MR-27, MR-04 | A1 |
| Set nickname | NICK | MR-28 | — |
| Set username | USER | MR-29 | — |
| Join channel | JOIN | MR-30 | A3 |
| Private messages | PRIVMSG | MR-31 | A2 |

**Common mistakes:**

- Implementing commands that the subject does not require (e.g., `WHOIS`, `LIST`, `OPER`) before the mandatory ones are complete.
- Forgetting that the reference client (MR-25, MR-26) may require additional commands beyond the mandatory set.

### 11. Parameters

**Why it exists:** Parameters carry the data that a command operates on — target nicknames, channel names, mode flags, message text, etc.

**Relation to the subject:** Every mandatory command uses parameters. The subject does not specify parameter formats directly, but the reference client (MR-25, MR-26) expects standard IRC parameter handling.

**Related MR IDs:** MR-25, MR-26, MR-34–MR-42

**Key points:**

- Parameters are space-separated.
- The number of parameters varies per command.
- The last parameter can be a **trailing parameter** introduced by `:`. It can contain spaces.

**Examples:**

| Message | Command | Parameters | Trailing |
| --- | --- | --- | --- |
| `NICK alice\r\n` | NICK | `alice` | — |
| `USER alice 0 * :Alice Smith\r\n` | USER | `alice`, `0`, `*` | `Alice Smith` |
| `PRIVMSG #general :Hello world\r\n` | PRIVMSG | `#general` | `Hello world` |
| `KICK #general bob :Goodbye\r\n` | KICK | `#general`, `bob` | `Goodbye` |
| `MODE #general +k secret\r\n` | MODE | `#general`, `+k`, `secret` | — |

**Common mistakes:**

- Not parsing the trailing parameter correctly. Everything after `:` (when it's the last parameter marker) is one parameter, including spaces.
- Hardcoding the number of parameters. Different commands have different parameter counts.

---

### 12. Trailing Parameter

**Why it exists:** Many IRC messages need a parameter that contains spaces — message text, topic text, real names, kick reasons. The trailing parameter solves this by designating the last parameter as free-form text.

**Relation to the subject:** Private messages (MR-31), channel messages (MR-32), topic text (MR-36), and kick reasons (MR-34) all use trailing parameters.

**Related MR IDs:** MR-31, MR-32, MR-34, MR-36

**Key points:**

- Introduced by `:` after the last regular parameter.
- Contains everything from the `:` to the end of the message (before `\r\n`).
- Can contain spaces.
- Only one trailing parameter per message — it is always the last one.

**Common mistakes:**

- Splitting the trailing parameter on spaces. The trailing parameter is one atomic value.
- Confusing the prefix `:` (at position 0) with the trailing `:` (after parameters). They have completely different meanings.

### 13. Numeric Replies

**Why it exists:** When the server needs to respond to a client — whether to confirm success, report an error, or provide information — it uses numeric reply codes. These are standardized three-digit numbers that the client can interpret programmatically.

**Relation to the subject:** The reference client (MR-25, MR-26) expects numeric replies to function correctly. Without proper numeric replies, the reference client will not behave "similar to using it with any official IRC server" (MR-26).

**Related MR IDs:** MR-25, MR-26

**Key points:**

- Numeric replies are three-digit codes sent by the server (e.g., `001` for welcome, `433` for nickname already in use, `482` for insufficient permissions).
- They follow the standard IRC message format: `:<server> <numeric> <target> [params] [:trailing]\r\n`.
- The target is usually the recipient's nickname.
- Replies can indicate success, errors, or information.

**Categories (conceptual):**

| Range | Category | Example |
| --- | --- | --- |
| 001–099 | Connection and registration | 001 (Welcome) |
| 200–399 | Command responses | 332 (Topic), 353 (Names list) |
| 400–599 | Errors | 433 (Nickname in use), 482 (Not operator) |

> **Note:** The exact numeric codes needed depend on the reference client. This skill teaches the **concept** of numeric replies. The `replies` skill will handle specific code selection and formatting.

**Common mistakes:**

- Not sending any numeric replies. The reference client expects them.
- Sending free-form error text instead of numeric codes. IRC clients parse numerics, not prose.
- Using wrong numeric codes that confuse the reference client.
- Forgetting the target nickname in the reply format.

### 14. Channels

**Why it exists:** Channels are the group communication mechanism in IRC. They allow multiple users to exchange messages in a shared space, which is one of IRC's core features.

**Relation to the subject:** The subject requires joining channels (MR-30) and forwarding messages to all channel members (MR-32). Channels are also the context for operator commands (MR-34–MR-37) and channel modes (MR-38–MR-42).

**Related MR IDs:** MR-30, MR-32, MR-33, MR-34–MR-42

**Key points:**

- Channel names typically start with `#` (e.g., `#general`, `#42`).
- Channels are created implicitly when the first user joins.
- Every message sent to a channel is forwarded to all other members (MR-32).
- Channels have operators and regular users (MR-33).
- Channels have modes that control behavior (MR-38–MR-42).

**Common mistakes:**

- Not forwarding channel messages to **all other** members. MR-32 says "every other client that joined the channel."
- Sending the message back to the sender. The forwarding goes to **other** members, not the sender.
- Not associating operator status with a specific channel. A user can be an operator in one channel and a regular user in another.

---

### 15. Operators and Regular Users

**Why it exists:** IRC channels have a permission model. Operators have elevated privileges; regular users have basic access. This distinction controls who can use certain commands.

**Relation to the subject:** MR-33 requires support for operators and regular users. MR-34–MR-37 define operator-specific commands. MR-41 allows granting/revoking operator privilege via `MODE o`.

**Related MR IDs:** MR-33, MR-34, MR-35, MR-36, MR-37, MR-41

**Key points:**

- Operator status is **per-channel**, not global. A user is an operator in a specific channel.
- The user who creates a channel (first to join) is typically the initial operator.
- Operator status can be granted or revoked via `MODE o` (MR-41).
- Operator commands: KICK (MR-34), INVITE (MR-35), TOPIC (MR-36), MODE (MR-37).
- Regular users can join channels, send messages, and receive messages.

> **Ambiguity A4:** The subject lists TOPIC under operator commands but describes it as "change or view." Whether regular users can **view** the topic is not explicitly stated.

**Common mistakes:**

- Making operator status global. A user's operator status is specific to each channel.
- Not checking permissions before executing operator commands.
- Confusing channel operators with IRC operators (`OPER` command). The subject only requires channel operators.

---

### 16. Operator Commands (Concept)

**Why it exists:** Operators need tools to manage channels — removing disruptive users, inviting people, setting topics, and configuring channel behavior.

**Relation to the subject:** MR-34–MR-37 explicitly name four operator commands: KICK, INVITE, TOPIC, MODE.

**Related MR IDs:** MR-34, MR-35, MR-36, MR-37

**Key points:**

| Command | Protocol Purpose | MR ID |
| --- | --- | --- |
| KICK | Remove a user from a channel | MR-34 |
| INVITE | Invite a user to join a channel (especially relevant for invite-only channels) | MR-35 |
| TOPIC | View or change the channel's topic text | MR-36 |
| MODE | Change the channel's mode flags | MR-37 |

- These commands are **channel-scoped** — they operate on a specific channel.
- Only operators should be allowed to execute them (with the possible exception of TOPIC viewing — see Ambiguity A4).
- When an operator command fails due to permissions, the server sends an appropriate error numeric.

**Common mistakes:**

- Implementing KICK without specifying which channel. KICK is channel-scoped.
- Not sending error responses when a non-operator tries to use an operator command.

### 17. Channel Modes (Concept)

**Why it exists:** Modes allow operators to configure channel behavior — restricting who can join, who can change the topic, setting passwords, limiting membership, and managing operator privileges.

**Relation to the subject:** MR-37 requires the MODE command. MR-38–MR-42 define exactly five mandatory mode flags.

**Related MR IDs:** MR-37, MR-38, MR-39, MR-40, MR-41, MR-42

**Key points:**

| Flag | Name | Subject Description | MR ID |
| --- | --- | --- | --- |
| `i` | Invite-only | Only invited users can join | MR-38 |
| `t` | Topic restriction | Only operators can change the topic | MR-39 |
| `k` | Channel key | A password is required to join | MR-40 |
| `o` | Operator privilege | Grant/revoke operator status | MR-41 |
| `l` | User limit | Maximum number of users in the channel | MR-42 |

- Modes are set with `+` and removed with `-` (e.g., `MODE #channel +i`, `MODE #channel -k`).
- Some modes take a parameter (e.g., `+k secret`, `+o alice`, `+l 10`).
- Only the five flags above are required by the subject. Any other modes are **Out of Scope**.

**Common mistakes:**

- Implementing modes not required by the subject (e.g., `+b` for ban, `+m` for muted).
- Forgetting that some modes require parameters when setting and no parameter when removing (or vice versa).
- Not enforcing that only operators can change modes.

### 18. Connection Password

**Why it exists:** The server requires a password to authenticate connecting clients. This prevents unauthorized access.

**Relation to the subject:** MR-04 defines the password as the second command-line argument. MR-27 requires authentication. The PASS command (implied, Ambiguity A1) sends the password from client to server.

**Related MR IDs:** MR-04, MR-27

**Key points:**

- The server password is set via the command-line argument: `./ircserv <port> <password>` (MR-02).
- Every connecting client must provide this password (MR-27).
- The password is sent via the PASS command before NICK and USER.
- If the password is wrong, the server should reject the connection.

> **Note:** This is the **server connection password** (MR-04). It is distinct from **channel keys** (MR-40), which are per-channel passwords.

**Common mistakes:**

- Confusing the server password with channel keys. They are completely separate.
- Allowing registration without the correct password.
- Not distinguishing between "no password sent" and "wrong password sent."

### 19. Private Messages

**Why it exists:** Direct user-to-user messaging is a core IRC feature. It allows two users to communicate without a channel.

**Relation to the subject:** MR-31 requires sending and receiving private messages.

**Related MR IDs:** MR-31

**Key points:**

- Private messages use the PRIVMSG command with a user nickname as the target (Ambiguity A2).
- The same PRIVMSG command is also used for channel messages — the target determines whether it's private or channel-scoped.
- The server receives the message from the sender and delivers it to the target user.

> **Ambiguity A2:** The subject does not name `PRIVMSG` explicitly. The reference client determines the exact command.

**Common mistakes:**

- Not distinguishing between private messages (target = nickname) and channel messages (target = channel name like `#general`).
- Sending private messages to all connected users instead of just the target.

### 20. Channel Message Forwarding

**Why it exists:** When a user sends a message to a channel, every other member of that channel must receive it. This is the fundamental group communication behavior.

**Relation to the subject:** MR-32 explicitly requires: "All messages sent from one client to a channel must be forwarded to every other client that joined the channel."

**Related MR IDs:** MR-32

**Key points:**

- Channel messages use the same command as private messages (typically PRIVMSG) with the channel name as the target.
- The server forwards the message to **every other client** in the channel — not back to the sender.
- The forwarded message includes a prefix identifying the sender.

**Common mistakes:**

- Echoing the message back to the sender.
- Not forwarding to all members.
- Not including the sender's prefix in the forwarded message.

# Concept

IRC Command vs. IRC Message

# Why It Exists

Students often confuse "command" and "message" in IRC. Understanding the distinction prevents misunderstanding the protocol structure:

- A **message** is the entire unit of communication — the full line sent over the wire, from optional prefix to CRLF.
- A **command** is one part of a message — the verb that tells the receiver what action to take.

Every command is inside a message. Not every part of a message is a command.

# Relation to the Mandatory Subject

The subject requires handling partial data (MR-43) — which means understanding message boundaries (CRLF). The subject names specific commands (MR-34–MR-37) and implies others (MR-27–MR-31). Understanding that commands live inside messages is essential for parsing.

Classification: Mandatory Requirement

# Related MR IDs

- MR-43: Partial data handling (message boundaries)
- MR-27–MR-31: Implied commands (PASS, NICK, USER, JOIN, PRIVMSG)
- MR-34–MR-37: Explicit commands (KICK, INVITE, TOPIC, MODE)

# Darija Explanation

Khlina nfhmou lfar9:

**Message** howa kol chi li kat-mchi 3la wire b CRLF f la fin. Howa l'unité complète. Matal:
`:alice PRIVMSG #general :Hello everyone\r\n`

Had message fiha:
- **Prefix**: `alice` (chkoun li b3t)
- **Command**: `PRIVMSG` (chno bghiti tdir)
- **Parameters**: `#general` (fin) w `Hello everyone` (chno)
- **CRLF**: `\r\n` (la fin dial message)

Donc: command howa juste lja verb — `PRIVMSG`. Message howa kol chi ensemble. Ila bghiti t-parsi, khassek t3rf fin message katbda w fin katsali (CRLF), w mn b3d t-extraiti command w parameters mn dakhel.

# Common Mistakes

- Using "message" and "command" interchangeably. A message contains a command, not the other way around.
- Parsing at the command level without first assembling complete messages (violates MR-43).
- Treating PRIVMSG as "the message command" and forgetting that KICK, MODE, etc. are also commands inside messages.

# What We Will Implement Later

- Message assembly from partial data → `parser` skill
- Command extraction and dispatch → `command-handling` skill

# Recommended Next Skill

`parser` — for implementation of message parsing. But verify with `@roadmap` that you have reached Phase 7 first.

## Integration

### With `ft-irc` (Orchestrator)

The `ft-irc` orchestrator routes students to `irc-protocol` during Phase 1 (Subject Analysis) and Phase 9 (Commands) for protocol understanding. The orchestrator decides **when** protocol concepts are needed; this skill provides the concepts themselves.

### With `roadmap`

The `roadmap` skill determines whether the student has reached a phase where protocol knowledge is relevant. `irc-protocol` defers phase progression decisions to `roadmap`.

### With `subject-reader`

`irc-protocol` consults `subject-reader` for MR ID verification, ambiguity details, and classification of requirements. It does not interpret the Knowledge Base directly for subject facts — it uses `subject-reader` as the interface.

### With `tcp-ip`

`tcp-ip` handles transport layer concepts (TCP streams, ports, connections). `irc-protocol` handles the application layer (IRC messages on top of TCP). They are complementary and do not overlap.

### With `sockets`

`sockets` handles the implementation of network connections. `irc-protocol` explains the protocol that runs over those connections. `irc-protocol` never discusses socket APIs.

### With `parser`

`parser` handles the implementation of message parsing. `irc-protocol` explains the message format that the parser must handle. `irc-protocol` teaches **what** messages look like; `parser` teaches **how** to parse them.

### With `replies`

`replies` handles the selection and formatting of specific numeric reply codes. `irc-protocol` teaches the **concept** of numeric replies — why they exist and what they look like. `replies` teaches which codes to use and how to format them.
