# TCP/IP Fundamentals

## Identity

This skill is a **networking theory teacher**.

It teaches the student what networks are, how TCP/IP works at the conceptual level, why IRC needs it, and what foundational concepts (ports, addresses, streams, file descriptors, blocking/non-blocking) the student must understand before touching any socket code.

It behaves like a senior engineer giving a networking primer to a junior 42 student who has never built a network application: patient, visual, grounded in the subject, and focused on building the mental model that future implementation skills will rely on.

### What This Skill Is

- A teacher of networking fundamentals.
- Scoped exclusively to concepts the mandatory ft_irc subject requires.
- The bridge between "I know what IRC is" (irc-protocol) and "I'm ready to create sockets" (sockets).

### What This Skill Is NOT

- Not a socket programming teacher → `sockets`
- Not a `poll()` / event loop teacher → `poll-loop`
- Not a parser teacher → `parser`
- Not an architecture advisor → `architecture`
- Not a code generator
- Not a university networking course — only what ft_irc needs

## Networking Concepts

### 1. What Is a Network?

**Why it exists:** A network connects computers so they can exchange data. Without a network, your IRC server would have no one to talk to.

**Relation to ft_irc:** The subject requires building an IRC server (MR-12) that communicates with clients via TCP/IP (MR-18). The server and client(s) are on a network — even if that network is just your own machine during testing.

**Related MR IDs:** MR-12, MR-18

**ASCII Diagram:**

```
  ┌──────────┐         Network          ┌──────────┐
  │  Client   │◄──────────────────────►│  Server   │
  │  (IRC)    │     TCP/IP connection   │  (ircserv)│
  └──────────┘                          └──────────┘
```

**Key points:**

- A network is a system of interconnected machines that can exchange data.
- The Internet is the largest network, but a local machine can also act as its own network (localhost).
- ft_irc runs on a network — even during testing on one machine, the client and server communicate over a TCP/IP connection.

**Common mistakes:**

- Thinking "network" means "the Internet." During development, your network is just your machine.
- Forgetting that even on localhost, communication still goes through the full TCP/IP stack.

---

### 2. Client and Server

**Why it exists:** Network communication follows a model where one side (the server) waits for connections, and the other side (the client) initiates them. This asymmetry defines roles and responsibilities.

**Relation to ft_irc:** The subject requires building only the server (MR-12), explicitly forbids building a client (MR-13), and forbids server-to-server (MR-14). Understanding this distinction prevents scope confusion.

**Related MR IDs:** MR-12, MR-13, MR-14, MR-18, MR-19

**ASCII Diagram:**

```
  ┌──────────┐                         ┌──────────┐
  │  Client 1 │───── connects to ────►│           │
  └──────────┘                         │           │
  ┌──────────┐                         │  Server   │
  │  Client 2 │───── connects to ────►│  (ircserv)│
  └──────────┘                         │           │
  ┌──────────┐                         │           │
  │  Client 3 │───── connects to ────►│           │
  └──────────┘                         └──────────┘

  • Server waits (listens) on a port
  • Clients initiate connections
  • Server handles multiple clients simultaneously (MR-19)
```

**Key points:**

- The **server** listens on a port and waits for connections. It is passive — it does not go find clients.
- The **client** actively connects to the server. You will use a reference IRC client (MR-24).
- Your ft_irc project is the server. The reference client is the client.
- The server must handle **multiple clients** simultaneously without hanging (MR-19).

**Common mistakes:**

- Trying to build both a client and a server. The subject forbids building a client (MR-13).
- Designing a server that handles only one client at a time. MR-19 requires simultaneous multi-client support.

### 3. IP Address

**Why it exists:** Every machine on a network needs an identity so that data can be addressed and routed to the correct destination. An IP address is that identity.

**Relation to ft_irc:** The subject requires communication via TCP/IP v4 or v6 (MR-18). IP addresses are how clients find the server.

**Related MR IDs:** MR-18

**ASCII Diagram:**

```
  ┌─────────────────┐                  ┌─────────────────┐
  │ Client            │                  │ Server            │
  │ IP: 192.168.1.10 │── TCP/IP ──────►│ IP: 192.168.1.20 │
  └─────────────────┘                  └─────────────────┘

  Each machine has an IP address.
  Data is sent FROM one IP address TO another.
```

**Key points:**

- An IP address uniquely identifies a machine on a network.
- IPv4 addresses look like `192.168.1.1` — four numbers (0–255) separated by dots.
- IPv6 addresses look like `::1` or `2001:db8::1` — longer, hexadecimal notation.
- The subject allows either v4 or v6 (MR-18). Most students use IPv4.
- During development, you will use `127.0.0.1` (localhost) — your own machine.

**Common mistakes:**

- Thinking you need to implement both IPv4 and IPv6. The subject says "v4 or v6" — either is acceptable.
- Hardcoding a specific IP address in the server. The server should listen on the port given as a command-line argument, and typically on all available interfaces.

---

### 4. IPv4

**Why it exists:** IPv4 is the most widely used version of the Internet Protocol. It defines 32-bit addresses (like `192.168.1.1`) and is the version most students will use for ft_irc.

**Relation to ft_irc:** MR-18 allows "v4 or v6." IPv4 is the simpler choice and is sufficient for the mandatory project.

**Related MR IDs:** MR-18

**Key points:**

- IPv4 uses 32-bit addresses → approximately 4.3 billion unique addresses.
- Written as four decimal numbers: `A.B.C.D` where each is 0–255.
- Special addresses: `127.0.0.1` (localhost), `0.0.0.0` (all interfaces).
- For ft_irc, IPv4 is the practical default unless you have a specific reason to use IPv6.

**Common mistakes:**

- Overcomplicating the project by trying to support both IPv4 and IPv6 simultaneously. Choose one.
- Confusing `0.0.0.0` (listen on all interfaces) with `127.0.0.1` (listen on localhost only).

### 5. Localhost

**Why it exists:** Localhost (`127.0.0.1` or `::1`) is the loopback address — it refers to your own machine. It lets you run both the server and client on the same computer, which is essential for development and testing.

**Relation to ft_irc:** The subject's `nc` test example uses `127.0.0.1` directly: `nc -C 127.0.0.1 6667`. During development and evaluation, the server and reference client will typically both run on localhost.

**Related MR IDs:** MR-18, MR-25

**ASCII Diagram:**

```
  ┌──────────────────────────────────────────┐
  │              Your Machine                  │
  │                                            │
  │   ┌──────────┐        ┌──────────┐        │
  │   │ Client    │◄─────►│  Server   │        │
  │   │ (irssi)   │        │ (ircserv) │        │
  │   └──────────┘        └──────────┘        │
  │         │                    │              │
  │         └──── 127.0.0.1 ────┘              │
  │              (localhost)                    │
  └──────────────────────────────────────────┘

  Both run on the same machine.
  Communication goes through 127.0.0.1.
  Still uses full TCP/IP stack.
```

**Key points:**

- `127.0.0.1` is the IPv4 loopback address. `::1` is the IPv6 equivalent.
- Traffic to localhost never leaves your machine, but it still goes through the TCP/IP stack.
- During evaluation, the reference client will connect to localhost (or possibly to a local network address).

**Common mistakes:**

- Thinking localhost bypasses networking. It doesn't — your server still needs proper TCP/IP handling.
- Assuming the server will only ever run on localhost. It should bind to the specified port and work on any network interface.

### 6. Port

**Why it exists:** A single machine can run many network services simultaneously (web server, SSH, IRC server, etc.). A port number distinguishes between them. It is like a door number on a building — the IP address is the building, and the port is which door you knock on.

**Relation to ft_irc:** The server's port is the first command-line argument: `./ircserv <port> <password>` (MR-02, MR-03). The server must listen on this port for incoming connections.

**Related MR IDs:** MR-02, MR-03, MR-18

**ASCII Diagram:**

```
  ┌─────────────────────────────────────┐
  │           Server Machine              │
  │                                       │
  │   Port 22   ──── SSH Server           │
  │   Port 80   ──── Web Server           │
  │   Port 6667 ──── IRC Server (ircserv) │  ◄── ft_irc
  │   Port 443  ──── HTTPS Server         │
  │                                       │
  └─────────────────────────────────────┘

  Client connects to IP:PORT
  Example: 127.0.0.1:6667
```

**Key points:**

- Ports range from 0 to 65535.
- Ports 0–1023 are "well-known ports" and typically require root privileges.
- Common IRC port: 6667 (but the subject lets you use any port via the command-line argument).
- The port is provided at runtime via `<port>` argument — it must not be hardcoded (MR-02, MR-03).

**Common mistakes:**

- Hardcoding port 6667. The subject says the port comes from the command line (MR-03).
- Using a port that requires root privileges (0–1023) during testing. Use a high port like 6667 or 8080.
- Forgetting that two servers cannot listen on the same port simultaneously.

### 7. TCP

**Why it exists:** TCP (Transmission Control Protocol) is a transport protocol that provides reliable, ordered, error-checked delivery of data between applications. It is the foundation for most Internet communication that requires reliability.

**Relation to ft_irc:** The subject explicitly requires TCP/IP communication (MR-18). IRC is a text-based protocol that requires messages to arrive completely, in order, and without corruption — exactly what TCP provides.

**Related MR IDs:** MR-18

**Key points:**

- TCP provides **reliable** delivery — data is guaranteed to arrive (or the connection fails).
- TCP provides **ordered** delivery — bytes arrive in the order they were sent.
- TCP provides **error checking** — corrupted data is detected and retransmitted.
- TCP is **connection-oriented** — a connection must be established before data flows.
- TCP is **stream-oriented** — it delivers a continuous stream of bytes, not individual messages.

**Common mistakes:**

- Assuming data arrives in neat, complete messages. TCP delivers a **stream of bytes** — message boundaries are not preserved. This is why MR-43 (partial data handling) exists.
- Confusing TCP with UDP. UDP is unreliable and unordered — the subject does not use it.

---

### 8. Why IRC Uses TCP

**Why it exists:** IRC needs a transport protocol that guarantees messages arrive completely, in order, and without corruption. TCP provides all of these guarantees. UDP does not.

**Relation to ft_irc:** MR-18 requires TCP/IP. Understanding **why** TCP (not UDP) helps the student appreciate why partial data handling (MR-43) is necessary and why the stream-oriented nature of TCP shapes the server's design.

**Related MR IDs:** MR-18, MR-43

**ASCII Diagram:**

```
  TCP guarantees:                      UDP does NOT guarantee:

  ┌─────────┐                          ┌─────────┐
  │ Message 1 │ ──► arrives first       │ Message 1 │ ──► might arrive second
  │ Message 2 │ ──► arrives second      │ Message 2 │ ──► might be lost
  │ Message 3 │ ──► arrives third       │ Message 3 │ ──► might arrive first
  └─────────┘                          └─────────┘

  IRC needs:
  ✓ Reliable (all messages arrive)
  ✓ Ordered (messages arrive in sequence)
  ✓ Error-free (no corruption)
  → TCP is the correct choice
```

**Key points:**

- IRC commands must arrive in order (e.g., PASS before NICK, NICK before USER).
- IRC messages must not be lost (a lost KICK command would leave a user in a channel they should have been removed from).
- IRC messages must not be corrupted.
- TCP provides all of these guarantees; UDP does not.
- The subject requires TCP/IP (MR-18) and does not mention UDP at all.

**Common mistakes:**

- Asking "can I use UDP instead?" — No. The subject requires TCP/IP (MR-18). UDP is Out of Scope.
- Not understanding that TCP's stream-oriented nature means data does NOT arrive as discrete messages — you must handle partial data (MR-43).

### 9. Connection Lifecycle

**Why it exists:** A TCP connection has a defined lifecycle: it is established, data flows, and eventually it is closed. Understanding this lifecycle is essential because the server must manage every connection through all stages.

**Relation to ft_irc:** The server must accept connections (MR-19), handle communication (MR-18), and deal with disconnections without crashing (MR-15, MR-16). Each connection goes through the full lifecycle.

**Related MR IDs:** MR-18, MR-19, MR-15, MR-16

**ASCII Diagram:**

```
  Client                                Server (ircserv)
    │                                      │
    │──── 1. TCP Handshake (SYN) ────────►│  Connection
    │◄─── 2. TCP Handshake (SYN-ACK) ────│  Establishment
    │──── 3. TCP Handshake (ACK) ────────►│
    │                                      │
    │◄───────── Data Exchange ───────────►│  Active Session
    │     (IRC commands and replies)       │
    │                                      │
    │──── 4. Close (FIN) ────────────────►│  Connection
    │◄─── 5. Close (FIN-ACK) ────────────│  Termination
    │                                      │
```

**Key points:**

1. **Establishment:** TCP uses a three-way handshake (SYN, SYN-ACK, ACK) to establish a connection. You don't code this — the operating system handles it. You just call the right system functions (which the `sockets` skill will teach).
2. **Active session:** Data flows in both directions. The client sends IRC commands; the server sends replies and forwarded messages.
3. **Termination:** Either side can close the connection. The server must handle both clean disconnections and abrupt disconnections (client crash, network failure).

**Common mistakes:**

- Not handling disconnections gracefully. When a client disconnects, the server must clean up without crashing (MR-15, MR-16).
- Assuming connections last forever. Clients disconnect for many reasons — the server must detect and handle this.
- Trying to implement the TCP handshake yourself. The OS does this. You just accept connections.

### 10. Reliable Communication

**Why it exists:** TCP provides reliability guarantees that application protocols like IRC depend on. Understanding what "reliable" means helps the student trust TCP for delivery while focusing on application-level concerns.

**Relation to ft_irc:** The subject requires TCP/IP (MR-18). The server can rely on TCP to deliver data correctly — but it must still handle partial delivery (MR-43) because TCP delivers a stream, not messages.

**Related MR IDs:** MR-18, MR-43

**Key points:**

TCP guarantees:

- **Delivery:** If a connection is alive, data will eventually arrive. If it can't, the connection will be closed.
- **Order:** Bytes arrive in the order they were sent.
- **Integrity:** Corrupted data is detected and retransmitted.

TCP does NOT guarantee:

- **Message boundaries.** TCP does not know what a "message" is. It delivers a stream of bytes.
- **Timing.** Data may arrive quickly or slowly depending on network conditions.

**Common mistakes:**

- Thinking "reliable" means "instant." TCP guarantees delivery, not speed.
- Thinking "reliable" means "one message per read." TCP delivers a byte stream — you may read half a message, or three messages at once.

### 11. Packets vs Streams

**Why it exists:** This is the single most important networking concept for ft_irc. TCP is stream-oriented, which means data arrives as a continuous sequence of bytes without message boundaries. This is why the subject requires partial data handling (MR-43).

**Relation to ft_irc:** MR-43 explicitly requires buffering and aggregating partial data. This requirement exists because of TCP's stream-oriented nature. Understanding packets vs streams is essential before implementing the parser.

**Related MR IDs:** MR-18, MR-43

**ASCII Diagram:**

```
  What the client SENDS:           What the server may RECEIVE:

  ┌────────────────────┐           ┌───────────┐  (first recv)
  │ NICK alice\r\n      │           │ NICK al    │
  └────────────────────┘           └───────────┘
  ┌────────────────────┐           ┌───────────────────────────┐ (second recv)
  │ USER alice 0 * :A\r\n│          │ ice\r\nUSER alice 0 * :A\r\n│
  └────────────────────┘           └───────────────────────────┘

  TCP does NOT preserve message boundaries!
  Data may be split or merged across recv() calls.
```

**Key points:**

- At the **application level**, the client sends discrete IRC messages (each ending with `\r\n`).
- At the **TCP level**, these messages become a stream of bytes. TCP does not know or care about `\r\n`.
- When the server reads data, it may receive:
  - A **partial message** — only some bytes of a complete message.
  - **Multiple messages** — several complete messages in one read.
  - A **mix** — the end of one message and the beginning of another.
- The server must **buffer** incoming data and extract complete messages by looking for `\r\n` delimiters (MR-43).

**This is the most common source of bugs in ft_irc projects.**

**Common mistakes:**

- Assuming each `recv()` returns exactly one complete message. This is almost never guaranteed.
- Not buffering data per client. Each client needs its own buffer because partial data is per-connection.
- Processing data before a complete `\r\n`-terminated message has been assembled.

### 12. Why TCP Is Stream-Oriented

**Why it exists:** Students need to understand *why* data arrives in fragments, not just *that* it does. TCP operates on bytes, not messages. It segments data into packets for transmission and reassembles them on the receiving end — but it does not tell the application where one "message" ends and another begins.

**Relation to ft_irc:** This directly explains why MR-43 exists. The subject even provides a test case: send `com`, then `man`, then `d\n` using `ctrl+D` in `nc`. The server must aggregate these fragments.

**Related MR IDs:** MR-43

**ASCII Diagram:**

```
  Application layer:     "NICK alice\r\n"  (one message)
                              │
                              ▼
  TCP layer:             [NIC] [K a] [lic] [e\r\n]  (four TCP segments)
                              │
                              ▼
  Network layer:         Sent as separate packets
                              │
                              ▼
  Receiving TCP:         Reassembles bytes in order
                              │
                              ▼
  Receiving application: May read "NIC", then "K alice\r\n"
                         Or "NICK alice\r\n" all at once
                         Or "NICK alice\r\nUSER..."
                         → It depends on timing and network conditions
```

**Key points:**

- TCP breaks data into segments for efficient network transmission.
- The receiving TCP stack reassembles bytes in order — but it does not reassemble **messages**.
- The application (your server) is responsible for detecting message boundaries.
- In IRC, the message boundary is `\r\n`.
- The `nc -C` test in the subject simulates this by sending data in fragments.

**Common mistakes:**

- Treating `recv()` as "read one message." It reads available bytes, not messages.
- Not implementing a per-client buffer. Without buffering, partial messages are lost.

### 13. Latency

**Why it exists:** Network communication takes time. Data must travel from one machine to another (or even through the same machine's networking stack). This delay is called latency, and it affects how the server must handle I/O.

**Relation to ft_irc:** Latency is why blocking I/O is problematic (MR-21). If the server blocks while waiting for data from one slow client, it cannot serve other clients — violating MR-19 (handle multiple clients simultaneously).

**Related MR IDs:** MR-19, MR-21

**ASCII Diagram:**

```
  Blocking I/O (WRONG for ft_irc):

  Server ───── waiting for Client 1 ─────────── waiting ─────── finally got data
                    │                                              │
                    │  Client 2: "hello?"                          │
                    │  Client 3: "anyone there?"                   │
                    │  (both ignored — server is blocked)          │
                    ▼                                              ▼

  Non-blocking I/O (CORRECT for ft_irc):

  Server ─── check Client 1: no data ─── check Client 2: data! ─── process
                                                 │
                                    check Client 3: data! ─── process
                                                 │
                                    check Client 1: data now! ─── process
```

**Key points:**

- Network operations are not instant — data takes time to travel.
- On localhost, latency is very small but still nonzero.
- Over a real network, latency can be significant (milliseconds to seconds).
- Blocking on one client's data means ignoring all other clients.
- The subject prohibits this by requiring non-blocking I/O (MR-21) and multi-client support (MR-19).

**Common mistakes:**

- Assuming localhost is "instant" and not worrying about latency. Even on localhost, slow clients (or `nc` with manual input) expose timing issues.
- Blocking on `recv()` for one client while others wait. This is exactly what MR-21 prevents.

### 14. Blocking vs Non-Blocking I/O

**Why it exists:** By default, system calls like `recv()` and `send()` **block** — they wait until data is available or can be sent. In a server that handles multiple clients, blocking is catastrophic because it freezes the entire server while waiting for one client.

**Relation to ft_irc:** MR-21 explicitly requires all I/O to be non-blocking. MR-23 adds a grade-zero penalty for doing I/O without readiness checking. MR-20 prohibits forking (so you can't work around blocking with child processes).

**Related MR IDs:** MR-19, MR-20, MR-21, MR-22, MR-23

**ASCII Diagram:**

```
  BLOCKING (forbidden by MR-21):

  recv(client_1) ──── WAITS ──── WAITS ──── data arrives ──── continues
                       │
                       └── server is FROZEN
                           client_2, client_3... all ignored

  NON-BLOCKING (required by MR-21):

  recv(client_1) ──── no data available ──── returns immediately
  recv(client_2) ──── data available! ──── returns data
  recv(client_3) ──── no data available ──── returns immediately
                       │
                       └── server is NEVER frozen
                           all clients are served
```

**Key points:**

- **Blocking I/O:** The function call waits until the operation completes. The program stops executing.
- **Non-blocking I/O:** The function call returns immediately, whether data is available or not. If no data is available, it returns an indicator (like `EAGAIN` or `EWOULDBLOCK`).
- The subject requires **all** I/O to be non-blocking (MR-21).
- Forking is forbidden (MR-20), so you cannot use child processes to handle blocking.
- Instead, you use an event loop with `poll()` or equivalent (MR-22) to check which file descriptors are ready before reading or writing.
- Doing I/O without checking readiness first results in **grade 0** (MR-23).

> **Note:** This skill teaches the **concept** of blocking vs non-blocking. The **implementation** (how to set non-blocking mode, how to use poll) belongs to the `sockets` and `poll-loop` skills.

**Common mistakes:**

- Using blocking I/O "because it works on localhost." It may seem to work with one client, but it will fail with multiple clients.
- Trying to use `fork()` to handle blocking. Forking is forbidden (MR-20).
- Using threads instead of non-blocking I/O. The subject does not require or encourage threading.
- Reading/writing without checking `poll()` readiness first. This is a grade-zero violation (MR-23).

### 15. File Descriptors

**Why it exists:** In Unix-like operating systems, everything is a file — including network connections. A file descriptor (FD) is an integer that represents an open file, socket, pipe, or other I/O resource. The server uses file descriptors to manage all its connections.

**Relation to ft_irc:** MR-22 requires that one `poll()` (or equivalent) handles **all** I/O on **all** file descriptors. MR-23 requires that every read/write is preceded by poll readiness checking on the file descriptor. Understanding what a file descriptor is is essential before learning the socket API.

**Related MR IDs:** MR-22, MR-23

**ASCII Diagram:**

```
  ┌─────────────────────────────────────────┐
  │           Server (ircserv)                │
  │                                           │
  │   FD 3 ──── Server listening socket       │
  │   FD 4 ──── Client 1 connection           │
  │   FD 5 ──── Client 2 connection           │
  │   FD 6 ──── Client 3 connection           │
  │                                           │
  │   poll() monitors ALL of these FDs        │
  │   for readiness before any I/O            │
  └─────────────────────────────────────────┘

  FD = just an integer
  The OS maps it to the actual resource
```

**Key points:**

- A file descriptor is an integer (like 3, 4, 5, 6...).
- FDs 0, 1, 2 are reserved: stdin, stdout, stderr.
- When the server creates a listening socket, the OS returns a file descriptor for it.
- When a client connects, the OS returns a new file descriptor for that connection.
- The server uses `poll()` to monitor all file descriptors for readiness (MR-22).
- Before reading from or writing to any FD, poll must confirm it is ready (MR-23).
- When a connection closes, its file descriptor must be closed too.

> **Note:** This skill teaches the **concept** of file descriptors. The `sockets` skill teaches how to create them, and the `poll-loop` skill teaches how to monitor them.

**Common mistakes:**

- Leaking file descriptors by not closing them when a client disconnects.
- Not monitoring all file descriptors with poll. MR-22 says "all I/O operations" — including the listening socket, not just client sockets.
- Confusing file descriptor numbers with client identifiers. FD numbers are assigned by the OS and can be reused.

### 16. Multiple Simultaneous Clients

**Why it exists:** An IRC server is useless if it can only handle one client at a time. The entire point of IRC is group communication — multiple clients connected simultaneously, chatting in channels, sending private messages.

**Relation to ft_irc:** MR-19 requires the server to "handle multiple clients simultaneously without hanging." MR-20 prohibits forking. This combination means the server must use non-blocking I/O (MR-21) and an event loop (MR-22) to serve all clients in a single process.

**Related MR IDs:** MR-19, MR-20, MR-21, MR-22

**ASCII Diagram:**

```
  ┌─────────┐
  │ Client 1 │──┐
  └─────────┘   │
  ┌─────────┐   │      ┌──────────────────────┐
  │ Client 2 │──┼────►│     Server (ircserv)    │
  └─────────┘   │      │                        │
  ┌─────────┐   │      │   Single process       │
  │ Client 3 │──┘      │   Non-blocking I/O     │
  └─────────┘          │   One event loop       │
  ┌─────────┐          │   No forking           │
  │ Client N │────────►│                        │
  └─────────┘          └──────────────────────┘

  How NOT to do it (forbidden):
  ✗ fork() per client (MR-20)
  ✗ block on one client (MR-21)
  ✗ multiple event loops (MR-22)

  How to do it (required):
  ✓ Single process
  ✓ Non-blocking file descriptors
  ✓ One poll() (or equivalent) monitoring all FDs
```

**Key points:**

- The server must serve any number of clients in a single process.
- Forking is forbidden (MR-20) — you cannot create child processes for each client.
- Blocking is forbidden (MR-21) — you cannot wait on one client.
- One event loop (MR-22) monitors all file descriptors for readiness.
- This is the standard event-driven, single-threaded server model.

**Common mistakes:**

- Designing a "one client at a time" server during early development and planning to "add multi-client later." The multi-client requirement is foundational — design for it from the start.
- Using threads as a workaround. The subject does not require or encourage multi-threading, and it adds unnecessary complexity.
- Using `fork()` because it "seems easier." It is explicitly forbidden (MR-20).

**Response:**

```markdown
# Concept

Non-blocking I/O

# Why It Exists

By default, I/O operations (reading from or writing to a file descriptor) block — they wait until the operation can complete. In a server handling multiple clients, this is disastrous: if one client is slow, the entire server freezes.

Non-blocking I/O lets the server check for data without waiting. Combined with an event loop, it enables serving many clients in a single process.

# Relation to ft_irc

The subject explicitly requires:
- All I/O must be non-blocking (MR-21)
- No forking (MR-20) — cannot use child processes as a workaround
- One poll() (or equivalent) for all I/O (MR-22)
- I/O without poll readiness = grade 0 (MR-23)
- Must handle multiple clients simultaneously (MR-19)

These five requirements together define the server's concurrency model: a single-process, event-driven, non-blocking server.

Classification: Mandatory Requirement

# Related Mandatory Requirements (MR IDs)

- MR-19: Handle multiple clients simultaneously without hanging
- MR-20: Forking is prohibited
- MR-21: All I/O operations must be non-blocking
- MR-22: Only 1 poll() (or equivalent) for all I/O
- MR-23: I/O without poll readiness = grade 0

# Darija Explanation

Blocking I/O b7al tgls f restaurant w tweqf 7ta plat dyalek ytjhz — w dak sa3a ma kat-servi 7ta client akhor. Ila 3ndk 10 clients, kolhom khass y-tsennaw 7ta wa7d ytsla.

Non-blocking I/O b7al waiter li kaydor 3la gaa ltables: "3ndk chi 7aja? la? ok, nmchi l table khra." Ma kayweqfch 3nd 7ta wa7d.

Subject gal:
- I/O khass tkoun non-blocking (MR-21)
- Fork mamnou3 (MR-20) — ma t9drch tkhdem b child processes
- Khass poll() wa7d l gaa I/O (MR-22)
- Ila qriti wla ktbti bla poll readiness = note 0 (MR-23)

Hadchi kolchi kaydire b7al un système wa7d: event loop b poll() li kaychof kol les FDs, w ghir ila FD ready, server kayqra wla ykteb.

# ASCII Diagram

    Blocking (WRONG):
    ─── recv(client1) ────── WAITS ────── WAITS ──── data ───►
        client2: ignored
        client3: ignored
        server: FROZEN

    Non-blocking + poll (CORRECT):
    ─── poll() ─── client1: not ready ──┐
                   client2: READY! ─────┼─── recv(client2) ── data
                   client3: not ready ──┘
    ─── poll() ─── client1: READY! ─────── recv(client1) ── data
                   client3: READY! ─────── recv(client3) ── data

    Server is NEVER frozen. All clients are served fairly.

# Common Mistakes

- Using blocking I/O "just for testing" and planning to fix it later. Design for non-blocking from the start.
- Using fork() as a workaround for blocking. Forbidden by MR-20.
- Doing recv/send without checking poll() readiness first. Grade 0 (MR-23).
```
