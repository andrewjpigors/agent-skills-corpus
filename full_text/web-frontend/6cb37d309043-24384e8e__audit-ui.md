# Audit-UI — Audit UI multi-axes pour composants Angular

Analyse statique d'un ou plusieurs composants Angular sous l'angle UI/UX/A11y. **Aucune modification de code** — uniquement un rapport structuré.

## Étape 1 — Détection du scope

### Mode par défaut (sans argument) — branche courante

```bash
# Fichiers modifiés/ajoutés sur la branche
git status --porcelain
git diff --name-only dev...HEAD 2>/dev/null || git diff --name-only main...HEAD 2>/dev/null || git diff --name-only master...HEAD
```

Filtrer pour ne garder que les fichiers UI :
- `*.component.ts` (template inline ou logique de présentation)
- `*.component.html`
- `*.component.scss` (styles locaux)
- `*.directive.ts` (si manipulation DOM/UI)
- Inclure le **trio complet** : si seul le `.html` est modifié, lire aussi le `.ts` et `.scss` correspondants pour l'analyse.

Exclure :
- `*.spec.ts`, `*.module.ts`, `*.routes.ts`, `*.guard.ts`, `*.interceptor.ts`
- `core/services/`, `core/interfaces/`, `core/types/`, `core/utils/` (pas de logique UI)
- Add-ins Office ou équivalents non-web

### Mode argument explicite

```
/audit-ui src/app/ui/pages/foo/foo.component.ts
/audit-ui src/app/ui/components/commons/bar/
```

- Chemin fichier → audit ce fichier (+ trio HTML/SCSS si applicable)
- Chemin dossier → audit récursif tous les composants du dossier (warning si > 10 composants, demander confirmation)

### Modes de filtrage des axes (optionnel)

```
/audit-ui --a11y               # uniquement [A11Y]
/audit-ui --vis                # uniquement [VIS]
/audit-ui --ux                 # uniquement [UX]
/audit-ui --rwd                # uniquement [RWD]
/audit-ui --ng                 # uniquement [NG]
/audit-ui --blocking           # uniquement les findings 🔴
```

Si scope vide → "Aucun composant modifié à auditer." et s'arrêter.

## Étape 2 — Lecture du contexte projet

Lire en début d'audit (cache pour la session) :

1. **`CLAUDE.md` du projet** — conventions documentées (form controls custom, pièges connus, patterns spécifiques). **Les règles documentées priment sur les règles génériques** ci-dessous.
2. **`tailwind.config.js` / `tailwind.config.ts`** si présent — palette custom, breakpoints custom (pour ne pas flagger des classes valides comme inconnues).
3. **`src/styles/`** ou équivalent — variables SCSS globales.

Cela permet d'auditer **vs les conventions du projet**, pas vs des standards génériques.

## Étape 3 — Audit par axes

Pour chaque composant du scope, exécuter les 5 axes ci-dessous. Chaque finding est **taggé** + **gravité**.

### 🎨 [VIS] — Visuel (Refactoring UI + Laws of UX)

#### Hiérarchie visuelle

- 🟠 Texte secondaire en gris uniquement (pas de variation taille/poids) → faiblesse hiérarchique
- 🟠 Plusieurs niveaux de gras dans la même zone sans hiérarchie claire
- 🟡 Plus de 3 tailles de texte différentes dans un même composant (sauf justification)
- 🔴 Aucune hiérarchie : tout en `text-base font-normal text-gray-700` sur un composant complexe

#### Couleurs

- 🟠 Usage de `text-black` ou `bg-black` (Refactoring UI : éviter le noir pur, préférer `gray-900` ou cool gray)
- 🟠 Usage de gris neutres (`gray-*`) dans une UI dense → préférer `slate-*` / `zinc-*` (cool grays)
- 🟡 Couleur unique pour tous les states (hover/active/disabled identiques visuellement)

#### Espacements

- 🟠 Espacements aléatoires hors échelle (`p-[7px]`, `mt-[13px]`) sans justification
- 🟡 Densité excessive : `p-1` ou `p-2` partout sur du contenu de lecture (Laws of UX : Aesthetic-Usability)
- 🟡 Whitespace insuffisant entre groupes logiques (manque de respiration)

#### Typographie

- 🟠 Plus de 2 familles de fonts différentes
- 🟠 `font-thin` ou `font-extralight` sur du texte de lecture (lisibilité dégradée)
- 🟡 Line-height par défaut sur du paragraphe long (devrait être `leading-relaxed` ≈ 1.5-1.6)

#### Laws of UX

- 🟠 **Hick's Law** : menu/dropdown > 7 items sans groupage/recherche → charge cognitive excessive
- 🟠 **Fitts's Law** : zone cliquable < 44×44px sur mobile (cf. axe RWD aussi)
- 🟡 **Miller's Law** : groupes > 7±2 items affichés simultanément sans pagination/grouping
- 🟡 **Jakob's Law** : pattern non-standard pour une action commune (ex: bouton "X" pour fermer placé ailleurs qu'en haut à droite)

### ♿ [A11Y] — Accessibilité (WCAG 2.2 niveau AA)

#### Sémantique HTML

- 🔴 `<div onclick>` ou `<span onclick>` sans `role="button"` ni `tabindex="0"` ni gestion clavier (WCAG 2.1.1)
- 🔴 Boutons en `<a>` sans `href` (utiliser `<button>` ou un composant bouton du projet)
- 🔴 Liens en `<button>` qui devraient être `<a>` (navigation = anchor)
- 🟠 Hiérarchie de titres cassée (`<h1>` → `<h3>` sans `<h2>`) (WCAG 1.3.1)
- 🟠 `<img>` sans `alt` (ou `alt=""` non justifié pour image décorative) (WCAG 1.1.1)
- 🟠 Listes avec `<div>` au lieu de `<ul>/<ol>/<li>` (WCAG 1.3.1)

#### ARIA

- 🔴 `aria-label` ou `aria-labelledby` manquant sur un bouton icône-only
- 🔴 `role` invalide ou contradictoire (ex: `role="button"` sur un vrai `<button>`)
- 🟠 `aria-hidden="true"` sur un élément focusable
- 🟠 `<button>` désactivé via `pointer-events: none` au lieu de `disabled` (pas annoncé au lecteur d'écran)
- 🟠 Live regions manquantes pour notifications/toasts (utiliser `Angular CDK LiveAnnouncer` ou `aria-live`)

#### Contraste (approximation via classes Tailwind)

- 🔴 Texte sur fond avec ratio probable < 4.5:1, exemples détectables :
  - `text-gray-400` sur `bg-white` (~2.8:1) ❌
  - `text-gray-500` sur `bg-white` (~4.6:1) ✅ limite
  - `text-gray-300` sur `bg-gray-100` (très faible)
  - `text-white` sur `bg-yellow-300` ou `bg-amber-300` (jaune sur blanc = problème classique)
- 🟠 Texte ≥ 18px (`text-lg`, `text-xl`) ou bold ≥ 14px : ratio 3:1 minimum (plus tolérant)
- 🟡 Mention : "Vérifier le contraste réel avec axe DevTools / Lighthouse — l'analyse statique approxime via les classes Tailwind."

#### Focus & navigation clavier

- 🔴 `outline-none` sans alternative `focus:ring-*` ou `focus-visible:*` (WCAG 2.4.7)
- 🔴 Modal / side panel sans focus trap (utiliser `cdkTrapFocus` du `@angular/cdk/a11y`)
- 🟠 Ordre de tabulation non logique (`tabindex` > 0 dans le template — anti-pattern)
- 🟠 Skip link absent sur les pages avec navigation lourde (WCAG 2.4.1)
- 🟠 Pas de gestion `Escape` pour fermer modal/dropdown/side-panel

#### Cibles tactiles (WCAG 2.5.8 nouveau en 2.2)

- 🔴 `<button>` ou élément interactif < 24×24px (estimer via classes : `text-xs p-0.5` sans `min-h/min-w`)
- 🟠 Cibles tactiles < 44×44px sur breakpoints mobiles (recommandation Apple/WCAG AAA mais bonne pratique)

#### Formulaires (WCAG 3.3.x)

- 🔴 `<input>` sans `<label>` associé (`for=` ou wrapping)
- 🔴 Erreur de validation non liée à l'input via `aria-describedby` ou `aria-invalid`
- 🟠 Placeholder utilisé comme label unique (disparaît à la saisie, gros problème d'a11y)
- 🟠 Champ `required` sans indication visuelle ET sans `aria-required="true"`
- 🟠 Messages d'erreur génériques ("Erreur") au lieu de spécifiques ("Le numéro de dossier doit contenir 8 chiffres")

#### Lecteurs d'écran

- 🟠 Texte uniquement visuel pour info importante (icône seule sans `sr-only` ou `aria-label`)
- 🟠 `display: none` sur du contenu qui devrait être lu (préférer `sr-only` Tailwind = visible aux SR seulement)

### 🧠 [UX] — Heuristiques Nielsen

#### 1. Visibilité de l'état système

- 🔴 Action async > 1s sans feedback visuel (loading spinner, skeleton, désactivation bouton)
- 🟠 Bouton submit qui ne change pas d'état après clic (utilisateur clique 2x)
- 🟠 Pas de confirmation visuelle après succès (toast / inline message)

#### 2. Cohérence avec le monde réel

- 🟡 Vocabulaire technique inadapté au public cible : "Erreur 500", "Token expiré" au lieu de messages métier compréhensibles

#### 3. Contrôle utilisateur

- 🔴 Action destructive (delete, archive) sans confirmation OU sans undo
- 🟠 Pas d'échappatoire claire dans un wizard / multi-step (bouton "Retour" ou "Annuler")
- 🟠 Pas de fermeture visible sur modal/side-panel (croix en haut à droite)

#### 4. Cohérence interne

- 🟠 Pattern différent du reste de l'app pour une action similaire
- 🟡 Variations de wording pour la même action ("Enregistrer" vs "Sauvegarder" vs "Valider")

#### 5. Prévention d'erreur

- 🔴 Champ critique sans validation côté client (laisser passer une saisie qui sera rejetée par le back uniquement)
- 🟠 Pas de masque/format guide sur input formaté (date, IBAN, SIRET, etc.)

#### 9. Aide au diagnostic d'erreur

- 🔴 Erreur affichée sans message clair ("Une erreur est survenue") sans détail ni action proposée
- 🟠 Code technique exposé à l'utilisateur (`HTTP 422`, stack trace)

#### États oubliés

- 🔴 Pas d'état **empty** (liste vide → écran blanc au lieu d'illustration + CTA)
- 🟠 Pas d'état **loading** distinct du **empty** (skeleton vs liste vide)
- 🟠 Pas d'état **error** (erreur silencieuse côté UI alors que le back a échoué)

### 📱 [RWD] — Responsive / touch

- 🟠 Aucune classe responsive (`sm:`, `md:`, `lg:`) sur un composant qui devrait s'adapter
- 🟠 `width` ou `height` fixés en pixels (`w-[420px]`) sans alternative responsive
- 🟠 Tableau dense sans scroll horizontal mobile (`overflow-x-auto`) ou alternative card-based
- 🟡 Texte trop petit sur mobile (`text-xs` sans bump responsive)
- 🟡 Hover-only interactions (pas de fallback tap pour mobile)

### ⚡ [NG] — Conventions Angular modernes

#### Change Detection

- 🟠 Composant sans `changeDetection: ChangeDetectionStrategy.OnPush`
- 🟠 Fonction appelée dans le template (`{{ computeStuff() }}`) → préférer `computed()`

#### Patterns signal-first

- 🟠 `@Input` au lieu de `input()` ou `input.required<T>()`
- 🟠 `@Output` au lieu de `output<T>()`
- 🟠 `@ViewChild` au lieu de `viewChild<T>()`
- 🟠 `ngOnInit` au lieu de `constructor()` + signaux
- 🟡 `BehaviorSubject` qui pourrait être migré en `signal`

#### Standalone & DI

- 🟠 Nouveau composant non `standalone: true`
- 🟠 Injection via constructeur au lieu de `inject()`

#### Control flow

- 🟠 `*ngIf` / `*ngFor` / `*ngSwitch` → préférer `@if` / `@for` / `@switch` (Angular 17+)
- 🟠 `@for` sans `track`

#### Conventions projet (depuis `CLAUDE.md`)

**Étape obligatoire** : si `CLAUDE.md` projet existe et documente des conventions UI spécifiques, les appliquer comme checks supplémentaires. Exemples typiques :

- **Form controls custom** : si le projet a des composants comme `<app-select>`, `<app-multi-select>`, `<app-textarea>`, `<app-button>`, etc. documentés → flagger l'usage des contrôles bruts (PrimeNG, HTML natif) à la place quand le custom existe.
- **Pièges API documentés** : si `CLAUDE.md` documente un piège (ex: "ButtonComponent utilise content projection, pas d'input `label`/`iconClass`/`iconRight`") → flagger les violations.
- **Renommages tiers** : si `CLAUDE.md` documente une migration de lib (ex: "PrimeNG 19 : `<p-inputSwitch>` → `<p-toggleswitch>`") → flagger l'ancien nom.
- **Side panels vs popups** : si `CLAUDE.md` documente une migration → flagger l'usage du legacy.

**Règle générale** : tout ce qui est dans `CLAUDE.md` projet est **prioritaire** et doit être checké. Le skill ne hardcode aucune convention spécifique — il s'adapte au projet via `CLAUDE.md`.

## Règles absolues

- **Aucune modification de code** — rapport seulement. Le développeur applique les fixes lui-même.
- **Aucune commande git** au-delà de `git status`, `git diff --name-only`, `git branch --show-current` (lecture seule).
- **Pas de double-comptage** : si un même problème touche [A11Y] et [VIS] (ex: contraste insuffisant), le ranger dans le tag le plus critique ([A11Y]) avec mention de l'autre axe en note.
- **Pas de bruit** : ne pas remonter un finding si la convention est respectée. Mieux vaut 5 findings actionnables que 50 dilués.
- **Référence précise** : chaque finding cite le critère (WCAG 2.4.7, Nielsen #1, Refactoring UI "Hiérarchie", etc.) pour que le développeur puisse approfondir.
- **Approximations explicites** : pour le contraste, mentionner que c'est une estimation via classes Tailwind, pas un calcul runtime exact.
- **Conventions projet > règles génériques** : si `CLAUDE.md` projet définit une règle plus stricte ou différente d'un standard, suivre la règle projet.
- **Langue** : rapport en **français**. Citations de critères WCAG/Nielsen en anglais (référence officielle).
- **Volume** : si scope > 5 composants → demander confirmation avant de lancer (rapport potentiellement long).
- **Confidentialité** : ne jamais lire ni mentionner de fichiers `.env*`, secrets, configs perso.
