# dev-loop — plan + state + /step ハーネス

会話履歴ではなく **2 つのファイル** を正典にして、検証ゲートを挟みながら **1 ステップずつ** 開発を進める
loop-engineering ハーネス。状態を外部化しているので `/clear` で文脈を消しても再開できる。

- **仕様（何をやるか）**: `dev-plan.md`（`/plan-init` が `.claude/dev-plans/<date>-<slug>.md` に**新規作成し上書きしない**。アクティブな計画は `dev-state.json` の `planDoc` が指す）— 順序付きステップの正典。過去の計画はファイル＋git 履歴として残り、意思決定を失わない。
- **状態台帳（何が起きたか・設定）**: `dev-state.json`（`.claude/dev-state.json`。**git 管理しない＝`.gitignore` 済み・ローカル/開発者ごと**。多人数開発でのマージコンフリクトを避けるため）— `/step` が読み書きする。状態はコミットされないので、他メンバー/別マシンでは進捗を計画ファイル＋コミット履歴 `Step N: title` から辿る。

設定値（ブランチ・ゲートコマンド・プロジェクト名・計画パス）は **すべて `dev-state.json` に置く**。
コマンドの prose にハードコードしないので、どのプロダクトでも同じコマンドが動く。

## コマンド

| コマンド | 役割 |
|---|---|
| `/plan-init [ゴール/仕様/レビュー文書]` | **既定で `.worktrees/<slug>/` に git worktree を作成**（ブランチ `dev-loop/<slug>`。「現ツリーで」と明示時のみスキップ）し、計画を `.claude/dev-plans/<date>-<slug>.md` に**新規生成（上書きしない）** + `dev-state.json` を生成し `.gitignore` へ登録（＝git 管理外）——いずれも worktree 内に。ゲート自動検出・ベースライン記録・レビュー設定。曖昧なゴールには任意グリリング。 |
| `/step [id]` | 1 ステップ実行（依存確認→実装→ゲート→**レビューゲート**→state 更新(ローカル)→計画+実装を 1 コミット）。空なら次の pending。 |
| `/step-review [id]` | レビューゲートだけを現作業ツリーに対して回す**読み取り専用**ビュー（コミット/前進しない）。 |
| `/plan-status` | 進捗の読み取り専用ビュー。 |
| `/plan-finish` | 計画の仕上げ。完了確認 → ゲートを**その場で再実行**（エビデンス）→ base 同期 → merge / push+PR / keep / discard → **出自ゲート付き** worktree cleanup。 |

## 実行プロトコル（`/step` が毎回守る 12 + 1）

```
[開始前]
  1. dev-state.json を読み、設定(planDoc/branch/worktree/gateCommands/review/currentStep/steps/globalLearnings)を取得
  2. 対象ステップ確定（引数 > currentStep。in-progress があれば再開。mid-review 中断は verification.review/baseCommit を参照）
  3. worktree が非 null なら現作業ツリー root（git rev-parse --path-format=absolute --show-toplevel）と worktree.path の一致を確認（不一致は停止＝「ワークツリー分離」節）。branch があればそのブランチ上＆作業ツリー clean を確認（違えば停止。計画ファイル(planDoc)や初回の .gitignore が未コミットなのは正常＝clean 判定から除外。dev-state.json は .gitignore 済みで元から git status に出ない。※mid-review 再開時の dirty は「レビューゲート」節を参照）
  4. dependsOn が全て done＋検証緑か確認。未完/退行は先に是正
  5. globalLearnings で既知の地雷を確認
  6. planDoc で「ゴール/成功条件/検証方法」を読み、file:line を現物コードで再確認
[実行中]
  7. 当ステップを status=in-progress, startedAt に更新。review.enabled なら verification.review.baseCommit に現 HEAD を記録
  8. 実装 → 「検証方法」＋ gateCommands の各ゲートを実行（定義キーのみ。**その場で実行し出力を読む**＝「通るはず」で done にしない）。退行ゼロを確認
[レビューゲート（review.enabled のとき。round r = 1..maxRounds。詳細は次節）]
  9. 観点レビュー並行起動: まず ?? の新規ファイルを git add -N で diff に載せ（untracked は diff に写らない）、
     前提検証（fail-closed）＝ git rev-parse --verify -q <baseCommit>^{commit} が成功し、かつ
     git diff --quiet <baseCommit> が非 0 終了（=差分あり）であることを確認（どちらか偽なら reviewer を起動せず停止＝「前提検証」節）。
     git diff <baseCommit> を対象に perspectives[] の各観点を dev-reviewer で並行起動。
     各 reviewer は severity/scope/autoFixable/requiresHuman＋安定キーを自己申告した JSON findings を返す
 10. 統合・裁定・収束判定（メインエージェント自身。裁定用サブエージェントは起動しない）: マージ・重複排除（同一 key／file:line＋趣旨）
     → blockOn 以上を現物照合して偽陽性棄却 → 未解決無し→収束（verdict は followups or clean）。
     有＋autoFix＆全て autoFixable→修正し gateCommands 再実行→r++ で 9 へ。
     オシレーション(未解決キー集合が縮小しない)/maxRounds 超過/reviewer 失敗→収束失敗(blocked)
[完了時]
 11. state を最終形まで一括更新する（currentStep/lastUpdated も含めて）。dev-state.json は git 管理外＝コミットされない（ローカルのみ）。
     収束時: status=done(見送りは deferred＋理由), completedAt, verification(gates＋review), learnings, out-of-scope は steps[]＋planDoc に新規ステップ＋globalLearnings に追記, さらに currentStep を次へ・lastUpdated を更新。steps[].commit は自分のハッシュを埋め込めないため null のまま（次ステップ手順7で backfill）
     収束失敗時: status=blocked, verification.review を記録, currentStep は据え置き, コミットせず作業ツリー dirty のまま停止・報告
 12. 収束時のみステージング: git add -A で planDoc(計画ファイル)＋実装を一括ステージ（dev-state.json は .gitignore 済みで staged されない＝ローカルのまま。git commit -am や部分 add は使わない）
 13. 収束時のみ 1 ステップ=1 コミット（このステップの最後の操作）: メッセージは Step <id>: <title>、レビュー実施時は末尾に [review: <verdict>, <rounds>r]
     → 直後に git status --porcelain で clean を確認（ignored な dev-state.json は表示されない。計画ファイルの残差分はコミット漏れ＝追従コミットで取り込む）
```

> `review.enabled=false`（または `review` ブロック不在）なら 9〜10 を**丸ごとスキップ**し、従来の 10+1 として動く（後方互換）。

## レビューゲート（review gate）

各ステップの**実装＋品質ゲートが緑になった後・done 記録/コミット/前進の前**に挟む、自己完結のレビュー機構。
「全観点のサブエージェントが並行レビューし、メインエージェントが統合・現物照合・裁定し、
収束するまで修正と再レビューを反復し、最終結果で次の処理を決める」を実現する。
**外部プラグインに依存しない**（エンジンは dev-loop 同梱）。

### エンジン（dev-loop 同梱）

- 観点カタログ: `assets/review-perspectives.md`（カタログ 13 観点・既定セット 10 観点。キー＋焦点チェックリスト）。
- 観点別 reviewer: `dev-loop:dev-reviewer`（単一観点・読み取り専用）。観点数だけ並行起動。
  各指摘に severity に加えて scope / autoFixable / requiresHuman を**自己申告**する。
- オーケストレーション＋裁定: `/step` 本体（メインエージェント）。統合・重複排除・現物照合・verdict 決定・修正を
  すべて担う（reviewer は編集しない。**裁定用の追加サブエージェントは起動しない**）。
- ※もしエージェント型が解決できない環境なら、同じプロンプトで `general-purpose` 代替起動してもよい。

### レビュー対象 diff

- 常に **`git diff <baseCommit>`（作業ツリー＋staged の累積差分）**。`baseCommit` はステップ着手時の HEAD で、
  着手時（プロトコル 7）に `verification.review.baseCommit` へ**永続化**する（`/clear` 後の再開の鍵）。
- 再レビュー（round r≥2）は cold review せず、**前ラウンドの未解決キー**を seed に渡し、
  「解決済みが本当に直ったか＋修正で混入した退行」を累積 diff 上で検証する。

### 前提検証（fail-closed）

reviewer を起動する**前に**、レビュー対象が実在することを確認する。どちらか一方でも満たさなければ
**reviewer を起動せず停止**して報告する（「レビュー対象なし」を clean と誤判定しない——
下記ループの「reviewer 失敗を『指摘なし』と誤判定しない」と同じ思想）:

1. `git rev-parse --verify -q <baseCommit>^{commit}` が**成功**する（rebase / amend / GC で baseCommit が
   消えていると失敗する → baseCommit を取り直してから再開する）。
2. `git diff --quiet <baseCommit>` が**非 0 終了**する（終了コード 0 = 差分なし）。**untracked は diff に写らない**ため、
   この検証の前に `git status --porcelain` の `??` を確認し、当ステップで作った新規ファイルは
   `git add -N <paths>`（intent-to-add。コミットはしない）で diff に載せておく——空 diff の誤停止を防ぐだけでなく、
   追跡ファイルの変更と混在するステップで**新規ファイルだけがレビューから漏れる**のも防ぐ。
   その上でなお空 diff なら「実装が本当に行われたか」を疑い、実装が本当に不要なステップなら deferred を検討する。

### ループ（round r = 1..maxRounds）

1. **観点レビュー（並行）**: `perspectives[]` の各観点を `dev-reviewer` で**並行起動**。各 reviewer は担当観点のみで、
   severity（`must/ask/suggestion/nits`）・scope（`in-step`/`out-of-scope`/`dependency`）・`autoFixable`・`requiresHuman` を
   **自己申告**した JSON findings を返す（安定キー `key = sha1(観点|file|rule|要約)` 先頭 8 桁・根拠引用 `evidence` 付き）。
2. **統合・裁定（メインエージェント）**: 全 findings をマージし重複排除する（同一 key は 1 件。観点跨ぎで `file:line`＋趣旨が
   同じ指摘は最重 severity で統合し、由来観点を `fromPerspective` に併記。代表 key は `perspectives[]` の並び順で最初に
   現れた指摘の key ＝ 決定的に選んでラウンド間で安定させる）。`blockOn`（既定 `must`）以上の指摘は該当 `file:line` を
   **現物コードで最小限検証**（reviewer の `evidence` と突合）し、読み違い・存在しない問題・設計原則
   （implement-vs-gate の意図的スタブ等）で正当化されるものは**棄却**して理由を控える。blockOn 未満は自己申告のまま扱ってよい。
3. **収束判定**:
   - `blockOn` 以上の未解決が**無い** → **収束**。verdict は out-of-scope の妥当な指摘（フォローアップ化）があれば
     `followups`、無ければ `clean`。
   - 未解決があり `autoFix=true` かつ**全て `autoFixable`（in-step ＆ !requiresHuman ＆ 機械修正可）** →
     メインエージェントが修正 → **`gateCommands` を再実行**（退行ゼロをコミット時に保証）→ r++ で 1 へ。
   - **オシレーション検知**: round r の未解決 must キー集合が round r-1 の**真部分集合に縮小しない**
     （直したはずが再燃／A↔B 往復）→ **即停止＝収束失敗**（maxRounds より早く止める）。
   - **maxRounds 超過** / **reviewer 失敗**（エラー・パース不能）→ **収束失敗**（失敗を「指摘なし」と誤判定しない）。

観点カバレッジは `perspectives[]` から決定的に全観点を起動するため**構成上保証**される（欠落補充の機構は持たない）。

### 次に適切な処理（最終結果 → state アクション 決定表）

| 最終結果 | 判定（verdict） | 次アクション |
|---|---|---|
| `blockOn` 以上の未解決なし（最初から clean / 修正後 clean） | 合格（`clean`） | state を最終形へ（`status=done`、`verification.review` 記録、**`currentStep` 前進・`lastUpdated` 更新まで最終形に**）→ `git add -A` で planDoc(計画ファイル)＋実装をステージ（dev-state.json は git 管理外で staged されない）→ **収束時に 1 回だけ**コミット（メッセージ末尾に `[review: <verdict>, <rounds>r]`）→ `git status --porcelain` で clean 確認（ignored な state は出ない） |
| 未解決 must が `requiresHuman`（インフラ等）/ in-step で直せない / approach 誤り | 不合格（`blocked`） | **コミットしない**・dirty 維持・`status=blocked`、人間タスクを `verification.review.remaining[]` と `verification.notes` に明記し**停止・報告** |
| `dependency` 起因（先行ステップの退行/前提崩れ） | 差し戻し（`blocked`） | 該当 `dependsOn` ステップへ戻って是正（既存原則「退行は該当ステップへ戻る」） |
| out-of-scope だが妥当な指摘（in-step 成功条件は満たす） | 合格（`followups`） | `steps[]` に新規 pending ステップ追記（`followups[].stepId` で相互参照）＋`globalLearnings` 記録。当ステップは done で前進 |

reviewer と裁定を行うメインエージェントは `assets/review-perspectives.md` の設計原則（implement-vs-gate で意図的に維持した
experimental スタブを「未実装」と咎めない、無言のスタブは咎める 等）を尊重する。

### 再開（`/clear` を跨ぐ mid-review）

- `/step` 開始時、`in-progress` かつ `verification.review.verdict` が未確定/`blocked` を **mid-review** として検出する。
- **clean-tree チェックを緩和**: mid-review 再開では dirty が正常（実装＋適用済み修正を保持）。`baseCommit` と照合し、
  ステップ対象ファイル外の無関係変更が混じる場合のみ停止して確認する。
- round 途中は復元せず **round 1 からやり直す**が、永続化済み `remaining[]` のキーを seed に渡すため冪等
  （キーは内容ハッシュで安定、収束はキー集合縮小の不変条件で支配される）。
- `verdict:"blocked"` のステップは既定で**読み取り報告のみ**（無人の再 `/step` で再スラッシングしない）。
  明示的な `/step <id>`、または人間が修正後に `/step-review`／state 手編集で再挑戦する。

## ワークツリー分離（/plan-init の既定）

並行 LLM セッションが同一作業ツリーを編集すると、ファイル競合・リンターエラー・clean-tree 前提の衝突が起きる。
dev-loop はこれを **1 プラン = 1 worktree = 1 セッション** で構造的に回避する（`/plan-init` の既定動作。
ユーザが「現ツリーで」と明示したときのみ従来どおり現ツリーで進める）。

- **配置**: `<main root>/.worktrees/<slug>/` にブランチ `dev-loop/<slug>` をチェックアウトする。
  計画ファイルと `dev-state.json` は **worktree 内**に生成する。
- **state 分離は構造的**: `dev-state.json` は作業ツリーごとの untracked ファイル（git 管理外）なので、
  worktree ごとに自然に分離される。スキーマ側に分離機構は不要。
- **排他も構造的**: git は同一ブランチの二重チェックアウトを拒否する。別セッションが同じプランを掴むことは
  できない（所有の確認は `git worktree list --porcelain` で行う——`-b` 付き `git worktree add` の失敗メッセージは
  チェックアウト済みと残骸ブランチを区別しないため。チェックアウト済みなら停止＝排他が働いた正常動作）。
- **ネスト禁止（検出は 2 段・この順で常に両方走らせる）**: (1) まず submodule 検査——
  `git rev-parse --show-superproject-working-tree` が非空なら submodule 内 → worktree 化せずユーザに確認する。
  (2) 次にネスト検査——`git rev-parse --path-format=absolute --git-dir` ≠ 同 `--git-common-dir` なら既に
  linked worktree 内 → 新規作成せず現ツリーをそのまま使い、`worktree: {path: <現 root>, createdByDevLoop: false}`
  を記録する。
- **ignore 安全ゲート**: 作成前に main root で `git check-ignore -q .worktrees/` を確認する（**引数は末尾
  スラッシュ付き**——ディレクトリ未作成の時点では、`.worktrees/` パターンが登録済みでもスラッシュ無し引数だと
  非 0 を返すため）。未 ignore なら
  **`.git/info/exclude`**（`git rev-parse --git-common-dir` 配下。全 worktree 共有・コミット不要）へ
  `.worktrees/` を追記する。committed `.gitignore` に既に登録済みならそれを尊重する（check-ignore が成功する
  ので何もしない）。committed `.gitignore` へは追記**しない**——plan-init は非コミット設計であり、main tree 側の
  `.gitignore` 変更は worktree 内で走る初回 `/step` のコミットに乗らず、永久に未コミットの dirty として残るため。
- **ネイティブツール優先**: ハーネスが worktree 作成/移動ツールを持つならそれを優先し、`git worktree add` の
  直接実行は無い場合のフォールバックとする（ハーネスの管理外の worktree を作らない）。
- **セッションハンドオフ**: 作成後も現セッションは main tree にいる。ハーネスの worktree 移動ツールで移動するか、
  `.worktrees/<slug>` で新しいセッションを開いて `/step` を実行する（main tree のセッションで `/step` を打たない。
  誤実行は `/step` 手順 3 の worktree ガードが停止する）。
- **後始末は `/plan-finish`**: worktree の削除は出自ゲート（`createdByDevLoop: true` かつ `.worktrees/` 配下）を
  満たすときだけ行う（次節）。

## /plan-finish プロトコル

計画の出口。全ステップ完了後（または部分完了を明示確認後）に、検証済みの状態で作業ブランチを畳む。
メインエージェントのみで実行する（追加サブエージェントは起動しない）。

1. **前提**: state を読む（worktree ガード・branch 照合は `/step` 手順 3 と同一。復帰実行の例外は下記 ※）。全 steps が done/deferred でなければ
   一覧を提示して部分完了の続行可否を確認する（blocked は先に解消を推奨）。作業ツリーは clean 必須
   （dirty なら停止。自動 stash/commit しない）。
2. **fresh ゲート**: gateCommands を**その場で全て再実行し出力を読む**（検証エビデンス規律）。赤なら停止。
3. **base 同期**: `baseBranch`（旧 state で null なら検出して確認）に対して、remote があれば fetch し、
   **進行判定・merge とも fetch 済みの `origin/<baseBranch>` を対象**に（remote 無しなら local `<baseBranch>`。
   fetch は remote-tracking ref しか更新しない）、base が進んでいれば作業ブランチへ merge する
   （コンフリクトは停止して人間が解消）。**merge が発生したらゲートを再実行**する（stale なまま merge/PR しない）。
4. **4 択**（ユーザに確認）→ 実行:

| 選択 | 動作 | cleanup |
|---|---|---|
| **merge** | main root で base がチェックアウト済み＆clean を確認（違えば停止・勝手に checkout しない。remote があれば local base が origin から分岐していないことも確認——独自コミットは停止）→ `git merge --no-ff <branch>` | する（branch はマージ済み検証付きの `-d`） |
| **push + PR** | `git push -u origin <branch>` → `gh pr create`（gh 不在なら push＋compare URL 提示） | **しない**（PR レビュー用に保持。マージ後に再度 `/plan-finish` → 取り込み済み検出で cleanup 直行） |
| **keep** | 何もしない（現状と手動 cleanup 手順を提示） | しない |
| **discard** | 破壊的。**ブランチ名をそのままタイプさせて確認**後に破棄 | する（`--force`・branch は `-D`） |

※ 現ツリー実行（`worktree: null`）の merge は、main root に作業ブランチ自身がチェックアウトされているため
そのままでは停止する——人間が base を checkout してから `/plan-finish` を再実行する。復帰実行
（HEAD == baseBranch ＆ clean。**自動では merge せず、復帰実行として続行するかを 1 回確認する**）では
branch 不一致を merge 目的の正常とみなし、手順 2〜3 は初回実行で
作業ブランチに対して済んでいるためスキップして手順 4 の merge に直行し、**merge 後に gateCommands を
再実行してエビデンスを取ってから確定する**（赤なら停止・報告し、merge 直後なら main root で
`git reset --hard ORIG_HEAD` により base を merge 前へ戻す手順を提示する）。discard も現ツリー実行では
**自動実行しない**（チェックアウト中のブランチは削除できない）——人間が base を checkout した後の
手動手順として提示する。

5. **cleanup（出自ゲート）**: `worktree.createdByDevLoop === true` **かつ** path が `<main root>/.worktrees/` 配下——
   の両方を満たすときだけ、**先に main root へ移ってから** `git worktree remove <path>` する（discard のみ
   `--force`。通常は dirty を git が拒否する安全弁を活かす）。branch 削除（merge 時 `-d`＝マージ済み検証付き / discard・PR 取り込み確認済み時 `-D`）は
   worktree remove の**後**に行う（チェックアウト中のブランチは削除できない）。条件を満たさない worktree
   （ユーザ自作・現ツリー・`createdByDevLoop: false`）は**削除しない**——手動手順の提示に留める。
6. **報告**: 実施内容とゲートのエビデンス要約。cleanup した場合の報告は経路で分ける——merge:
   「`dev-state.json` は worktree と共に消えた。恒久記録は計画ファイル（base に取り込み済み）＋ `Step N:`
   コミット履歴」。discard: 「worktree・state・計画ファイルのコミット・`Step N:` 履歴ともに破棄済み」。

## 設計原則

1. **実働経路を最優先** — 実際にユーザが通る経路の実バグを最初に潰す。
2. **品質ゲートを早期に緑化** — 赤いゲートは検証の信頼性を奪う。早く緑にして本物のゲートにする。
3. **広告 == 実装（正直さ）** — 各スタブは「実装する」か「experimental 明示／呼んだら throw」の二択。無言のスタブを作らない。
4. **DX・テストを機能網羅より優先** — トレードオフ時は機能数より DX とテスト網羅を取る。重インフラは需要が出るまで experimental 維持可。
5. **小さく・独立・検証可能** — 1 ステップ = 1 コミットで完結し、必ず検証できる粒度に保つ。
6. **縦切り（tracer bullet）** — ステップはレイヤ単位の横切りではなく、レイヤを貫通する細い完全経路で切る。
   各ステップが単独で end-to-end 検証可能になり、ステップ間・並行プラン間の同一ファイル接触が減る。

### implement-vs-gate 判断フレーム（スタブ機能を扱うステップ冒頭で適用）

- **Q-A**: 今すぐ動く必要のある具体的ユースケース/example があるか？
- **Q-B**: DX 価値は高いか（多くの利用者が最初に触るか）？
- **Q-C**: 実装コスト（永続化・外部プロトコル・セキュリティ）は妥当か？

いずれも Yes 寄り → **実装**。そうでなければ **experimental 維持**（本ステップは「ゲート文言＋未実装テストの確定」だけ行い、実装は将来のトリガ発生時）。

### 検証エビデンス規律

done の記録・verdict の判断・`/plan-finish` の実行の前には、ゲートコマンドを**その場で実行して出力を読む**。
過去の実行結果・「通るはずです」は証拠ではない。reviewer の findings を評価するときも同じ——
`evidence` を現物コードと突合してから裁定する（レビューゲートの現物照合と同じ思想）。

## 計画ファイル（dev-plan.md）の構造

1. ヘッダ: プロジェクト名 / 出典 / 起点コミット / 作業ブランチ / 作業ツリー（worktree 分離時は絶対パス・現ツリー実行なら「現ツリー」） / 計画バージョン。
2. **§0 実行プロトコル**（上記の 12+1。レビューゲートを含む）と「起動方法（`/step` / `/step-review` / `/plan-finish`）」。
3. **品質ゲート表**（gateCommands と起点/不変条件）。
4. **設計原則** ＋ **implement-vs-gate フレーム**。
5. **フェーズ & ステップ一覧表**（id / title / reviewIds / 区分 / 既定方針）。
6. **各ステップ詳細**（§1, §2, …）: ゴール / 背景 / 成功条件（チェックリスト）/ 検証方法 / 想定変更ファイル(`file:line`) / 依存 / コミットメッセージ雛形。

テンプレートは `assets/dev-plan.template.md` と `assets/dev-state.template.json` を参照。

## 運用のコツ

- **1 セッション 1 ステップ**を基本に、ステップ間で `/clear` してよい（state から復元できる）。
- **並行開発は 1 worktree = 1 プラン = 1 セッション**: 並行プランは `.worktrees/` 下に並び、state（git 管理外・
  作業ツリーごと）も自然に分離される。仕上げ（merge/PR/破棄と後始末）は `/plan-finish`。
- **ファイル管理方針**: 計画ファイルは `.claude/dev-plans/<date>-<slug>.md` に永続化され**上書きされない**（過去の意思決定を保持）。
  `dev-state.json` は **git 管理外・ローカル**（`.gitignore` 済み）で、多人数開発のマージコンフリクトを避ける。進捗は計画ファイル＋
  `Step N: title` のコミット履歴で共有する。
- **コミット規律**: state（`dev-state.json`）は **git 管理外＝コミットしない**。更新は最終形まで一括で行う（半端なローカル state を
  残さない）。コミットは `git add -A` で `planDoc`（計画ファイル）＋実装を**まとめてステージ**し（`dev-state.json` は ignored で
  staged されない）、直後に `git status --porcelain` で clean を確認する（ignored な `dev-state.json` は表示されない。計画ファイルが
  未コミットで残るのがコミット漏れの典型）。
- 着手前に必ず `file:line` を現物で再確認する（計画は時点情報）。
- 退行を見つけたら新ステップを足すより、**該当ステップへ戻って是正**する（dependsOn の前提を守る）。
- 重い/外部依存の機能は焦って実装せず implement-vs-gate で判断し、`deferred` を恐れない。
- レビューゲートが `blocked` を返したら、`remaining[]` の人間タスク（`requiresHuman`）を片付けてから
  `/step-review` で再チェックし、緑になったら `/step <id>` で確定する。reviewer に直させず**人間が直す**前提のものは無理に autoFix しない。
- 観点レビューは観点数だけ並行起動されるためコストが上がる。軽いステップは `perspectives[]` を絞る／`maxRounds` を下げる。
