# xiaolu-brand-proposal · 品牌提案工作流

为品牌升级项目提供从需求收集到完整交付的标准化工作流。产出包括：专业 Word 提案文档、设计感 HTML 报价单、品牌视觉方向稿、数据图表、以及网页 PPT。

## 适用场景

- 自由职业品牌顾问为客户做品牌升级提案
- 小型创意工作室的标准化提案流程
- 需要快速产出专业级提案文档的场景

## 核心原则

1. **对话式 intake**：不问表格，一问一答收集品牌信息
2. **AI 推断风格**：Agent 根据品牌信息（行业、产品、用户）自行推断最合适的调性、视觉风格、PPT 风格，然后向用户确认
3. **渐进加载 skill**：每个 stage 只读取当前需要的 skill
4. **并行执行**：独立任务同时跑
5. **去 AI 化**：产物要有"手工感"，不是模板堆砌
6. **单一事实来源**：所有产物共享同一个 brand-brief.md，确保数据、文案、风格完全一致
7. **产物归集**：所有产物必须输出到统一命名的项目文件夹，交付时明确告知用户完整路径

## 强制执行规则（必须遵守）

本 skill 是一个**总控工作流**，不是普通写作提示词。Agent 必须严格执行以下规则，不能自行降级为“快速生成文件包”。

### 0. 依赖 Skill 检查

在 Stage 1 开始前，Agent 必须检查以下依赖是否可用：

| Stage   | 必需依赖                                                | 用途                              |
| ------- | ------------------------------------------------------- | --------------------------------- |
| Stage 1 | `deep-research-swarm` 或同等深度研究 skill              | 市场研究、竞品分析、用户洞察      |
| Stage 2 | `xlsx` 或 `spreadsheets`                                | 报价模型、工时拆分、方案对比      |
| Stage 3 | `copywriting`                                           | Tagline、Hero、转化文案、品牌故事 |
| Stage 4 | `report-writing` + `docx` 或 `documents`                | 正式 Word 提案                    |
| Stage 5 | `seaborn-visualization` 或同等数据可视化 skill          | 数据图表                          |
| Stage 6 | 本 skill 内置 HTML 模板                                 | 视觉方向稿                        |
| Stage 7 | `guizang-ppt-skill` 或同等网页 PPT / presentation skill | 网页 PPT                          |
| Stage 8 | 自动化检查脚本；`pdf` 可选                              | 质量检查、PDF 备份                |

检查规则：

1. 如果依赖 skill 已存在，Agent 必须读取对应 `SKILL.md`，并按其流程执行。
2. 如果依赖 skill 不存在，Agent 必须先检查是否有同等能力的已安装 skill 或插件可替代。
3. 如果存在同等能力替代项，Agent 必须列出“原依赖 → 替代项 → 替代原因”，并询问用户是否接受该步骤替代。
4. 如果不存在同等能力替代项，Agent 必须询问用户是否要尝试下载/安装该 skill。
5. 在用户确认前，Agent 不得继续进入对应 Stage。
6. 禁止在未使用依赖 skill、未安装依赖 skill、或未获得用户替代授权的情况下声称“已按完整流程生成”。
7. 如果用户明确允许替代或降级，Agent 必须在 `execution-log.md` 和最终回复中标注“替代/降级生成”的范围和原因。

### 0.1 缺失依赖决策确认

如果检查到一个或多个依赖 skill 缺失，Agent 必须先生成依赖检查结果，并向用户询问下一步处理方式。

必须按以下格式向用户汇报：

```markdown
检测到以下依赖缺失：

| Stage   | 原依赖                | 状态 | 可选替代项                            | 建议               |
| ------- | --------------------- | ---- | ------------------------------------- | ------------------ |
| Stage 1 | deep-research-swarm   | 缺失 | Market Research / web research / 其他 | 建议安装或确认替代 |
| Stage 5 | seaborn-visualization | 缺失 | Python 数据可视化 / canvas-design     | 建议安装或确认替代 |

请选择处理方式：

A. 全部尝试下载/安装缺失 skill
B. 全部使用建议替代项
C. 逐项确认：我会逐个告诉你哪些 Stage 用替代、哪些 Stage 下载
D. 停止流程，等我提供 skill 文件或安装源
```

询问规则：

1. 如果缺失项超过 1 个，必须提供“全部下载/安装”和“逐项确认”两个选项。
2. 如果某个 Stage 有可用替代项，必须说明替代项是否等价、是否会影响产物质量。
3. 如果某个 Stage 只能降级、不能等价替代，必须明确标注“降级”，不能写成“替代”。
4. 用户选择后，Agent 必须把选择写入 `execution-log.md`。
5. 用户没有确认前，不得继续执行缺失依赖对应的 Stage。

### 1. 禁止降级生成

除非用户明确同意，否则 Agent 不得将以下产物降级为简化版：

- `research.md` 不能用普通趋势判断替代深度研究 skill
- `copy.md` 不能用普通文案摘要替代 `copywriting`
- `proposal.docx` 不能用简单脚本生成的短文档替代 `report-writing` + `docx/documents`
- `chart_*.png` 不能用手绘示意图替代数据可视化 skill
- `guizang-ppt/index.html` 不能用普通横向 HTML 页面替代网页 PPT / presentation skill

如果某个依赖不可用且用户尚未授权替代/降级，必须暂停并说明：

- 缺失依赖
- 已完成步骤
- 无法继续的原因
- 可选择全部下载、逐项确认、使用替代方案或停止等待安装源

### 2. Stage 执行日志

项目文件夹内必须生成 `execution-log.md`。每完成一个 Stage，立即追加记录：

```markdown
## Stage [编号] · [名称]

- 使用 skill：
- 是否成功读取 SKILL.md：
- 输入文件：
- 输出文件：
- 是否更新 brand-brief.md：
- 是否降级：
- 备注：
```

最终交付前，`execution-log.md` 必须完整，且必须明确列出每个 Stage 是否真正使用了指定 skill。

### 3. brand-brief 强制更新

每个 Stage 完成后，必须先更新 `brand-brief.md`，再进入下一个 Stage。

禁止直接从用户原始信息生成下游产物。顺序必须是：

```text
Stage 1 输出 research.md
→ 提取关键市场数据、竞品结论、用户洞察，更新 brand-brief.md
→ Stage 2 读取更新后的 brand-brief.md

Stage 2 输出 pricing-model.xlsx / pricing.html
→ 提取价格、工时、周期、付款节点，更新 brand-brief.md

Stage 3 输出 copy.md
→ 提取 Tagline、Hero、转化文案、品牌故事，更新 brand-brief.md

Stage 4-7 均只能读取最新 brand-brief.md
```

### 4. 多 Subagent 并行规则

如果当前环境支持 subagent / multi-agent 工具，Agent 必须优先使用 subagent 并行执行可独立完成的 Stage。推荐拆分如下：

| Subagent       | 任务                           | 输入                                  | 输出                              |
| -------------- | ------------------------------ | ------------------------------------- | --------------------------------- |
| Research Agent | 市场研究、竞品分析、用户洞察   | `brand-brief.md`、用户素材、竞品信息  | `research.md`、研究摘要           |
| Pricing Agent  | 三档报价、工时拆分、ROI 假设   | `brand-brief.md`、预算范围            | `pricing-model.xlsx`、报价摘要    |
| Copy Agent     | 品牌文案系统                   | `brand-brief.md`、研究摘要            | `copy.md`、文案摘要               |
| Visual Agent   | 视觉方向稿                     | `brand-brief.md`、品牌素材图片        | `visual-direction.html`、视觉摘要 |
| Proposal Agent | 正式提案文档                   | 最新 `brand-brief.md`                 | `proposal.docx`                   |
| PPT Agent      | 网页 PPT / 演示稿              | 最新 `brand-brief.md`、图表、视觉方向 | `guizang-ppt/index.html`          |
| QA Agent       | 一致性检查、文件检查、截图检查 | 全部产物                              | `qa-report.md`                    |

并行执行约束：

1. Stage 1-3 可以并行执行，但它们完成后必须由主 Agent 汇总并更新 `brand-brief.md`。
2. Stage 4-7 必须读取汇总后的最新 `brand-brief.md`。
3. Subagent 产物不能直接作为最终交付，必须由主 Agent 统一归集、校对和写入执行日志。
4. 如果当前环境不支持 subagent，Agent 必须在 `execution-log.md` 标注“subagent 不可用”，并使用可并行的工具调用或串行执行替代。
5. 不得因为 subagent 不可用而降低产物质量标准。

### 5. 自动安装缺失 Skill

如果依赖 skill 缺失，Agent 必须按以下顺序处理：

1. 检查当前可用 skills 列表。
2. 检查是否有可用插件或同等能力 skill。
3. 生成缺失依赖清单和可选替代方案。
4. 向用户询问：全部下载/安装、全部使用替代、逐项确认、或停止等待安装源。
5. 如果用户选择下载/安装，且存在 `skill-installer`，尝试安装缺失 skill。
6. 如果用户提供 GitHub、文件夹、压缩包或 `SKILL.md` 路径，优先从该来源安装。
7. 如果用户选择替代，使用可用插件或同等能力 skill，并在 `execution-log.md` 记录替代关系。
8. 如果无法定位安装源，停止并向用户报告缺失项。
9. 未经用户确认，不得用普通脚本、手写 HTML、简化图表替代缺失 skill。

## 工作流程

```
Stage 0: Intake（对话收集）
  → 收集品牌信息 + 风格偏好
  → 输出: brand-brief.md（品牌简报，后续所有产物的单一事实来源）
  → 触发：用户说"我要做品牌提案"

Stage 1: 市场研究（可选）
  → Skill: deep-research-swarm
  → 输入: brand-brief.md
  → 输出: research.md（竞品/市场/用户洞察）
  → 更新: brand-brief.md（提取关键数据）
  → 触发：用户提到"竞品分析"或"市场数据"

Stage 2: 定价模型
  → Skill: xlsx（基础版）或 HTML 报价单（高级版）
  → 输入: brand-brief.md
  → 输出: pricing-model.xlsx 或 pricing.html
  → 更新: brand-brief.md（提取定价方案）
  → 触发：用户提到"报价"、"预算"、"三档方案"

Stage 3: 文案撰写
  → Skill: copywriting
  → 输入: brand-brief.md
  → 输出: copy.md（Tagline / Hero / 转化 / 融资金句）
  → 更新: brand-brief.md（提取文案）
  → 触发：用户提到"文案"、"定位语"、"品牌故事"

Stage 4: 提案文档
  → Skill: report-writing → docx
  → 输入: brand-brief.md（唯一信息源）
  → 输出: proposal.docx（完整书面提案）
  → 触发：信息收齐后自动生成

Stage 5: 数据图表
  → Skill: seaborn-visualization
  → 输入: brand-brief.md（提取数据）
  → 输出: chart_*.png（漏斗/竞品/市场/定价）
  → 触发：用户提到"数据"、"图表"、"可视化"

Stage 6: 视觉方向稿
  → 自定义 HTML（本 skill 提供模板）
  → 输入: brand-brief.md（提取风格规范）
  → 输出: visual-direction.html
  → 触发：用户提到"视觉方向"、"设计稿"、"mood board"

Stage 7: 网页 PPT
  → Skill: guizang-ppt-skill
  → 输入: brand-brief.md（提取内容和风格）
  → 输出: index.html（横向翻页，WebGL 背景）
  → 触发：用户提到"PPT"、"演示"、"路演"

Stage 8: 质量检查
  → 验证所有产物完整性 + 一致性
  → 检查清单见下方
```

## Intake 问题模板

### 基础信息（必问，逐问进行）

**规则：每次只问一个问题，等用户回答后再问下一个。每个问题提供 3-4 个选项 + "其他"。**

| #   | 问题                              | 选项                                                                                                                                       | 收集信息                       |
| --- | --------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------ |
| 1   | 品牌名和做什么的？                | —                                                                                                                                          | 品牌名、行业、产品             |
| 2   | 目标用户是谁？                    | A. 企业/B2B / B. 消费者/B2C / C. 创作者/开发者 / D. 其他：\_\_\_\_ / E. 我不清楚，你来帮我决定                                             | 用户画像                       |
| 3   | 这次提案要解决什么问题？          | A. 品牌升级重塑 / B. 新产品上市 / C. 融资路演 / D. 其他：\_\_\_\_ / E. 我不清楚，你来帮我决定                                              | 核心需求                       |
| 4   | 预算范围？期望多久交付？          | A. 5万以下 / B. 5-15万 / C. 15-30万 / D. 其他：\_\_\_\_ / E. 我不清楚，你来帮我决定                                                        | 商务信息                       |
| 5   | 希望呈现什么感觉/调性？           | A. 专业可信 / B. 年轻活力 / C. 高端精致 / D. 其他：\_\_\_\_ / E. 我不清楚，你来帮我决定                                                    | 风格线索                       |
| 6   | 有喜欢的品牌参考吗？              | A. 科技类（如 Notion/Apple） / B. 生活方式（如 Aesop/Muji） / C. 消费类（如 Nike/Spotify） / D. 其他：\_\_\_\_ / E. 我不清楚，你来帮我决定 | 视觉参考                       |
| 7   | 需要 PPT 吗？现场演示还是发文件？ | A. 现场演示 / B. 发文件阅读 / C. 两者都要 / D. 不需要 PPT / E. 我不清楚，你来帮我决定                                                      | 交付形式                       |
| 8   | 有品牌素材可以分享吗？            | —                                                                                                                                          | 品牌素材（图片、网址、文档等） |

### Intake 流程规则

1. **逐问进行**：Agent 每次只问一个问题，等用户回答后再问下一个
2. **选项式提问**：每个问题提供 3-4 个预设选项 + "其他"，用户选择或自定义
3. **自然对话**：根据用户的回答可以灵活追问，不 rigidly 按顺序
4. **素材收集时机**：Q8 可以在任何时候提出，如果用户提前提到素材，直接收集
5. **风格推断时机**：Q8 回答后（或用户表示没有素材后），Agent 进行风格推断并向用户确认

### 风格推断规则

Agent 根据 Q1-Q8 的回答，结合以下维度自行推断风格：

| 推断维度 | 依据                                                                        | 输出                            |
| -------- | --------------------------------------------------------------------------- | ------------------------------- |
| 品牌调性 | 行业属性 + 产品类型 + Q2 用户类型 + Q3 需求类型 + Q5 调性选择 + Q8 素材分析 | 从配色库中选择最匹配的方案      |
| 视觉风格 | 品牌调性 + Q6 参考品牌 + Q8 现有视觉分析 + 行业惯例                         | 从视觉风格库中选择              |
| PPT 风格 | 品牌调性 + Q7 使用场景（演示 vs 发文件）                                    | 从 guizang-ppt-skill 选项中选择 |

**Q8 素材分析要点**：

- 如果有品牌官网/产品截图：分析现有配色、字体、排版、图片风格
- 如果有竞品参考：分析竞品视觉策略，确定差异化方向
- 如果有品牌文档（PDF/PPT）：提取现有品牌元素和调性
- 如果没有素材：基于行业惯例和 Q1-Q7 的回答进行推断

**推断后必须向用户确认**：

> "根据「知言 AI」的定位（AI 写作工具 / 面向创作者 / 融资场景）以及你选择的调性（专业可信）和参考（Notion），我建议采用 **极简科技** 调性 + **留白克制** 视觉风格 + **瑞士国际主义** PPT 风格。你觉得合适吗？"

**如果用户选择"E. 我不清楚，你来帮我决定"**：

> "根据「知言 AI」的定位（AI 写作工具），我推断目标用户应该是 **创作者/开发者**。你觉得对吗？"

用户确认后再进入下一阶段。如果用户有异议，根据反馈调整。

## 步骤优化建议

每个 Stage 可以按需优化，以下是各阶段的优化方向：

### Stage 0: Intake 优化

- **增加追问**：如果用户回答模糊，主动追问细节（如"具体是什么类型的创作者？"）
- **素材预分析**：用户提到官网/图片时，立即访问分析，不要等到 Q8
- **风格预推断**：Q1-Q3 回答后，可以开始初步推断，Q5-Q6 只是验证

### Stage 1: 市场研究优化

- **深度定制**：根据品牌行业选择研究深度（AI 工具需要技术趋势，消费品需要用户洞察）
- **数据源扩展**：除了网络搜索，可以分析用户提供的竞品官网、行业报告 PDF
- **可视化增强**：研究结论直接生成图表数据，减少 Stage 5 的重复工作

### Stage 2: 定价模型优化

- **动态定价**：根据品牌预算范围自动调整三档方案的价格区间
- **ROI 计算**：增加具体的 ROI 计算公式，让用户看到投资回报
- **方案对比**：Excel 中增加方案对比矩阵，直观展示差异

### Stage 3: 文案撰写优化

- **多语言版本**：如果品牌有出海需求，增加英文版文案
- **场景化文案**：针对不同使用场景（官网、PPT、演讲）生成不同版本
- **A/B 测试建议**：为关键文案提供 A/B 测试方案

### Stage 4: 提案文档优化

- **模块化结构**：根据提案目的（融资/品牌升级/新产品）选择不同的章节模板
- **案例嵌入**：自动插入相关行业案例，增强说服力
- **交互元素**：Word 中增加目录、交叉引用、书签，提升专业感

### Stage 5: 数据图表优化

- **动态数据**：图表数据直接从 brand-brief.md 读取，确保一致性
- **图表类型**：根据数据类型选择最合适的图表（漏斗图、雷达图、热力图等）
- **品牌配色**：图表配色严格遵循 brand-brief.md 中的配色方案

### Stage 6: 视觉方向稿优化

- **真实截图**：如果用户提供了官网，直接截图并做改造对比
- **多设备展示**：增加手机端、平板端的视觉展示
- **动效预览**：关键交互增加 CSS 动效，让方向稿更生动

### Stage 7: 网页 PPT 优化

- **内容同步**：PPT 内容直接从 brand-brief.md 读取，确保与提案文档一致
- **数据联动**：PPT 中的数据图表直接引用 chart\_\*.png，不重新生成
- **演讲备注**：增加演讲者备注，帮助用户现场发挥
- **页数校验**：生成后必须检查页数，确保不少于 8 页（封面+目录+品牌介绍+市场分析+策略+视觉+报价+结尾）

### Stage 8: 质量检查优化

- **自动化检查**：用脚本自动检查品牌名一致性、价格一致性
- **截图验证**：每个 HTML 产物生成后截图，确保视觉效果
- **用户确认**：交付前让用户确认关键信息（品牌名、价格、时间线）

## 质量检查清单

### 完整性检查

```
□ brand-brief.md 已生成且内容完整
□ 品牌名正确无误
□ 所有数据有来源标注
□ 三档方案价格公式可验证
□ 时间线有具体里程碑
□ 交付物清单无遗漏
□ 视觉方向稿有"升级后长什么样"
□ 下一步行动明确（3 步以内）
□ 联系方式正确
□ Word 字体为 Microsoft YaHei（非 PingFang SC）
□ 所有产物风格一致（跟随 AI 推断的风格）
□ 文件能在客户设备上正常打开
□ **网页 PPT 页数 ≥ 8 页**（封面+目录+品牌+市场+策略+视觉+报价+结尾）
```

### 一致性检查（关键）

```
□ 品牌名：brand-brief.md = proposal.docx = pricing.html = visual-direction.html = index.html
□ 定价：pricing.html 的三档价格 = proposal.docx 的报价 = brand-brief.md 的定价方案
□ 市场数据：chart_*.png 的数据 = proposal.docx 的数据 = brand-brief.md 的研究摘要
□ 品牌文案：copy.md 的 tagline = proposal.docx 的定位语 = index.html 的标题
□ 配色：chart_*.png 的配色 = visual-direction.html 的配色 = pricing.html 的配色 = brand-brief.md 的配色方案
□ 时间线：proposal.docx 的里程碑 = pricing.html 的交付时间 = brand-brief.md 的时间线
□ 竞品分析：research.md 的结论 = proposal.docx 的策略建议 = index.html 的竞品页
□ 用户画像：brand-brief.md 的用户描述 = proposal.docx 的目标用户 = index.html 的用户页
```

### 不一致时的处理流程

1. **发现不一致**：对比两个产物，找出差异点
2. **以 brand-brief.md 为准**：brand-brief.md 是单一事实来源，其他产物向它对齐
3. **更新 brand-brief.md**：如果 brand-brief.md 本身有误，先修正它
4. **同步更新所有产物**：修正后的 brand-brief.md 内容同步到所有引用它的产物
5. **重新验证**：再次运行一致性检查清单

### PPT 页数校验流程

1. **生成后检查**：网页 PPT 生成后，统计实际页数
2. **最低标准**：页数必须 ≥ 8 页，标准结构为：
   - 第 1 页：封面（品牌名 + 提案主题）
   - 第 2 页：目录/议程
   - 第 3 页：品牌介绍（品牌故事/定位）
   - 第 4 页：市场分析（市场规模/竞品）
   - 第 5 页：策略建议（品牌策略/视觉方向）
   - 第 6 页：视觉展示（升级后长什么样）
   - 第 7 页：报价方案（三档方案）
   - 第 8 页：结尾/下一步行动
3. **不足时补充**：若页数 < 8，根据 brand-brief.md 内容补充缺失页面
4. **重新验证**：补充后再次统计页数，确认 ≥ 8 页

## 注意事项

1. **字体兼容性**：macOS WPS 不识别 "PingFang SC"，Word 必须用 "Microsoft YaHei"
2. **AI 推断风格**：Agent 根据品牌信息自行推断风格，向用户确认后再执行，不替用户做决定但主动提供专业建议
3. **内容精简**：报价单首屏直接展示价格，不要堆砌信息
4. **去 AI 化**：产物要有"设计师手工做的"质感，不是模板
5. **迭代机制**：每个产物生成后截图验证，用户反馈 → 修改 → 确认
6. **风格一致性**：一旦用户确认风格，所有产物必须统一应用，不能混搭
7. **数据一致性**：所有产物中的数据（价格、时间线、市场数据）必须来自 brand-brief.md，不能各自编造
8. **文案一致性**：所有产物中的品牌文案（tagline、定位语）必须来自 brand-brief.md 或 copy.md
9. **产物依赖**：Stage 4-7 的产物生成时，必须读取 brand-brief.md 作为唯一信息源，不能独立生成内容
10. **产物归集**：所有产物必须输出到 `[品牌名]-brand-proposal-[日期]` 文件夹，禁止散落在 workspace 根目录
11. **交付规范**：交付时必须明确告知用户完整的文件夹路径和产物清单，不能让用户自己找文件
12. **PPT 页数校验**：网页 PPT 生成后必须检查页数，若少于 8 页需补充内容（封面、目录、品牌介绍、市场分析、策略、视觉、报价、结尾）
