# nixify

Generate ergonomic, maintainable Nix build infrastructure for an existing
project — or replace a hand-rolled build system with Nix — while keeping the
developer's native inner loop intact.

## Core philosophy (read this first)

Six principles drive every decision this skill makes. When in doubt, return to
them.

1. **Transform lockfiles, never hand-maintain dependency lists.** The developer
   keeps editing `Cargo.toml` / `go.mod` / `Gemfile` / `pyproject.toml` /
   `package.json` and running their normal package manager. Nix consumes the
   resulting lockfile (`Cargo.lock`, `go.sum`, `Gemfile.lock`, `uv.lock` /
   `poetry.lock`, `package-lock.json`). Nobody hand-edits a Nix list of
   dependencies, ever.
2. **The native dev loop is sacred.** Inside `nix develop` (auto-loaded by
   direnv), `cargo build`, `go test`, `bundle exec`, `pytest`, `npm run`, `mise
   build` all behave exactly as before. Nix governs *toolchain versions* and the
   *reproducible build/CI path* — not the developer's daily commands.
3. **`flake.nix` stays thin; real logic lives in `lib/` + `pkgs/`.** `flake.nix`
   only declares inputs, instantiates `pkgs`, maps over systems, and assigns
   outputs from `pkgs/` (autoloaded) and `lib/` (helpers). Every package is a
   `callPackage`-style function in `pkgs/<name>/package.nix`.
4. **Default to plain flakes.** Reach for a framework (flake-parts) only when
   module composition earns its learning-curve cost. See
   `references/flake-frameworks.md`.
5. **One self-contained, reviewable MR.** Add Nix files; don't restructure the
   app's source or change how developers work. A reviewer should be able to read
   the whole change and understand it.
6. **Pin the toolchain, cache the rest, update in one command.** Lock toolchain
   versions via `flake.lock`, wire a binary cache (Cachix/attic) so dependency
   compilation isn't repeated, and always ship a single-command update path. You
   don't want a dependency bump to mean hand-editing hashes. See
   `references/ergonomics.md` and `scripts/update-deps.sh`.

## Workflow

This skill runs in stages. **Always do Stage 0.** Then pick the track based on
what the project is.

```
Stage 0: Detect & plan        (always)
   │
   ├─ project has a normal language build (cargo/go/bundler/…)
   │     └─► Stage 1 → Stage 2  ("Nixify an application project" track)
   │
   └─ project IS a hand-rolled build system (Make/shell/Omnibus/multi-tool)
         └─► Stage 3            ("replace a build system" track)
```

### Stage 0 — Detect & plan (always)

Run the detector to inventory the repo, then read the project's own docs to
understand its *purpose* (not just its file types) before proposing anything.

```bash
bash scripts/detect.sh /path/to/repo
```

It reports: languages present, lockfiles/manifests found, the existing build
system (Make / shell / Omnibus / Docker / mise / Bazel), entry points and
services, and a first-guess track. Treat its output as a starting point — then
read `README`, `CONTRIBUTING`, `docs/`, CI config, and the build scripts
themselves to confirm intent.

Produce a short written plan for the user before generating files:

- What the project is and how it currently builds.
- The proposed track (application vs build-system replacement).
- Per language, which builder this skill will use and why (cite the relevant
  `references/<lang>.md`).
- The file layout the MR will add.
- Anything that needs a human decision (IFD tolerance in CI, container target,
  whether to keep an existing consumer contract).

**Decision: which track?** If the repo's primary product is *software it
builds* (Makefiles/shell orchestrating many tools, Omnibus software
definitions, a staged Docker pipeline that compiles a toolchain), it's a
build-system-replacement → Stage 3. Otherwise it's an application project →
Stages 1–2.

### Stage 1 — Dev shell first (lowest risk)

Get a working `nix develop` before packaging anything. This alone delivers
pinned toolchains and a one-command environment, and it's the safest possible
first MR.

1. Scaffold the thin `flake.nix` and `lib/eachSystem.nix` from
   `assets/templates/` (see `references/flake-layout.md`).
2. Add a `devShells.default` exposing the project's native toolchain, pinned.
   Per-language toolchain choices (e.g. oxalica `rust-overlay` reading
   `rust-toolchain.toml`) are in `references/<lang>.md`.
3. Add `.envrc` (`use flake`) for nix-direnv auto-loading, plus `watch_file` for
   any generated dep files. See `references/ergonomics.md`.
4. Add `treefmt-nix` (formatting) and `git-hooks.nix` (pre-commit) wired as
   `formatter` + a `checks` entry. See `references/ergonomics.md`.

**Done when:** `nix develop` works and the project's own build/test commands
pass *inside* it, unchanged.

### Stage 2 — Reproducible package + checks + container

Add the actual reproducible build, validation, and (optionally) a container
image as scoped outputs.

1. Add `pkgs/<name>/package.nix` using the recommended builder for the language.
   **Pick the builder from the per-language reference — don't guess:**

   | Language | Default builder | Lockfile transform | Reference |
   |---|---|---|---|
   | Ruby | `bundlerEnv` / `bundlerApp` | bundix → committed `gemset.nix` | `references/ruby.md` |
   | Go | `buildGoModule` + `vendorHash` | FOD hash (no codegen) | `references/go.md` |
   | Rust | `crane` + oxalica `rust-overlay` | parses `Cargo.lock` | `references/rust.md` |
   | Python | `uv2nix` (uv) / `poetry2nix` (Poetry) | parses lockfile | `references/python.md` |
   | Node | `buildNpmPackage` (pnpm hook / yarn-berry for workspaces) | FOD hash | `references/nodejs.md` |
   | C/C++ | `stdenv.mkDerivation` + cmake/meson/pkg-config hooks | vendored FODs | `references/c-cpp.md` |

2. Wire packages via `lib.packagesFromDirectoryRecursive` so `pkgs/` autoloads.
   See `references/flake-layout.md`.
3. Add `checks`: at minimum `pkgs.testers.testVersion` (or a `runCommand`
   smoke check), plus at least one `runNixOSTest` VM test that boots the
   built artifact and asserts it works. See `references/vm-tests.md`.
4. Expose `overlays.default` so other flakes/NixOS configs can consume the
   packages. See `references/scoped-outputs.md`.
5. Add a container image as a scoped output (e.g.
   `packages.<system>.<name>-image`). Default to **nix2container**; use
   `dockerTools.streamLayeredImage` when you want zero extra inputs. See
   `references/containers.md`.

**Done when:** `nix build` and `nix flake check` are green in CI, and a binary
cache (Cachix/attic) is configured so dependency compilation is cached.

### Stage 3 — Replace a hand-rolled build system

For repos whose product is the software they build (the gitlab-toolchain case).
The decisive win is that **Nix's dependency graph replaces hand-ordered build
chains**, and every component is independently cached and rebuildable.

1. Map each built artifact to its own `pkgs/<component>/package.nix`
   (`stdenv.mkDerivation` or a language builder).
2. Compose components through an **overlay** so they depend on each other via
   the `stdenv` fixpoint instead of an explicit ordering file. The ordering that
   was "buried in script sequence" becomes the derivation graph.
3. Express any custom toolchain / bootstrap (e.g. a crosstool-ng glibc stage) as
   a custom `stdenv` or `crossSystem`.
4. Expose **per-tool scoped outputs** (`packages.<system>.<tool>`) and
   `overlays.default`.
5. **Preserve the existing consumer contract.** If downstream consumers fetch
   `URL + SHA256` tarballs, add a thin publish adapter that emits reproducible
   tarballs and their hashes from the Nix outputs — consumers don't change.
6. Validate each tool with `checks` (`testVersion`, link-against-expected-lib
   assertions) and VM tests.

Read `references/worked-example-gitlab-toolchain.md` for a full worked design,
and `references/worked-example-gkg-orbit.md` for an application-track example
(Rust workspace + embedded Node frontend → single binary).

## Cross-cutting defaults (bake these in)

- **CI eval performance:** prefer vendor-hash or committed-generated lockfile
  transforms over IFD. When using IFD-based tooling (crane, poetry2nix, uv2nix),
  confirm the team's CI tolerates the eval cost and document the
  `allow-import-from-derivation` implication. See `references/transforms-and-ifd.md`.
- **One-command dependency updates:** always ship an update path (a `just
  update` / `nix run .#update-deps` / CI job) so bumping a hash or regenerating
  `gemset.nix`/`gomod2nix.toml` is a single command. See `scripts/update-deps.sh`.
- **Dedupe inputs:** use `inputs.<x>.inputs.nixpkgs.follows = "nixpkgs"` to avoid
  multiple nixpkgs copies.
- **Multi-arch: native (emulated) is the reproducible default, cross is opt-in.**
  Cross-compiled binaries aren't guaranteed byte-identical to native ones, so the
  shipped/validated/cached artifact should be the *native* build (`localSystem =
  <target>`, QEMU-emulated on a foreign-arch builder); expose cross as a separate
  fast-iteration output, never as the default `packages`. Don't wire `crossSystem`
  with `localSystem = system` and assume you got cross — verify the drvPaths. See
  `references/native-vs-cross.md`.
- **Never** alter the app's native dev workflow or source layout.
