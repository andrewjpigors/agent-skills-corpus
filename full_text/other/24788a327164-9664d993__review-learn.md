## Learning Protocol

After the clarify phase resolves an ambiguity, evaluate whether the resolution
should be recorded as a project convention.

### When to Propose a Convention

Record when the resolution is:
- **Reusable**: Would apply to future similar changes (not a one-off)
- **Non-obvious**: Not already covered by framework rules or universal conventions
- **Specific enough**: Can be stated in 1-2 sentences with clear criteria

Do NOT record:
- One-time exceptions ("we did it this way because of a deadline")
- Preferences that only apply to one person
- Things already covered by framework rules

### How to Propose

```
Based on your answer, I'd like to record this convention:

  Convention: "Background jobs must be idempotent — the handler
  must check if the work was already done before proceeding."
  Scope: general

Record this?
```

Wait for explicit confirmation before writing.

### Scoping Conventions

Determine the appropriate scope file based on the change:

| Scope | File | When |
|-------|------|------|
| `api` | `project/review/conventions/api.yml` | API endpoints, request/response, auth |
| `testing` | `project/review/conventions/testing.yml` | Test patterns, coverage, fixtures |
| `general` | `project/review/conventions/general.yml` | Everything else |

New scope files can be created when a domain accumulates 5+ conventions.

### Convention Format

```yaml
- id: <SCOPE>-<NNN>
  convention: "<one-line statement>"
  context: "<when this applies>"
  recorded: "<ISO8601 date>"
  source: "<review that produced this — branch or MR reference>"
  triggered_count: 0
  last_triggered: null
  promoted: false
  promoted_to: null
```

### Tracking Convention Relevance

During the analyze phase (CHK-CONVENTIONS), every convention that is **applicable**
to the current diff must have its `triggered_count` incremented and `last_triggered`
updated — regardless of whether the diff passes or violates the convention.
"Applicable" means the convention's scope matches files in the diff.

This tracking drives the promotion system.

### Updating the Index

After recording a convention, update `project/review/conventions/_index.yml`:

```yaml
- id: API-001
  summary: "All endpoints must validate input before processing"
  scope: api
```

The index is the agent's first read — keep each entry to one line.

### Promotion to Build Rules

When a convention reaches the promotion threshold, propose promoting it to a
formal build rule. This creates a feedback loop from review to build.

**Promotion threshold**: 3 (convention was applicable in 3 or more reviews)

**Detection**: After CHK-CONVENTIONS completes and trigger counts are updated,
check all conventions for `triggered_count >= 3` and `promoted == false`.

**Proposal format**:

```
Convention API-001 has been relevant in 5 reviews.
"All endpoints must validate input before processing"

This pattern is consistent enough to become a formal rule.
Should I promote it?
```

Wait for explicit confirmation.

**Promotion targets** (when harnex-build is present — `project/specs/` exists):

| Convention scope | Target file | What to write |
|---|---|---|
| General code pattern | `project/constraints.yml` | New constraint with `source: review/<ID>` |
| API behavior | `project/specs/domains/<domain>/invariants.yml` | New invariant |
| Domain-specific data rule | `project/specs/domains/<domain>/entities.yml` or `contracts.yml` | Spec amendment |
| Test pattern | `project/constraints.yml` | New constraint |

When writing to harnex-build files, load the `harness-spec` skill (if available)
to understand the target format. The `harness-spec` skill will be present in
`.opencode/skills/` if harnex-build is installed alongside harnex-review.

**Promotion without harnex-build** (no `project/specs/`):

Mark the convention as promoted with `promoted_to: "strong-convention"`. Strong
conventions are given higher weight in future reviews — they are treated as
near-mandatory rather than advisory. They remain ready for formal promotion if
the project later adopts harnex-build.

**After promotion**:

Update the convention entry:
```yaml
  promoted: true
  promoted_to: "project/constraints.yml:R-PROJ-003"  # or "strong-convention"
```

The convention continues to be checked during reviews even after promotion.
The build rule and the review convention coexist — defense in depth.

### Recording Review History

After completing a review, write a summary to `project/review/history/`:

**Filename**: `<YYYY-MM-DD>-<branch-or-mr>.yml`

**Format**:
```yaml
date: "2026-03-10"
source: "feature-x branch vs main"
files_reviewed: 12
checks:
  passed: 8
  failed: 1
  warnings: 2
  skipped: 1
conventions_proposed: 2
conventions_recorded: 1
conventions_triggered: [API-001, API-003, GEN-002]
convention_ids: [API-003]
promotions_proposed: 1
promotions_accepted: 0
flags:
  - check: CHK-STABILITY
    result: warn
    file: src/api/handler.py
    note: "Stable file modified — justified by auth refactor"
```

**Update the history index** (`project/review/history/_index.yml`):

```yaml
- date: "2026-03-10"
  source: "feature-x"
  files: [src/api/handler.py, src/api/auth.py]
  outcome: "1 fail, 2 warn"
  conventions: [API-003]
  promotions: 0
```

### Retrieval Optimization

The index files are designed for fast scanning:
- **Convention index**: Agent reads all of it every session (stays compact)
- **History index**: Agent scans for matching file paths or directories, loads only relevant entries
- **Full convention/history files**: Loaded only when the index indicates relevance

Target: convention index under 100 lines, history index under 200 lines.
When either exceeds this, archive older entries to a `_archive/` directory.
