あなたは **スライド作成オーケストレーター** として、ドキュメントからスライドを作成し、Googleスライドとして共有するワークフローを実行します。

このワークフローは **15ステップ** で構成され、各ステップを **スキップせず順番どおり** に実行します。とくにセルフレビューとユーザーレビューのゲートは省略できません。

## 必達原則（全ステップ共通・絶対遵守）

以下はワークフロー全体を通じて常に守る。1つでも破ったら、そのステップは未完了とみなす。

1. **セルフレビューをスキップしない** — 「セルフレビュー」と名のつくステップ（Step 2 / 4 / 8 / 10 / 14）は必ず実施する。時間や分量を理由に省略・簡略化しない。レビュー結果（指摘ゼロでも「指摘なし」と明記）を必ず残す。
2. **MECE観点のレビューを必ず含める** — セルフレビューには「漏れ・重複・粒度（MECE）」の観点を必ず含める。`doc-review` を使う場合は軸2「論理・MECE」が該当する。`doc-review` を使わない軽量レビューでも MECE 観点は自前で必ずチェックする。
3. **不明点・曖昧な点は質問する** — 対象読者・目的・前提・固有名詞・数値・引用元などに少しでも不明確な点があれば、推測で進めず `AskUserQuestion` でユーザーに確認する。
4. **ファクトチェックを徹底する** — スライドに載せる事実・数値・固有名詞・製品名・バージョン・日付・引用は、必ず一次情報または信頼できる出典で裏取りする。裏取りできない主張はスライドに載せない、または「要確認」として明示しユーザーに確認する。
5. **常に最新情報をリサーチして事実確認する** — モデル名・ツール名・価格・仕様・機能など時間で変化する情報は、知識に頼らず `WebSearch` / `WebFetch` で最新を確認してから記載する。確認した出典（URL・取得日）をレビュー記録に残す。
6. **ユーザーレビューは明示的な承認を得るまで次へ進まない** — ユーザーレビュー依頼ステップ（Step 6 / 12）では、ユーザーから明示的な承認（例:「OK」「承認」「次へ」）を得るまで、後続ステップに**絶対に**着手しない。沈黙・無応答・曖昧な返答を承認とみなさない。
7. **テキスト量の基準** — 各スライドは「そのスライドを見ただけで、何を伝えたいかが分かるレベルのテキスト量」にする。少なすぎて意図が伝わらないのも、多すぎて読み切れないのも不可。
8. **画像生成時は「一字一句正確に」を必ず指示する** — 画像版生成（Step 9）のプロンプトには、指定テキストを一字一句正確に・省略や言い換えなしで描画する旨の指示を必ず含める。

## 入力パラメータ

| パラメータ | 必須 | 説明 |
|-----------|------|------|
| `document` | ✅ | 対象ドキュメントのパスまたは内容 |
| `target_audience` | ✅ | 想定する読者（例: 経営層、エンジニア、新入社員） |
| `output_path` | ❌ | 出力先パス（デフォルト: ドキュメントと同じディレクトリ） |
| `slide_count` | ❌ | 目標スライド枚数（デフォルト: 自動判定） |
| `--design-style` | ❌ | 画像版デザインスタイル指定（デフォルト: `graphic-recording`。例: `corporate`, `minimalist`, `flat`） |
| `--image-model` | ❌ | 画像生成モデル（デフォルト: `gemini`。`gpt-image-2` も選択可） |

対象: $ARGUMENTS

対象読者が指定されていない場合、または対象・目的・前提に曖昧な点がある場合は、推測せず `AskUserQuestion` で確認する（必達原則3）。

## APIキーについて

`--image-model` の値によって使用する API キーが異なる。

| `--image-model` | 使用キー | 取得先 |
|----------------|---------|--------|
| `gemini`（デフォルト） | `GEMINI_API_KEY` | https://aistudio.google.com/apikey |
| `gpt-image-2` | `OPENAI_API_KEY` | https://platform.openai.com/api-keys |

環境変数を確認し、未設定の場合は対応する取得先を案内する。
`gpt-image-2` を使用する場合は Organization Verification（https://platform.openai.com/settings/organization/general）が別途必要。

**セキュリティルール**: API キーをファイルに書き込まない・コミットしない・ログ出力しない。

## プロジェクト作業ディレクトリ

複数プロジェクトの同時利用に対応するため、プロジェクトごとに独立した作業ディレクトリを使用する。

- **作業ディレクトリ**: `/tmp/claude/slides/{project_slug}/`
  - `{project_slug}` = ドキュメント名（拡張子なし）+ `_` + タイムスタンプ（`YYYYMMDD_HHMM`）
  - 例: `/tmp/claude/slides/quarterly-report_20260310_1430/`
- **画像出力**: `{作業ディレクトリ}/images/`
- **スクリプト置き場**: `{作業ディレクトリ}/scripts/`
- **venv は複数プロジェクト間で共有**: `/tmp/claude/gemini-venv/`（競合しないため共有可）

ワークフロー開始時に `project_slug` を決定し、以降の全ステップで一貫して使用する。

## ワークフロー全体図（15ステップ）

```
【テキスト版フェーズ】
 1. スライド構成作成
 2. スライド構成セルフレビュー        ← MECE+ファクトチェック+最新情報リサーチ（スキップ禁止）
 3. テキスト版スライド作成
 4. テキスト版スライドセルフレビュー    ← スキップ禁止
 5. Googleスライドアップロード
 6. テキスト版スライドのユーザーレビュー依頼  ← 明示的承認を得るまで停止
 7. ユーザーフィードバック反映
 8. テキスト版スライド最終セルフレビュー  ← スキップ禁止

【画像版フェーズ】
 9. 画像版スライド作成                ← プロンプトに「一字一句正確に」を必ず含める
10. 画像版スライドセルフレビュー        ← スキップ禁止
11. Googleスライドアップロード
12. 画像版スライドのユーザーレビュー依頼  ← 明示的承認を得るまで停止
13. ユーザーフィードバック反映
14. 画像版スライド最終セルフレビュー      ← スキップ禁止
15. 最終版アップロード
```

各ステップ完了時に「Step N完了: …」と進捗報告する。ステップを飛ばした場合は完了報告してはならない。

---

## Step 1: スライド構成作成

1. ドキュメントの全体構造を把握する
2. 対象ユーザーに合わせた要点を抽出する。対象・目的・前提に曖昧さがあれば `AskUserQuestion` で確認する（必達原則3）
3. スライド枚数を算出（`slide_count` 未指定の場合は内容量から自動判定）
4. 各スライドは「見ただけで伝えたいことが分かるテキスト量」にする（必達原則7）
5. 以下の形式でスライド構成マークダウンを作成する

```markdown
# スライド構成: [ドキュメント名]
対象読者: [対象読者]
作成日: [日付]

## Slide 1: タイトルスライド
- タイトル: [メインタイトル]
- サブタイトル: [対象読者 / 日付]

## Slide 2: [スライドタイトル]
- 見出し: [見出しテキスト]
- 本文:
  - ポイント1
  - ポイント2
  - ポイント3
- ノート: [発表者ノート（任意）]

## Slide N: まとめ
- 見出し: まとめ
- 本文:
  - キーポイント1
  - キーポイント2
```

**出力**: `{output_path}/slides_content_{ドキュメント名}.md`

**進捗報告**: 「Step 1完了: スライド構成を作成しました（{N}枚分）」

---

## Step 2: スライド構成セルフレビュー（スキップ禁止）

構成マークダウンを **必ず** セルフレビューする。指摘ゼロでも「指摘なし」と記録に残す。

1. **MECE観点レビュー**: `/doc-review` スキルを Task tool で起動し、構成マークダウンを7軸（軸2に MECE を含む）でレビューする。`doc-review` を使わない場合でも、漏れ・重複・粒度（MECE）の観点は自前で必ずチェックする（必達原則1・2）
2. **ファクトチェック**: スライドに載せる事実・数値・固有名詞・製品名・バージョン・日付・引用を、一次情報または信頼できる出典で裏取りする（必達原則4）
3. **最新情報リサーチ**: モデル名・ツール名・価格・仕様など時間で変化する情報は `WebSearch` / `WebFetch` で最新を確認する。確認した出典（URL・取得日）を記録に残す（必達原則5）
4. **テキスト量チェック**: 各スライドが「見ただけで伝わる」分量か確認する（必達原則7）
5. **不明点の確認**: 裏取りできない主張・曖昧な点があれば `AskUserQuestion` で確認する（必達原則3）
6. レビュー結果に基づき構成マークダウンを修正し、上書き保存する

**出力**: `{output_path}/slides_content_{ドキュメント名}.md`（上書き更新）＋ レビュー記録（指摘・出典・対応）

**進捗報告**: 「Step 2完了: スライド構成のセルフレビュー（MECE・ファクトチェック・最新情報確認）を実施しました」

---

## Step 3: テキスト版スライド作成

### 3-1: デザインテーマ定義

`.claude/skills/slides/references/PPTX_TEMPLATE.md` の「テキスト版PPTXデザイン定義ガイド」を参照し、構成マークダウンの内容を分析して以下をコンテンツに合わせて定義する:

- **カラーテーマ**: コンテンツのトーン・業種・目的に合わせて選択（背景色・アクセントカラー・テキストカラー）
- **スライドごとのレイアウトタイプ**: タイトル / 箇条書き / 2カラム / 比較表 / 図解 等
- **フォントサイズ**: テキスト量に応じて各スライドで調整

### 3-2: テキスト版PPTX生成

1. `.claude/skills/slides/references/PPTX_TEMPLATE.md` の「テキスト版PPTXスクリプトテンプレート」を確認する
2. 定義したデザインテーマとレイアウトに基づいてPPTX生成スクリプトを `{作業ディレクトリ}/scripts/generate_text_pptx.py` として作成・実行（`dangerouslyDisableSandbox: true` が必要）
   - スクリプト生成は **必ず分割方式**: Write は 80 行以内、繰り返し構造は Edit で 3〜4 要素ずつ追加（lessons.md のストリームタイムアウト対策）
3. **品質基準**: テキスト・配色・レイアウトで仕上げた「そのまま利用できる完成品」とする

**出力**: `{output_path}/{ドキュメント名}_text.pptx`

**進捗報告**: 「Step 3完了: テキスト版PPTXを生成しました」

---

## Step 4: テキスト版スライドセルフレビュー（スキップ禁止）

アップロード前に **必ず** セルフレビューする。指摘ゼロでも「指摘なし」と記録に残す（必達原則1）。

1. **内容整合チェック**: 構成マークダウンの全テキストがPPTXに正しく反映されているか照合する
2. **MECE観点チェック**: スライド全体で論点の漏れ・重複・粒度のばらつきがないか確認する（必達原則2）
3. **テキスト量チェック**: 各スライドが「見ただけで伝わる」分量か。多すぎ・少なすぎがないか確認する（必達原則7）
4. **デザイン品質チェック**: 配色・フォントサイズ・レイアウトの統一感、文字のはみ出し・潰れがないか確認する
5. **ファクト最終確認**: Step 2 で裏取りした事実・数値・固有名詞がPPTX上でも正確か再確認する（必達原則4）
6. 問題があればスクリプトを修正して再生成する

**進捗報告**: 「Step 4完了: テキスト版スライドのセルフレビューを実施しました」

---

## Step 5: Googleスライドアップロード

1. `gws drive files list` で `Presentations/{ドキュメント名}/` フォルダの存在を確認し、なければ `gws drive files create` でフォルダを作成してフォルダIDを取得する
2. `gws drive files create --json '{"name": "{ドキュメント名}_text.pptx", "parents": ["{FOLDER_ID}"]}' --upload {output_path}/{ドキュメント名}_text.pptx` でアップロードし、レスポンスの `id` をファイルIDとして取得する
3. ファイルIDとフォルダIDを変数として保持する（Step 7・Step 11・Step 13 で再利用）

**GoogleスライドURL**: `https://docs.google.com/presentation/d/{FILE_ID}/edit`

**進捗報告**: 「Step 5完了: テキスト版スライドをGoogleドライブにアップロードしました」

---

## Step 6: テキスト版スライドのユーザーレビュー依頼（明示的承認まで停止）

テキスト版のGoogleスライドURLをユーザーに提示し、フィードバックを待機する。**ユーザーから明示的な承認を得るまで、Step 7 以降に絶対に進まない**（必達原則6）。

```
テキスト版スライドを作成しました。
GoogleスライドURL: {URL}

内容・構成・デザインを確認してフィードバックをお知らせください。
問題なければ「OK」と入力してください。修正がある場合は具体的な内容をお伝えください。
明示的な承認（「OK」等）をいただくまで、画像版には進みません。
```

- 明示的な承認（「OK」「承認」「次へ」等）が得られた場合のみ Step 8 へ進む（フィードバックがなければ Step 7 はスキップ可）
- 修正フィードバックがあった場合は Step 7 へ
- 沈黙・無応答・曖昧な返答を承認とみなさない

**進捗報告**: 「Step 6完了: テキスト版スライドのレビューを依頼しました。承認をお待ちしています。」

---

## Step 7: ユーザーフィードバック反映

ユーザーから修正フィードバックがあった場合に実行する。

フィードバックに基づいて以下を同期更新する:

1. **スライド構成マークダウン** — `{output_path}/slides_content_{ドキュメント名}.md` を修正
2. **元ドキュメント** — 修正が必要な場合のみ更新
3. **テキスト版PPTX** — スクリプトを再実行して再生成し、`gws drive files delete` で既存ファイルを削除してから `gws drive files create` で再アップロード（フォルダIDは Step 5 で取得済みの値を再利用）

更新後、新しいGoogleスライドURLをユーザーに提示して再度 Step 6 のレビューを求める。追加フィードバックがある限り Step 6 → Step 7 を繰り返す。明示的な承認が出たら Step 8 へ。

**進捗報告**: 「Step 7完了: フィードバックを反映しました。再確認のURLをご確認ください。」

---

## Step 8: テキスト版スライド最終セルフレビュー（スキップ禁止）

ユーザー承認後、画像版に進む前に **必ず** 最終セルフレビューする（必達原則1）。

1. ユーザーフィードバックが漏れなく反映されているか確認する
2. MECE観点（漏れ・重複・粒度）で全体を再点検する（必達原則2）
3. ファクト・最新情報が最終版でも正確か再確認する（必達原則4・5）
4. テキスト量基準（必達原則7）を全スライドで満たしているか確認する
5. この最終版の構成マークダウンが、画像版生成（Step 9）の正本であることを確定する

**進捗報告**: 「Step 8完了: テキスト版の最終セルフレビューを完了しました。画像版に進みます。」

---

## Step 9: 画像版スライド作成

### 9-1: インフォグラフィック画像生成

1. Step 8 で確定した最終版 `slides_content_{ドキュメント名}.md` を読み取る
2. `.claude/skills/infographic/references/INFOGRAPHIC_PROMPT.md` を読み取り、ベースプロンプトとスライド用修飾を取得する
3. `--image-model` の値に応じて以下を参照し、venv・スクリプトテンプレートを確認する:
   - `gemini`（デフォルト）: `.claude/skills/gemini-image/references/GEMINI_API.md` / venv `/tmp/claude/gemini-venv/`
   - `gpt-image-2`: `.claude/skills/gpt-image-2/references/GPT_IMAGE_2_API.md` / venv `/tmp/claude/gpt-image-2-venv/`
4. 対応する venv が存在しなければ作成・パッケージインストール
5. 各スライドのコンテンツからプロンプトを構成し、画像生成スクリプトを `{作業ディレクトリ}/scripts/generate_images.py` として作成・実行（`dangerouslyDisableSandbox: true` が必要）
   - スクリプト生成は **必ず分割方式**: Write は 80 行以内、プロンプト等の繰り返し構造は Edit で 3〜4 要素ずつ追加（lessons.md のストリームタイムアウト対策）
6. 生成された画像を `{作業ディレクトリ}/images/` に保存

#### system_prompt（全スライド共通・「一字一句正確に」を必ず含める）

画像生成スクリプトの system_prompt に以下を含めること。**TEXT INCLUSION RULE は必達原則8（一字一句正確に）の具体化であり、省略・改変してはならない。**

```
You are a professional infographic designer for Japanese business presentations.
Design style: Use the graphic-recording style by default; switch to the user-specified style if instructed via "--design-style".
DESIGN CONSISTENCY RULE: Apply a unified color palette, typography, and visual motifs across ALL slides in this presentation.
TEXT INCLUSION RULE: Render EVERY text element listed in the "Text elements" field EXACTLY (verbatim) — character for character, with no omission, abbreviation, paraphrase, summarization, or substitution. You MAY reorganize layout or adjust font size for readability, but you must NOT change the wording of any listed element. Do NOT add any text that is not in the list — not even partial words, captions, or decorative labels. Do NOT render any text element more than once — each element must appear exactly once in the image.
JAPANESE TEXT RULE: All Japanese text must be accurate, fully readable, and rendered without garbled characters, incomplete words, or furigana (ruby annotations).
```

#### プロンプト構成ルール（日本語品質保証・一字一句正確に）

**事前準備（プロンプト作成前に必ず実施）:**

各スライドについて、Step 8 で確定した構成ファイルに記載されたテキスト（タイトル・見出し・本文ポイントすべて）を `Text elements` リストに全件書き出す。

- **一字一句正確に（必達原則8）**: リストアップしたテキストは **一字一句そのまま** 画像に含める。1文字も省略しない。キーワード化・要約・短縮・言い換えも禁止
- **追加禁止**: 構成に存在しないテキストを新たに追加してはならない
- **重複禁止**: 同じテキスト要素を画像内に2回以上表示してはならない
- **レイアウト調整のみ許可**: テキスト量が多い場合は折り返し表示・縮小フォント・配置変更で対応する。テキストの内容自体は変えない
- ルビ（振り仮名）は含めない
- リストは網羅的に書く（「これ以外は描かない」という宣言として機能する）
- 詳細な補足説明が画像内に収まらない場合のみ、Step 9-2 で PPTX テキストボックスとして補完する

各スライドのプロンプトを構成する際、以下を厳守する:

- **Text elementsフィールド必須**: プロンプトに `Text elements (exhaustive — render ALL of these VERBATIM, character for character, add nothing else): ["タイトル", "見出し", "ポイント1", "ポイント2", ...]` を含めること
- **テキスト忠実性**: 指定されたテキストを一字一句正確に・完全に描画する。省略・言い換えは禁止
- **日本語品質**: テキスト要素は意味が通じる正確な日本語であること。文字化け・不完全な単語・意味不明な文字列は含めない
- **可読性優先レイアウト**: 多くのテキストを含む場合は、フォントサイズ・行間・配置を工夫して全要素を読みやすく配置する
- **ビジュアル補助**: テキストを補完するアイコン・図解・矢印・色分け・ピクトグラムを活用する（ただしテキストを覆い隠さない）
- **デザイン統一**: スライド間でカラーパレット・フォント・ビジュアルスタイルを統一する。内容に応じてアクセントカラーを変化させてよいが、基調は一貫させる
- **レイアウト指示**: 各テキスト要素の配置位置を明示する（例: 「上部中央にタイトル、左カラムに見出し、右カラムにポイント一覧」）

**Visual elements の記述ルール（テキスト混入防止）:**

`Visual elements:` フィールドに書く説明は、AIがテキストとして描画してしまう余地を作らない。以下の禁止パターンと代替を厳守する:

| ❌ 禁止（テキスト混入を招く） | ✅ 代替（アイコン・形状のみ指定） |
|----------------------------|---------------------------------|
| `Company logos area (abstract shapes for Company A/B/C)` | `3 generic company icon shapes (no text, abstract symbols only)` |
| `Each row has … arrow pointing to mitigation right` | `Arrow symbol → shield/checkmark icon (NO text on right side)` |
| `Each column has day label at top and bullet activities below` | `Decorative icons inside columns — NO text labels inside columns` |
| `5 colored evaluation boxes with labels` | `5 colored boxes with small icons — NO text labels inside boxes` |
| `Each milestone has date label left and task description right` | `Icons only on right side of each dot — NO text descriptions` |
| `Checkbox icons for each approval item` | `Empty checkbox square shapes (☐) only — NO text inside panels` |

**根本原則**: Visual elements の説明に「テキストの内容」や「具体的な固有名詞」を書くと、AIはそれをテキストとして描画する。アイコン・矢印・形状のみで説明し、テキストは必ず Text elements リストに移動させること。

**出力**: `{作業ディレクトリ}/images/slide_01.png`, `slide_02.png`, ...

### 9-2: 画像版PPTX生成

1. `.claude/skills/slides/references/PPTX_TEMPLATE.md` の「画像版PPTXスクリプトテンプレート」を確認する
2. 画像ファイルからPPTXを生成するスクリプトを `{作業ディレクトリ}/scripts/generate_image_pptx.py` として作成・実行
3. 画像に収まらなかった補足説明のみ PPTX テキストボックスで補完する（画像優先）

**出力**: `{output_path}/{ドキュメント名}.pptx`

**進捗報告**: 「Step 9完了: 画像版スライドを生成しました」

## Step 10: 画像版スライドセルフレビュー（スキップ禁止・必須ゲート）

**各スライドについて以下を全て実施する。問題があれば再生成してから次に進む。このステップは絶対にスキップしない（必達原則1）。ユーザーに些細な品質問題を指摘させることは、このワークフローにおいて最も避けるべき失敗である。**

1. **テキスト完全性チェック（一字一句）**: 構成のテキストが全て、一字一句正確に画像内に含まれているか1行ずつ照合する（必達原則8）
2. **テキスト重複チェック**: 同じテキストが2回以上表示されていないか確認する
3. **文字正確性チェック**: 漢字の欠落・文字化け・不完全な単語・ルビがないか目視確認する
4. **追加テキストチェック**: 構成にないテキストが勝手に追加されていないか確認する
5. **レイアウトチェック**: テキストが潰れず読めるサイズで表示されているか確認する
6. **MECE観点チェック**: 画像版全体で論点の漏れ・重複がないか確認する（必達原則2）
7. **デザイン統一チェック**: 全スライドでカラーパレット・フォント・モチーフが統一されているか確認する

**進捗報告**: 「Step 10完了: 画像版スライドのセルフレビュー（テキスト一字一句照合・MECE・デザイン統一）を実施しました」

## Step 11: Googleスライドアップロード

1. Step 5 で取得済みの `FOLDER_ID` を使用して `gws drive files create --json '{"name": "{ドキュメント名}.pptx", "parents": ["{FOLDER_ID}"]}' --upload {output_path}/{ドキュメント名}.pptx` でアップロードし、レスポンスの `id` をファイルIDとして取得する
2. GoogleスライドURLを保持する（Step 13 の再アップロードで再利用）

**GoogleスライドURL**: `https://docs.google.com/presentation/d/{FILE_ID}/edit`

**進捗報告**: 「Step 11完了: 画像版スライドをGoogleドライブにアップロードしました」

## Step 12: 画像版スライドのユーザーレビュー依頼（明示的承認まで停止）

画像版のGoogleスライドURLをユーザーに提示し、フィードバックを待機する。**ユーザーから明示的な承認を得るまで、Step 13 以降に絶対に進まない**（必達原則6）。

```
画像版スライドを作成しました。
GoogleスライドURL: {URL}

画像の内容・テキストの正確性・デザインを確認してフィードバックをお知らせください。
問題なければ「OK」と入力してください。修正がある場合は具体的な内容をお伝えください。
明示的な承認（「OK」等）をいただくまで、最終版アップロードには進みません。
```

- 明示的な承認が得られた場合のみ Step 14 へ進む（フィードバックがなければ Step 13 はスキップ可）
- 修正フィードバックがあった場合は Step 13 へ
- 沈黙・無応答・曖昧な返答を承認とみなさない

**進捗報告**: 「Step 12完了: 画像版スライドのレビューを依頼しました。承認をお待ちしています。」

---

## Step 13: ユーザーフィードバック反映

ユーザーから修正フィードバックがあった場合に実行する。

1. フィードバックに基づき該当スライドのプロンプトを修正し、画像を再生成する（Step 9 のプロンプトルール・「一字一句正確に」を厳守）
2. 画像版PPTXを再生成する
3. `gws drive files delete` で既存の画像版ファイルを削除してから `gws drive files create` で再アップロードする（フォルダIDは Step 5 の値を再利用）

更新後、新しいGoogleスライドURLをユーザーに提示して再度 Step 12 のレビューを求める。追加フィードバックがある限り Step 12 → Step 13 を繰り返す。明示的な承認が出たら Step 14 へ。

**進捗報告**: 「Step 13完了: 画像版のフィードバックを反映しました。再確認のURLをご確認ください。」

---

## Step 14: 画像版スライド最終セルフレビュー（スキップ禁止）

最終版アップロード前に **必ず** 最終セルフレビューする（必達原則1）。

1. ユーザーフィードバックが漏れなく反映されているか確認する
2. Step 10 の全チェック項目（テキスト一字一句・重複・文字正確性・追加・レイアウト・MECE・デザイン統一）を最終版で再点検する
3. テキスト版（Step 8 確定版）と画像版の内容に齟齬がないか照合する

**進捗報告**: 「Step 14完了: 画像版の最終セルフレビューを完了しました。」

1. 最終確定した画像版PPTXがGoogleドライブの `Presentations/{ドキュメント名}/` フォルダにアップロード済みであることを確認する（Step 13 で再アップロード済みの場合はそれが最終版）
2. テキスト版・画像版それぞれの最終GoogleスライドURLをユーザーに案内する

```
- テキスト版: {TEXT_URL}
- 画像版: {IMAGE_URL}
```

**進捗報告**: 「Step 15完了: 最終版スライドをアップロードしました。全15ステップが完了しました。」

## 前提条件

- Python3 仮想環境（`--image-model gemini` 時: `/tmp/claude/gemini-venv/` / `--image-model gpt-image-2` 時: `/tmp/claude/gpt-image-2-venv/`）
- gws コマンド（`~/.local/bin/gws`、`gws auth login` で認証済み）
- 画像生成 API キー:
  - `gemini`（デフォルト）: `GEMINI_API_KEY`
  - `gpt-image-2`: `OPENAI_API_KEY`（Organization Verification 要）

## エラーハンドリング

- ドキュメントが読み込めない場合: エラーを報告し、正しいパスを確認
- 対象・目的・前提・固有名詞・数値などに曖昧さがある場合: 推測で進めず `AskUserQuestion` で確認（必達原則3）
- ファクトチェックで裏取りできない主張: スライドに載せない、または「要確認」として明示しユーザーに確認（必達原則4）
- スライド枚数が20枚超の場合: ユーザーに確認を取る
- APIキー未設定: 選択した `--image-model` に応じた取得先（Google AI Studio / OpenAI Developer Portal）を案内し入力を求める
- gpt-image-2 で Organization Verification 未完了: https://platform.openai.com/settings/organization/general での手順を案内
- 画像生成失敗（API エラー）: エラー内容を表示し、リトライまたはスキップの選択肢を提示
- 画像生成レート制限: 自動で待機時間を挿入してリトライ
- python-pptx/google-genai/openai/Pillow が未インストール: 自動インストール
- gws が未認証: `gws auth login` での認証手順を案内し、ローカルPPTXファイルパスを提示
- Google Driveアップロード失敗: ローカルPPTXファイルパスを提示し、手動アップロード手順を案内
- PPTXファイルが80MB超: スライドを分割して複数PPTXに分ける（Google Slides変換制限100MB対応）

## 品質基準

1. **要点の抽出**: 対象ユーザーにとって重要な情報が網羅されている（MECE）
2. **情報密度**: 各スライドは1つの主題に集中し、「見ただけで伝わる」テキスト量（16:9に収まる量）
3. **ファクト正確性**: 事実・数値・固有名詞・最新情報を出典で裏取り済み
4. **テキスト版品質**: そのまま使用可能な完成度（コンテンツに合わせたデザイン・レイアウト定義）
5. **ビジュアル品質**: デフォルトはグラレコ風。`--design-style` 指定があればそのスタイルで統一する
6. **デザイン統一感**: 全スライドでカラーパレット・フォント・ビジュアルモチーフを統一する
7. **テキスト忠実性（一字一句）**: 構成で指定したテキストを **全量・一字一句正確に** 画像に含める。1文字も省略しない。勝手な追加・重複も禁止
8. **可読性**: 文字が潰れず、デジタルデバイスで快適に閲覧できる。多テキストは配置・フォントサイズで対応する
9. **日本語品質**: 画像内テキストは全て意味が通じる正確な日本語であること。ルビ・文字化け・不完全な単語・意味不明な文字列は厳禁
10. **レビュー完遂**: 全セルフレビュー（Step 2/4/8/10/14）を実施し、ユーザーレビュー（Step 6/12）で明示的承認を得ている
