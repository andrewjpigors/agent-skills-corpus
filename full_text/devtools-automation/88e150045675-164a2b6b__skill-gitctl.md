# Skill: gitctl Usage

gitctl is a kubectl-like CLI for managing git repositories across multiple forge platforms. It provides a unified noun-verb command interface that auto-detects the forge from git remote URLs and delegates to the appropriate platform CLI tool (`gh` for GitHub, `glab` for GitLab, `fj` for Forgejo, `tea` for Gitea).

## When to Use

- When managing pull requests, issues, repos, releases, or other forge resources from the command line
- When the user needs to interact with GitHub, GitLab, Forgejo, or Gitea and wants a single unified interface
- When the user asks about `gitctl` or wants to know how to use it
- When scripting cross-forge workflows (e.g., mirroring, notifications, CI monitoring)
- When the user wants machine-readable output (JSON, YAML, CSV) from forge operations
- When previewing destructive operations with `--dry-run`

## Prerequisites

- `gitctl` must be installed and in `$PATH`
- At least one forge CLI tool must be installed:
  - GitHub: `gh` (https://cli.github.com/)
  - GitLab: `glab` (https://gitlab.com/gitlab-org/cli)
  - Forgejo: `fj` (https://forgejo.org/docs/latest/admin/command-line/)
  - Gitea: `tea` (https://gitea.com/gitea/tea)
- The forge CLI tool must be authenticated (e.g., `gh auth login`, `glab auth login`)
- For auto-detection: the current directory must be a git repo with a remote pointing to a supported forge

## Instructions

### Command Pattern

gitctl follows a **noun-verb** pattern:

```
gitctl [global-options] <noun> <verb> [args] [flags]
```

The noun identifies the resource type (pr, issue, repo, etc.) and the verb identifies the action (list, get, create, etc.).

**Exception:** The `api` command uses `gitctl api <METHOD> <endpoint>` instead of noun-verb, and `status` takes no verb.

### Global Options

These flags apply to **all** commands and must appear **before** the noun:

| Flag | Short | Description | Default |
|------|-------|-------------|---------|
| `--help` | `-h` | Show help | |
| `--version` | `-v` | Show version | |
| `--license` | | Show AGPLv3 license text | |
| `--dry-run` | `-n` | Print commands without executing | off |
| `--verbose` | | Enable verbose output (prints commands to stderr) | off |
| `--output FORMAT` | `-o` | Output format: `table`, `json`, `yaml`, `csv` | `table` |
| `--forge TYPE` | `-f` | Force forge: `github`, `gitlab`, `forgejo`, `gitea` | auto-detect |
| `--remote NAME` | `-r` | Git remote to resolve forge from | `origin` |
| `--config PATH` | `-c` | Configuration file path | `~/.config/gitctl/config.yaml` |
| `--repo OWNER/REPO` | `-R` | Override repository (bypasses git remote parsing) | auto-detect |

**Flag placement matters.** Global flags go before the noun:

```bash
# correct
gitctl -o json pr list
gitctl --dry-run pr merge 123

# wrong - flags after noun are passed to the verb handler
gitctl pr list -o json    # -o is NOT a global flag here
```

### Environment Variables

Environment variables provide defaults. CLI flags always take precedence.

| Variable | Description | Equivalent Flag |
|----------|-------------|-----------------|
| `GITCTL_CONFIG` | Configuration file path | `--config` |
| `GITCTL_FORGE` | Force forge type | `--forge` |
| `GITCTL_REMOTE` | Git remote name | `--remote` |
| `GITCTL_OUTPUT` | Output format | `--output` |
| `GITCTL_REPO` | Override repository (owner/repo) | `--repo` |
| `PAGER` | Pager for list output (default: `less -FRSX`) | n/a |

### Configuration

**Location:** `~/.config/gitctl/config.yaml` (or `$XDG_CONFIG_HOME/gitctl/config.yaml`)

```yaml
# Default output format: table, json, yaml, csv
output: table

# Default git remote to resolve forge from
remote: origin

# Fallback forge type if auto-detection fails
default_forge: github

# Forge-specific configuration
forges:
  github:
    hosts:
      - github.com
    cli: gh
  gitlab:
    hosts:
      - gitlab.com
    cli: glab
  forgejo:
    hosts:
      - codeberg.org
    cli: fj
  gitea:
    hosts: []
    cli: tea

# Command aliases (expanded before dispatch)
aliases:
  prl: "pr list"
  prc: "pr create"
  il: "issue list"
  ic: "issue create"
```

**Configuration precedence** (highest to lowest):

1. CLI flags (`--output json`)
2. Environment variables (`GITCTL_OUTPUT=json`)
3. Configuration file (`~/.config/gitctl/config.yaml`)
4. Built-in defaults (hardcoded)

**Managing configuration via CLI:**

```bash
gitctl config list                    # Show all config values
gitctl config get output              # Get a single value
gitctl config set output json         # Set a value
gitctl config set default_forge gitlab
```

### Forge Auto-Detection

gitctl resolves the forge type automatically:

1. Runs `git remote get-url <remote>` (default remote: `origin`)
2. Parses the URL (supports both HTTPS and SSH formats)
3. Extracts the hostname, owner, and repo name
4. Maps the hostname to a forge type using the `forges.*.hosts` config

**Override auto-detection:**
- `--forge github` forces a specific forge type
- `--repo owner/name` overrides the parsed owner/repo
- Both can be combined: `gitctl -f gitlab -R myorg/myrepo pr list`

**Self-hosted instances:** Add your hostname to the appropriate forge's `hosts` list in the config file:

```yaml
forges:
  gitlab:
    hosts:
      - gitlab.com
      - gitlab.mycompany.com
```

### Alias System

Aliases are defined in the config YAML under `aliases:` and are expanded before command lookup. Alias expansion prepends the alias value and appends any extra user arguments.

```yaml
aliases:
  prl: "pr list"
  prc: "pr create"
  myissues: "issue list --author @me"
```

```bash
gitctl prl --state closed
# expands to: gitctl pr list --state closed

gitctl myissues --limit 10
# expands to: gitctl issue list --author @me --limit 10
```

With `--verbose`, alias expansion is printed to stderr:

```
alias: prl -> pr list
```

#### `repo` -- Repositories

| Verb | Usage | Description |
|------|-------|-------------|
| `list` | `repo list [flags]` | List your repositories |
| `get` | `repo get [name]` | View repository details (default: current repo) |
| `create` | `repo create <name> [flags]` | Create a new repository |
| `edit` | `repo edit [flags]` | Edit repository settings |
| `fork` | `repo fork [owner/repo]` | Fork a repository |
| `clone` | `repo clone <owner/repo>` | Clone a repository |
| `delete` | `repo delete <name> --yes` | Delete a repository (requires `--yes`) |
| `browse` | `repo browse` | Open repo in browser |
| `star` | `repo star` | Star/favourite the repository |
| `unstar` | `repo unstar` | Remove star from repository |
| `migrate` | `repo migrate [flags]` | Migrate repo to another forge |

**List flags:**

| Flag | Description | Default |
|------|-------------|---------|
| `--limit N` | Maximum results | 30 |
| `--visibility VIS` | `public`, `private`, `all` | |

**Create flags:**

| Flag | Description |
|------|-------------|
| `--private` | Create as private |
| `--description TEXT` | Repository description |

**Delete flags:**

| Flag | Short | Description |
|------|-------|-------------|
| `--yes` | `-y` | Confirm deletion (required for destructive operation) |

**Migrate flags:**

| Flag | Short | Description | Default |
|------|-------|-------------|---------|
| `--to FORGE` | | Target forge: `github`, `gitlab`, `forgejo`, `gitea` | (required) |
| `--owner OWNER` | `-o` | Owner/org on the target forge | same as source URL owner |
| `--mirror-to` | | Create destination repo and add push mirror from source | |
| `--mirror-back` | | Add push mirror on target pointing back to source (skips repo creation) | |

**Migrate behavior:**
- The source URL is the current repo's remote (or `--repo` override)
- By default, the migrated repo is created under the same owner as the source URL. Use `--owner` to override
- `--mirror-to` creates the destination repo on the target forge, then configures a push mirror from the source forge to push to it
- `--mirror-back` skips destination repo creation (the source repo already exists) and directly adds a push mirror API call on the target forge pointing back to the source. It auto-detects the source forge token from environment variables (`GITHUB_TOKEN`, `GITLAB_TOKEN`, `FORGEJO_TOKEN`, `GITEA_TOKEN`)
- `--dry-run` bypasses the `--yes` requirement on delete operations

```bash
gitctl repo list                            # List your repos
gitctl repo list --visibility private       # Only private repos
gitctl repo get                             # Current repo details
gitctl repo create myproject --private      # Create private repo
gitctl repo fork user/project               # Fork a repo
gitctl repo clone user/project              # Clone a repo
gitctl repo browse                          # Open in browser
gitctl repo star                            # Star current repo
gitctl repo delete myproject --yes          # Delete (--yes required)
gitctl repo delete myproject                # ERROR: missing --yes flag

# Migrate repo to another forge
gitctl repo migrate --to forgejo            # Migrate (owner from source URL)
gitctl repo migrate --to forgejo --owner other-org  # Override destination owner
gitctl repo migrate --to forgejo --mirror-to        # Create + set up push mirror
gitctl repo migrate --to forgejo --mirror-back      # Push mirror back (no repo creation)
```

#### `api` -- Raw API Passthrough

The `api` command does **not** follow the noun-verb pattern. It passes a raw HTTP method and endpoint directly to the forge CLI's API interface.

```
gitctl api <METHOD> <endpoint> [--body JSON]
```

Template variables `{owner}` and `{repo}` are expanded from the current forge context.

```bash
gitctl api GET /repos/{owner}/{repo}                 # Repo info
gitctl api GET /repos/{owner}/{repo}/pulls            # List PRs via API
gitctl api POST /repos/{owner}/{repo}/issues \
    --body '{"title":"Bug","body":"Details"}'          # Create issue
gitctl -o json api GET /user                          # Authenticated user
gitctl api PATCH /repos/{owner}/{repo} \
    --body '{"description":"Updated"}'                 # Edit repo
```

### Behavioral Details

#### Output Formats

| Format | Flag | Description |
|--------|------|-------------|
| `table` | `-o table` | Human-readable columnar output with aligned headers (default) |
| `json` | `-o json` | Compact JSON array of resources |
| `yaml` | `-o yaml` | YAML serialization of resources |
| `csv` | `-o csv` | CSV format for list output |

For scripting, use `-o json` or `-o yaml` and pipe through `jq`/`yq`.

#### Dry-Run Mode

`--dry-run` (or `-n`) prints the command that **would** be executed (prefixed with `[dry-run]`) without actually running it. The executor returns a synthetic success result with empty stdout.

```bash
gitctl --dry-run pr merge 123
# [dry-run] gh pr merge 123
```

Use this to verify destructive operations before executing them.

#### Pager Behavior

LIST verbs automatically pipe through a pager when stdout is a TTY. The pager is:

1. `$PAGER` environment variable (if set)
2. `less -FRSX` (default fallback)

If stdout is not a TTY (e.g., piped to another command), paging is disabled automatically.

#### API Fallback

When a forge CLI tool does not support an operation natively, gitctl falls back to raw REST API calls:

1. Looks up the operation in an internal fallback table mapping resource kind + verb to HTTP method + endpoint
2. Expands template variables (`{owner}`, `{repo}`, `{number}`, `{mirror_id}`) from context
3. For PATCH/POST without an explicit `--body`, auto-builds a JSON body from the provided parameters
4. With `--verbose` or `--dry-run`, prints a note: `note: <kind> <verb> unsupported by CLI, falling back to API: <METHOD> <endpoint>`

This means operations like `mirror sync` or `repo star` work even if the underlying CLI tool has no direct command for them.

#### Signal Handling

SIGINT (Ctrl+C) and SIGTERM trigger graceful interruption. The exit code is `128 + signal number` (e.g., 130 for SIGINT).

#### Error Codes

gitctl uses a structured error domain (`GCTL_ERROR`) with these codes:

| Error | Meaning |
|-------|---------|
| `CONFIG_PARSE` | Failed to parse the YAML config file |
| `CONFIG_INVALID` | A config value is invalid |
| `MODULE_LOAD` | Failed to load a forge backend `.so` module |
| `MODULE_SYMBOL` | Module missing required `gctl_module_register()` symbol |
| `FORGE_UNAVAILABLE` | Required CLI tool not found in `$PATH` |
| `FORGE_UNSUPPORTED` | Operation not supported by this forge backend |
| `FORGE_DETECT` | Could not auto-detect forge type from remote URL |
| `EXECUTOR_SPAWN` | Failed to spawn subprocess |
| `EXECUTOR_TIMEOUT` | Subprocess timed out (default: 30 seconds) |
| `EXECUTOR_FAILED` | Subprocess exited with non-zero status |
| `PARSE_OUTPUT` | Failed to parse forge CLI output |
| `INVALID_ARGS` | Invalid command-line arguments |
| `NO_REPO` | Not inside a git repository |
| `NO_REMOTE` | No git remote configured |

Errors are printed to stderr with an `error:` prefix. When the forge CLI tool is missing, gitctl also prints install instructions.

## Output Format

gitctl produces output in the format specified by `--output` / `-o`:

- **table** (default): Human-readable columnar output with header alignment, auto-paged on TTY
- **json**: Compact JSON -- array for `list` verbs, single object for `get` verbs
- **yaml**: YAML serialization -- list for `list` verbs, mapping for `get` verbs
- **csv**: Comma-separated values with header row (primarily for `list` verbs)

For non-list/get verbs (create, close, merge, etc.), raw stdout from the underlying forge CLI is printed directly.

In dry-run mode, no output is produced (the command is only printed to stderr).

## Examples

### Daily PR workflow

```bash
# See what's open
gitctl pr list

# Review a specific PR
gitctl pr get 42
gitctl pr diff 42

# Check out locally, test, then merge
gitctl pr checkout 42
# ... run tests ...
gitctl pr merge 42
```

### Cross-forge scripting

```bash
# List all open issues as JSON for processing
gitctl -o json issue list | yq '.[] | .title'

# Force GitLab even if origin points to GitHub
gitctl -f gitlab -R myorg/myrepo pr list

# Use environment variables in a script
export GITCTL_FORGE=gitlab
export GITCTL_OUTPUT=json
gitctl pr list --limit 100
```

### Using aliases for speed

```bash
# With default aliases in config:
gitctl prl                    # pr list
gitctl prc --title "Feature"  # pr create --title "Feature"
gitctl il --state closed      # issue list --state closed
gitctl ic --title "Bug"       # issue create --title "Bug"
```

### Previewing destructive operations

```bash
# Dry-run bypasses the --yes requirement
gitctl --dry-run repo delete myproject
gitctl --dry-run pr merge 123
gitctl --dry-run release delete v0.1.0

# Without dry-run, destructive operations require --yes
gitctl repo delete myproject --yes
gitctl release delete v0.1.0 --yes
gitctl mirror remove 42 --yes
```

# Get repo info as YAML

gitctl api POST /repos/{owner}/{repo}/issues \

## Constraints

- **All destructive gitctl commands** (`repo delete`, `release delete`, `label delete`, `key remove`, `webhook delete`, `mirror remove`) require the `--yes` / `-y` flag. Without it, gitctl prints a warning and exits with error code 1. `--dry-run` bypasses the `--yes` requirement. Always confirm with the user before passing `--yes`
- gitctl requires an authenticated forge CLI tool -- if `gh`/`glab`/`fj`/`tea` is not authenticated, commands will fail with the underlying tool's auth error
- The `commit` command uses local git directly and does not go through the forge backend
- The `status` and `completion` commands do not follow the noun-verb pattern
- Aliases are expanded once (no recursive alias expansion)
- The subprocess timeout is 30 seconds by default -- long-running API calls may time out
