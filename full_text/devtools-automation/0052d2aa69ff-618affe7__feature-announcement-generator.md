# Feature Announcement Generator

This skill analyzes actual code changes (not just commit messages) to create compelling, user-focused marketing announcements for new features.

## How It Works

1. **CLI Tool Collects Data:** The `write-feature-release` command gathers:
   - Files changed in the feature branch
   - Code diff statistics
   - Branch information
   - Target language and product context

2. **AI Analyzes Code Structure:** This skill reads the JSON data and:
   - Examines which files were modified/added/deleted
   - Analyzes the scope and nature of changes
   - Infers user-facing features from code patterns
   - Generates marketing copy in the target language

3. **Output:** Creates a polished announcement saved to `tmp/feature-releases/`

## When to Use This Skill

- After completing a feature on a branch
- Before merging to master/main
- When preparing release notes
- For internal team updates
- For customer-facing feature announcements

## Workflow

### Step 1: Read the Git Data File

Read the JSON file at `{{git_data_file}}` which contains:

```json
{
  "meta": { "language": "en|fr|es", "product_name": "..." },
  "git": {
    "current_branch": "feature/name",
    "files_changed": ["internal/cmd/...", "internal/api/..."],
    "files_summary": { "added": 5, "modified": 12, "deleted": 2 },
    "diff_stats": "42 files changed, 1500 insertions, 300 deletions",
    "commits": [...]
  },
  "context": { "title_hint": "...", "product_name": "..." }
}
```

### Step 2: Analyze Code Changes

**Focus on FILES CHANGED and their locations, NOT commit messages.**

Look for patterns like:

- **New commands:** Likely a new major feature
- **API client changes:** Backend integration improvements
- **Configuration changes:** System-wide updates
- **Test additions:** Feature validation
- **Documentation updates:** User-facing improvements

**Example Analysis:**
```
Files changed:
- internal/cmd/bridge.go (new) → New CLI command
- internal/api/bridge.go (new) → API client for bridges
- internal/config/bridge.go (new) → Bridge configuration
- cmd/arkipel/main.go (modified) → Command registration

Inference: This is a "Bridge Management" feature for connecting external systems
```

### Step 3: Categorize Changes

Group files into categories:

- **New Features:** New files in key directories (controllers, models, components)
- **Improvements:** Enhancements to existing files
- **Infrastructure:** Config, migrations, setup
- **Internal:** Tests, documentation (mark as internal)

### Step 4: Generate Marketing Content

**Title:**
- Use `{{context.title_hint}}` or improve it
- Make it catchy and benefit-driven (under 10 words)
- Example: "DevKit Bridges" → "Connect Your Tools with DevKit Bridges"

**Language:** `{{context.language}}` (en, fr, or es)

**Output Structure:**

```markdown
# {{improved_title}}

**Release Date:** {{current_date}}

## Summary
{{one_sentence_benefit_statement}}

## What's New

### ✨ {{new_features_heading}}
{{bullet_list_describing_user_facing_features}}

### 🔧 {{improvements_heading}}
{{enhancements_and_optimizations}}

### 🐛 {{bug_fixes_heading}}
{{fixes_if_any}}

## How It Works
{{simple_explanation_of_feature_usage}}

## Why It Matters
{{user_benefits_and_use_cases}}

## Get Started
{{call_to_action}}

## Technical Details
- **Files Changed:** {{files_summary}}
- **Scope:** {{diff_stats}}
- **Branch:** {{git.current_branch}}

## Screenshots to Capture
Suggest 2-3 UI moments that showcase the feature:
1. {{screenshot_1_description}}
2. {{screenshot_2_description}}
3. {{screenshot_3_description}}

---
*Feature announcement for {{context.product_name}}*
```

### Step 5: Language-Specific Guidelines

**English (en):**
- Professional yet enthusiastic tone
- Lead with benefits, then explain features
- Active voice: "You can now..." "Connect your..."
- Clear, concise sentences

**French (fr):**
- Elegant, polished language
- Use formal "vous" for users
- Emphasis on user experience and simplicity
- Example: "Découvrez", "Simplifiez", "Améliorez"

**Spanish (es):**
- Friendly, inclusive tone
- Clear explanations for diverse audiences
- Warm, welcoming language
- Example: "Descubre", "Conecta", "Mejora"

### Step 6: Write Output File

**Filename format:** `tmp/feature-releases/TITLE-DATE-LANG.md`

Extract from JSON:
- Title: `{{context.title_hint}}`
- Date: current date
- Language: `{{context.language}}`

Example: `devkit-bridges-2026-03-13-fr.md`

## Analysis Guidelines

### Analyzing File Patterns

When you see these file types, infer these features:

**CLI Commands:**
- `internal/cmd/*.go` (new) → New CLI commands/subcommands
- `cmd/arkipel/main.go` (modified) → Command registration

**API Client:**
- `internal/api/*.go` (new/modified) → API client methods
- `internal/client/*.go` (new) → HTTP client enhancements

**Configuration:**
- `internal/config/*.go` (modified) → Configuration changes
- `go.mod` (modified) → Dependency updates

**Core Logic:**
- `internal/crypto/*.go` (new) → Cryptographic functions
- `internal/utils/*.go` (new) → Shared utilities
- `internal/models/*.go` (new) → Data structures

**Tests:**
- `*_test.go` (new/modified) → Test coverage for features

### Avoid These Mistakes

❌ **Don't** rely on commit messages for content
❌ **Don't** include internal/refactoring details prominently
❌ **Don't** use technical jargon without explanation
❌ **Don't** forget the call-to-action

✅ **Do** analyze file structure and code patterns
✅ **Do** focus on user benefits
✅ **Do** explain "why" not just "what"
✅ **Do** suggest specific screenshots

## Variables

Use these placeholders when generating:

- `{{context.product_name}}` - Product name (e.g., "Arkipel")
- `{{context.title_hint}}` - Suggested title from CLI
- `{{context.language}}` - Target language code (en/fr/es)
- `{{git.current_branch}}` - Feature branch name
- `{{git.base_branch}}` - Comparison branch (usually master)
- `{{git.files_changed}}` - Array of modified file paths
- `{{git.files_summary}}` - Object with added/modified/deleted counts
- `{{git.diff_stats}}` - Summary string like "15 files changed, 420 insertions..."
- `{{git.commits}}` - Array of commit objects (for metadata only)

## Error Handling

### File Not Found
If `{{git_data_file}}` doesn't exist:
```
Error: Could not find git data file at {{git_data_file}}

Please run the CLI command first:
  write-feature-release --lang {{language}} --title "Feature Name"
```

### Invalid JSON
If the file is malformed:
```
Error: Invalid JSON format in {{git_data_file}}

The file may be corrupted. Please regenerate it with:
  write-feature-release --lang {{language}} --title "Feature Name"
```

### No Meaningful Changes
If only internal files changed (tests, docs, config):
```
Warning: No user-facing features detected in the changes.

Files changed appear to be internal only (tests, documentation, configuration).
Consider if this announcement is necessary, or check if you're on the correct branch.
```

## Tips

- **Always analyze file paths first** - they tell you what changed
- **Look for new files** - these often indicate new features
- **Check file sizes** - large additions suggest major features
- **Consider the user perspective** - what will they see/experience?
- **Use the title_hint** but improve it to be marketing-ready
- **Suggest specific screenshots** - guide the user on what to capture
