# React + Figma → Flutter Conversion

## Setup

Before first use, ensure `conversion_config.json` exists at the project root. If not, create it with the user's project paths:

```json
{
  "project_name": "climbing_app",
  "figma_url": "https://figma.com/design/YOUR_FILE_KEY/your-project",
  "react_src": "src/app",
  "css_theme": "src/styles/globals.css",
  "output_dir": "output",
  "flutter_output": "output/flutter_app",
  "icon_mode": "native_package"
}
```

**`icon_mode`** — choose how icons are handled during conversion:

- `"figma_svg"` **(default)** — Export actual SVG icons from Figma design via API, deduplicate, and use as custom Flutter assets with `flutter_svg`. Most faithful to the design.
- `"native_package"` — Scan React icon imports, search/verify matching Flutter packages on pub.dev, and use native icon refs such as `LucideIcons.mapPin`. Best long-term path when the React icon pack has a maintained Flutter equivalent.

**All paths are relative to the project root.** Read this config at the start of every phase.

## Principles

1. **Plan first, then execute** - Create detailed plan before any conversion
2. **Figma is the source of truth for layout** - Read Figma XML FIRST for visual structure, React TSX second for logic/state
3. Convert ONE page at a time. Verify compilation before proceeding
4. Each page gets its own package with standalone `main.dart`
5. Use Task tool for parallel batch conversion
6. Two data sources: per-page JSON at `{config.output_dir}/plans/pages/*.json` (positions) + React TSX (logic)
7. Output: mono-repo at `{config.flutter_output}/` with `shared/` + `pages/*/` + `full_app/`

## Argument Handling

| Argument     | Action                                                                                                                         |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------ |
| _(none)_     | Show conversion options menu                                                                                                   |
| `fetch`      | **Fetch from Figma** - Read `figma_url` from config, get metadata via MCP, then run matcher                                    |
| `match`      | **Run matcher only** - Split Figma metadata + match React↔Figma → generate `page_matches_with_layout.json`                     |
| `plan`       | **Phase 1 only** - Fetch + match if needed, then generate conversion plan + auto-generate patterns.md, DO NOT start conversion |
| `theme`      | Phase 2 only                                                                                                                   |
| `shared`     | Phase 2 + base widgets                                                                                                         |
| `{PageName}` | Phase 2 (if needed) + Phase 3 for that page                                                                                    |
| `batch-N`    | Phase 3 in parallel for batch N (requires plan to exist)                                                                       |
| `full-app`   | Phase 7 - assemble all pages into one app                                                                                      |

## Data Sources

Read `conversion_config.json` to resolve all paths below.

**Primary** - Per-page JSON files at `{config.output_dir}/plans/pages/{snake_name}.json` (~1-5KB each): Pre-split from `{config.output_dir}/page_matches_with_layout.json`. Each file contains main component position data (x, y, width, height), react_file_path, figma_node_id, and child components. Generated by Phase 1.

**Secondary** - React TSX at `{config.react_src}/*.tsx`: Extract props, state, callbacks, mock data, icons, Tailwind classes.

**Theme** - `{config.css_theme}`: CSS variables for light/dark colors. Preserve every literal CSS color variable as an `AppColors.token*` design token, and map exact Figma colors to existing/generated `AppColors` tokens whenever possible.

## Conversion Workflow

### Phase 1: Discovery & Planning

**Trigger**: User runs `/convert-to-flutter plan`

**Purpose**: Auto-discover all pages, generate page layout patterns from React source, and create a comprehensive conversion plan with detailed checklists.

**Step 1 - Load config**: Read `conversion_config.json` from the project root. If it doesn't exist, prompt the user to create it from the template.

**Step 2 - Fetch Figma metadata via MCP** (if `{config.output_dir}/figma_raw_metadata.txt` doesn't exist):

1. Read `figma_url` from `conversion_config.json`. If empty or missing, prompt the user to add their Figma URL to the config and stop.
2. Extract file key from the URL (e.g., `https://figma.com/design/AbCdEfGhIjKlMnOpQrStUv/my-project` → `AbCdEfGhIjKlMnOpQrStUv`)
3. Call MCP tool: `mcp__figma__get_file(fileKey="AbCdEfGhIjKlMnOpQrStUv")`
4. Save the response to `{config.output_dir}/figma_raw_metadata.txt` in XML format
5. If MCP is not configured, inform user to set up Figma MCP server first

**Step 2.5 - Set up icons** (based on `config.icon_mode`, default `"figma_svg"`):

**Option A — `"figma_svg"` mode** (if `{config.output_dir}/icon_manifest.json` doesn't exist):
Run `python .claude/skills/convert-to-flutter/scripts/extract_figma_icons.py` which will:

1. Parse Figma metadata to find all `Icon` FRAME nodes (Figma stores icons as generic frames with Vector children — no names)
2. Export each as SVG via Figma REST API (batched, max 100 per request)
3. Deduplicate by SVG content hash (441 nodes may yield ~60-80 unique shapes)
4. Name icons using React TSX cross-reference (sibling text, parent context, Lucide import names)
5. Clean SVGs (replace hardcoded colors with `currentColor` so Flutter can tint them)
6. Save unique SVGs to `{config.flutter_output}/shared/assets/icons/`
7. Generate `{config.flutter_output}/shared/lib/icons/app_icons.dart` with `AppIcons.iconName(size:, color:)` helpers
8. Write `{config.output_dir}/icon_manifest.json` for reference during conversion

After running, add to `shared/pubspec.yaml`:

- Dependency: `flutter_svg: ^2.0.10`
- Assets: `assets/icons/`

**Option B — `"native_package"` mode** (preferred when a matching Flutter package exists):
Run `python .claude/skills/convert-to-flutter/scripts/discover_icons.py --print-imports` which will:

1. Scan all TSX/JSX files for supported icon imports, including `lucide-react`, versioned `lucide-react@...`, `@heroicons/react`, `phosphor-react` / `@phosphor-icons/react`, `react-icons/fi`, `react-icons/hi`, `@tabler/icons-react`, and Font Awesome icon packs.
2. Search/verify candidate Flutter packages on pub.dev, then download the selected package archive to validate that every generated icon symbol exists. If a single icon is missing from the primary pack, the script may resolve it through a secondary native package such as `font_awesome_flutter` instead of guessing a Material replacement.
3. Generate `{config.output_dir}/icon_mapping.json` with native package refs, for example:
   ```json
   {
     "react_name": "MapPin",
     "imported_name": "MapPin",
     "package": "lucide_icons_flutter",
     "flutter_ref": "LucideIcons.mapPin",
     "resolved": true,
     "used_in": ["climbing_bolders_indoor/src/components/MapPage.tsx"]
   }
   ```
4. Print the dependencies and exports to add to shared:
   ```yaml
   dependencies:
     lucide_icons_flutter: ^3.1.14+2
   ```
   ```dart
   export 'package:lucide_icons_flutter/lucide_icons.dart';
   ```
5. If any icon is still unresolved or no Flutter package exists, use `"figma_svg"` for those icons/pages instead of guessing a Material replacement.

**Important**: Icons from native packages are NOT compile-time constants. During conversion:

- Never use `const Icon(LucideIcons.xxx)` — use `Icon(LucideIcons.xxx)` instead
- Never use `const` on lists/records containing icon references
- Constructor default parameters using icons require removing `const` from the constructor

If the output file already exists, skip. Use `--force` flag to regenerate.

**Step 3 - Run matcher** (if `{config.output_dir}/page_matches_with_layout.json` doesn't exist):
Execute `python .claude/skills/convert-to-flutter/scripts/run_matcher.py` which will:

1. Split raw Figma metadata (`{config.output_dir}/figma_raw_metadata.txt`) into per-page XML files at `{config.output_dir}/figma_pages/`
2. Scan React components in `{config.react_src}`
3. Match React components to Figma pages using 4-phase matching (exact main → exact page → exact child → fuzzy)
4. Generate `{config.output_dir}/page_matches_with_layout.json` with all matches grouped by page

If `{config.output_dir}/page_matches_with_layout.json` already exists, skip this step. Use `--force` flag to regenerate.

**Step 4 - Run discovery script**:
Execute `python .claude/skills/convert-to-flutter/scripts/generate_conversion_plan.py` which will:

1. Read `{config.output_dir}/page_matches_with_layout.json`
2. Extract and **deduplicate** all main components (where `is_main_component: true`)
3. Count child components for each page
4. Group by complexity (simple: 0-5 children, medium: 6-15, complex: 16+)
5. Create batches (max 8 pages per batch)
6. Generate **chunked** output:
   - `{config.output_dir}/conversion_plan.md` - Short summary (~100 lines)
   - `{config.output_dir}/plans/batch-1.md` - Detailed checklists for batch 1
   - `{config.output_dir}/plans/batch-2.md` - Detailed checklists for batch 2
   - ... one file per batch
   - `{config.output_dir}/conversion_progress.json` - Progress tracker with batch info

**Step 5 - Build the complete page manifest**:

The matcher only flags `is_main_component: true` for top-level React components. Many navigable screens (subpages, modals, variant states) get missed. This step builds a **single authoritative manifest** at `{config.output_dir}/page_manifest.json` that maps EVERY Figma XML page to a Flutter target.

A) **List every Figma XML** from `{config.output_dir}/figma_pages/`. This is the ground truth — if it has a Figma design, it needs a Flutter decision.

B) **For each Figma XML**, classify it as one of:

- **page** — gets its own Flutter package + route (main screens, detail pages, settings, subpages with back navigation)
- **tab** — embedded in a tab host, no independent route (e.g., profile tabs like liked/sent/saved)
- **modal** — shown via `showModalBottomSheet` (e.g., filter, gym picker)
- **state** — a visual variant of another page (e.g., "map with user click open"), converted as a state within that page's StatefulWidget, NOT a separate page. Record which parent page owns it.
- **duplicate** — same layout as another page with only data differences. Record which page it duplicates — will be handled as a parameter variant, not a separate page.

C) **For each non-state/non-duplicate entry**, determine its data source:

- **React + Figma**: Has a matched TSX file — use Figma XML for layout, React for logic
- **Figma-only**: No React match — derive everything from Figma XML, infer callbacks from visible buttons/actions
- **Tab subpage reuse**: If multiple Figma pages share the same React component (e.g., `profile_liked`, `profile_saved` → same list layout), plan ONE configurable widget with a data-source parameter

D) **Write `{config.output_dir}/page_manifest.json`**:

```json
{
  "pages": [
    {
      "figma_xml": "browse_1_2.xml",
      "flutter_name": "browse_page",
      "type": "page",
      "source": "react+figma",
      "react_file": "SprayWallBrowser.tsx",
      "parent": null,
      "batch": 1
    },
    {
      "figma_xml": "map_user_click_10_3887.xml",
      "flutter_name": "map_page",
      "type": "state",
      "source": "figma-only",
      "react_file": null,
      "parent": "map_page",
      "state_name": "user_selected"
    }
  ]
}
```

E) **Add ALL page/tab/modal entries to batches**. Every entry that needs a Flutter package MUST appear in a batch file. No page is "discovered" without being scheduled for conversion.

F) **Validate completeness**: Count of Figma XMLs must equal count of manifest entries. Every Figma XML must map to exactly one manifest entry. Print a summary: N pages, N tabs, N modals, N states, N duplicates.

**Step 6 - Generate page patterns** (auto-generate `{config.output_dir}/patterns.md`):

If `{config.output_dir}/patterns.md` does not exist, generate it by reading React source code:

1. Read `{config.output_dir}/plans/pages/_index.json` to get all pages with their child counts and TSX paths
2. Select **5-8 representative TSX files** covering diverse page types:
   - 2 most complex pages (highest child count) — likely feed or profile pages
   - 1 page with "Profile" or "Tab" in name — for tabbed layout pattern
   - 1 page with "Settings" or "Privacy" in name — for settings list pattern
   - 1 page with "Map" or "Location" in name — for map/stack pattern
   - 1 page with "Log" or "Upload" or "Edit" in name — for form/input pattern
   - 1 page with "Detail" in name — for detail page pattern
   - 1 modal file (if any) — for bottom sheet pattern
3. Read each selected TSX file (**first 200 lines** is enough to identify structure)
4. For each file, identify the structural pattern:
   - Scrollable list with `.map()` + filter chips → **Scrollable Feed**
   - Tabs + cover image + stats → **Profile with Tabs**
   - Hero image + metadata + description → **Detail Page**
   - Grid/list toggle + sort → **List/Grid with Toggle**
   - Stack + absolute positioning + map → **Map Page**
   - Form inputs + validation + submit → **Form/Input Page**
   - ListTile items + SwitchListTile + sections → **Settings Page**
   - Modal/bottom sheet overlay → **Modal/Bottom Sheet**
   - ListView with conversation items → **Messages/Chat**
5. Write `{config.output_dir}/patterns.md` with this format for each detected pattern:

   ```
   ## Pattern: {Name}

   **Used by**: {list of pages matching this pattern}

   Structure:
   (widget tree showing Scaffold → body → children hierarchy)

   Key decisions:
   - {non-obvious Flutter widget choices}
   - {when to use SliverAppBar vs AppBar, CustomScrollView vs ListView, etc.}
   ```

6. Include a "Common Page Structure" section at the top with shared conventions:
   - Accept `VoidCallback? onBack` and `ValueChanged<String>? onNavigate`
   - Use `Theme.of(context)` for all colors
   - Import from `package:shared/theme/app_theme.dart`
7. Include a "Navigation Patterns" section at the bottom with routing conventions

**Keep patterns.md under 200 lines.** Only document patterns that need non-obvious structural decisions. If a page is a simple Scaffold + ListView, it doesn't need a pattern.

**Step 7 - Present summary to user**: Show total pages, batching strategy, detected patterns, next steps.

**Important**: After Phase 1, **STOP**. Let user review `{config.output_dir}/conversion_plan.md` and `{config.output_dir}/patterns.md` before proceeding.

### Phase 2: Theme Generation

If `{config.flutter_output}/shared/` doesn't exist:

1. Run `python .claude/skills/convert-to-flutter/scripts/generate_theme.py --config conversion_config.json` — auto-parses CSS and generates `app_colors.dart`, `app_typography.dart`, `app_theme.dart` into `{config.flutter_output}/shared/lib/theme/`. `app_colors.dart` must include the core Flutter theme colors, semantic colors from CSS (`--success`, `--warning`, `--error`, `--info`), and every literal CSS hex variable as an `AppColors.token*` constant.
2. Generate `shared/pubspec.yaml`, barrel files (`widgets.dart`, `models.dart`, `utils.dart`)

### Phase 3: Per-Page Conversion

**Prerequisites**:

- Phase 1 completed (plan + `page_manifest.json` exist)
- Phase 2 completed (theme exists at `{config.flutter_output}/shared/`)

**What to convert**: Read `{config.output_dir}/page_manifest.json`. Convert every entry with type `page`, `tab`, or `modal`. Entries with type `state` are handled as states within their parent page. Entries with type `duplicate` are parameter variants of another page.

For each page/tab/modal in the current batch:

**Step 1 - Load data**: Read the manifest entry to get `figma_xml`, `source`, and `react_file`. Also read the per-page JSON at `{config.output_dir}/plans/pages/{snake_name}.json` if it exists.

**Step 2 - Read Figma XML (PRIMARY source)**: Read the Figma XML file from `{config.output_dir}/figma_pages/{figma_xml}`. This is the **design source of truth**. Extract:

- Every visible element: text labels, buttons, icons, images, cards, lists
- Element hierarchy: which elements are children of which containers
- Positions and sizes: x, y, width, height for layout inference
- Visual styling: colors, font sizes, border radius, shadows, opacity

If the Figma XML includes `fill`, `stroke`, `background`, opacity, radius, or shadow attributes, treat those as exact design values. Map exact colors to the closest existing/generated `AppColors` token by hex value. If no token exists, add a descriptive token to `AppColors` instead of inlining a raw `Color(0x...)` in a page widget. If the current MCP XML lacks styling attributes, use the CSS/React theme tokens as the fallback source of truth and note the limitation.

Then, if `source` is `react+figma`, read the React TSX at `{config.react_src}/{react_file}`. Extract:

- Props interface → constructor params (see [references/mappings.md](references/mappings.md))
- useState → StatefulWidget state variables with setState
- Callbacks → VoidCallback/ValueChanged parameters
- Child component usage → shared widget imports
- Mock data → Dart constants
- Conditional rendering → if/else in build()
- .map() loops → ListView.builder or spread operator
- Icons → see icon handling below (depends on `config.icon_mode`)
- Tailwind classes → Flutter styles (see [references/mappings.md](references/mappings.md))

**CRITICAL — Icon handling** (depends on `config.icon_mode`):

Figma metadata represents ALL icons as generic `Icon` FRAME nodes with `Vector` children — icon names are NOT preserved. How you handle them depends on the chosen mode:

**If `icon_mode` is `"figma_svg"` (default)**:

1. Read `{config.output_dir}/icon_manifest.json` (generated by `extract_figma_icons.py` in Phase 1)
2. Use `AppIcons.iconName(size: 24, color: theme.colorScheme.primary)` from `package:shared/icons/app_icons.dart`
3. To find the right icon name: parse the React TSX `import { Heart, Mountain } from 'lucide-react'`, convert to kebab-case, and look up in `icon_manifest.json`
4. Add `import 'package:shared/icons/app_icons.dart';` to the page

**If `icon_mode` is `"native_package"`**:

1. Read `{config.output_dir}/icon_mapping.json` (generated by `discover_icons.py` in Phase 1)
2. Parse the icon import in the TSX file and match the component/alias to the `react_name` field
3. Use the `flutter_ref` field directly, for example `Icon(LucideIcons.mapPin, size: 24, color: theme.colorScheme.primary)`
4. Import the selected package through `package:shared/shared.dart` after re-exporting it from shared
5. If the mapping entry has `"resolved": false`, do not guess. Switch that icon/page to `"figma_svg"` or rerun discovery after choosing a package that contains the icon.

For **Figma-only pages** (`source: "figma-only"`): check if a nearby React component uses the same icon pattern and reuse its icon choices. If no React reference exists, infer the icon from surrounding text labels (e.g., a "Settings" label next to an Icon frame → `AppIcons.settings()` or `LucideIcons.settings`).

**Step 2.5 - Collect state variants**: Check the manifest for entries with `type: "state"` that reference this page as `parent`. Read each state's Figma XML to understand what changes (e.g., a panel opens, a selection highlights, a list filters). These become states in the StatefulWidget — toggled by user actions like taps or selections.

**Step 3 - Build layout from Figma**: Use the Figma XML element hierarchy as the widget tree skeleton:

- Map Figma groups/frames → Column, Row, Stack based on child arrangement
- Sort children by y-coordinate within vertical containers, x within horizontal
- Calculate gaps between elements → SizedBox or padding
- Overlapping elements → Stack + Positioned
- Total content height > screen → SingleChildScrollView or ListView
- **Every visible element in the Figma XML must appear in the Flutter widget tree.** If an element exists in the design, it must exist in the code.

**Step 4 - Generate Flutter page widget**: Write `pages/{snake_name}/lib/{snake_name}_page.dart`

- StatefulWidget if it has states (from Step 2.5) or React has useState, else StatelessWidget
- Accept navigation callbacks (onBack, onNavigate) as parameters
- Use `Theme.of(context)` for semantic Material roles and `AppColors` for exact design tokens. Never inline raw `Color(0x...)` values in page widgets; add or reuse named `AppColors` tokens instead.
- See `{config.output_dir}/patterns.md` for page type patterns
- For `type: "modal"` pages: add a `static Future<T?> show(BuildContext context)` method that calls `showModalBottomSheet`
- For `type: "tab"` pages: accept data-source parameters so the same widget can be reused for duplicate variants

**Step 4.5 - Validate against Figma (MANDATORY)**: Re-read the Figma XML. Walk through every element in the design and verify the generated Flutter code contains a corresponding widget. Check:

- All text labels present with correct content
- All buttons/icons present and tappable
- **All icons match the React source** — in `figma_svg` mode, every `AppIcons.xxx()` call must correspond to a React icon import or Figma SVG; in `native_package` mode, every `Icon(LucideIcons.xxx)`/package ref must come from `icon_mapping.json` with `"resolved": true`. No fallback icons unless the React source actually uses that icon.
- All list items / cards present
- Layout direction matches (vertical vs horizontal grouping)
- If anything is missing, fix it before proceeding. Do NOT skip this step.

**Step 5 - Generate standalone runner**: Write `pages/{snake_name}/lib/main.dart` with MaterialApp wrapping the page, `AppTheme.light()`, `AppTheme.dark()` (these are methods — always use parentheses), all callbacks stubbed with debugPrint.

**Step 6 - Generate pubspec.yaml**: Standard Flutter package depending on `shared` at `../../shared`.

**Step 7 - Verify**: Run `flutter pub get && flutter analyze` in the page directory. Fix errors before proceeding.

**Step 8 - Update progress**: Mark this page as done in `conversion_progress.json`. If it was the last page in a batch, mark the batch as complete.

### Phase 4: Shared Widgets

When child components (is_main_component=false) are needed:

1. Check if already exists in `shared/lib/widgets/`
2. If not, convert using same process as Phase 3
3. Export from `shared/lib/widgets.dart` barrel file

### Phase 5: Models

Extract TypeScript interfaces from React → Dart classes in `shared/lib/models/`. All fields final, const constructor with required/optional params.

### Phase 6: Mock Data

**Mock Data**: Hardcoded arrays/objects from React → `shared/lib/utils/mock_data.dart` as const Lists.

### Phase 7: Full App Assembly

**Step 0 - Verify all pages are built**: Read `{config.output_dir}/page_manifest.json`. For every entry with type `page`, `tab`, or `modal`, verify a Flutter package exists at `{config.flutter_output}/pages/{flutter_name}/`. If any are missing, **convert them now** using the Phase 3 process before proceeding. Do NOT assemble an incomplete app.

Generate `full_app/`:

- `lib/navigation/app_router.dart` - onGenerateRoute switch for all pages
- `lib/main.dart` - MaterialApp with AppTheme and router
- `pubspec.yaml` - depends on shared + all page packages

**Deep navigation wiring** — this phase must go beyond just creating a router skeleton:

1. **Read the manifest for all routes**: Use `page_manifest.json` as the authoritative list. Every `type: "page"` entry gets a named route. Every `type: "tab"` entry gets wired into its tab host. Every `type: "modal"` entry gets invoked via `showModalBottomSheet`.

2. **Scan all `onNavigate` callbacks from React TSX**: For every converted page, read the React source and find all navigation triggers (button clicks, list item taps, icon presses). Map each to a route string.

3. **Replace ALL `debugPrint` stubs**: Scan every built page for `debugPrint` calls that were used as callback placeholders during Phase 3 standalone runner generation. Replace each with a real `onNavigate?.call('route-name')` or `onBack?.call()` invocation.

4. **Build central `_handleNavigate` dispatcher**: The router's `_handleNavigate` method must handle every route string emitted by every page. Use pattern matching:
   - Exact matches: `'settings'`, `'leaderboard'`, `'create-post'`
   - Prefix patterns: `'climber-{id}'`, `'wall-{id}'`, `'list-{id}'`, `'route-{id}'`
   - Special actions: `'gym-picker'` → show bottom sheet, `'filter'` → show modal

5. **Wire every button/action**: Every tappable element that navigates in the React app must navigate in the Flutter app. No button should produce only a debugPrint in the assembled full app.

6. **Bottom sheets and modals**: Pages with `type: "modal"` in the manifest must be invoked via their `static show()` method from the router, not pushed as full routes.

### Phase 8: Figma Coverage Audit

**Trigger**: Run after full-app assembly is complete.

**Purpose**: Final validation that every Figma design is accounted for.

1. **Walk `page_manifest.json`**: For every entry:
   - `type: "page"` / `type: "tab"` / `type: "modal"` → verify Flutter package exists at `{config.flutter_output}/pages/{flutter_name}/`
   - `type: "state"` → verify the parent page's StatefulWidget has a state that corresponds to this entry
   - `type: "duplicate"` → verify the target page accepts parameters to render this variant

2. **Validate design fidelity per page**: For each built page, re-read its Figma XML and the generated `_page.dart`. Check:
   - All major sections from the design are present (header, body, footer, cards, lists)
   - Element count is proportional (a Figma page with 20 elements shouldn't produce a Flutter page with 5)
   - No raw inline colors — all colors come from `Theme.of(context)` / named `AppColors` tokens, with exact Figma colors mapped by hex when available

3. **Verify router completeness**: Read `app_router.dart`. Every `type: "page"` must have a named route. Every `type: "modal"` must be invoked via `showModalBottomSheet`. Every `type: "tab"` must be reachable from its tab host.

4. **Generate coverage report**: Output `{config.output_dir}/figma_coverage_report.md`:
   - Total: N Figma designs → N manifest entries → N Flutter packages → N routes
   - Per-entry status: built / missing / design-mismatch / unrouted
   - Action items for anything not at 100%

## Parallelization

For batch conversion, spawn parallel Task agents:

```
Task(subagent_type="general-purpose", prompt="Convert {PageName} to Flutter. Read conversion_config.json for paths. Read the per-page data at {config.output_dir}/plans/pages/{snake_name}.json, then read the React TSX source, and generate the Flutter page at {config.flutter_output}/pages/{snake_name}/. Use shared theme at ../../shared. Verify with flutter analyze.")
```

Batch definitions: Read `{config.output_dir}/conversion_progress.json` to get batch page list, then read `{config.output_dir}/plans/batch-N.md` for the detailed checklists per page.

## Progress Tracking

Maintain `{config.output_dir}/conversion_progress.json`:

```json
{ "converted_pages": [], "remaining_pages": [], "failed_pages": [] }
```

Update after each page. If conversion fails, log to `{config.output_dir}/conversion_errors.log`, add to failed_pages, continue.

## Verification Checklist

Per page: compiles with `flutter analyze`, runs standalone, shows content, uses theme colors from generated AppColors, callbacks produce debugPrint output.
