## The Server Socket Lifecycle

Before diving into individual system calls, understand the complete lifecycle. Every TCP server follows this sequence:

```
┌─────────────────────────────────────────────────────────────┐
│                    SERVER SOCKET LIFECYCLE                     │
│                                                               │
│   1. socket()    ──── Create the communication endpoint       │
│        │                                                      │
│   2. setsockopt()──── Configure socket behavior               │
│        │                                                      │
│   3. bind()      ──── Attach to a specific port               │
│        │                                                      │
│   4. listen()    ──── Start accepting connection requests      │
│        │                                                      │
│   5. accept()    ──── Accept one client → new FD              │
│        │                                                      │
│   6. recv()      ──── Read data from client FD                │
│        │                                                      │
│   7. send()      ──── Write data to client FD                 │
│        │                                                      │
│   8. close()     ──── Close client FD when done               │
│                                                               │
│   Steps 5–8 repeat for every client connection.               │
│   The listening socket (from step 4) stays open forever.      │
└─────────────────────────────────────────────────────────────┘
```

> **Critical:** In ft_irc, steps 5–8 do NOT happen sequentially for one client at a time. The `poll-loop` skill teaches how to interleave these operations across many clients using a single event loop (MR-22). This skill teaches each step individually.

## Socket Concepts

### 1. socket() — Create the Communication Endpoint

**What it is:** `socket()` creates a new communication endpoint and returns a file descriptor (integer) that represents it. It is the very first step in building a network server.

**Why it exists:** Before you can send or receive any data over the network, the operating system needs to allocate internal resources for a network connection. `socket()` requests those resources and gives you a handle (file descriptor) to interact with them.

**When it is used:** At server startup, before anything else. You call `socket()` once to create the **listening socket** — the socket that will accept incoming client connections.

**Relation to ft_irc:** The subject requires TCP/IP communication (MR-18). `socket()` creates the TCP socket that makes this possible. It is listed in the allowed functions (`references/subject/allowed-functions.md`).

**Related MR IDs:**

- MR-18: Communication via TCP/IP (v4 or v6)

**Internal behavior:**

1. The OS allocates kernel resources for a new socket.
2. The OS assigns a file descriptor number (e.g., 3, 4, 5...).
3. The socket is not yet bound to any address or port — it exists but cannot do anything.
4. The returned FD is your handle for all future operations on this socket.

**ASCII Diagram:**

```
  Before socket():              After socket():

  (nothing)                     ┌─────────────────┐
                                │ Socket (FD = 3)   │
                                │ Type: TCP          │
                                │ Bound: No          │
                                │ Listening: No      │
                                │ Connected: No      │
                                └─────────────────┘

  socket(AF_INET, SOCK_STREAM, 0) → returns FD 3
```

**Parameters explained:**

| Parameter | Value for ft_irc | Meaning |
| --- | --- | --- |
| `domain` | `AF_INET` | IPv4 address family (MR-18: v4 or v6) |
| `type` | `SOCK_STREAM` | TCP stream socket (MR-18: TCP/IP) |
| `protocol` | `0` | Let the OS choose the default protocol for the type (TCP for SOCK_STREAM) |

> For IPv6, use `AF_INET6` instead of `AF_INET`. The subject allows either (MR-18).

**Common mistakes:**

- Not checking the return value. `socket()` returns `-1` on failure. Not handling this can crash the server (MR-15).
- Using `SOCK_DGRAM` (UDP) instead of `SOCK_STREAM` (TCP). The subject requires TCP (MR-18).
- Creating multiple listening sockets when only one is needed.
- Forgetting to close the socket on error paths — leaking file descriptors.

**Evaluation notes:**

- Evaluators may check that you use `SOCK_STREAM` (TCP).
- The server must not crash if `socket()` fails (MR-15, MR-16).

### 2. sockaddr_in — The Address Structure

**What it is:** `sockaddr_in` is a C structure that holds an IPv4 address and port number. It tells the OS *where* the socket should bind — which network interface and which port to listen on.

**Why it exists:** `bind()` needs to know what address and port to attach the socket to. `sockaddr_in` packages this information into a format the OS understands.

**When it is used:** You fill a `sockaddr_in` structure before calling `bind()`.

**Relation to ft_irc:** The subject requires listening on a port from the command line (MR-03) via TCP/IP (MR-18). The `sockaddr_in` structure is how you express this to the OS.

**Related MR IDs:**

- MR-03: Listen on the provided port
- MR-18: TCP/IP (v4 or v6)

**Internal behavior:**

The structure has three important fields:

| Field | Purpose | Typical value for ft_irc |
| --- | --- | --- |
| `sin_family` | Address family | `AF_INET` (IPv4) |
| `sin_port` | Port number (network byte order) | `htons(port)` |
| `sin_addr.s_addr` | IP address (network byte order) | `INADDR_ANY` (all interfaces) or `inet_addr("127.0.0.1")` |

**ASCII Diagram:**

```
  sockaddr_in structure:

  ┌───────────────────────────────────┐
  │  sin_family:   AF_INET            │  ← IPv4
  │  sin_port:     htons(6667)        │  ← Port from command line
  │  sin_addr:     INADDR_ANY         │  ← Listen on all interfaces
  └───────────────────────────────────┘
       │
       ▼
  Passed to bind() to attach socket to this address
```

> For IPv6, use `sockaddr_in6` with `AF_INET6` instead. The concept is identical.

**Common mistakes:**

- Forgetting to use `htons()` for the port. Without byte order conversion, the port will be wrong on most machines.
- Not zeroing the structure before filling it. Use `memset()` or aggregate initialization to clear all fields first.
- Using `inet_addr("127.0.0.1")` instead of `INADDR_ANY`. This restricts the server to localhost only — `INADDR_ANY` listens on all interfaces.
- Confusing `sockaddr_in` (IPv4) with `sockaddr_in6` (IPv6). They have different sizes and fields.

**Evaluation notes:**

- Evaluators may ask why `htons()` is needed. Understand byte order (see Section 4).

### 3. AF_INET and SOCK_STREAM — Socket Type Selection

**What it is:** `AF_INET` selects the IPv4 address family. `SOCK_STREAM` selects a stream-oriented (TCP) socket. Together, they tell `socket()` to create an IPv4 TCP socket — exactly what ft_irc needs.

**Why it exists:** The socket API is generic — it supports many protocols and address families. These constants narrow the choice to the specific combination the subject requires.

**When it is used:** As arguments to `socket()`.

**Relation to ft_irc:** MR-18 requires TCP/IP (v4 or v6). `AF_INET` + `SOCK_STREAM` = IPv4 TCP.

**Related MR IDs:**

- MR-18: Communication via TCP/IP (v4 or v6)

**ASCII Diagram:**

```
  socket(domain, type, protocol)

  Domain:                        Type:
  ┌─────────────┐                ┌──────────────┐
  │ AF_INET      │ ← IPv4        │ SOCK_STREAM   │ ← TCP
  │ AF_INET6     │ ← IPv6        │ SOCK_DGRAM    │ ← UDP (NOT for ft_irc)
  │ AF_UNIX      │ ← Local       │ SOCK_RAW      │ ← Raw (NOT for ft_irc)
  └─────────────┘                └──────────────┘

  ft_irc: AF_INET + SOCK_STREAM = IPv4 TCP socket ✓
```

**Common mistakes:**

- Using `SOCK_DGRAM`. That creates a UDP socket. The subject requires TCP (MR-18).
- Using `AF_UNIX`. That creates a local Unix socket, not a network socket. The subject requires TCP/IP (MR-18).

### 4. htons() and htonl() — Byte Order Conversion

**What it is:** `htons()` converts a 16-bit number from **host byte order** to **network byte order**. `htonl()` does the same for 32-bit numbers. "Host byte order" is how your CPU stores numbers; "network byte order" is the standardized format for network protocols (big-endian).

**Why it exists:** Different CPUs store multi-byte numbers in different orders (big-endian vs little-endian). Network protocols standardize on big-endian. Without conversion, a port number like `6667` would be interpreted incorrectly by a big-endian machine receiving data from a little-endian machine.

**When it is used:** When setting `sin_port` in `sockaddr_in` (use `htons()`), and when setting `sin_addr` (use `htonl()` for `INADDR_ANY`).

**Relation to ft_irc:** The port comes from the command line (MR-03). To bind to it, you must convert it to network byte order with `htons()`. Both functions are listed in the allowed functions.

**Related MR IDs:**

- MR-03: Listen on the provided port
- MR-18: TCP/IP communication

**ASCII Diagram:**

```
  Port 6667 on a little-endian machine:

  Host byte order:    0x0A 0x1B  (little-endian stores low byte first)
  Network byte order: 0x1B 0x0A  (big-endian — high byte first)

  htons(6667) converts:
  Host order → Network order

  ┌────────────────┐          ┌────────────────┐
  │ 0x0A 0x1B       │  ─────► │ 0x1B 0x0A       │
  │ (host order)    │  htons  │ (network order) │
  └────────────────┘          └────────────────┘

  Without htons(), the port would be interpreted as
  a completely different number on the network.
```

**Common mistakes:**

- Forgetting `htons()` when setting `sin_port`. The socket will bind to a wrong port.
- Using `htons()` on `INADDR_ANY`. `INADDR_ANY` is typically defined as 0 — `htonl(INADDR_ANY)` is correct but `INADDR_ANY` is 0 in any byte order. Still, using `htonl()` is good practice.
- Applying `htons()` when reading port numbers back from the OS. Use `ntohs()` to convert back.

### 5. inet_addr() — String to Binary Address

**What it is:** `inet_addr()` converts a dotted-decimal IPv4 address string (like `"127.0.0.1"`) into the binary format that `sockaddr_in.sin_addr.s_addr` expects.

**Why it exists:** Humans write IP addresses as strings. The OS needs them as 32-bit binary numbers in network byte order. `inet_addr()` bridges this gap.

**When it is used:** When you need to bind to a specific IP address. For ft_irc, you typically use `INADDR_ANY` instead, but `inet_addr()` is useful for testing and is listed in the allowed functions.

**Relation to ft_irc:** Listed in allowed functions. Used when a specific address is needed. For most ft_irc implementations, `INADDR_ANY` is sufficient.

**Related MR IDs:**

- MR-18: TCP/IP communication

**ASCII Diagram:**

```
  inet_addr("127.0.0.1")

  "127.0.0.1"  ──────►  0x0100007F  (binary, network byte order)
   (string)               (uint32_t)

  Used as: addr.sin_addr.s_addr = inet_addr("127.0.0.1");

  For ft_irc, prefer:
  addr.sin_addr.s_addr = INADDR_ANY;  (listen on all interfaces)
```

**Common mistakes:**

- Using `inet_addr()` when `INADDR_ANY` would be simpler and more flexible.
- Not checking for `INADDR_NONE` (returned on invalid input).
- Using `inet_addr()` for IPv6 addresses. It only works with IPv4. For IPv6, use `inet_pton()`.

### 6. setsockopt() — Configure Socket Behavior

**What it is:** `setsockopt()` sets options on a socket. The most important option for ft_irc is `SO_REUSEADDR`, which allows the server to reuse a port that was recently closed.

**Why it exists:** When a server stops and restarts, the OS may keep the port reserved for a short time (the TIME_WAIT state). Without `SO_REUSEADDR`, `bind()` would fail with "Address already in use" during this period. This is extremely annoying during development.

**When it is used:** After `socket()`, before `bind()`.

**Relation to ft_irc:** Listed in the allowed functions. `SO_REUSEADDR` is an Engineering Recommendation — the subject does not require it, but every experienced developer uses it.

**Related MR IDs:**

- MR-18: TCP/IP communication (socket setup)

**Classification:** Engineering Recommendation

**ASCII Diagram:**

```
  Without SO_REUSEADDR:                With SO_REUSEADDR:

  Server stops.                        Server stops.
  Port 6667 in TIME_WAIT.              Port 6667 in TIME_WAIT.
  Server restarts.                     Server restarts.
  bind() → "Address already in use" ✗  bind() → Success ✓
  Wait 60 seconds...                   Immediately usable.
  bind() → Success (finally)
```

**Common mistakes:**

- Not using `SO_REUSEADDR` and getting confused by "Address already in use" during development.
- Calling `setsockopt()` after `bind()`. It should be called before.
- Confusing `SO_REUSEADDR` with `SO_REUSEPORT` (different behavior, not needed for ft_irc).

### 7. bind() — Attach Socket to a Port

**What it is:** `bind()` associates a socket with a specific address and port number. After `bind()`, the socket "owns" that port — incoming connections to that port will reach this socket.

**Why it exists:** A socket created by `socket()` has no address or port. It is like a phone with no phone number. `bind()` assigns the number so that clients can call.

**When it is used:** After `socket()` and `setsockopt()`, before `listen()`.

**Relation to ft_irc:** MR-03 requires listening on the port from the command line: `./ircserv <port> <password>` (MR-02). `bind()` is what makes the socket listen on that port.

**Related MR IDs:**

- MR-02: Program accepts `<port>` and `<password>`
- MR-03: Listen on the provided port
- MR-18: TCP/IP communication

**Internal behavior:**

1. The OS registers that this socket is attached to the specified address and port.
2. No other socket can bind to the same address:port combination (unless `SO_REUSEADDR` is set).
3. The socket is still not listening — `bind()` only assigns the address.

**ASCII Diagram:**

```
  Before bind():                After bind():

  ┌─────────────────┐          ┌─────────────────────┐
  │ Socket (FD = 3)   │          │ Socket (FD = 3)       │
  │ Address: none     │  ─────►  │ Address: 0.0.0.0:6667 │
  │ Listening: No     │  bind()  │ Listening: No         │
  └─────────────────┘          └─────────────────────┘

  The socket now "owns" port 6667.
  But it is NOT yet accepting connections.
```

**Common mistakes:**

- Not checking the return value. `bind()` returns `-1` on failure (e.g., port already in use). Not handling this crashes the server (MR-15).
- Binding to a port below 1024 without root. Use a high port for testing.
- Hardcoding the port number instead of using the command-line argument (MR-03).
- Calling `bind()` before `socket()`. The FD must exist first.
- Forgetting byte order conversion: `addr.sin_port = htons(port)`.

**Evaluation notes:**

- Evaluators will check that the server binds to the port provided on the command line (MR-03).
- If `bind()` fails, the server must handle it gracefully (MR-15, MR-16).

### 8. listen() — Start Accepting Connection Requests

**What it is:** `listen()` marks the socket as a **passive socket** — one that will accept incoming connections rather than initiate them. It also sets the **backlog** — the maximum number of pending connections the OS will queue before rejecting new ones.

**Why it exists:** After `bind()`, the socket owns a port but is not yet accepting connections. `listen()` transitions it from "I have a port" to "I am waiting for clients."

**When it is used:** After `bind()`, before `accept()`.

**Relation to ft_irc:** MR-03 says the server listens on the provided port. `listen()` is the call that enables this. The server must handle multiple clients (MR-19), and the backlog parameter controls how many pending connections are queued.

**Related MR IDs:**

- MR-03: Listen on the provided port
- MR-19: Handle multiple clients simultaneously

**Internal behavior:**

1. The OS marks the socket as passive (listening).
2. The OS creates an internal queue for pending connection requests.
3. The backlog parameter sets the maximum size of this queue.
4. When a client sends a TCP SYN, the OS queues the connection request.
5. `accept()` (next step) dequeues and completes a connection.

**ASCII Diagram:**

```
  Before listen():              After listen():

  ┌─────────────────────┐      ┌─────────────────────┐
  │ Socket (FD = 3)       │      │ Socket (FD = 3)       │
  │ Address: 0.0.0.0:6667│      │ Address: 0.0.0.0:6667│
  │ Listening: No         │      │ Listening: YES        │
  └─────────────────────┘      │ Backlog: 10           │
                                │ Queue: [empty]        │
                                └─────────────────────┘

  listen(fd, backlog)
  Now the OS queues incoming TCP connections.
```

**Common mistakes:**

- Setting the backlog too low (e.g., 1). This may cause connection rejections under load. A value like `SOMAXCONN` or 10+ is typical.
- Calling `listen()` before `bind()`. The socket must be bound first.
- Confusing `listen()` with `accept()`. `listen()` enables accepting — `accept()` actually accepts each connection.

### 9. accept() — Accept One Client Connection

**What it is:** `accept()` takes one pending connection from the listening socket's queue and creates a **new socket** — a new file descriptor — dedicated to that specific client. The listening socket remains open and continues accepting future connections.

**Why it exists:** Each client connection needs its own communication channel. `accept()` creates this channel by returning a new FD for the client while the original FD continues listening.

**When it is used:** After `listen()`. In ft_irc, `accept()` is called inside the event loop whenever the listening socket signals readiness. But the concept is the same: one call per new client.

**Relation to ft_irc:** MR-19 requires handling multiple clients simultaneously. `accept()` creates the per-client file descriptor that makes this possible.

**Related MR IDs:**

- MR-19: Handle multiple clients simultaneously
- MR-18: TCP/IP communication

**Internal behavior:**

1. `accept()` blocks (in blocking mode) or returns immediately (non-blocking) if no pending connections exist.
2. When a connection is pending, the OS completes the TCP handshake with the client.
3. The OS creates a **new socket** with a new file descriptor dedicated to this client.
4. The original listening socket is **unchanged** — it continues accepting future connections.
5. The returned FD can be used with `recv()` and `send()` to communicate with this specific client.

**This is the most important concept in socket programming for ft_irc.**

**ASCII Diagram:**

```
  ┌─────────────────────┐
  │ Listening Socket      │
  │ FD = 3                │
  │ Port: 6667            │
  │ Queue: [Client A,     │
  │         Client B]     │
  └───────┬─────────────┘
          │
          │ accept()
          │
          ├──────► Returns FD = 4 (Client A's socket)
          │
          │ accept() again
          │
          ├──────► Returns FD = 5 (Client B's socket)
          │
          │ Listening socket (FD 3) is STILL listening
          │ for future connections.
          ▼

  ┌─────────────────┐  ┌─────────────────┐  ┌─────────────────┐
  │ FD 3 (Listening)  │  │ FD 4 (Client A)   │  │ FD 5 (Client B)   │
  │ Keeps accepting   │  │ recv/send with A  │  │ recv/send with B  │
  └─────────────────┘  └─────────────────┘  └─────────────────┘
```

**Why the listening socket stays open:**

- If `accept()` consumed the listening socket, the server could only ever accept one client.
- The listening socket is like a receptionist — it greets new arrivals and assigns them to a meeting room (new FD). The receptionist does not leave with the first visitor.

**Why every client gets a different FD:**

- Each client connection is independent. Client A's data must not mix with Client B's data.
- The OS tracks each connection separately via its FD.
- `recv(fd4, ...)` reads Client A's data. `recv(fd5, ...)` reads Client B's data. They never interfere.

**Common mistakes:**

- Closing the listening socket after `accept()`. The listening socket must remain open for the server's entire lifetime.
- Not storing the returned client FD. Without it, you lose the connection.
- Not checking the return value. `accept()` returns `-1` on failure (MR-15).
- Calling `accept()` in a tight loop without `poll()` readiness. This wastes CPU or blocks. In ft_irc, `accept()` is called only when `poll()` signals the listening socket is ready (MR-23).

**Evaluation notes:**

- Evaluators will verify that multiple clients can connect simultaneously (MR-19).
- `accept()` without poll readiness = grade 0 (MR-23). The `poll-loop` skill covers this.

### 10. recv() — Read Data from a Client

**What it is:** `recv()` reads available data from a client's socket into a buffer. It returns the number of bytes read, 0 if the client disconnected, or `-1` on error.

**Why it exists:** After a client connects, it sends IRC commands (like `NICK alice\r\n`). `recv()` is how the server reads this data from the client's file descriptor.

**When it is used:** Inside the event loop, when `poll()` signals that a client's FD has data available. This skill teaches what `recv()` does; the `poll-loop` skill teaches when to call it.

**Relation to ft_irc:** MR-43 requires handling partial data. `recv()` may return only part of a message — the server must buffer and aggregate. MR-23 requires poll readiness before calling `recv()`.

**Related MR IDs:**

- MR-43: Handle partial data — aggregate to rebuild commands
- MR-23: No recv without poll readiness (grade 0)
- MR-15, MR-16: No crash on disconnection

**Internal behavior:**

1. `recv()` copies available bytes from the OS kernel's receive buffer into your application buffer.
2. It returns the number of bytes actually read — this may be **less** than you requested.
3. If the client has disconnected, it returns `0`.
4. If no data is available and the socket is non-blocking, it returns `-1` with `errno` set to `EAGAIN` or `EWOULDBLOCK`.
5. `recv()` does NOT guarantee message boundaries. It may return half a message, or three messages at once.

**Why recv() may return partial data:**

```
  Client sends:                    Server recv() returns:

  "NICK alice\r\n"                 recv 1: "NICK al"     (6 bytes)
                                   recv 2: "ice\r\n"     (5 bytes)

  OR:

  "NICK alice\r\n"                 recv 1: "NICK alice\r\n" (14 bytes)
  "USER alice 0 * :A\r\n"         recv 1 continued: "USER alice 0 * :A\r\n"
                                   (both in one read!)
```

**ASCII Diagram:**

```
  ┌────────────┐                      ┌────────────┐
  │ Client A    │── sends "NICK al" ──►│ OS Kernel   │
  │              │── sends "ice\r\n" ──►│ recv buffer │
  └────────────┘                      └─────┬──────┘
                                            │
                                      recv(fd, buf, size, 0)
                                            │
                                            ▼
                                   Returns: "NICK alice\r\n"
                                   OR partial: "NICK al"
                                   OR multiple messages combined

  You CANNOT control how much data arrives.
  You MUST buffer and look for \r\n.
```

**Common mistakes:**

- Assuming `recv()` returns one complete IRC message. It does not. This is the most common ft_irc bug.
- Not checking the return value. `0` means disconnection — handle it (MR-15). `-1` means error — handle it.
- Calling `recv()` without `poll()` readiness. Grade 0 (MR-23).
- Using a buffer that is too small. IRC messages can be up to 512 bytes (RFC limit, but the subject does not specify a maximum — handle reasonable sizes).
- Not buffering remaining data. After extracting one complete message, leftover bytes in the buffer may be the start of the next message.

**Why send() may not send everything:**

> The same principle applies to `send()` — see Section 11.

**Evaluation notes:**

- Evaluators specifically test partial data (MR-43). The subject provides a `nc` test.
- `recv()` without poll readiness = grade 0 (MR-23).

### 11. send() — Write Data to a Client

**What it is:** `send()` writes data to a client's socket. It returns the number of bytes actually sent, which may be **less** than requested.

**Why it exists:** The server needs to send IRC replies, forwarded messages, and error responses to clients. `send()` is how data goes from the server to a specific client's file descriptor.

**When it is used:** Inside the event loop, when `poll()` signals that a client's FD is ready for writing. This skill teaches what `send()` does; the `poll-loop` skill teaches when to call it.

**Relation to ft_irc:** MR-23 requires poll readiness before calling `send()`. The server sends replies and forwarded channel messages to clients.

**Related MR IDs:**

- MR-23: No send without poll readiness (grade 0)
- MR-32: Forward channel messages to all members
- MR-25: Reference client connects without errors

**Internal behavior:**

1. `send()` copies bytes from your application buffer into the OS kernel's send buffer.
2. It returns the number of bytes actually copied — this may be **less** than you provided.
3. If the kernel buffer is full and the socket is non-blocking, it returns `-1` with `EAGAIN`/`EWOULDBLOCK`.
4. A partial send means you must send the remaining bytes later.

**Why send() may not send everything:**

```
  You want to send:     "001 alice :Welcome to the server\r\n"  (37 bytes)

  Scenario 1:           send() → returns 37 (all sent)         ✓
  Scenario 2:           send() → returns 20 (only 20 sent)     !
                         You must send remaining 17 bytes later.
```

**ASCII Diagram:**

```
  Server                              Client A
    │                                     │
    │  send(fd4, ":server 001 alice      │
    │         :Welcome\r\n", 37, 0)       │
    │                                     │
    │  OS kernel send buffer:             │
    │  ┌────────────────────────────┐    │
    │  │ ":server 001 alice :Welc"  │    │
    │  │ (buffer may be partially   │────►│  Receives data
    │  │  flushed by TCP)           │    │
    │  └────────────────────────────┘    │
    │                                     │
    │  send() returns: 37 (or less)      │
```

**Common mistakes:**

- Ignoring the return value. If `send()` returns less than the total, you lose data.
- Calling `send()` without `poll()` readiness. Grade 0 (MR-23).
- Not implementing a per-client write buffer. When `send()` cannot send everything, the remainder must be queued and sent when the FD is ready again.
- Blocking on `send()` with a blocking socket. In non-blocking mode, `send()` returns immediately even if it cannot send everything.

### 12. close() — Close a File Descriptor

**What it is:** `close()` releases a file descriptor and its associated resources. For a socket, this terminates the connection and frees the OS resources.

**Why it exists:** Resources are finite. Every open socket consumes kernel memory and a file descriptor slot. When a client disconnects or the server shuts down, sockets must be closed to prevent resource leaks.

**When it is used:** When a client disconnects (voluntarily or due to error), and when the server shuts down.

**Relation to ft_irc:** MR-15 and MR-16 require the server to never crash or quit unexpectedly. Proper cleanup with `close()` prevents resource exhaustion. The server must handle client disconnections gracefully.

**Related MR IDs:**

- MR-15: Program must not crash
- MR-16: Program must not quit unexpectedly

**ASCII Diagram:**

```
  Client disconnects:

  ┌─────────────────┐
  │ FD 4 (Client A)   │  ──── recv() returns 0 ──── client disconnected
  └─────────────────┘
           │
           │ close(4)
           ▼
  FD 4 is freed. Resources released.
  FD 4 can be reused by the OS for a future connection.

  Server shutdown:

  close(fd_client_A)
  close(fd_client_B)
  close(fd_client_C)
  close(fd_listening)    ← close the listening socket last
```

**Common mistakes:**

- Not closing sockets when clients disconnect. This leaks file descriptors — the server will eventually run out and crash (MR-15).
- Closing the listening socket when any client disconnects. Only close it at server shutdown.
- Using a socket after closing it. This causes undefined behavior.
- Not removing the closed FD from the poll set. After closing, the FD must not be monitored by `poll()` anymore — the `poll-loop` skill covers this.
- Double-closing a socket. Closing an FD twice is undefined behavior.

### 13. Server Socket vs Client Socket

**What it is:** In a server, there are two kinds of sockets — and understanding the difference is critical:

- The **server (listening) socket** — created once, listens for incoming connections.
- **Client sockets** — created by `accept()`, one per connected client.

**Why it exists:** The listening socket is a receptionist; client sockets are the actual communication channels. They serve fundamentally different purposes.

**Relation to ft_irc:** MR-19 requires multiple simultaneous clients. This is only possible because `accept()` creates new client sockets while the listening socket remains open.

**Related MR IDs:**

- MR-19: Handle multiple clients simultaneously
- MR-22: One poll() monitors all FDs (both listening and client sockets)

### 14. Connection Lifecycle (Implementation View)

**What it is:** Putting all the system calls together, here is the complete lifecycle of a connection from the server's perspective:

### 15. Blocking Sockets — The Default Problem

**What it is:** By default, sockets are **blocking** — `recv()` waits until data arrives, `send()` waits until data can be sent, and `accept()` waits until a client connects. This freezes the server.

**Why it matters for ft_irc:** The subject requires non-blocking I/O (MR-21) and forbids forking (MR-20). A blocking server can handle only one operation at a time — it cannot serve multiple clients simultaneously (violating MR-19).

**Related MR IDs:**

- MR-19: Multiple clients without hanging
- MR-20: Forking prohibited
- MR-21: All I/O must be non-blocking

**ASCII Diagram:**

```
  BLOCKING SERVER (WRONG for ft_irc):

  accept()          ← waits until a client connects (might wait forever)
     │
  recv(client_1)    ← waits until client 1 sends data
     │
  send(client_1)    ← waits until kernel buffer has space
     │
  recv(client_1)    ← waits again...
     │
     └── client 2 tries to connect → BLOCKED
         client 3 sends data → IGNORED
         server is FROZEN on client 1

  This violates MR-19 (multiple clients) and MR-21 (non-blocking).
```

**Why blocking is the default:**

- Blocking simplifies code — you just call `recv()` and it returns with data.
- For simple single-client programs, blocking is fine.
- For a multi-client server like ft_irc, blocking is fatal.

### 16. Non-Blocking Sockets — The Required Solution

**What it is:** A non-blocking socket is one where system calls like `recv()`, `send()`, and `accept()` return immediately even if they cannot complete. If no data is available, `recv()` returns `-1` with `errno` set to `EAGAIN` or `EWOULDBLOCK`.

**Why it exists:** Non-blocking mode allows the server to check many sockets quickly, serving whichever clients have data ready. Combined with `poll()` (taught by the `poll-loop` skill), this enables the event-driven model the subject requires.

**Relation to ft_irc:** MR-21 requires all I/O to be non-blocking. MR-20 prohibits forking (so you can't work around blocking with child processes). MR-22 requires one `poll()` for all I/O. MR-44/MR-45 restrict `fcntl()` on MacOS.

**Related MR IDs:**

- MR-21: All I/O operations must be non-blocking
- MR-20: Forking prohibited
- MR-22: One poll() for all I/O
- MR-23: No I/O without poll readiness (grade 0)
- MR-44: fcntl(fd, F_SETFL, O_NONBLOCK) allowed on MacOS
- MR-45: Any other fcntl flag forbidden on MacOS

**How to make a socket non-blocking:**

The standard approach uses `fcntl()`:

```
fcntl(fd, F_SETFL, O_NONBLOCK)
```

This sets the `O_NONBLOCK` flag on the file descriptor, making all I/O operations return immediately.

> **MacOS restriction (MR-44, MR-45):** On MacOS, `fcntl()` is explicitly permitted but *only* with `F_SETFL, O_NONBLOCK`. Any other `fcntl()` flag is forbidden. See Ambiguity A7 for non-MacOS interpretation.

**ASCII Diagram:**

```
  BLOCKING:                          NON-BLOCKING:

  recv(fd) ───────────────────►      recv(fd) ───► returns immediately
           waits for data...                        │
           waits...                                 ├── data? → return bytes
           waits...                                 ├── no data? → return -1
           data arrives → return                    │   (errno = EAGAIN)
                                                    └── client gone? → return 0

  NON-BLOCKING + POLL (ft_irc model):

  poll() ─── check all FDs ─── FD 4 ready ──── recv(4) → data
                                FD 5 not ready ── skip
                                FD 3 ready ──── accept() → new FD 6
  poll() ─── check all FDs ─── FD 5 ready ──── recv(5) → data
                                FD 6 ready ──── recv(6) → data
```

**Which sockets must be non-blocking:**

| Socket | Must be non-blocking? | Why |
| --- | --- | --- |
| Listening socket (FD 3) | Yes | `accept()` must not block (MR-21) |
| Every client socket (FD 4, 5, ...) | Yes | `recv()` and `send()` must not block (MR-21) |

**All** file descriptors must be non-blocking. MR-21 says "all I/O operations."

**Common mistakes:**

- Making the listening socket non-blocking but forgetting client sockets. All FDs must be non-blocking (MR-21).
- Forgetting to make the FD returned by `accept()` non-blocking. The new client FD inherits some properties but you should explicitly set non-blocking mode.
- Using `fcntl()` with flags other than `F_SETFL, O_NONBLOCK` on MacOS. Forbidden (MR-45).
- Calling `recv()`/`send()` without `poll()` readiness after setting non-blocking mode. Non-blocking makes the call possible without blocking, but MR-23 still requires poll readiness — violating this is grade 0.
- Treating `EAGAIN`/`EWOULDBLOCK` as an error. It simply means "try again later" — it is the normal non-blocking behavior when no data is available.

**Evaluation notes:**

- Evaluators will specifically check that all I/O is non-blocking (MR-21).
- `fcntl()` flags will be checked on MacOS (MR-44, MR-45).
- I/O without poll readiness = grade 0 (MR-23), even with non-blocking sockets.

## Implementation Thinking

This section answers the "why" questions about the socket call sequence without writing production code.

### Why does socket() come first?

Because every other call needs a file descriptor. You cannot bind, listen, or accept without first having a socket. `socket()` creates the raw communication endpoint.

### Why is bind() required?

Without `bind()`, the socket has no address or port. Clients would have no way to reach it. `bind()` assigns the port from the command line (MR-03) so that the socket is reachable.

### Why does listen() come after bind()?

`listen()` tells the OS "I am ready to accept connections on this address." The address must exist first (via `bind()`). You cannot listen on an unbound socket.

### Why does accept() create a new file descriptor?

Because the listening socket's job is to accept connections, not to communicate. If `accept()` reused the listening socket, the server could only serve one client at a time. The new FD provides a dedicated channel for each client, while the listening socket remains open for future connections.

### Why does the listening socket remain open?

Because the server must accept new clients for its entire lifetime. Closing the listening socket would prevent any new connections. The listening socket is closed only at server shutdown.

### Why does every client get a different file descriptor?

Because each client connection is independent. The OS uses file descriptors to track which bytes belong to which connection. If two clients shared an FD, their data would mix. Separate FDs guarantee isolation.

### Why may recv() return partial data?

Because TCP is stream-oriented (as taught by the `tcp-ip` skill). TCP delivers bytes, not messages. The OS gives you whatever bytes have arrived so far — which may be part of a message, a full message, or multiple messages. The server must buffer and look for `\r\n` to find complete IRC messages (MR-43).

### Why may send() not send everything?

Because the OS kernel's send buffer has limited space. If the buffer is full (e.g., the client is slow to read), `send()` copies only what fits and returns the count. The server must send the remainder later, after poll signals the FD is ready for writing again.

Ila port deja msta3ml, bind() ghadi tfchel. Hadchi 3lach setsockopt(SO_REUSEADDR) mohim qbl bind().

# ASCII Diagram

    └─────────────┘            │ State: bound          │
                                └────────────────────┘

# Common Mistakes

- Forgetting htons() for the port number. The port will be wrong and clients cannot connect.
- Not checking bind()'s return value. "Address already in use" is the most common bind failure.
- Hardcoding the port instead of reading it from argv (MR-03).
- Calling bind() before socket(). The FD must exist first.

# Evaluation Notes

- Evaluators will check that the server uses the port from the command line (MR-03).
- The server must handle bind() failure gracefully (MR-15, MR-16).

# What We Will Learn Next

After binding, the socket needs listen() to start accepting connections.

### Example 3: Why does accept() return another file descriptor?

**User:**

```text
@sockets
Why does accept() return another file descriptor?
```

**Response:**

```markdown
# Concept

accept() — Creating Per-Client Sockets

# Purpose

accept() takes a pending connection from the listening queue and creates a NEW socket — a new file descriptor — for that specific client. The listening socket remains open to accept future connections.

# Relation to ft_irc

MR-19 requires handling multiple clients simultaneously. This is only possible because accept() creates a separate FD for each client. If accept() reused the listening FD, only one client could connect at a time.

Classification: Mandatory Requirement

# Related MR IDs

- MR-19: Handle multiple clients simultaneously without hanging
- MR-18: TCP/IP communication

# Internal Behavior

1. A client sends a TCP SYN to the server's port.
2. The OS completes the three-way handshake and queues the connection.
3. Your code calls accept(listening_fd, ...).
4. The OS dequeues one pending connection.
5. The OS creates a NEW socket with a new FD number (e.g., 4).
6. accept() returns this new FD.
7. The listening socket (FD 3) is UNCHANGED — still listening.
8. You use recv(4, ...) and send(4, ...) to talk to this specific client.

# Darija Explanation

accept() b7al receptionniste f hotel. Ila wa7d jdid ja, receptionniste kayt-3tih chambre (FD jdid). Receptionniste (listening socket) kayb9a f blastou y-accueilli clients khorin.

3lach FD jdid? Hit kol client khasso communication privée dyalo. Ila client A w client B kaykhdmo nfs FD, data dyalhom ghadi ttkhlat. FD séparés kay-guarantiw isolation.

Listening socket (FD 3) ma kayt-bddlch — kayb9a y-accepti clients jdad. Client sockets (FD 4, 5, 6...) kaytkhel9o b accept() w kaytsddo b close() mli client ymchi.

# ASCII Diagram

    Listening Socket (FD 3)
    │
    │ Client A connects → accept() → returns FD 4
    │ Client B connects → accept() → returns FD 5
    │ Client C connects → accept() → returns FD 6
    │
    │ FD 3 is STILL listening!
    │
    ├── FD 4: recv/send with Client A
    ├── FD 5: recv/send with Client B
    └── FD 6: recv/send with Client C

    If Client B disconnects:
    close(5)     ← FD 5 is freed
    FD 3, 4, 6 continue normally

# Common Mistakes

- Closing the listening socket (FD 3) after the first accept(). This prevents any future connections.
- Not making the new client FD non-blocking. MR-21 requires ALL I/O to be non-blocking — including the new client socket.
- Calling accept() without poll() readiness. Grade 0 (MR-23).
- Forgetting to store the new FD. Without tracking it, you lose the connection and leak the FD.

# Evaluation Notes

- Evaluators will connect multiple clients to test MR-19.
- accept() without poll readiness = grade 0 (MR-23).
- New client FDs must be set to non-blocking (MR-21).

# What We Will Learn Next

After accept() creates client sockets, you need an event loop (poll) to monitor all FDs for readiness and decide when to call recv() and send() on each one.

# Recommended Next Skill

`poll-loop` — for the event loop that ties everything together. Verify with @roadmap that you have reached Phase 5.
```

### Example 5: Why can recv() return only part of a message?

**User:**

```text
@sockets
Why can recv() return only part of a message?
```

**Response:**

```markdown
# Concept

recv() and Partial Data

# Purpose

recv() reads whatever bytes are currently available in the kernel's receive buffer — which may be less than a complete IRC message. TCP is stream-oriented and does not preserve message boundaries.

# Relation to ft_irc

MR-43 explicitly requires handling partial data: "aggregate received packets to rebuild complete commands." This is the single most tested behavior in ft_irc evaluation.

Classification: Mandatory Requirement

# Related MR IDs

- MR-43: Handle partial data — buffer and aggregate
- MR-23: No recv without poll readiness (grade 0)

# Internal Behavior

1. The client sends "NICK alice\r\n" — but TCP may split this into multiple packets.
2. Packets arrive at the OS kernel at different times.
3. When you call recv(), the OS gives you whatever is in the buffer RIGHT NOW.
4. If only "NICK al" has arrived, recv() returns 6 bytes.
5. The remaining "ice\r\n" arrives later, returned by a future recv().

This is not a bug — it is how TCP works. The tcp-ip skill explains WHY (stream orientation). This skill explains the consequence for recv().

# Darija Explanation

recv() ma kayt-sennach 7ta message tkml. Kayrjj3 lik dak bytes li kaynin f buffer daba. Ila client b3t "NICK alice\r\n" walakin TCP qssem had data l jouj packets, recv() dial lwel ghadi yrjj3 "NICK al" bssah, w recv() dial tani ghadi yrjj3 "ice\r\n".

Had comportement machi bug — hadchi howa TCP. 3lach subject gal lazem t-bufferi data (MR-43). Kol client khasso buffer dyalo, w nta kat-accumuler bytes 7ta tlqa \r\n. Ghir dak sa3a 3ndk command complète.

Subject 3ta test spécifique: b nc -C kat-b3t "com" w "man" w "d\n" séparément. Server khasso y-reconstituia "command\n" mn had les fragments.

# ASCII Diagram

    Client sends:              Server recv() calls:

    "NICK alice\r\n"           recv 1: "NICK al"     ← partial!
                                recv 2: "ice\r\n"     ← rest arrives

    OR:

    "NICK alice\r\n"           recv 1: "NICK alice\r\nUSER..."  ← multiple!
    "USER alice 0 * :A\r\n"   (both messages in one recv!)

    Your buffer must handle BOTH scenarios:
    ┌──────────────────────────────────┐
    │ Buffer: "NICK al"                │ ← after recv 1, no \r\n found
    │ Buffer: "NICK alice\r\n"         │ ← after recv 2, \r\n found!
    │ → Extract "NICK alice\r\n"      │
    │ → Buffer now empty               │
    └──────────────────────────────────┘

# Common Mistakes

- Assuming each recv() returns exactly one complete message. Almost never true under load.
- Not buffering per client. Without per-client buffers, partial data is lost.
- Processing data before \r\n is found. This produces broken commands.
- Discarding leftover bytes after extracting one message. The buffer may contain the start of the next message.

# Evaluation Notes

- Evaluators specifically test partial data using the nc test from the subject (MR-43).
- This is one of the most common failure points in ft_irc evaluation.

# What We Will Learn Next

Buffering and extracting complete messages is the parser's job. This skill teaches why recv() behaves this way; the parser skill teaches how to handle it.

# Recommended Next Skill

`parser` — for implementing per-client buffering and message extraction (Phase 7).
```

### Example 6: When should I close a socket?

**User:**

```text
@sockets
When should I close a socket?
```

**Response:**

```markdown
# Concept

close() — Socket Cleanup

# Purpose

close() releases a file descriptor and its associated resources. It must be called when a client disconnects and when the server shuts down.

# Relation to ft_irc

MR-15 and MR-16 require the server to never crash or quit unexpectedly. Failing to close sockets leaks resources, eventually causing the server to crash when it runs out of file descriptors.

Classification: Mandatory Requirement

# Related MR IDs

- MR-15: Program must not crash
- MR-16: Program must not quit unexpectedly

# Internal Behavior

1. The OS marks the FD as closed.
2. Any pending data may be flushed or discarded (depends on socket options).
3. The FD number becomes available for reuse.
4. If the FD was in the poll set, it must be removed BEFORE or AFTER close (implementation detail for poll-loop skill).

# Darija Explanation

close() khassha ttwqer f jouj situations:

1. Client disconnecta (recv() rjj3 0): tsdd FD dial had client, t-supprimi mn poll set, w t-nettoyi ay data dyalo.

2. Server kayt-arret: tsdd kol client FDs, w mn b3d tsdd listening socket.

Ila ma tsdditech sockets, FDs ghadi y-leakiw. OS 3ndo limite (matal 1024 FD). Ila wsslti l limite, accept() ghadi tfchel w server ghadi ycrashi (MR-15).

# ASCII Diagram

    When to close:

    1. Client disconnect:
       recv(fd4) → returns 0
       │
       ├── Remove FD 4 from poll set
       ├── Clean up client data
       └── close(4)

    2. Server shutdown (e.g., SIGINT):
       │
       ├── close(fd4)    ← client A
       ├── close(fd5)    ← client B
       ├── close(fd6)    ← client C
       └── close(fd3)    ← listening socket (LAST)

    3. Error during setup:
       socket() → success (FD 3)
       bind() → FAILS
       │
       └── close(3)     ← clean up before exit

# Common Mistakes

- Not closing client sockets when they disconnect. FD leak → eventual crash (MR-15).
- Closing the listening socket when any client disconnects. Only close it at shutdown.
- Using a socket after closing it. Undefined behavior.
- Double-closing a socket. Also undefined behavior.
- Not removing the FD from the poll set before/after closing. poll() may report errors on closed FDs.

# Evaluation Notes

- Evaluators may test disconnection handling extensively.
- Server must not crash when clients disconnect unexpectedly (MR-15, MR-16).
- Resource leaks may cause failures during long evaluation sessions.

# What We Will Learn Next

Proper cleanup integrates with the event loop — the poll-loop skill teaches how to manage the poll set when FDs are added or removed.

# Recommended Next Skill

`poll-loop` — for event loop integration of socket lifecycle.
```
