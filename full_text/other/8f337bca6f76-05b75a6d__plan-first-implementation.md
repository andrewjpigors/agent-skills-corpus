# 플랜 퍼스트 구현

이 스킬은 `문서 먼저, 구현 나중`을 강하게 적용할 때 쓴다. 계획 문서가 이번 단계의 source of truth이고, 구현 가능한 작업에서는 계획 문서가 사용자가 열어보고 판단할 검토용 결과물과 테스트 링크로 이어지는 상위 인덱스 역할을 한다.

실행 경계: 이 스킬은 계획 문서 작성, 계획 보강, 검토용 결과물 준비, 후행 실행 단위 명시까지만 담당한다. 승인된 계획의 실제 구현 패치는 이 스킬이 직접 하지 않는다. 후행 실행은 반드시 `구현커밋`으로 넘긴다. 계획 MD 경로는 기본적으로 `구현커밋`이 직전 대화, 계획 문서 링크, 현재 repo의 active plan context에서 자동 탐지한다.

중요한 새 기본값: 이 스킬로 작성하거나 보강하는 모든 계획 MD에는 `## Skill Routing Manifest`가 있어야 한다. 이 계획 문서는 다음 단계에서 `구현커밋`의 실행 원본이 될 수 있으므로, 구현 가능한 계획 MD는 사람이 읽기 좋은 설명만으로 끝나면 안 되고, `구현커밋`이 Codex Flow 런타임에서 ticket과 queue로 뽑을 수 있는 명확한 실행 heading을 가져야 한다.

전역 스킬셋 안에서 이 스킬은 `주력 계획 스킬`로 취급한다. 유지 기준과 다른 계획 스킬과의 관계는 로컬 Codex skills README 또는 팀의 스킬 운영 문서를 참고한다.

## 언제 쓸까

- 사용자가 plan first를 원한다.
- 큰 수정이라 근거와 범위를 먼저 잠가야 한다.
- 구현 전에 파일 관계와 리스크를 시각화해야 한다.
- 계획 MD만 만들면 실행 가능한 결과물이 남지 않는 작업이다.
- 화면, 흐름, 상태, 인터랙션, 작은 기능을 HTML로 먼저 구체화해야 하는 작업이다.

## 실행 경계와 후행 스킬

- plan-first는 계획 문서 작성, 보강, 검토용 결과물 준비, 후행 실행 단위 명시까지만 담당한다.
- 승인된 계획을 실제 코드 패치로 실행하는 후행 스킬은 반드시 `구현커밋`이다.
- 사용자가 `이 계획대로 구현`, `다음 실행`, `모두 실행`처럼 말하면 이 스킬 안에서 패치를 시작하지 말고 `구현커밋`으로 넘긴다.
- 계획 MD 경로를 매번 요구하지 않는다. `구현커밋`이 직전 plan-first 산출물, 대화창 링크, 현재 repo의 active plan을 먼저 자동 탐지해야 한다.
- 후보가 없거나 둘 이상이면 그때만 후보 목록을 보여주고 Operator에게 고르게 한다.
- Codex Flow는 사용자가 직접 호출할 후행 스킬명이 아니라 `구현커밋`의 런타임/queue 구현으로 취급한다.
- 최종 답변이나 계획 문서에는 `후행 실행: 구현커밋`을 남긴다. 명시 경로는 자동 탐지가 애매할 때만 보조 정보로 붙인다.
- 이 자동 탐지 계약을 바꾸는 계획에는 `구현커밋/SKILL.md` 업데이트를 구현 대상에 포함한다.

## 에디터/문서 주석 경계

- 에디터 인라인 메모, 문서 안 주석, Codex App comment UI는 앱 기능이다. 이 스킬이 그 UI 동작을 구현하거나 흉내 내지 않는다.
- 다만 Operator가 주석이 달린 계획 문서나 메모를 다시 보내면, 그 메모를 계획 근거로 반영하고 문서를 갱신한다.
- 이 경우에도 Operator가 명시적으로 구현을 승인하기 전에는 `구현커밋`으로 넘기거나 코드 패치를 시작하지 않는다.

## 검토물 판정 게이트 (Review Artifact Gate)

계획 문서를 쓰기 전에 이번 요청에서 사용자가 무엇을 열어보고 판단해야 하는지 먼저 분류한다. 이 판정은 계획 문서의 `## 검토용 결과물` 섹션과 최종 답변에 그대로 반영한다.

| 요청 유형 | 기본 검토용 결과물 | HTML 생략 가능 여부 |
| --- | --- | --- |
| `계획만`, `문서만`, 조사/리뷰/백엔드/보안/운영 계획 | 계획 MD | 가능. 단, `검토용 결과물` 섹션에 생략 사유를 남긴다. |
| 화면, 흐름, 상태, 인터랙션, 폼, 대시보드, 목업, UX 비교 | 계획 MD + HTML artifact | 원칙적으로 불가. |
| 디자인 변경, 색상 토큰, 레이아웃, 시각 상태, 컴포넌트 규칙 변경 | 계획 MD + HTML mock/specimen + 후속 앱 구현 계획 | 불가. 기존 앱을 고치는 경우에도 먼저 사용자가 볼 HTML 검토물이 필요하다. |
| 기존 앱 화면 직접 수정 중 디자인 판단이 거의 없고 동작/버그 수정이 중심인 경우 | 계획 MD + dev server URL | HTML demo는 생략 가능하나 대체 URL과 생략 사유는 필수다. |
| 기존 앱 수정 전 독립 검토가 필요한 UI | 계획 MD + HTML artifact + 후속 앱 구현 계획 | 불가. |
| CLI, API, DB, 서버 로직 중심 | 계획 MD + 검증 명령/로그 | 가능. |

화면, 흐름, 상태, 인터랙션이 포함된 요청은 사용자가 명시적으로 `계획만`이라고 하지 않는 한 `계획 후 구현`으로 본다. 이때 단일 HTML artifact 또는 실행 중인 앱 URL 중 하나는 반드시 최종 답변에 있어야 한다.

디자인 변경 판정은 기존 앱 직접 수정 판정보다 우선한다. 색상, 간격, 타이포, 상태 칩, 표본화된 컴포넌트, 화면 구성, UX 비교처럼 사용자가 눈으로 보고 피드백해야 하는 작업은 기존 앱 파일을 고칠 예정이어도 HTML mock/specimen을 생략하지 않는다. dev server URL은 후속 검증 링크이지, 디자인 검토용 HTML의 대체물이 아니다. 단, 사용자가 명시적으로 `목업 생략`, `바로 앱에 적용`, `계획만`이라고 말한 경우에만 HTML 생략을 고려한다.

## 검토용 결과물 계약 (Review Artifact Contract)

기본 검토용 결과물은 한 장짜리 계획 파일이 아니라 아래 계층이다.

1. 상위 계획 MD
   - 이번 작업의 source of truth다.
   - 범위, 근거, 리스크, 검증, 구현 순서, 관련 파일을 담는다.
   - 검토용 결과물 링크를 반드시 가진다.
2. HTML 검토물
   - 계획이 다루는 실제 기능, 화면, 흐름, 상태 변화를 작게라도 실행 가능하게 만든다.
   - 새 프로젝트나 독립 프로토타입이면 `docs/plans/artifacts/<plan-slug>.html` 또는 계획 문서 옆의 `<plan-slug>.html`에 둔다.
   - 기존 앱 코드가 주 구현 대상이어도 디자인 변경이면 HTML mock/specimen을 먼저 만든다. 실제 앱 파일과 dev server URL은 사용자가 HTML 검토물을 승인한 뒤 `구현커밋`이 적용/검증할 단계다.
   - 동작 버그 수정처럼 디자인 판단이 거의 없는 경우에만 후행 `구현커밋` 이후의 실제 앱 파일과 dev server URL을 검토용 결과물로 둘 수 있다.
3. 계획 MD의 참조 링크
   - 계획 문서 안에 `## 검토용 결과물` 섹션을 만들고 HTML 파일을 상대 링크로 건다.
   - 예: `- [HTML 기능 초안](artifacts/2026-05-10-feature-slice.html)`
4. 대화창 검토 링크
   - 검토물이 준비되면 최종 답변에도 사용자가 바로 누를 수 있는 링크를 보낸다.
   - 계획 MD 안의 링크만으로 끝내지 않는다.
   - 단일 HTML이면 현재 작업 저장소 기준으로 열 수 있는 파일 경로 링크를 쓴다. 예: `[HTML 기능 초안](docs/plans/artifacts/demo.html)`
   - dev server가 필요한 앱이면 서버를 실행한 뒤 URL을 쓴다. 예: `[로컬 미리보기](http://localhost:5173/path)`
5. 대화창 테스트 링크
   - 최종 답변에는 `테스트 링크:`를 반드시 포함한다.
   - 로컬호스트 확인이 필요한 작업이면 실행 중인 localhost/127.0.0.1 URL을 넣는다.
   - 배포 환경이 있으면 preview, staging, production 중 사용자가 확인해야 하는 배포 URL을 함께 넣는다.
   - 로컬 서버를 켤 수 없거나 배포 환경을 찾지 못하면 링크를 비워두지 말고 이유와 실행 명령 또는 확인한 사실을 적는다.

사용자가 명시적으로 `계획만` 원하면 HTML을 만들지 않는다. 그 대신 계획 문서의 `검토용 결과물` 섹션에 어떤 HTML을 만들지와 왜 지금 생략하는지를 적는다.

## Operator 결정 게이트 (Operator Decision Gate)

계획 문서를 쓰기 전에 사용자가 직접 결정해야만 하는 사항을 분류한다. 이 분류는 계획 문서의 `## Operator 결정 필요 사항` 섹션과 최종 답변의 `Operator 결정 필요 사항:` 블록에 그대로 반영한다.

결정 필요 여부는 아래 기준으로 나눈다.

- `없음`: Codex가 기존 코드 패턴, 좁은 범위, 되돌리기 쉬운 변경, 검증 가능한 기본값으로 진행할 수 있다.
- `필요`: 보안, 계정, 결제, 공개 발행, production deploy, 파괴적 변경, 큰 UX 방향, 작업 범위 확대, 되돌리기 어려운 브랜드/콘텐츠 방향처럼 Operator가 직접 골라야 한다.
- `보류됨`: 결정이 필요하지만 이번 계획/구현 범위 밖으로 빼도 현재 단계가 깨지지 않는다. 이 경우 임시 기본값과 보류 시 영향을 함께 쓴다.

각 결정은 반드시 아래 필드를 가진다.

- 결정 제목
- 맥락
- A/B/C 선택지
- 추천안
- 기본값
- 보류 시 영향

`기본값`은 Operator가 별도로 선택하지 않았을 때 실제로 진행할 선택이다. 따라서 일반적인 선택에서는 반드시 `추천안`과 같은 선택지를 써야 한다. 추천안과 기본값을 다르게 두지 않는다.

예외는 hard stop뿐이다. 결제, production deploy, 공개 발행, 파괴적 변경처럼 Operator 승인이 없으면 진행하면 안 되는 선택에서는 `기본값: 없음. Operator 승인 전 진행하지 않음`으로 쓴다.

`mission-completion-harness`처럼 Codex가 중간 선택을 대신 처리하는 흐름에서도 이 게이트는 유지한다. 다만 안전한 기본값으로 진행 가능한 선택은 `상태: 없음` 또는 `상태: 보류됨`으로 처리하고, hard stop 성격의 선택만 `상태: 필요`로 남긴다.

## 핵심 흐름 (Core Flow)

1. 검토물 판정 게이트로 이번 요청이 `계획만`, `계획 후 구현`, `HTML 필수`, `앱 URL 대체`, `HTML 생략 가능` 중 어디에 해당하는지 먼저 정한다.
2. 기존 계획 문서가 있으면 이어서 쓰고, 없으면 새 상위 계획 MD를 만든다.
3. 관련 코드와 문서를 읽어 현재 동작, 변경 지점, 검증 표면을 정리한다.
4. 비사소한 구현, 새 기능, 통합, 큰 리팩터처럼 계획의 근거가 부족하면 먼저 `research`를 사용해 코드베이스, 문서, 외부 근거, 커뮤니티/디자인 패턴을 Research Brief로 정리한다.
5. Operator 결정 게이트로 사용자가 직접 결정해야 하는 항목과 Codex가 기본값으로 처리할 항목을 분리한다.
6. 디자인, UX, 카피, 정보 구조처럼 방향 선택이 필요한 작업이면 계획 문서를 쓰기 전에 짧은 질문으로 방향을 잠근다. 질문은 한 번에 하나씩 하고, 사용자가 바로 고를 수 있는 A/B/C 선택지, 추천안, 기본값, 보류 시 영향을 제공한다.
7. 계획 문서에 범위, 근거, 리스크, 검증, 구현 순서, 관련 파일, 코드 스니펫, 트레이드오프, `검토용 결과물`, `Operator 결정 필요 사항`, `구현 후 검토 리스트` 섹션을 적는다.
8. 모든 plan-first 계획 문서에 `## Skill Routing Manifest` 표를 만든다. 이 표는 계획 작성자, 구현자, 검토자가 어떤 스킬을 반드시 읽고 적용해야 하는지 확인하는 라우팅 계약이다.
9. `구현커밋`으로 실행될 수 있는 계획이면 `## Implementation Plan` 아래에 `### Commit N:` 또는 `### Phase N:` heading을 만든다. 단순 번호 목록이나 큰 bullet만 남기지 않는다.
10. 주석이 달린 계획 문서나 Operator 메모가 돌아오면 문서만 갱신한다. Operator가 구현을 명시적으로 승인하기 전에는 패치를 시작하지 않는다.
11. 문서가 구현 직전 수준으로 준비됐을 때만 HTML 검토물 또는 후행 `구현커밋` 핸드오프로 넘어간다.
12. `계획 후 구현`이고 디자인 판단이 있으면 HTML 검토물을 먼저 만든다.
13. 기존 앱 직접 수정이 후행 검토 표면이라면 `구현커밋` 이후 확인할 dev server URL을 계획 문서와 최종 답변의 테스트 링크 후보로 연결한다.
14. HTML을 만들지 않았다면 `HTML 생략 보고서`를 계획 문서와 최종 답변에 남긴다.
15. HTML 또는 앱 URL이 이미 생성/실행된 경우 브라우저에서 열 수 있는지, 중요한 인터랙션이 실제로 동작하는지 검증한다.
16. 최종 답변에 `검토 링크:`, `테스트 링크:`, `Operator 결정 필요 사항:`, `후행 실행:`을 넣고, 사용자가 대화창에서 바로 열 수 있는 HTML 파일 링크, 실행 중인 dev server URL, 확인 가능한 배포 URL, 바로 고를 수 있는 결정 선택지를 제공한다. `후행 실행:`은 기본적으로 `구현커밋`만 적고, 경로는 자동 탐지가 애매할 때만 덧붙인다.

## 구현커밋 실행 문서 계약 (Implementation Commit Execution Document Contract)

모든 plan-first 계획 MD에는 `## Skill Routing Manifest`를 포함한다. 계획 MD가 구현으로 이어질 수 있거나, 사용자가 이후 `구현커밋`으로 실행할 가능성이 있으면 Commit/Phase heading까지 함께 적용한다.

`구현커밋`은 내부적으로 Codex Flow 런타임을 사용해 plan-first Markdown 문서에서 아래 heading을 찾아 실행 단위로 뽑을 수 있다.

- `### Commit N: <작고 커밋 가능한 작업 이름>`
- `### Phase N: <조사, 문서, 검증처럼 커밋보다 넓은 실행 단계 이름>`

`## Skill Routing Manifest`는 실행자와 검토자가 각 Commit/Phase 또는 문서 단계에서 어떤 스킬을 실제로 읽고 적용해야 하는지 알려주는 라우팅 계약이다. 사람이 보기 좋은 권장 목록이 아니라 계획 문서의 source of truth로 취급한다. `구현커밋`으로 실행되는 문서에서는 Codex Flow 실행 프롬프트에 들어갈 실행 계약으로 취급한다.

Codex Flow는 후행 스킬명이 아니라 `구현커밋`의 런타임 명이다. 사용자-facing 후행 실행 스킬은 `구현커밋`이다.

`구현커밋`은 plan-first 산출물을 자동 탐지해야 한다. plan-first 계획이 `구현커밋` 입력 계약이나 자동 탐지 규칙을 바꾸면, 그 계획의 `## Implementation Plan`에는 `구현커밋/SKILL.md` 수정 단위를 포함한다.

필수 형식:

```md
## Skill Routing Manifest

| Phase | Required skills | Optional skills | Evidence |
| --- | --- | --- | --- |
| Commit 1: <작업 이름> | `<필수 스킬>` | `<선택 스킬>` | <왜 이 스킬이 필요한지와 확인할 근거> |
| Final Gate | `review-all-in-one`, `qa-gate` | `테스트` | <최종 검토와 검증 근거> |
```

Manifest 작성 규칙:

- `Phase` 값은 `## Implementation Plan`의 `### Commit N:` 또는 `### Phase N:` 제목과 번호, 의미가 일치해야 한다.
- 계획만, 검토만, 문서 보강처럼 `## Implementation Plan`이 없는 계획에서도 Manifest는 생략하지 않는다. 이 경우 `Phase`에는 `Plan Draft`, `Review Pass`, `Final Gate`처럼 문서 단계 이름을 쓰고, Evidence에 구현 실행 단위가 없는 이유를 적는다.
- `Required skills`에는 해당 실행 단위를 완료하려면 반드시 읽고 적용해야 하는 스킬만 적는다.
- `Optional skills`에는 상황이 맞을 때만 추가로 쓰는 스킬을 적는다. 비워 두지 말고 없으면 `없음`이라고 쓴다.
- `Evidence`에는 그 스킬을 왜 넣었는지, 어떤 파일/테스트/검토 표면을 근거로 볼지 적는다.
- plan-first 계획에서 이 표가 없으면 계획 완료 또는 구현 직전 수준으로 보지 않는다.
- Commit/Phase를 추가, 삭제, 이름 변경하면 manifest도 같은 턴에 갱신한다.

작성 규칙:

- 구현 패치는 기본적으로 `### Commit N:`을 쓴다.
- 조사, 검토, 문서 보강, 배포 준비처럼 실제 코드 커밋으로 바로 묶기 애매한 실행은 `### Phase N:`을 쓴다.
- 각 Commit/Phase는 한 번에 실행할 수 있을 만큼 작아야 한다.
- 각 Commit/Phase에는 대상 파일, 변경 내용, 검증 방법, 성공 기준, 중단 조건을 넣는다.
- 각 Commit/Phase에는 판단에 필요한 코드 스니펫과 핵심 트레이드오프를 넣는다. 필요 없으면 `코드 스니펫: 필요 없음`처럼 이유를 적는다.
- Commit/Phase 제목 없이 `1.`, `Step 1`, `작업 목록`, 큰 bullet만 남기면 Codex Flow가 low-confidence로 판단할 수 있다.
- low-confidence 계획은 Codex Flow에서 `human_gate`로 멈춘다. 즉 자동 실행되지 않고, 사람이 문서를 더 작게 나눠야 한다.

좋은 실행 단위 예:

```md
## Implementation Plan

### Commit 1: 구현커밋 source contract를 plan-first Markdown 전용으로 고정

- 대상 파일:
  - `codex_flow/cli.py`
  - `tests/test_route_plan_first_source.py`
- 변경:
  - `route`가 짧은 자연어 요청을 받으면 실패 안내를 출력한다.
  - 명시 경로, 직전 계획 링크, active plan context에서 단일 plan-first Markdown source가 확정될 때만 새 실행 queue를 만든다.
- 검증:
  - `python3 -m pytest tests/test_route_plan_first_source.py`
- 성공 기준:
  - 짧은 요청은 ticket/plan을 만들지 않는다.
  - 단일 source가 자동 탐지되면 Operator에게 경로를 다시 요구하지 않는다.
  - Markdown source는 `source-plan.md`, `source.json`, `queue.json`을 만든다.
- 중단 조건:
  - 기존 public command가 이 입력 계약에 의존하고 있으면 계획을 재검토한다.

### Commit 2: Source drift와 human_gate 안전장치 추가

- 대상 파일:
  - `codex_flow/source_plan.py`
  - `codex_flow/runner.py`
- 변경:
  - 원본 문서 hash가 달라지면 `source_drift`로 멈춘다.
  - Commit/Phase heading이 없는 문서는 `human_gate`로 멈춘다.
- 검증:
  - `python3 -m pytest tests/test_route_plan_first_source.py`
- 성공 기준:
  - 변경된 원본과 넓은 문서가 자동 실행되지 않는다.
- 중단 조건:
  - 실행자가 기준본과 현재 원본 중 무엇을 따라야 하는지 불명확하면 멈춘다.
```

나쁜 예:

```md
## 구현 순서

1. route를 고친다.
2. 테스트를 추가한다.
3. 문서를 정리한다.
```

위 예시는 사람이 대충 이해할 수는 있지만 Codex Flow가 안정적으로 ticket과 queue를 만들기에는 너무 흐리다. 이런 문서는 실행 원본으로 넘기기 전에 `### Commit N:` 또는 `### Phase N:`로 다시 써야 한다.

## Plan Quality Check

계획 문서를 쓴 뒤, 후행 실행으로 넘기기 전에 계획 자체가 문제를 좁히거나 약하게 만들지 않았는지 확인한다.

계획 MD에는 아래 항목을 짧게 남긴다.

- Alternative considered: 검토했지만 채택하지 않은 접근과 이유
- Why this plan: 이 계획을 선택한 핵심 근거
- Tradeoff: 이 선택으로 얻는 것, 잃는 것, 감수 가능한 이유
- What this plan may still miss: 이 계획이 놓칠 수 있는 부분
- When to stop and revise: 어떤 증거가 나오면 계획을 멈추고 다시 볼지

이 체크는 새 판정 게이트가 아니다. 이미 정한 범위 안에서 계획의 사고 품질을 점검하는 단계다.

## 코드 스니펫과 트레이드오프

- 코드 스니펫은 전체 구현이 아니라 판단에 필요한 짧은 예시다.
- API shape, schema, data contract, selector, state transition, migration, error handling처럼 말로만 쓰면 오해하기 쉬운 부분에 스니펫을 둔다.
- 각 스니펫은 대상 파일/함수/API와 연결하고, 실제 적용 코드인지 illustrative/proposed 예시인지 표시한다.
- 긴 파일 전체를 붙이지 않는다. 필요한 줄 또는 작은 함수 조각만 남긴다.
- 트레이드오프는 `채택안`, `대안`, `비용/리스크`, `감수 이유`, `재검토 조건`을 포함한다.
- 트레이드오프가 없다고 판단하면 `의미 있는 대안 없음`이라고 쓰고, 왜 대안이 약한지 한 줄로 설명한다.

## 구현 후 검토 리스트

계획 문서에는 todo list를 필수 산출물로 요구하지 않는다. 대신 구현이 모두 끝난 뒤 확인할 `## 구현 후 검토 리스트`를 둔다.

리스트에는 아래 항목을 짧게 남긴다.

- 회귀 확인: 기존 동작 중 깨지면 안 되는 부분
- 검증 확인: 실행할 테스트, 브라우저 확인, 로그 확인, 배포 전 확인
- 리뷰 관점: 구현 후 `review-all-in-one`, `review-swarm`, `qa-gate`가 봐야 할 위험
- Operator 재확인: 구현 후 사용자가 눈으로 보거나 선택해야 할 항목

## 구현 직전 완료 정의 (Implementation-Ready Definition)

계획은 다른 Codex가 추가 질문 없이 바로 패치할 수 있을 때만 구현 직전 수준으로 본다.

완료 전 self-check:

- 대상 파일, 대상 함수/selector/API, 변경 순서, 유지할 동작, 검증 명령/URL, 커밋 단위, 성공 기준이 명시되어 있다.
- `## Skill Routing Manifest`가 있고, 표의 Phase가 `## Implementation Plan`의 Commit/Phase heading 또는 문서 단계와 일치한다.
- `구현커밋`으로 실행될 수 있는 계획이면 `## Implementation Plan` 아래에 `### Commit N:` 또는 `### Phase N:` heading이 있다.
- 각 Commit/Phase는 대상 파일, 변경 내용, 검증, 성공 기준, 중단 조건을 가진다.
- Commit/Phase 없이 큰 bullet 목록만 남긴 계획은 구현 직전 수준으로 보지 않는다.
- 각 Commit/Phase에는 필요한 코드 스니펫, 핵심 트레이드오프, 후행 실행 방식이 있다.
- 계획 MD와 HTML artifact 또는 dev server 검토물이 같은 selector, breakpoint, copy, state 이름을 사용한다. 다르게 써야 하면 mapping 표를 둔다.
- 계획 MD의 `Plan Quality Check`가 대안, 선택 근거, 놓칠 수 있는 부분, 중단/수정 조건을 짧게라도 말한다.
- 계획 MD에 `## 구현 후 검토 리스트`가 있고, 구현 완료 뒤 확인할 회귀/검증/리뷰 항목이 적혀 있다.
- 계획 MD의 `Operator 결정 필요 사항`과 최종 답변의 `Operator 결정 필요 사항:` 블록이 같은 결정 제목, A/B/C 선택지, 추천안, 기본값, 보류 시 영향을 말한다.
- 계획에서 금지한 스타일, breakpoint, copy, interaction이 검토물에 들어가지 않았다.
- 보존해야 할 route, `href`, `mailto`, `tel`, `data-*`, storage key, API path, 기존 copy는 원문 또는 상수명 수준으로 적혀 있다.
- 검증 명령은 `무엇을 확인하는지`가 assertion 단위로 적혀 있다.

하나라도 비어 있거나 계획과 검토물이 충돌하면 완료로 보고하지 않는다. 먼저 계획이나 검토물을 수정한다.

## 근거 수집용 CLI 우선 규칙 (Evidence Collection CLI Priority)

- 파일 맵을 만들 때는 `fd`를 먼저 보고, 텍스트 근거를 모을 때는 `rg`를 먼저 쓴다.
- 구조화된 설정이나 워크플로 파일은 손으로 훑기보다 `yq`와 `jq`를 먼저 고려한다.
- 검증 명령은 임의 조합보다 repo의 `justfile` 유무를 먼저 확인한다.
- `bat`은 사람 눈으로 읽기 좋은 spot inspection에만 쓰고, 구조화 추출의 기본 도구로 쓰지 않는다.
- 자세한 매핑은 팀 또는 로컬 저장소의 CLI core tools reference 문서를 따른다.

## 보조 스크립트 (Helper Scripts)

- 관련 파일 후보를 빠르게 좁힐 때는 [scripts/collect_related_files.sh](scripts/collect_related_files.sh)를 사용한다.
- 기존 계획 문서의 누락 섹션과 얇은 섹션을 점검할 때는 [scripts/seed_plan_update.py](scripts/seed_plan_update.py)를 사용한다.
- 두 스크립트는 read-only 보조 도구다. 출력은 계획 근거 후보로만 쓰고, 실제 판단은 코드/문서 확인으로 확정한다.

## 꼭 남겨야 할 것 (Required Plan Contents)

- 범위와 구조: in-scope 시스템 그림, 바뀌는 파일, 유지해야 할 동작
- 판단 품질: `## Plan Quality Check`, 남은 미확정 사항
- 코드 예시: 실제 변경 의도를 보여 주는 짧은 코드 스니펫, illustrative/proposed 여부, 대상 파일/함수/API
- 트레이드오프: 채택안, 대안, 비용/리스크, 감수 이유, 재검토 조건
- 결정: `## Operator 결정 필요 사항`, 최종 답변의 대화창 선택지 블록
- 실행 기준: 구현 순서, 검증 방법, 성공 기준, 커밋 단위
- Skill Routing Manifest: 모든 plan-first 계획에서는 각 Commit/Phase 또는 문서 단계의 필수/선택 스킬과 근거를 담은 `## Skill Routing Manifest` 표
- 구현커밋 실행 단위: `### Commit N:` 또는 `### Phase N:` heading, 각 단위의 대상 파일, 검증, 성공 기준, 중단 조건
- 후행 실행: 승인 후 실제 구현은 `구현커밋`으로 넘기고, 계획 경로는 자동 탐지가 기본이라는 문구
- 구현 후 검토 리스트: 구현 완료 뒤 확인할 회귀, 검증, 리뷰, Operator 재확인 항목
- 검토물: `## 검토용 결과물`, 계획 MD에서 HTML/앱 URL로 가는 링크, 실제 동작과 mock의 구분
- 테스트 링크: 최종 답변의 `테스트 링크:` 한 줄, 필요한 localhost URL, 배포 환경이 있을 때 배포 URL
- 생략 보고: HTML을 만들지 않았다면 `HTML 생략 보고서`와 최종 답변의 `HTML 생략 사유:` 한 줄

## HTML 구현 기준 (HTML Artifact Criteria)

- HTML은 장식용 목업이 아니라 최소 기능 단위여야 한다.
- 버튼, 입력, 토글, 탭, 필터, 상태 변경처럼 계획의 핵심 행동은 실제 JavaScript로 동작하게 한다.
- 외부 빌드가 필요 없는 단일 HTML을 우선한다. 기존 앱 맥락이 더 중요하고 디자인 판단이 거의 없으면 repo의 프레임워크를 따르고 dev server URL을 검토 링크로 둔다.
- 데이터가 아직 없으면 작은 샘플 데이터를 HTML 안에 넣고 `mock`이라고 명시한다.
- 사용자가 inspect할 수 있게 레이아웃, 상태, 에러/빈 상태, 성공 상태 중 핵심 상태를 포함한다.
- 스타일은 과하게 꾸미기보다 기능 판단에 필요한 구조와 가독성을 우선한다.

## 계획 MD 템플릿과 참고 자료 (Plan MD Templates)

새 계획 문서는 [assets/plan-document-template.md](assets/plan-document-template.md)를 시작점으로 사용한다.

섹션별 작성 의도와 판단 기준이 필요하면 [references/plan-template.md](references/plan-template.md)를 읽는다. 실제 결과물의 밀도와 표현 예시는 [assets/sample-plan-output.md](assets/sample-plan-output.md)를 참고한다.

이 파일들은 이 SKILL.md와 같은 계약을 따라야 한다. 특히 `Tradeoff`, 코드 스니펫, `구현 후 검토 리스트`, `후행 실행: 구현커밋`, `구현커밋` 자동 탐지 기본값이 빠지면 템플릿을 최신 상태로 보지 않는다.

## 최종 답변 링크 규칙 (Final Answer Link Rules)

플랜퍼스트 흐름의 최종 답변에는 `검토 링크:`와 `테스트 링크:`를 반드시 넣는다. 정적 HTML이면 절대 경로 Markdown 링크를, dev server가 필요한 앱이면 실행 중인 로컬 URL을 쓴다. 계획만/문서만 작업처럼 테스트 표면이 없을 때도 `테스트 링크:`를 생략하지 말고, 링크가 없는 이유와 대체 검증 명령 또는 문서 링크를 적는다.

- 링크는 사용자가 대화창에서 바로 누를 수 있어야 한다.
- `테스트 링크:`에는 필요한 localhost/127.0.0.1 URL을 반드시 포함한다.
- 배포 환경이 있으면 `테스트 링크:`에 preview, staging, production 등 해당 배포 URL도 반드시 포함한다.
- 테스트 표면이 없는 계획/문서 작업이면 `테스트 링크:` 아래에 `해당 없음`과 대체 검증 수단을 적는다.
- 서버를 켤 수 없으면 실행 명령, 예상 URL, 막힌 이유를 함께 말한다.
- 배포 환경을 찾지 못했거나 아직 배포하지 않았다면 그 사실을 `테스트 링크:` 아래에 명시한다.
- 계획 문서 링크와 검토 링크를 둘 다 주되, 검토 링크를 먼저 둔다.
- HTML을 만들지 않았다면 최종 답변에 `HTML 생략 사유:`를 반드시 쓴다. 이 줄이 없으면 검토용 결과물 계약을 완료한 것으로 보지 않는다.

최종 답변에는 아래 항목을 우선 포함한다.

```md
- 계획 MD:
- 검토 링크:
- 테스트 링크:
- Operator 결정 필요 사항:
- 후행 실행: 구현커밋
- HTML 생략 사유: <생략하지 않았으면 `해당 없음`>
- 검증 상태:
```

`Operator 결정 필요 사항:`은 대화창에서 바로 고를 수 있게 쓰고, 결정할 항목이 없으면 `없음. 적용한 기본값: <기본값과 이유>`라고 쓴다.

## 가드레일 (Guardrails)

- 계획이 덜 끝났는데 습관적으로 구현부터 하지 않는다.
- 근거 없는 추측을 계획 문서에 사실처럼 적지 않는다.
- 사용자가 계획만 원하면 후행 실행으로 넘어가지 않는다.
- 사용자가 계획 실행을 승인하면 이 스킬에서 패치하지 않고 `구현커밋`으로 넘긴다.
- 계획 MD 경로를 매번 요구하지 않는다. 경로가 없으면 `구현커밋`이 직전 대화, 계획 링크, active plan context에서 단일 후보를 자동 탐지해야 한다.
- todo list를 plan-first의 필수 완료 산출물로 만들지 않는다. 구현 뒤 확인할 `구현 후 검토 리스트`를 남긴다.
- `계획 후 구현` 요청에서 계획 MD만 만들고 후행 실행 경계, 검토물, `구현커밋` 경로 없이 멈추지 않는다.
- HTML 검토물을 만들었다면 상위 계획 MD 링크를 빠뜨리지 않는다.
- HTML 검토물을 만들었다면 최종 답변의 대화창 링크를 빠뜨리지 않는다.
- 로컬호스트 확인이 필요한 작업에서 최종 답변의 `테스트 링크:`에 localhost/127.0.0.1 URL을 빠뜨리지 않는다.
- 배포 환경이 있는 작업에서 최종 답변의 `테스트 링크:`에 배포 URL을 빠뜨리지 않는다.
- HTML 검토물을 만들지 않았다면 계획 문서와 최종 답변의 `HTML 생략 사유`를 빠뜨리지 않는다.
- 링크만 걸고 HTML 안의 핵심 인터랙션이 비어 있는 상태를 완료로 보지 않는다.
- 계획 MD와 HTML artifact/dev URL이 서로 다른 selector, breakpoint, 금지 스타일, 보존 값을 말하면 완료로 보지 않는다.
- `구현 직전 수준` 요청에서는 Commit/Phase마다 대상 파일, 함수/selector/API, 변경 순서, 검증 방법, 성공 기준, 커밋 단위, 중단 조건을 적는다.
- 사용자가 직접 결정해야 하는 사항이 있는데 `Operator 결정 필요 사항` 섹션을 생략하거나 `남은 미확정 사항`에만 뭉뚱그려 쓰면 완료로 보지 않는다.
- Operator 결정 항목에서 A/B/C, 추천안, 기본값, 보류 시 영향 중 하나라도 빠지면 완료로 보지 않는다.
- 일반 선택에서 추천안과 기본값이 서로 다르면 완료로 보지 않는다. 기본값은 선택이 없을 때 적용할 추천안이다.
- `mission-completion-harness` 흐름이라고 해도 hard stop 성격의 선택을 Codex 기본값으로 묻지 않고 넘기지 않는다.
- 여러 질문을 한꺼번에 던져 사용자를 피곤하게 만들지 않는다. 방향을 가르는 질문부터 한 개씩 잠근다.
- 사용자가 좋아한 질문 방식이나 결정 패턴이 드러나면, 같은 세션에서는 그 상호작용 스타일을 유지한다.
