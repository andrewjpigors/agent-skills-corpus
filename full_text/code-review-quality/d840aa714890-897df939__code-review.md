# Code Review

Review code systematically before it ships. Catch bugs, security issues, and style problems early.

## Quick Start

Run through these checks in order:
1. **Critical** — Security holes, data loss, crashes
2. **Important** — Logic bugs, performance issues, poor error handling
3. **Correctness** — Race conditions, edge cases, resource leaks
4. **Minor** — Style violations, naming, comments

Fix Critical issues immediately. Important issues before merge. Minor issues are optional.

## When to Use This Skill

- Reviewing pull requests or merge requests before approval
- Pre-commit review of significant changes touching multiple files
- Auditing code after a security incident or bug report
- Evaluating third-party code before integration

## Review Checklist

### Critical Issues (Block merge)

**Dependencies (MUST verify with package registry):**
- [ ] **ALL dependencies updated to latest versions**
- [ ] No known vulnerabilities in dependencies
- [ ] Dependency update tools installed (cargo-edit, ncu, etc.)
- [ ] Security audit passing (cargo-audit, npm audit, etc.)

**Security vulnerabilities:**
- [ ] No SQL injection (parameterized queries only)
- [ ] No command injection (no shell execution with user input)
- [ ] No XSS (sanitize all user-generated output)
- [ ] No hardcoded secrets (keys, passwords, tokens)
- [ ] Authentication/authorization checks present
- [ ] Sensitive data encrypted in transit and at rest
- [ ] No unsafe deserialization

**Data integrity:**
- [ ] No race conditions in concurrent code
- [ ] Database transactions used correctly
- [ ] No data loss paths (confirm before delete/overwrite)
- [ ] Migrations are reversible

**Crash risks:**
- [ ] Null/nil checks before dereferencing
- [ ] Array bounds checked
- [ ] Division by zero handled
- [ ] Resource limits enforced (file size, memory, timeout)

### Important Issues (Fix before merge)

**Correctness:**
- [ ] Tests cover the new code
- [ ] Edge cases handled (empty, null, max values)
- [ ] Error conditions return appropriate codes/messages
- [ ] Logic matches specification
- [ ] No off-by-one errors

**Performance:**
- [ ] No N+1 queries
- [ ] Appropriate indexes on database queries
- [ ] Large datasets paginated or streamed
- [ ] Expensive operations cached when possible
- [ ] No unnecessary loops or redundant work

**Error handling:**
- [ ] All errors caught and logged
- [ ] User-facing errors are helpful
- [ ] Cleanup happens in finally blocks or defer
- [ ] No swallowed exceptions
- [ ] Retry logic for transient failures

**Testing:**
- [ ] Unit tests for new functions
- [ ] Integration tests for API changes
- [ ] Tests actually run (not skipped)
- [ ] Tests fail when they should
- [ ] **Mutation testing on changed lines** — zero surviving mutants in the diff (Rust: `cargo mutants --in-diff <(git diff origin/main)`; Python: `mutmut`; JS/TS: Stryker)
- [ ] **CRAP score** ≤ 30 on touched files (Rust: `cargo crap --lcov lcov.info`) — above the threshold means complex code with thin tests, which the reviewer can't validate
- When you encounter dead code annotations or ignored tests, consider running the `implementation-review` skill for deeper classification and documentation cross-referencing.

### Minor Issues (Nice to have)

**Code style:**
- [ ] Follows project conventions
- [ ] Consistent naming (camelCase, snake_case, etc.)
- [ ] No commented-out code
- [ ] No debug print statements
- [ ] Imports organized per project style

**Clarity:**
- [ ] Function names describe what they do
- [ ] Variables have meaningful names
- [ ] Complex logic has explanatory comments
- [ ] Magic numbers replaced with named constants
- [ ] Functions are reasonably sized (<50 lines)

**Documentation:**
- [ ] Public APIs have docstrings
- [ ] Complex algorithms explained
- [ ] Non-obvious behavior documented
- [ ] Breaking changes noted

## Language-Specific Checks

### Python
```python
# CRITICAL - SQL injection
cursor.execute(f"SELECT * FROM users WHERE id = {user_id}")  # BAD
cursor.execute("SELECT * FROM users WHERE id = %s", (user_id,))  # GOOD

# IMPORTANT - Resource cleanup
f = open("file.txt")  # BAD - no cleanup
with open("file.txt") as f:  # GOOD - automatic cleanup
    data = f.read()

# MINOR - Style
def getData(): pass  # BAD - not snake_case
def get_data(): pass  # GOOD
```

### JavaScript/TypeScript
```javascript
// CRITICAL - XSS
div.innerHTML = userInput;  // BAD
div.textContent = userInput;  // GOOD

// IMPORTANT - Error handling
const data = JSON.parse(input);  # BAD - no error handling
try {
  const data = JSON.parse(input);
} catch (e) {
  console.error("Invalid JSON:", e);
  return null;
}  // GOOD

// MINOR - Const vs let
let config = {...};  // BAD - doesn't change
const config = {...};  // GOOD
```

### C
```c
// CRITICAL - Buffer overflow
strcpy(dest, src);  // BAD
strlcpy(dest, src, sizeof(dest));  // GOOD (OpenBSD)
strncpy(dest, src, sizeof(dest) - 1);  // GOOD (POSIX)

// IMPORTANT - NULL checks
*ptr = value;  // BAD - no NULL check
if (ptr != NULL) {
    *ptr = value;
}  // GOOD

// MINOR - Return type placement (OpenBSD KNF)
static int function_name(int arg) { }  // BAD
static int
function_name(int arg)
{
    ...
}  // GOOD
```

### Rust
```rust
// CRITICAL - Unwrap in production
let value = result.unwrap();  // BAD - panics on error
let value = result?;  // GOOD - propagates error

// IMPORTANT - Missing unsafe documentation
unsafe {
    // BAD - no SAFETY comment
    *ptr = value;
}

unsafe {
    // GOOD - documents why it's safe
    // SAFETY: ptr is valid, aligned, and exclusively owned
    *ptr = value;
}

// MINOR - Unnecessary clone
let s2 = s1.clone();  // BAD if s1 isn't used after
let s2 = s1;  // GOOD - move instead
```

## Review Workflow

### 1. Understand the Change

Read the specification or ticket. If no context was provided, scan the changed files first, then **use `AskUserQuestion`** to ask: "I can see [X files changed] touching [list key areas]. Is there a ticket or spec I should read, or should I review against current behavior?" Know what the code is supposed to do before reviewing how it does it. You can't review effectively without this context.

### 2. Check Critical Issues First

Scan for security and crash risks. These block everything else.

### 3. Verify Tests

Run the test suite. If tests fail or don't exist, stop here. You won't find deeper issues if the basics aren't passing.

### 4. Review Important Issues

Check correctness, error handling, and performance.

### 5. Note Minor Issues

Style and clarity problems. Don't block the merge for these.

### 6. Provide Feedback

Structure feedback by severity:

```markdown
## Critical
- Line 45: SQL injection in user search (use parameterized query)
- Line 78: Unchecked buffer copy (use strlcpy or check bounds)

## Important
- Line 23: Missing error handling for network timeout
- Line 56: N+1 query in loop (use join or batch load)

## Minor
- Line 12: Variable name `d` is unclear (consider `duration`)
- Line 89: Debug print statement should be removed
```

## Automated Tools

Catch common issues before manual review:

**Linters:**
- Python: `ruff`, `pylint`, `mypy` (type checking)
- JavaScript: `eslint`, `prettier`
- C: `clang-tidy`, `cppcheck`, `splint`
- Rust: `clippy`, `rustfmt`

**Security scanners:**
- Semgrep (multi-language)
- CodeQL (GitHub)
- Bandit (Python)
- npm audit (JavaScript)
- cargo audit (Rust)

**Run these in CI before human review.**

See [references/static-analysis-by-language.md](references/static-analysis-by-language.md) for per-ecosystem tool recommendations with install commands and one-liner invocations. Covers C, Rust, Go, Python, JavaScript/TypeScript, Ruby, and Java.

### Test-effectiveness signals (run on every non-trivial PR)

Linters and security scanners catch broken or unsafe code. They don't catch *tests that don't actually test anything*. Two signals close that gap and belong in every code review:

- **Mutation testing on the diff** — Rust: `cargo mutants --in-diff <(git diff origin/main) --timeout-multiplier 2.0`. Python: `mutmut run --paths-to-mutate=<changed-file>`. JS/TS: `npx stryker run`. Any surviving mutant on a changed line means the new code isn't constrained by tests — treat it as a Critical finding (the reviewer can't tell whether the line's correct). The full reading guide lives in `bugfix/references/reproducer-and-mutation.md`.
- **CRAP score on touched modules** — Rust: `cargo llvm-cov --lcov --output-path lcov.info && cargo crap --lcov lcov.info`. The CRAP formula (`comp² × (1 − cov)³ + comp`) highlights code that's both complex *and* undertested. Anything above 30 in a file touched by the PR is an Important finding — request either tests or a refactor before merge. Cross-language: `crap4java` (Java), NDepend (.NET); for languages without a packaged tool, compute by hand from complexity + lcov.

See `.claude/rules/static-analysis.md` for the canonical guidance and tool table.

## Writing Style

Review feedback is prose that developers read carefully. Apply the `natural-writing-style` skill to all comments and summaries:

- Be direct and specific — "This will crash on null input at line 45" beats "this might cause issues"
- Show competence through precision, not decorative warmth — skip generic praise like "Great work!"
- Use contractions naturally; don't sound like a legal brief
- Never claim code is "production ready" or "fully secure" unless you've verified the entire surface
- State what you reviewed, what you verified, what you didn't examine

- [ ] All feedback follows `natural-writing-style` guidelines
