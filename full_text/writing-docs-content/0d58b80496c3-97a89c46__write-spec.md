# Skill: Write a layered functional spec

Drives the layered specification framework. The canonical guide and blank templates live in
[`instructions/template/`](../../instructions/template/INSTRUCTIONS.md). Specs are written
**outside-in and top-down**: why → what → how-users → detailed rules.

## The four layers (write in order, validate each before the next)
- **Layer 0 — Purpose & Context** *(mandatory, first)*: why the software exists, the domain,
  users, and scope. Reviewable by a domain expert who knows nothing about software.
  Template: `layer0_purpose_and_context.md`.
- **Layer 1 — Functional Areas**: what users can do, one paragraph each, no UI/DB/tech.
  Each area carries a scope label: **In scope** / **Out of scope** / **Under review**.
  Template: `layer1_functional_areas.md`.
- **Layer 2 — Workflows**: how users accomplish goals — steps, decisions, error cases, in the
  user's language. One file per functional area. Template: `layer2_workflow.md`.
- **Layer 3 — Detailed specs** *(only after 0–2 are stable)*: data models, field constraints,
  business rules, acceptance criteria. Templates: `layer3_domain_entity.md`,
  `layer3_feature_spec.md`.

## Writing rules
- Plain English, active voice, present tense ("The user selects a project").
- Describe **observable behavior**, not internals. No UI at Layers 0–2.
- Use stable IDs so specs are referenceable in prompts: `FA-NN`, `WF-XX-NN`, `BR-XX-NN`,
  `AC-XX-NN`, `ENT-XX`.
- Every functional area must carry a scope label. Resolve **Under review** items explicitly
  to In/Out of scope with a recorded rationale (see `out_of_scope.md`) — never delete silently.
- Mark sections `STATUS: DRAFT | REVIEW | APPROVED`.

## Stop-anywhere
Each layer is independently useful — stop at any layer and you still have a valid artefact.
Layers 0–1 are short; include them in full at the start of any LLM session on the app.

## Tie-in
A finalized scope decision is also a decision — capture it with
**[`record-decision`](../record-decision/SKILL.md)**.
