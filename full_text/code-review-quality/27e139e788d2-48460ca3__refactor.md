# Codebase Refactoring

You're here to make a codebase better — find anti-patterns, duplication, missing docs,
underused helpers, and test coverage gaps. Then fix them systematically, one verified
change at a time. Not "looks better" — *tests prove it's better*.

## Quick Start

1. Detect project languages and load the right rules (see Language Detection below)
2. Catalog existing helper libraries — **before** you write anything new
3. Establish a baseline: run tests, measure coverage, count lint warnings
4. Analyze using language-specific detection commands from the loaded rules
5. Prioritize findings (see Priority Matrix) and work through them with test-first refactoring
6. Verify: all tests pass, metrics improved, no new debt introduced

## When to Use This

- Starting a quality improvement pass on an existing codebase
- Reviewing code for anti-patterns and duplication after a feature lands
- Cleaning up technical debt before a release or major feature
- Improving test coverage in undertested areas
- After a big refactor to verify nothing regressed
- When you notice repeated patterns that should be consolidated

## Phase 1: Baseline

Before changing anything, capture the current state. You can't prove improvement without
a starting point.

```
Progress:
- [ ] Run existing tests, record pass/fail state
- [ ] Measure test coverage percentage
- [ ] Capture CRAP scores (cargo crap, crap4java, NDepend, or hand-computed) for the modules in scope
- [ ] Capture mutation-survivor count on the diff baseline (cargo mutants / mutmut / Stryker)
- [ ] Catalog existing helpers (see Critical Rule below)
- [ ] Count linter warnings/errors
- [ ] Document current code metrics (complexity, duplication, file sizes)
```

See [references/workflow.md](references/workflow.md) for the full 6-phase workflow.

### Critical Rule: Catalog Helpers First

**Before ANY refactoring**, thoroughly analyze existing helper libraries. This prevents
creating duplicates, writing pointless wrappers, or placing new helpers in the wrong
module.

```bash
# Adapt to your language — the goal is listing all public helpers
# Go:
grep -r '^func ' pkg/common/ pkg/util/ | head -40
# Rust:
rg '^pub fn|^pub const|^pub struct|^pub enum' --type rust crates/shared*/
# Python:
rg '^def |^class ' --type py src/utils/ src/helpers/
```

Create a written catalog documenting what functions, constants, and types exist. Then
**use them**. Don't reinvent what's already there.

Full patterns: [references/helper-library-patterns.md](references/helper-library-patterns.md)

## Phase 2: Analysis

Run language-specific linters and detection commands from the loaded rules reference file.
Every language file includes a "Detection Commands" section with copy-paste commands.

What you're looking for:

- **Anti-patterns**: Language-specific bad practices (unwrap in Rust, ignored errors in Go, bare except in Python, unchecked malloc in C, `with` abuse in Nix)
- **Duplication**: Repeated code blocks, similar function signatures, copy-pasted logic
- **Missing docs**: Public APIs without documentation
- **Magic values**: Hardcoded strings/numbers that should be constants
- **Inline logic**: Code that should use centralized helpers instead
- **Test gaps**: Untested public functions, missing edge case coverage
- **Security smells**: Injection risks, memory safety issues, credential handling

For duplication tools and complexity thresholds, see [references/duplication-detection.md](references/duplication-detection.md).

## Phase 3: Priority Matrix

Sort findings into these buckets. Work top-down — don't polish edge cases while security
issues remain open.

**P0 — Blockers** (fix before anything else)
- Security vulnerabilities (injection, memory safety, auth bypass)
- Crashes and panics in production paths
- Data corruption risks
- Undefined behavior

**P1 — Core gaps**
- Architecture violations (code in wrong layer/module)
- Large duplicate blocks (100+ lines)
- Missing error handling or resource leaks
- Functions with cyclomatic complexity >20

**P2 — Quality improvements**
- Code style violations and unnecessary complexity
- Minor duplication (50-100 lines)
- Missing documentation for public APIs
- Suboptimal patterns (see [references/refactoring-catalog.md](references/refactoring-catalog.md) for common refactoring techniques)

**P3 — Track for later**
- Minor style preferences
- Test file duplication (often intentional)
- Performance micro-tuning

## Phase 4: Test-First Refactoring

For each finding, follow this cycle. No exceptions.

1. **Write or improve tests** for the code being refactored — BEFORE changing it
2. Tests establish expected behavior. If you can't write a test, you don't understand the code well enough to refactor it.
3. **Make one logical change** at a time. Extract a function. Rename a variable. Consolidate duplicates. One thing.
4. **Run tests** after every change. Must still pass. If they don't, revert and try a smaller change.
5. **Commit** each working increment. Small, incremental commits protect you.
6. Repeat until the finding is resolved.

See [references/test-improvement.md](references/test-improvement.md) for test patterns
by type and coverage goals.

## Phase 5: Verification

After each batch of refactoring, verify you haven't introduced new problems:

```
Verification:
- [ ] All original tests still pass
- [ ] All new tests pass
- [ ] Coverage improved or stayed flat (never decreased)
- [ ] Linter warnings reduced or eliminated
- [ ] No new duplication introduced
- [ ] Helper catalog updated if you added new helpers
- [ ] Documentation added for new/changed public APIs
```

## Phase 6: Reporting

what didn't. Don't round up.


## Static Analysis

Each language reference file includes detection commands. Here's a quick summary of the
tools you should be reaching for:

| Language | Linter | Security | Dependencies | Test effectiveness |
|---|---|---|---|---|
| Go | golangci-lint | gosec, govulncheck | govulncheck | go-mutesting |
| Rust | clippy (pedantic) | cargo-audit | cargo-deny | **cargo-mutants + cargo-crap** |
| Python | ruff, mypy | bandit | pip-audit | mutmut |
| C | clang-tidy, cppcheck | flawfinder | — | mull |
| Nix | statix, deadnix | — | — | — |

Run the linter and security scanner from your language's reference file before and after
refactoring. The delta tells you if you're making things better or worse.

### CRAP-driven target selection (run BEFORE Phase 3 prioritisation)

Refactoring blind is a recipe for breaking things you didn't realise were undertested. The CRAP score (`comp² × (1 − cov)³ + comp`, Savoia & Evans 2007) finds code that's both complex *and* undertested — exactly the code where a refactor without test backing is most dangerous. Use it to pick targets.

```bash
# Rust
cargo install cargo-llvm-cov cargo-crap
cargo llvm-cov --lcov --output-path lcov.info
cargo crap --lcov lcov.info             # default threshold 30
```

Treat every function above the CRAP threshold as a Phase 4 candidate where the first move is **add tests, then refactor** — never the reverse. Cross-language tools: `crap4java` (Java), NDepend (.NET); for others compute by hand from complexity + lcov. See `.claude/rules/static-analysis.md` for the full table.

### Mutation testing — verify the new tests are real

After Phase 4 ("Write or improve tests for the code being refactored — BEFORE changing it"), run mutation testing on the new tests to prove they actually catch bugs:

```bash
cargo mutants --in-diff <(git diff origin/main) --timeout-multiplier 2.0
```

Any surviving mutant means the new test passes regardless of whether the code is correct — fix the test before refactoring. The reading guide is in `bugfix/references/reproducer-and-mutation.md`.

## Key Rules

**Don't create wrapper functions.** If a helper exists, call it directly. Wrappers add
indirection without value.

**Don't duplicate helpers.** Search before writing. If it feels like a utility, it
probably already exists somewhere.

**Constants for repeated literals.** Any string or number appearing 3+ times should be a
named constant in the appropriate helper module.

**Normalization must be idempotent.** `normalize(normalize(x))` must equal `normalize(x)`.
If it doesn't, you've got a bug.
