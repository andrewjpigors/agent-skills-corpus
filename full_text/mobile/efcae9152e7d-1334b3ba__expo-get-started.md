# Expo Get Started

## Как запускать

Открой этот файл в Cursor или Claude Code и напиши:

```text
Что сегодня?
```

ИИ должен:

1. Найти первый незавершенный урок (первый `[ ]` сверху).
2. Сказать, какой это раздел и сколько уроков уже сделано (посчитать по `[x]`).
3. Дать теорию на 2-5 минут.
4. Дать одну практическую задачу.
5. Задать 2-3 вопроса для проверки.
6. Дождаться ответа ученика.
7. Если практика сделана и ответы нормальные — поменять `[ ]` на `[x]` у этого урока.
8. Обновить строки "Дата обновления" и "Последний завершенный урок".

Правила:

- Один урок за раз.
- Не перескакивать вперед без просьбы.
- Без длинных лекций.
- Если ученик не понял — короткое объяснение и мини-задача, без перехода к следующему уроку.
- Источник истины по прогрессу — только чекбоксы уроков. Не вести отдельные счетчики и таблицы вручную.
- Сквозной проект — приложение прогноза погоды. Не предлагать другие примеры (todo, заметки и т.п.) без явной просьбы.
- Целевая платформа — только iOS. Не предлагать команды, инструкции и проверки под Android (нет Android Studio, эмуляторов, Play Store, `--platform android`).

### [ ] TS-10 Опциональные поля и nullish

Теория:

- Реальные API-данные часто бывают пустыми, `null` или с отсутствующими полями.
- Optional field: `humidity?: number` — поле может отсутствовать.
- Optional chaining `data?.city` — если `data` это `null` или `undefined`, выражение вернет `undefined` без ошибки.
- Nullish coalescing `value ?? fallback` — берет `fallback`, только если `value` это `null` или `undefined` (но не `0` и не `""`).

Практика:

- Создать `type WeatherResponse` с optional `humidity` и `wind`.
- Написать функцию, которая читает `response?.city` и `response?.humidity`.
- Через `??` подставить дефолты: город `"Unknown"`, влажность `0`.
- Передать `null` и убедиться, что код не падает.

Вопросы:

1. Когда `??` ведет себя иначе, чем `||`?
2. Что вернет `data?.foo?.bar`, если `data` это `null`?
3. Почему `humidity?: number` чаще лучше, чем `humidity: number | null`?

### [ ] TS-11 Асинхронность и Open-Meteo

Теория:

- Сетевые запросы асинхронные — результат приходит не сразу.
- `Promise` — это объект, который однажды получит результат (resolve) или ошибку (reject).
- `await` ждет результат Promise и возвращает значение. Работает только внутри `async`-функции.
- `try/catch` ловит ошибки `await`. Без него ошибка распространится дальше и упадет приложение.
- Три состояния запроса: `loading`, `success`, `error`. UI должен показывать каждое.
- В курсе используем **Open-Meteo** — публичный API погоды без регистрации и ключа.
- Forecast endpoint принимает координаты, а не имя города: `https://api.open-meteo.com/v1/forecast?latitude=...&longitude=...&current=temperature_2m,weather_code`.

Практика:

- Создать `practice/get-weather.ts`.
- Написать `async function getWeatherByCoords(lat: number, lon: number): Promise<Weather>`.
- Внутри `fetch` к Open-Meteo forecast endpoint.
- Из ответа достать `current.temperature_2m` и `current.weather_code`.
- Обернуть в `try/catch`.
- Залогировать все три состояния: до запроса, после успеха, при ошибке.
- Вызвать с координатами Тбилиси: `lat=41.7151`, `lon=44.8271`.

Вопросы:

1. Что произойдет с ошибкой `await`, если не написать `try/catch`?
2. Чем `await fetch(...)` отличается от `fetch(...)` без `await`?
3. Что должен увидеть пользователь на каждом из трех состояний?

### [ ] TS-12 Сквозной TS-модуль для погоды

Теория:

- Маленькое приложение состоит из ввода, запроса, ответа и UI-состояний.
- Логику можно собрать и проверить отдельно от UI, прямо из терминала.
- Open-Meteo дает два разных API: **geocoding** (имя города → координаты) и **forecast** (координаты → погода).
- Один пользовательский запрос "погода в Тбилиси" превращается в два запроса подряд.
- Geocoding endpoint: `https://geocoding-api.open-meteo.com/v1/search?name=${city}&count=1`.

Практика:

  - иначе вызывает `getWeatherByCoords` из TS-11,
  - возвращает `{ status: "loading" | "success" | "error", data?: Weather, error?: string }`.
- Вызвать с правильным городом ("Tbilisi") и заведомо несуществующим ("zzzzz").

Вопросы:

### [ ] GIT-04 Safety и конфликты

Теория:

- AI-изменения надо проверять через `git diff` перед commit.
- `.env`, `node_modules` и секреты нельзя коммитить — для этого `.gitignore`.
- Merge conflict возникает, когда две правки меняют одни и те же строки.
- Конфликт решается руками: открыть файл, выбрать нужную версию, удалить маркеры `<<<<<<<`, `=======`, `>>>>>>>`, закоммитить.

Практика:

- Создать ветку `feature/conflict`, изменить одну строку в любом файле.
- Вернуться на `main`, изменить ту же строку иначе, закоммитить.
- Смержить `feature/conflict` в `main` и руками разрешить конфликт.
