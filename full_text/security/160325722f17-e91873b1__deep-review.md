# Deep Review — Revue approfondie multi-agents Angular

Revue approfondie spécialisée Angular avec dispatch parallèle en 4 sous-agents spécialisés. Chaque sous-agent charge uniquement ses références, lit les fichiers dont il a besoin, et retourne des findings structurés. Le main agent merge et produit le rapport final.

## Étape 1 — Détection du périmètre

**Priorité au working tree** (fichiers modifiés sur la branche courante) :

1. `git status --porcelain` → extraire les fichiers modifiés/ajoutés (`M`, `A`, `??` hors ignorés).
2. **Si la liste n'est pas vide** → `SCOPE_FILES` = cette liste, `SCOPE_MODE = "working-tree"`.
3. **Sinon** :
   - Identifier la branche principale (`dev`, `main`, `master`) via `git remote show origin | grep "HEAD branch"` ou convention du repo.
   - `git diff --name-only <main-branch>...HEAD` → `SCOPE_FILES`, `SCOPE_MODE = "branch-diff"`.
4. Lire `CLAUDE.md` à la racine du projet s'il existe — contient les conventions du projet à respecter.
5. Filtrer `SCOPE_FILES` :
   - Garder uniquement `.ts`, `.html`, `.scss`, `.css`, `.json` pertinents.
   - Ignorer `node_modules`, `dist`, `.angular`, fichiers générés.

**Si `SCOPE_FILES` est vide** → répondre "Aucun fichier à reviewer (working tree propre + pas de diff vs branche principale)." et s'arrêter.

### Heuristique petit scope (économie de tokens)

Avant de lancer les 4 sous-agents, compter les fichiers de code (hors `.json`, `.xml`, manifestes) dans `SCOPE_FILES` :

- **Si ≤ 2 fichiers code** → **review inline** par le main agent (pas de dispatch).
  - Le main agent lit lui-même les fichiers et consulte les références à la demande.
  - Raison : 4 sous-agents parallèles × re-lecture du même fichier × chargement de refs = gaspillage de tokens disproportionné par rapport au volume à analyser.
  - Le format de sortie (Étape 3) reste identique.
- **Si ≥ 3 fichiers code** → dispatch parallèle normal (Étape 2 complète).

Seuil à tuner selon usage — remonter si un scope de 2 fichiers s'avère trop lourd pour le main agent.

## Étape 2 — Dispatch parallèle (4 sous-agents)

Lancer **en parallèle** via le Agent tool (`subagent_type: "code-reviewer"` ou `general-purpose` selon disponibilité) les 4 sous-agents suivants. Chaque sous-agent reçoit :

- `SCOPE_FILES` : liste complète des fichiers à analyser
- `SCOPE_MODE` : `working-tree` ou `branch-diff`
- Son prompt de scope spécifique (ci-dessous)
- Consigne : lire chaque fichier du scope, consulter ses références, retourner un JSON de findings

**IMPORTANT** : les 4 scopes sont **non-overlapping**. Chaque sous-agent doit **refuser** de commenter sur un scope qui n'est pas le sien, même s'il repère un problème. Le main agent évite ainsi les doublons.

Les références sont des fichiers `.md` co-localisés avec ce SKILL.md, dans le sous-dossier `references/`. Les sous-agents doivent lire ces fichiers en chemin relatif au SKILL : `references/<nom>.md`. Si le skill est installé dans `~/.claude/skills/deep-review/`, les références sont dans `~/.claude/skills/deep-review/references/`.

### Sous-agent 1 — Security

```
Scope : vulnérabilités uniquement. Pas de clean code, pas de perf.

Références à consulter :
- references/security-checklist.md
- references/angular-security.md

Fichiers à analyser : {SCOPE_FILES}

Checks :
- XSS : innerHTML non sanitizé, bypassSecurityTrust* injustifié, DomSanitizer mal utilisé
- Auth : vérification rôle/permission avant logique métier, guards canActivate présents
- Secrets : credentials hardcodés, tokens en clair, logs de données sensibles
- Input validation : données user validées côté front + boundary API
- OWASP Top 10 applicables au frontend (XSS, broken access control, security misconfig)
- HTTP : bon ordre des interceptors, CSRF, headers contextuels
```

### Sous-agent 2 — Signals & Performance Angular

```
Scope : Angular signals, reactivity, performance templates. Pas de sécu, pas d'architecture générale.

Références à consulter :
- references/angular-signals.md
- references/angular-performance.md
- references/rxjs-traps.md

Fichiers à analyser : {SCOPE_FILES}

Checks :
- Signal-first : signal/computed/effect au lieu de BehaviorSubject (sauf flux complexes)
- Pas de toObservable(signal).subscribe() (anti-pattern)
- Pas de "version counter" signals pour forcer un refresh d'un form — bridge via toSignal(valueChanges)
- effect() ciblés (1 effect = 1 responsabilité)
- Risque de boucle infinie (effect qui modifie un signal qu'il lit)
- computed() dans templates au lieu de fonctions
- OnPush change detection sur tous nouveaux composants
- @for avec track, @defer pour lazy
- Fuites mémoire : takeUntilDestroyed, DestroyRef, ResizeObserver/IntersectionObserver cleanup
- toSignal avec initialValue (évite le type undefined)
- RxJS : switchMap/mergeMap/concatMap bien choisis, pas de nested subscribe, shareReplay pour dédup
- Error handler redondant : subscribe({ error }) où le handler fait juste un log/toast générique alors qu'un ErrorInterceptor global gère déjà — flag en [SUGGESTION] ou [BLOCKING] (risque de double toast). Garder l'error local uniquement si la gestion est contextuelle (404 → fallback, 409 → side panel, retry custom, etc.) et le commenter.
- Cleanup dupliqué : logique de cleanup (loader off, reset state) dupliquée entre next et error → doit aller dans finalize(). Le next garde la logique de succès, l'error est supprimé si non contextuel.
- setTimeout / setInterval (avoid-first) : flag tout setTimeout du diff. [BLOCKING] si `setTimeout(() => signal.set(...), 0)` (anti-pattern) ou setInterval sans cleanup. [SUGGESTION] sinon — proposer une alternative seulement si pertinente (effect, afterNextRender, queueMicrotask, debounceTime, timer+takeUntilDestroyed). Si aucune alternative propre ne résout mieux, tolérer mais exiger un commentaire justificatif.
- Magic numbers : valeurs numériques métier (seuils, durées, tailles) en dur dans le code → [SUGGESTION] extraire en const nommée. Tolérer les indices triviaux (0, 1, -1) et l'arithmétique évidente (% = /100).
```

### Sous-agent 3 — Clean Code & Design Patterns (GoF)

```
Scope : clean code, SOLID, GoF, KISS/DRY/YAGNI. Pas de sécu, pas de perf, pas de signals.

Références à consulter :
- references/clean-code-principles.md
- references/gof-patterns.md
- references/code-quality-metrics.md
- references/feedback-patterns.md

Fichiers à analyser : {SCOPE_FILES}

Checks :
- SOLID : SRP (composants/services à responsabilité unique), OCP, DIP via inject()
- KISS : code inutilement complexe, simplifiable
- DRY : duplication réelle (3+ lignes) — PAS d'abstraction prématurée pour 2 lignes
- YAGNI : fonctionnalités non demandées, over-engineering
- GoF : Strategy (policies), Facade (services wrapper), Adapter, Observer — opportunités manquées OU usages abusifs
- Code smells : large functions (>50 lignes), deep nesting (>3), long parameter lists (>3), magic numbers
- Anti-patterns GoF : God Object, Singleton abusif, Spaghetti via subscriptions orphelines
- Métriques : cognitive complexity <15, cyclomatic <10 par fonction
- Nommage : explicite, pas d'abréviations cryptiques
- Code mort, commenté, console.log oubliés
- any évitable (any autorisé UNIQUEMENT aux frontières non typées avec commentaire)
- Commentaires : pas de prénom utilisateur ni numéro de ticket dans le code (vit dans commit/PR)
```

### Sous-agent 4 — Architecture & Conventions Angular

```
Scope : patterns Angular modernes, architecture, forms. Pas de sécu, pas de signals reactivity (déjà agent 2), pas de clean code générique (déjà agent 3).

Références à consulter :
- references/angular-architecture.md
- references/angular-forms.md

Fichiers à analyser : {SCOPE_FILES}

Checks :
- Standalone components (pas de NgModule pour nouveau code)
- inject() systématique, jamais d'injection via constructor
- input() / output() / viewChild() / model() au lieu de @Input/@Output/@ViewChild
- input.required() quand l'input est obligatoire
- constructor() au lieu de ngOnInit
- Types/interfaces dans `core/interfaces/` (ou structure équivalente documentée dans CLAUDE.md), pas dans les composants
- Services : entity (CRUD d'une entité) vs feature (workflows métier) — séparation cohérente
- Syntaxe Angular 17+ (@if/@for/@switch, pas de *ngIf/*ngFor)
- Form controls : si CLAUDE.md projet documente des controls custom (ex: <app-select>, <app-textarea>), les utiliser à la place des contrôles bruts. Sinon, contrôles natifs de la lib UI (PrimeNG, Material, etc.).
- computed() pour initialiser FormGroup (au lieu de fonctions FormGroupInit)
- Conventions CLAUDE.md du projet respectées (priorité absolue)
```

## Étape 3 — Merge & rapport final

Quand les 4 sous-agents ont retourné leurs findings, le main agent produit le rapport suivant.

### 3.1 Tableau des problèmes (tri par sévérité puis par fichier)

| # | Sévérité | Fichier:Ligne | Catégorie | Problème | Correction proposée |
|---|----------|---------------|-----------|----------|---------------------|

**Sévérités (labels explicites)** :
- **[BLOCKING]** — Bug, fuite mémoire, boucle infinie, faille sécurité, régression, violation critique convention projet → à corriger avant merge
- **[SUGGESTION]** — Anti-pattern, violation convention mineure, dette technique significative, opportunité GoF manquée → amélioration recommandée
- **[NIT]** — Nommage, lisibilité, micro-simplification → à lire mais pas bloquant

**Catégories** : `Security`, `Signals`, `Performance`, `RxJS`, `CleanCode`, `GoF`, `Architecture`, `Forms`, `Conventions`.

### 3.2 Résumé

- **Périmètre** : `SCOPE_MODE` + nombre de fichiers analysés
- **Points positifs** observés
- **Décompte** : X [BLOCKING], Y [SUGGESTION], Z [NIT]
- **Top 3 corrections prioritaires** avec explication du pourquoi (impact concret : régression ? sécu ? perf ?)

### 3.3 Code avant/après

Uniquement pour les **[BLOCKING]** (pas pour les suggestions — évite le rapport-fleuve). Format :

```
[Fichier:Ligne]
Avant :
  <code actuel>
Après :
  <code corrigé>
```

## Étape 4 — Mode `fix` (argument optionnel)

Déclenché quand la commande est invoquée avec l'argument `fix` (ex: `/deep-review fix`). **N'active aucune application automatique** — uniquement l'affichage détaillé des patchs proposés et un protocole d'autorisation.

### Règle absolue d'autorisation

**Le skill n'applique JAMAIS aucune modification sans accord explicite et ciblé de l'utilisateur.** Les Edit ne sont déclenchés qu'après l'un de ces messages utilisateur :

- `go all` / `apply all` / `tous les fix` → applique tous les [BLOCKING] proposés
- `apply #N` / `fix #N` / `go #N` → applique uniquement le fix N
- `apply #1, #3` → fixes ciblés
- Accord explicite formulé en clair

**Sans accord explicite** : le skill s'arrête après avoir affiché les patchs, en une dernière ligne "En attente de ton accord : `go all`, `apply #N`, ou instructions spécifiques."

### Déroulé après le rapport (Étape 3)

1. Afficher le tableau complet (Étape 3.1) + résumé (3.2).
2. Pour chaque **[BLOCKING]**, présenter le patch au format :
   ```
   ### Fix #N — [titre court]
   Fichier : path:ligne
   Avant :
     <code actuel>

   Après :
     <code corrigé>

   Risque : [faible / à valider / élevé]
   ```
3. Pour chaque **[SUGGESTION]** : **ne pas** proposer de patch par défaut. Simplement rappeler le numéro + une phrase. Si l'utilisateur demande un patch pour une suggestion, le fournir à ce moment-là.
4. Pour les **[NIT]** : ne rien proposer.
5. Terminer par la ligne d'attente d'accord.

### Classification du risque

- **Faible** : patch mécanique non ambigu (suppression duplication exacte, renommage import obsolète, typage `unknown` en remplacement d'`any`).
- **À valider** : patch où l'intention est supposée (ex: supprimer un `setTimeout` qui compense peut-être une race condition back).
- **Élevé** : patch qui touche la logique métier ou peut casser un flux. Le skill **doit** demander précision avant proposition.

Pour les patches "À valider" ou "Élevé", proposer plusieurs alternatives plutôt qu'un seul patch.

### Garde-fous

- **Pas d'Edit sur un fichier hors `SCOPE_FILES`** — jamais de fix sur un fichier non reviewé.
- **Pas de fix sur du code commenté / `// TODO`** — respect des intentions existantes.
- **Jamais d'amendement / commit / push** — l'application des fixes ne touche qu'au working tree, git reste à l'utilisateur.
- **Pas d'Edit en cascade** : si un fix en nécessite un autre (ex: supprimer un `as any` impose de typer un paramètre en amont), s'arrêter après le premier et signaler la dépendance.
- **Après application** : relire le fichier modifié et afficher les 3 lignes autour de chaque patch appliqué pour que l'utilisateur valide visuellement.

## Les 3 questions d'auto-review — CHECK OBLIGATOIRE

Pour **chaque** fichier code du scope, chaque sous-agent (ou le main agent en mode inline) DOIT se poser ces 3 questions. Si la réponse est "oui" ou "incertain", créer un finding.

### 1. Régression potentielle

- Ce code modifié peut-il casser une fonctionnalité existante ?
- Qui d'autre utilise ce code (autres composants, services, pages) ? Les autres flows sont-ils toujours OK ?
- Un changement de signature (param ajouté/retiré/renommé) casse-t-il des callers non modifiés ?
- Un changement de comportement silencieux (ordre de tri, valeur par défaut, filtre) affecte-t-il des vues downstream ?

### 2. Risque de boucle infinie

- `effect()` qui lit ET modifie le même signal (`.set()` / `.update()`) — **CRITIQUE**
- Cascade infinie : `effect A` → set `signalX` → `computed Y` qui lit `signalX` → `effect B` qui lit `Y` → set `signalX`…
- Circular dependency entre `computed()` (A dépend de B, B dépend de A)
- Subscription RxJS qui re-déclenche sa propre source (`valueChanges` → `patchValue` sans `emitEvent: false`)
- **Défaut** : la garde anti-loop implicite d'Angular ne capte pas tous les cas, surtout en prod.

### 3. Fuite mémoire

- Subscription RxJS longue sans `takeUntilDestroyed()` / `DestroyRef`
- Event listener (`window.addEventListener`, `document.addEventListener`) non retiré
- `ResizeObserver` / `IntersectionObserver` / `MutationObserver` sans `.disconnect()`
- Timer (`setInterval`, `setTimeout` longue durée) non cleared
- WebSocket / socket.io sans `.disconnect()` au logout / destroy

**Chaque réponse positive → finding [BLOCKING]**. Ces 3 checks sont la **priorité n°1** du skill avant tout autre finding stylistique.

## Règles transverses

- **Langue du rapport** : français.
- **Un findings = un problème réel**. Pas de "pourrait être mieux" sans justification.
- **What + Why + How** : chaque problème doit dire quoi, pourquoi ça pose problème, comment le corriger.
- **Scope du diff uniquement** : ne pas commenter sur du code non modifié (sauf si un import cassé ou une régression évidente est induite par le changement).
- **Respect CLAUDE.md** : les conventions du projet priment sur les conventions génériques.
- **3 questions obligatoires** — régression / boucle infinie / fuite mémoire (voir section dédiée).
- **Aucune modification sans accord explicite** — voir Étape 4 pour le protocole du mode `fix`.
