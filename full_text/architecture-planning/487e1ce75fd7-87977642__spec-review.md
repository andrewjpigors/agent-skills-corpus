# Spec Review

Review specs for completeness, find gaps between what the spec says and what the code actually does, and make sure every requirement is testable, traceable, and unambiguous. If no spec exists, you'll analyze the codebase and create one.

## Quick Start

A spec review checks four things: **Completeness** (does the spec cover everything that's been built?), **Correctness** (does the spec match what the code actually does?), **Traceability** (does every requirement link to tests, ADRs, and threat model entries?), and **Quality** (is every requirement unambiguous and testable?).

When there's no spec at all, this skill creates one by analyzing the existing codebase — then reviews its own output.

The built-in Stop hook keeps the review running until all gates pass — you don't need to re-invoke it manually. See [HOOKS.md](HOOKS.md) for details.

**Running in opencode:** the `hooks:` frontmatter is ignored, so the loop isn't automatic. Either re-run the skill until it reports no gaps, or opt into the `.opencode/plugins/completion-loop.ts` plugin by setting `OPENCODE_REVIEW_LOOP=spec-review` while it runs. Tool-name mapping is in [docs/OPENCODE-COMPATIBILITY.md](../../../docs/OPENCODE-COMPATIBILITY.md).

## When to Use This Skill

- Auditing an existing spec after significant development
- Checking whether an existing spec still reflects the implementation
- Reviewing spec quality before a major release or milestone
- A project has code but no spec — need to create and review one retroactively
- The `adr-review` or `threat-model-review` skill flagged spec gaps
- Verifying the traceability matrix is current

## Workflow

```
Spec Review Progress:
- [ ] Phase 1: Discover and inventory
- [ ] Phase 2: Gap analysis (spec vs. code)
- [ ] Phase 3: Quality assessment
- [ ] Phase 4: Cross-reference validation
- [ ] Phase 5: Report findings
- [ ] Phase 6: Recommend fixes
```

### Phase 1: Discover and Inventory

**Find existing specs:**

```bash
find docs/specs/ -name "*.md" -type f 2>/dev/null
find docs/ -name "*spec*" -o -name "*requirement*" -o -name "*srs*" 2>/dev/null
```

**If no spec exists:**
- **Use `AskUserQuestion`** to alert the user: "No specification found. Should I analyze the codebase and create one from scratch, or is there a spec in a non-standard location I should look in first?"
- Use `spec-create` workflow to produce a spec from the existing code
- Note any partial specs, READMEs, or inline documentation that hint at intended behavior
- Then continue with the review phases below

**If specs exist, inventory them:**
- Count total requirements (FR-XXX, NFR-XXX, etc.)
- Check for a traceability matrix
- Note the last-modified date — stale specs are common
- Read each spec to understand coverage

### Phase 2: Gap Analysis (Spec vs. Code)

This is the most valuable part. Find what's in the code but not in the spec, and what's in the spec but isn't in the code.

**Code not covered by spec (implementation drift):**

Scan the codebase for functionality that lacks spec coverage:

- API endpoints without corresponding requirements
- Data models with fields not mentioned in data requirements
- Error handling paths without acceptance criteria
- Configuration options not documented in the spec
- Authentication/authorization checks not traced to requirements
- Background jobs, scheduled tasks, or event handlers missing from spec

```bash
# Find API endpoints
grep -r "route\|handler\|endpoint\|@app\.\|@Get\|@Post" --include="*.py" --include="*.rs" --include="*.go" --include="*.js" --include="*.ts" -l

# Find data models
grep -r "class.*Model\|struct\|CREATE TABLE\|schema" --include="*.py" --include="*.rs" --include="*.go" --include="*.sql" -l
```

For each gap found, document:
```markdown
**Gap:** POST /api/v2/webhooks endpoint exists in code but has no spec requirement
**Impact:** Untested, undocumented functionality that may have security implications
**Recommendation:** Add FR-XXX covering webhook registration, validation, and delivery
```

**Spec requirements not in code (unimplemented specs):**

For each requirement in the spec, check if corresponding code exists:
- Search for implementation files referenced in the traceability matrix
- Verify `**File:**` markers point to files that actually exist (the iterate script checks these — missing files are P1 gaps)
- Verify `**Test File:**` markers point to files that actually exist (missing test files are P2 gaps)
- Verify test cases exist for acceptance criteria
- Check if "In Progress" requirements have any code at all
- Confirm that deprecated or removed requirements are marked as `[DEPRECATED]` rather than silently deleted

**File reference validation (see `artifact-status-tracking` rule):**

The iterate skill's completion check script parses `**File:**` and `**Test File:**` markers from spec task sections. During review, verify that:
- Every `### Task N:` section has a `**File:**` marker with an accurate path
- Referenced files exist in the codebase (check with `ls` or `test -f`)
- File paths use the project-relative format: `crates/donbiki-tasks/src/urgency.rs`
- Deprecated tasks have their `**File:**` markers annotated `[DEPRECATED]` or removed

### Phase 3: Quality Assessment

Review each requirement against quality criteria:

**Testability check:**
```markdown
BAD:  "The system should be user-friendly" (can't test this)
GOOD: "The checkout flow SHALL complete in 4 or fewer steps" (measurable)
```

- [ ] Every functional requirement has Gherkin acceptance criteria
- [ ] Every non-functional requirement has a measurable threshold
- [ ] No vague terms: "fast", "secure", "user-friendly", "reliable", "scalable"
- [ ] Requirements use RFC 2119 keywords correctly (MUST vs SHOULD vs MAY)

**Ambiguity check:**
- [ ] Requirements follow EARS syntax patterns
- [ ] No requirement says "and" connecting unrelated behaviors (split into separate requirements)
- [ ] No requirements use "etc.", "and so on", or "as appropriate"
- [ ] Edge cases are explicitly addressed (empty input, max values, concurrent access)

**Completeness check:**
- [ ] Error handling is specified (not just happy paths)
- [ ] Security requirements exist for authentication, authorization, data protection
- [ ] Performance requirements have specific thresholds
- [ ] Data retention and cleanup requirements are present
- [ ] Deployment and operational requirements are documented
- [ ] Monitoring and alerting requirements are present

**INVEST criteria for user stories (if present):**
- [ ] **Independent** — Can be implemented without depending on another story
- [ ] **Negotiable** — Not a contract; details can be discussed
- [ ] **Valuable** — Delivers value to a stakeholder
- [ ] **Estimable** — Team can estimate effort
- [ ] **Small** — Fits in a sprint/iteration
- [ ] **Testable** — Acceptance criteria are verifiable

### Phase 4: Cross-Reference Validation

**Traceability matrix audit:**

If a traceability matrix exists:
- [ ] Every requirement appears in the matrix
- [ ] Every requirement has at least one test case
- [ ] Security requirements trace to threat model entries
- [ ] Technology decisions trace to ADRs
- [ ] No orphan test cases (tests without requirements)
- [ ] Status column is current

If no traceability matrix exists, build one as part of the review.

**ADR cross-references:**
- [ ] Technology choices in the spec reference ADRs
- [ ] Missing ADRs are flagged (run `adr-create` or `adr-review`)

**Threat model cross-references:**
- [ ] Security requirements reference threat model entries
- [ ] Missing threat model coverage is flagged (run `threat-model-create` or `threat-model-review`)

### Phase 5: Report Findings

Write the report to `docs/spec-review-report.md` (the Stop hook checks this location). Structure your findings by severity — don't bury critical issues under suggestions.

### Phase 6: Recommend Fixes

For each finding, provide a specific fix. Here's the report structure:

```markdown
## Spec Review: [Spec Name]

### Summary
- **Requirements reviewed:** [count]
- **Gaps found:** [count]
- **Quality issues:** [count]
- **Missing cross-references:** [count]

### Critical Issues (block release)
- [ ] [Issue with specific fix]

### Important Issues (fix soon)
- [ ] [Issue with specific fix]

### Suggestions (improve when possible)
- [ ] [Suggestion with reasoning]

### Gap Inventory
| Type | Description | Recommendation |
|---|---|---|
| Code without spec | POST /webhooks endpoint | Add FR-XXX |
| Spec without code | FR-009 password reset | Implement or remove |
| Missing test | FR-003 session expiry | Write TC-003 |
| Missing ADR | Redis technology choice | Run /adr-create |
| Missing threat entry | File upload security | Run /threat-model-create |

### Recommendations
[Prioritized list of actions to bring the spec to compliance]
```

## Creating a Spec from Scratch

When no spec exists and you need to create one:

1. **Analyze the codebase** following the `spec-create` Phase 1 discovery process
2. **Generate requirements** from code analysis (each endpoint, model, integration = requirement)
3. **Write the spec** using the `spec-create` template and process
4. **Immediately review your own output** using Phases 2-4 above
5. **Flag known gaps** honestly — you can't spec what you can't observe from code alone
6. **Cross-reference** existing ADRs and threat model entries into the new spec

State clearly: "This spec was generated from code analysis on [date]. It covers observable behavior but may miss business logic, edge cases, or design intent that aren't evident from the implementation alone." Don't pretend you've captured everything when you haven't.

## Writing Style

Apply the `natural-writing-style` skill. Review findings should be specific and actionable — "FR-003 uses 'should be fast' without a measurable threshold; replace with 'SHALL respond within 200ms at p95'" is useful. "Some requirements could be improved" is not.

Never claim a spec review is "complete" or "thorough" — state what you reviewed, what criteria you applied, and what wasn't examined.
