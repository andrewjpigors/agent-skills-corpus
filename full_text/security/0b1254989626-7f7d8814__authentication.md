# Authentication and Registration

## Identity

This skill is an **IRC authentication and registration concept teacher**.

It teaches the student how to design and reason about the client registration state machine, how the server processes the `PASS`, `NICK`, and `USER` commands, how to handle registration transitions (both valid and invalid), and how to send the welcome sequence.

It behaves like a senior IRC protocol engineer mentoring a 42 student: explaining the protocol sequence, showing how states are tracked internally, identifying common edge cases, and helping the student structure their state transitions before writing any C++ code.

### What This Skill Is

- A teacher of client registration and authentication flow.
- The conceptual guide to Roadmap **Phase 8** (Authentication).
- An implementation-oriented design resource.

### What This Skill Is NOT

- Not a C++ code generator.
- Not a parser implementation teacher → `parser`
- Not a command routing / dispatcher teacher → `command-dispatch`
- Not a channel manager or operator skill → `channels` / `modes`
- Not a reply formatting implementation teacher → `replies`

## The Client State Machine

An IRC client cannot execute general commands (like `JOIN` or `PRIVMSG`) until it completes the registration phase. The server tracks each client's progress using a state machine.

```
                  ┌──────────────┐
                  │ Disconnected │
                  └──────┬───────┘
                         │
                         │  TCP connection accepted (accept)
                         ▼
                  ┌──────────────┐
                  │  Connected   │  ◄── Client object created
                  └──────┬───────┘      State: Unauthenticated
                         │
                         │  PASS <password> received & valid
                         ▼
                  ┌──────────────┐
                  │Authenticated │  ◄── State: Password validated
                  └──────┬───────┘
                         │
         ┌───────────────┴───────────────┐
         │ NICK received                 │ USER received
         ▼                               ▼
  ┌──────────────┐               ┌──────────────┐
  │  Nick Set    │               │  User Set    │
  └──────┬───────┘               └──────┬───────┘
         │                               │
         │ USER received                 │ NICK received
         └───────────────┬───────────────┘
                         ▼
                  ┌──────────────┐
                  │  Registered  │  ◄── Registration complete
                  └──────────────┘      Sends 001, 002, 003, 004
```

### Valid Transitions

1. **Connected → Authenticated**: The client sends `PASS <password>`. The password must match the one provided to the server at startup (MR-04).
2. **Authenticated → Nick Set**: The client sends `NICK <nickname>`. The nickname must be unique and valid.
3. **Authenticated → User Set**: The client sends `USER <username> <hostname> <servername> <realname>`.
4. **Nick Set → Registered**: The client sends `USER` (after `NICK`).
5. **User Set → Registered**: The client sends `NICK` (after `USER`).

### Invalid Transitions and Server Reactions

- **NICK or USER before PASS**:
  - *Reaction*: The server rejects the command. Depending on the reference client, it either ignores the command or returns `ERR_NOTREGISTERED` (451).
- **PASS after Registered**:
  - *Reaction*: The server returns `ERR_ALREADYREGISTERED` (462) and ignores the command.
- **NICK to a duplicate nickname**:
  - *Reaction*: The server returns `ERR_NICKNAMEINUSE` (433). The client's state remains unchanged (they must try a different nickname).
- **Command before Registered**:
  - *Reaction*: If the client attempts to send `JOIN`, `PRIVMSG`, etc., before the state reaches `Registered`, the server returns `ERR_NOTREGISTERED` (451).

## Authentication and Registration Concepts

### 1. Client State Machine and Registration States

**What it is:** The internal state tracking for each connected client to enforce the protocol phase sequence.

**Why it exists:** An IRC server must not process chat messages or channel actions from unverified connections. The state machine acts as a gatekeeper, verifying the password first, then collecting identity before granting access.

**Relation to ft_irc:** MR-27 requires clients to authenticate, and MR-25/26 require compatibility with reference clients. Tracking state ensures the server behaves correctly during connection setup.

**Classification:** Engineering Recommendation (implementing it as a state machine; the behavior itself is a Mandatory Requirement).

**Internal server state:**

The Client object tracks these flags:

- `has_pass` (bool): `true` if a valid connection password has been verified.
- `has_nick` (bool): `true` if a unique nickname has been set.
- `has_user` (bool): `true` if a username has been set.
- `is_registered` (bool): `true` only when `has_pass`, `has_nick`, and `has_user` are all `true`.

**ASCII Diagram:**

```
  Unregistered Clients:
  ┌────────────────────────────────────────────────────────┐
  │ State check in dispatcher:                             │
  │                                                        │
  │  Client sends JOIN #42                                 │
  │  Check: is_registered == true?                         │
  │  → No!                                                 │
  │  → Return :servername 451 * :You have not registered   │
  └────────────────────────────────────────────────────────┐

  Registered Clients:
  ┌────────────────────────────────────────────────────────┐
  │ Client sends JOIN #42                                 │
  │ Check: is_registered == true?                         │
  │  → Yes!                                                │
  │  → Route to joinHandler()                              │
  └────────────────────────────────────────────────────────┐
```

**Common mistakes:**

- Letting clients join channels or send messages before completing registration.
- Allowing `NICK` and `USER` commands to proceed even if the correct password was not provided via `PASS`.
- Forgetting to reset registration flags if the client disconnects or fails registration.

### 2. PASS Command & Password Verification

**What it is:** The command used by the client to send the connection password. The server compares it to the password given in the command-line arguments (MR-04).

**Why it exists:** To restrict access to authorized clients only. Without this, anyone could connect to your server.

**Relation to ft_irc:**

- MR-02: Program accepts `<password>` as the second argument.
- MR-04: `<password>` is the connection password required by any client.
- MR-27: Must be able to authenticate.

**Classification:** Mandatory Requirement

**Internal server state:**

- The server stores the startup password globally.
- The client starts with `has_pass = false`.
- When `PASS <key>` is received:
  - If `is_registered == true`, return `ERR_ALREADYREGISTERED` (462).
  - If `<key>` matches the server password, set `has_pass = true`.
  - If `<key>` does not match, return an error (or close the connection, depending on reference client requirements).

**ASCII Diagram:**

```
  PASS command processing:

  Client                                  Server
    │                                       │
    │────── PASS wrong_pwd ───────────────►│  Verify: "wrong_pwd" == "secret"
    │                                       │  → No!
    │◄───── 464 (ERR_PASSWDMISMATCH) ───────│  (or disconnect client)
    │                                       │
    │────── PASS secret ───────────────────►│  Verify: "secret" == "secret"
    │                                       │  → Yes!
    │                                       │  Client state: has_pass = true
```

**Common mistakes:**

- Accepting `PASS` after the client is already registered. Standard IRC protocol forbids changing the password post-registration (returns 462).
- Hardcoding the password instead of using the command-line argument.
- Allowing clients to bypass password verification by sending `NICK` or `USER` directly.

### 3. NICK Command & Nickname Uniqueness

**What it is:** The command used to set or change a client's nickname. The server must verify that the nickname is syntactically valid and not currently in use by another connected client.

**Why it exists:** Nicknames are the primary identifiers on IRC. Messages are routed using nicknames, so they must be unique across the entire server.

**Relation to ft_irc:**

- MR-28: Must be able to set a nickname.
- MR-19: Multiple clients simultaneously (uniqueness check across all connected clients).

**Classification:** Mandatory Requirement

**Internal server state:**

- The server maintains a collection of all registered nicknames (e.g., a map of `nickname -> Client*`).
- When `NICK <new_nick>` is received:
  - If `has_pass == false`, reject the command (ERR_NOTREGISTERED).
  - If `<new_nick>` is empty, return `ERR_NONICKNAMEGIVEN` (431).
  - If `<new_nick>` contains invalid characters, return `ERR_ERRONEUSNICKNAME` (432).
  - If `<new_nick>` is already in use by another client, return `ERR_NICKNAMEINUSE` (433).
  - If valid and unique:
    - Update the client's nickname.
    - Set `has_nick = true`.
    - If the client was already registered, broadcast the nick change to all channels the client is in.

**ASCII Diagram:**

```
  Duplicate nickname check:

  Client A (nick: alice)                  Client B
    │                                       │
    │                                       │────── NICK alice ─────────► Server
    │                                       │                             │
    │                                       │                             │ Check: "alice" in use?
    │                                       │                             │ → Yes (Client A has it)
    │                                       │◄───── 433 (NICKNAMEINUSE) ──│
```

**Common mistakes:**

- Allowing duplicate nicknames. This breaks routing for `PRIVMSG` (MR-31).
- Forgetting that a client can change their nickname *after* registration. If they do, the server must notify other users in their channels.
- Accepting nicknames with invalid characters (like spaces, commas, or `@` symbols).

---

### 4. USER Command & Username Validation

**What it is:** The command used to provide the client's username, hostname, servername, and real name during registration.

**Why it exists:** To associate real identity details with the connection for diagnostic and logging purposes.

**Relation to ft_irc:** MR-29: Must be able to set a username.

**Classification:** Mandatory Requirement

**Internal server state:**

- When `USER <username> <hostname> <servername> <realname>` is received:
  - If `has_pass == false`, reject (ERR_NOTREGISTERED).
  - If `is_registered == true`, return `ERR_ALREADYREGISTERED` (462).
  - If parameters are missing, return `ERR_NEEDMOREPARAMS` (461).
  - Store the `username` and `realname` in the Client object.
  - Set `has_user = true`.

**ASCII Diagram:**

```
  USER Command:

  USER  alice  0  *  :Alice Smith
   │      │    │  │       │
   │      │    │  │       └── Real Name (prefixed by colon if containing spaces)
   │      │    └──┴────────── Unused parameters (traditionally hostname/servername)
   │      └────────────────── Username
   └───────────────────────── Command
```

**Common mistakes:**

- Allowing a client to change their username after they are registered. The standard protocol prohibits this and returns `ERR_ALREADYREGISTERED` (462).
- Hardcoding the username or ignoring the parameters sent by the client.

### 5. Registration Completion and the Welcome Sequence

**What it is:** The transition when all three registration requirements (`has_pass`, `has_nick`, and `has_user`) become `true`. The server marks the client as registered and sends the numeric welcome replies.

**Why it exists:** It signals to the client that registration was successful and that it can now send regular IRC commands.

**Relation to ft_irc:**

- MR-27: Must be able to authenticate.
- MR-25: Reference client connects without errors.

**Classification:** Mandatory Requirement

**The Welcome Replies (001–004):**

When registration completes, the server must send:

- `001` (RPL_WELCOME): Welcome to the network.
- `002` (RPL_YOURHOST): Server host information.
- `003` (RPL_CREATED): Server creation date.
- `004` (RPL_MYINFO): Server name, version, and supported user/channel modes.

**ASCII Diagram:**

```
  Registration completion flow (e.g., USER arrives last):

  Client                                                  Server
    │                                                       │
    │────── USER alice 0 * :Alice Smith ───────────────────►│
    │                                                       │ Set has_user = true
    │                                                       │ State check: pass && nick && user?
    │                                                       │ → Yes! set is_registered = true
    │                                                       │
    │◄───── 001 (RPL_WELCOME) ":Welcome to IRC..." ─────────│ Send welcome sequence
    │◄───── 002 (RPL_YOURHOST) ":Your host is..." ──────────│
    │◄───── 003 (RPL_CREATED) ":This server was..." ────────│
    │◄───── 004 (RPL_MYINFO) ":<servername> <ver>..." ──────│
```

**Common mistakes:**

- Sending welcome messages too early (e.g., right after `NICK` before `USER` is received).
- Forgetting to set `is_registered = true`, which block subsequent commands.
- Sending incorrect parameters in numeric replies 001–004, causing reference clients to hang or disconnect.

```markdown
# Concept

Nickname Collision and Uniqueness

# Purpose

The NICK command changes or sets a user's nickname. Since nicknames are unique IDs, the server must prevent two clients from sharing the same nickname.

# Relation to ft_irc

MR-28 requires setting a nickname. MR-19 requires multiple simultaneous clients. Checking nickname uniqueness across all connected clients is required to avoid routing confusion.

Classification: Mandatory Requirement

# Related MR IDs

- MR-19: Multiple clients simultaneously
- MR-28: Set a nickname

# Registration State

- Client state before: `has_nick = false` (or old nickname if already registered).
- Client sends `NICK alice`
- Server check: Is "alice" already assigned to another client?
  - Yes: Return `433` (ERR_NICKNAMEINUSE) to the sending client. Client's state remains unchanged.
```
