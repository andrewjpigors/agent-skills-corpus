# Vibe Learning — 从项目仓库中提炼真正的开发能力

## 目标

将用户已有的项目代码仓库（架构设计 → 代码实现 → 排错修复 → 部署配置）转化为**个人可内化的知识**，解决 Vibe Coding 时代"离开 Agent 就不会写代码"的核心痛点。

具体目标：

1. **复盘**：从仓库代码、提交历史、配置文件中提炼关键决策、排错思路、架构选型等有价值信息
2. **出题**：生成 10 类面试场景题，帮助用户在面试中能独立回答
3. **沉淀**：将知识结构化存储，形成持续增长的专属题库与避坑清单

## 触发条件

当用户出现以下意图时激活本 Skill：

- 想复盘一个已有项目仓库
- 想从项目代码中生成面试题
- 想整理避坑清单或知识库
- 提到"项目复盘"、"代码复盘"、"面试准备"、"知识沉淀"、"这个仓库做了什么"等关键词
- 提供了一个项目仓库路径（本地路径或 Git URL），希望基于该仓库进行复盘
- 提供了项目名称并请求分析其架构和代码

## 用户画像与冷启动

### 启动门控：画像检查（每次激活必执行）

**每次本 Skill 被激活时，必须执行以下检查流程，不得跳过：**

```
1. 检查 knowledge/user-profile.md 是否存在
2. 如果不存在 → 进入「首次画像采集」流程（见下方）
3. 如果存在 → 读取画像，跳过采集，直接进入工作流
4. 如果用户主动要求修改画像 → 进入「画像更新」流程，覆盖旧画像
```

> **强制门控**：在画像文件不存在且用户未完成画像采集之前，不得进入模式一/二/三的任何流程。这是硬性前置条件，不是"建议"。

### 首次画像采集

当 `knowledge/user-profile.md` 不存在时，必须向用户采集以下 3 项信息。**逐项提问，等用户回答后再问下一项**，不要一次性列出所有问题：

**第 1 项 — 准备阶段**（单选，必填）：

> "你目前处于哪个准备阶段？
> - A. 基础积累（刚开始系统学习，需要打地基）
> - B. 能力提升（有基础，想提升到面试-ready）
> - C. 查漏补缺（经验丰富，针对薄弱点突破）"

**第 2 项 — 主要技术栈**（自由填写，必填）：

> "你的主要技术栈是什么？（如 Python/Django/React/K8s，多个用逗号分隔）"

**第 3 项 — 学习目标**（单选，必填）：

> "这次主要是为了什么？
> - A. 面试准备
> - B. 技术能力提升
> - C. 项目复盘沉淀"

3 项全部采集完成后，**立即写入** `knowledge/user-profile.md`（文件格式见下方），并向用户确认：

> "画像已保存。后续每次使用将自动加载，无需重复填写。如需修改，随时说'更新画像'。"

### 用户画像文件（knowledge/user-profile.md）

画像必须持久化存储到本地知识库目录，格式如下：

```markdown
# 用户画像

> 创建日期：{YYYY-MM-DD}
> 最后更新：{YYYY-MM-DD}

## 自评信息

- **准备阶段**：{基础积累 / 能力提升 / 查漏补缺}
- **主要技术栈**：{用户填写的技术栈}
- **学习目标**：{面试准备 / 技术能力提升 / 项目复盘沉淀}

## 难度分布（根据准备阶段自动生成）

- 基础题：{X}%
- 进阶题：{Y}%
- 高级题：{Z}%

## 复盘历史

- 总复盘次数：{N}
- 已复盘项目：{项目1}, {项目2}, ...
- 最后复盘日期：{YYYY-MM-DD}

## 备注

{用户的特殊偏好或补充信息，如"重点关注分布式系统""不想生成基础题"等}
```

> **存储位置**：`knowledge/user-profile.md`。与其他知识库文件同级目录。该文件是 Skill 运行的前置依赖——没有它，无法确定难度分布和输出侧重。

**难度自适应的具体规则**（根据画像中的"准备阶段"自动应用）：

| 准备阶段 | 基础 | 进阶 | 高级 | 说明 |
|----------|------|------|------|------|
| 基础积累 | 35% | 50% | 15% | 进阶为主，面试里没人因为基础答得好就让过 |
| 能力提升 | 15% | 55% | 30% | 进阶是主战场，基础用于快速自检，高级用于拔高 |
| 查漏补缺 | 10% | 45% | 45% | 进阶兜底 + 高级看天花板，基础仅做扫盲确认 |

### 冷启动：没有可复盘的仓库怎么办？

如果用户尚无可复盘的项目仓库，不硬凑知识点。Skill 会提供以下最小启动路径：

1. **确认仓库来源**：你可以提供一个本地项目路径（如 `~/projects/my-app`）或一个 Git 仓库地址（如 `https://github.com/user/repo`）。任何你自己参与开发的项目都可以。
2. **接受最小项目**：即使是一个只有几百行代码的小项目，只要有真实的技术决策（选型、排错、架构设计），就值得复盘。
3. **备选：手动构造**：如果你有纯手工完成但尚未版本管理的项目，可以直接提供项目目录路径，Skill 会扫描代码结构进行分析。
4. **设定首次复盘时间**：在项目完成一个功能模块（指包含至少一个完整业务逻辑的模块，如用户认证、API 接口、数据模型）后，立即回来复盘。此时上下文最清晰。

> **原则**：宁缺毋滥。一条从真实项目代码中提炼的知识点，胜过十条臆造的假问题。

## 核心原则

**不是记录代码写了什么，而是理解背后的"为什么"。**

- 追问每个架构决策的**理由**，而不只看代码结果
- 将具体实现**泛化**为可迁移的方法论
- 用**场景题**的形式组织知识，模拟真实面试环境
- 强制用户**用自己的话复述**，确保真正内化而非"看懂了"
- 代码是结果，决策过程才是知识——仓库不会说话，但代码结构、提交历史和配置文件会留下决策的痕迹

## 完整工作流

### 第零步：确定仓库来源与复盘范围

首先与用户确认两件事：

**仓库来源**（支持两种模式）：

| 模式 | 说明 | 适用场景 |
|------|------|----------|
| 本地仓库模式 | 用户提供本地项目路径（如 `~/projects/my-app`），Skill 直接读取代码文件、目录结构、Git 历史 | 最常用，信息最完整 |
| 远程仓库模式 | 用户提供 Git URL，Skill 先 `git clone` 到临时目录再分析 | 分析他人项目、开源项目学习 |

**复盘范围**（必须选择，避免上下文过长导致质量下降）：

按项目维度分段复盘，每次只处理一个维度。不得跨维度同时复盘：

- 架构与目录结构：整体架构设计、模块划分、设计模式
- 核心代码实现：关键业务逻辑、数据模型、API 设计、状态管理
- 排错与修复痕迹：Git 历史中的 bugfix commit、错误处理模式、异常处理策略
- 部署与运维配置：Dockerfile、CI/CD 配置、环境管理、监控配置
- 测试与质量：测试策略、测试覆盖、代码质量工具配置
- 全量复盘（仅在项目较小时使用，建议 < 50 个源文件）

> **防御机制 — 范围限制**：如果项目源文件超过 200 个，必须主动建议分段处理。每段独立生成输出，避免信息过载导致提炼质量下降。

## 仓库分层递进拆解法

**核心理念**：仓库拆解不是扁平地"扫一遍文件"，而是从宏观到微观的四层递进分析。每一层的产出决定下一层的分析重点——L0 画像决定 L1 看什么架构，L1 骨架决定 L2 深潜哪些模块，L2 模块分析决定 L3 精读哪些代码。

> **强制要求**：在进入模式一（信号提取）之前，必须完成 L0 和 L1 的分析。这两层的产出是后续所有提取工作的地基。L2 必须执行，深潜模块数量上限为 5 个（按优先级 P0→P3 取前 5）。L3 精读队列上限为 10 段代码，超出部分记入备选列表，不在本轮分析。

### L0：仓库画像（5 分钟搞清"这是什么项目"）

**目标**：建立项目全景认知，输出一份"仓库画像卡"，后续所有分析都基于这张卡。

**分析清单**：

| 分析项 | 怎么做 | 产出 |
|--------|--------|------|
| 技术栈指纹 | 解析所有 manifest 文件（`package.json` / `requirements.txt` / `go.mod` / `Cargo.toml` / `pom.xml` 等），提取核心依赖 | 语言 + 框架 + 数据库 + 中间件的完整清单 |
| 项目分类 | 根据目录结构和入口文件判断类型 | Web 应用 / API 服务 / CLI 工具 / 库 / Monorepo / 数据管线 / 其他 |
| 规模评估 | 统计源文件数、模块数、Git 提交数 | 决定是否需要分段复盘 |
| 成熟度信号 | 检查 CI/CD 配置、测试目录、文档完整度、Git 历史长度 | 判断项目阶段（原型 / 成长期 / 成熟期 / 维护期） |
| 外部依赖拓扑 | 识别项目依赖了哪些外部服务（DB / 缓存 / MQ / 第三方 API） | 理解系统的集成边界 |

**仓库画像卡输出格式**：

```
📋 仓库画像卡
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
项目名称：{名称}
项目类型：{Web/API/CLI/Library/Monorepo/...}
技术栈：{语言 + 框架 + 数据库 + 中间件}
规模：{N} 个源文件 | {M} 个模块 | {K} 个 Git 提交
成熟度：{原型/成长期/成熟期/维护期}
外部依赖：{PostgreSQL / Redis / RabbitMQ / Stripe API / ...}
入口文件：{路径}
复盘建议：{可全量复盘 / 建议分 N 段 / 推荐先复盘 XX 维度}
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

> **L0 → L1 传递**：画像卡中的"项目类型"决定 L1 的架构模式识别方向（Web 应用看路由分层，Monorepo 看子包关系，库看公开 API 设计）。"成熟度信号"决定 Git 历史分析的深度——原型项目 Git 历史短，重点看代码本身；成熟项目 Git 历史丰富，重点看演进轨迹。

### L1：架构骨架（理解高层结构和组件连接方式）

**目标**：识别项目的架构模式和组件间的连接关系，画出"架构骨架图"。

**分析清单**：

| 分析项 | 怎么做 | 产出 |
|--------|--------|------|
| 目录拓扑 | 读取顶层目录结构，识别分层模式 | 架构模式判断（MVC / Clean Architecture / Hexagonal / 微服务 / 插件式 / ...） |
| 依赖图 | 分析模块间的 import / require 关系 | 模块依赖图，标记是否有循环依赖 |
| 入口链追踪 | 从入口文件出发，追踪初始化调用链 | 理解应用启动流程和核心组件装配方式 |
| 接口边界 | 识别内部模块接口 vs 外部暴露 API | 理解系统的封装边界和对外契约 |
| 配置架构 | 分析配置文件的组织方式（环境变量 / config 文件 / .env） | 理解环境管理策略和配置分层 |

**架构骨架图输出格式**：

```
🏗️ 架构骨架图
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
架构模式：{MVC / Clean / Hexagonal / 微服务 / ...}

  ┌──────────┐    ┌──────────┐    ┌──────────┐
  │ {模块A}  │───▶│ {模块B}  │───▶│ {模块C}  │
  │ 职责:... │    │ 职责:... │    │ 职责:... │
  └──────────┘    └──────────┘    └──────────┘
                        │
                        ▼
                  ┌──────────┐
                  │ {外部依赖}│
                  └──────────┘

关键依赖路径：{入口} → {核心模块} → {数据层}
循环依赖：无 / 有（{模块A} ↔ {模块B}）
架构亮点：{值得深挖的设计决策}
架构疑点：{看起来不合理或值得追问的地方}
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

> **L1 → L2 传递**：骨架图中的"架构亮点"和"架构疑点"直接决定 L2 深潜哪些模块。依赖图中的核心节点（被依赖最多的模块）优先深潜。循环依赖或异常依赖模式标记为必分析项。

### L2：模块深潜（聚焦高价值模块的实现决策）

**目标**：对 L1 识别出的核心模块进行深度分析，提取实现层面的技术决策。

**模块选择优先级**（根据知识密度从高到低排序）：

| 优先级 | 模块类型 | 为什么值得深潜 |
|--------|----------|----------------|
| 🔴 P0 | 核心业务逻辑模块 | 包含最重要的领域知识和业务规则 |
| 🔴 P0 | 数据模型 / Schema 定义 | 反映了对问题域的建模思路 |
| 🟠 P1 | 集成点（DB / 缓存 / MQ / 第三方 API） | 包含选型决策和容错策略 |
| 🟠 P1 | 自定义抽象层（基类 / 装饰器 / 中间件） | 体现了设计模式的应用决策 |
| 🟡 P2 | 安全相关模块（认证 / 授权 / 加密） | 包含安全权衡决策 |
| 🟡 P2 | 错误处理基础设施 | 反映了容错策略和异常设计 |
| 🟢 P3 | API handler / 控制器 | 通常不深潜，仅当包含非标准逻辑时分析（如自定义中间件链、复杂权限校验、非 CRUD 操作） |
| ⬜ 跳过 | 工具函数 / 类型定义 / 配置常量 | 不深潜，仅当包含非标准算法或技巧时例外 |

**每个目标模块的分析清单**：

| 分析项 | 关注什么 | 产出 |
|--------|----------|------|
| 模块职责 | 这个模块解决什么问题？它的边界在哪？ | 一句话模块职责描述 |
| 数据模型 | 数据如何组织？关系是什么？索引策略？ | 数据模型摘要 |
| 核心逻辑 | 最复杂/最重要的业务规则怎么实现的？ | 关键逻辑路径 |
| 集成方式 | 怎么和外部系统交互？同步/异步？容错策略？ | 集成模式分析 |
| 错误处理 | 异常怎么传播？有哪些防御性措施？ | 错误处理策略 |

> **L2 → L3 传递**：每个深潜模块中标记为"关键逻辑路径"的代码段，进入 L3 精读队列。模块分析中发现的异常模式（奇怪的 workaround、TODO/FIXME 密集区、过度复杂的函数）也进入 L3。

---

### L3：代码微观（从具体代码模式提取洞察）

**目标**：对 L2 标记的关键代码段进行逐行精读，提取微观层面的技术洞察。

**精读队列来源**：
- L2 标记的"关键逻辑路径"代码段
- L2 发现的异常模式代码段
- Git 历史中 `fix:` 提交改动的代码段
- L1 骨架图中标记的"架构亮点"对应代码

**微观分析维度**：

| 维度 | 识别什么 | 信号特征 |
|------|----------|----------|
| 设计模式 | 使用了哪些设计模式？用得是否恰当？ | 工厂/策略/观察者/装饰器等模式的代码结构 |
| 性能模式 | 有哪些性能优化手段？ | 缓存策略、查询优化、懒加载、批处理、并发控制 |
| 安全模式 | 有哪些安全措施？ | 输入校验、参数化查询、认证授权检查、敏感数据处理 |
| 代码质量信号 | 哪里可能有技术债？ | 高复杂度函数、TODO/FIXME/HACK 注释、重复代码、过长函数 |
| 防御性编程 | 对哪些边界做了防护？ | 空值检查、类型断言、超时控制、重试逻辑、熔断 |

### 决策信号识别框架

**目标**：在 L1-L3 的分析过程中，明确知道在找什么样的"信号"，以及找到后怎么判定它的知识价值。

**六类决策信号**：

| 信号类型 | 在代码里长什么样 | 检测方法 | 知识价值 |
|----------|-----------------|----------|----------|
| **选型决策** | import 了特定库、Dockerfile 的 FROM、DB 引擎选择、序列化格式选择 | 检查配置文件、import 语句、Dockerfile、build 脚本 | 高 — 理解 trade-off |
| **架构决策** | 分层方式、模块边界划分、通信模式（同步/异步/事件驱动） | L1 架构骨架图分析 | 高 — 可迁移设计思维 |
| **权衡决策** | 性能 vs 可读性、一致性 vs 可用性、速度 vs 安全、简洁 vs 灵活 | 代码注释、配置取舍、防御性编程模式 | 极高 — 决策背后的"为什么" |
| **排错决策** | bugfix 提交、新增错误处理、防御性代码、workaround | Git `fix:` 提交 + `git show`、try/catch 块、校验逻辑 | 高 — 真实踩坑经验 |
| **演进决策** | 重构、模式迁移、架构变更、技术栈升级 | Git `refactor:` 提交、废弃代码标记、迁移脚本 | 中 — 理解成长过程 |
| **约束决策** | 外部约束的 workaround、兼容性 hack、版本特判逻辑 | TODO/FIXME 注释、条件编译、版本判断分支 | 中 — 实际问题解决 |

**信号强度判定**：发现一个信号后，按以下标准判定是否值得提取为知识点：

| 强度 | 判定条件 | 处理方式 |
|------|----------|----------|
| 💎 强信号 | 有明确的代码证据 + 能推断出决策理由 + 可泛化为方法论 | 提取为完整知识点 |
| 🔶 中信号 | 有代码证据但决策理由需推断，或可迁移性不确定 | 提取并标注 `[待确认]` |
| ⚪ 弱信号 | 代码证据不充分，或可能是巧合而非刻意决策 | 记录但不提取，放入备选列表 |

### 跨层关联追踪

**核心规则**：一个知识点的价值取决于它能串联多少层。孤立的发现价值有限，跨层关联的发现才是金矿。

**关联追踪规则**：

| 起点 | 追踪方向 | 产出 |
|------|----------|------|
| 发现一个 `fix:` 提交（L3） | ↑ 追溯它改了哪个模块（L2）的哪段代码 → ↑ 该模块在架构中扮演什么角色（L1） | 还原"架构层面的问题 → 模块层面的表现 → 代码层面的修复"完整链路 |
| 发现一个设计模式（L3） | ↑ 追溯它服务于哪个模块职责（L2）→ ↑ 体现了什么架构选型（L1） | 理解"为什么这里需要这个模式"而非只是"用了什么模式" |
| 发现一个架构亮点（L1） | ↓ 追踪到具体模块（L2）→ ↓ 追踪到具体代码实现（L3） | 把抽象的架构优点落地为可学习的代码实践 |
| 发现一个选型决策（L0/L1） | ↓ 追踪到它在代码中如何被使用（L2/L3）→ 横向对比 Git 历史中是否有替换痕迹 | 理解"选了什么 → 怎么用的 → 后来有没有后悔" |

**关联记录格式**（每个提取的知识点必须填写）：

```
【跨层关联】
L0 画像层：{这个决策与项目的技术栈/类型有什么关系？}
L1 架构层：{这个决策在架构骨架中处于什么位置？}
L2 模块层：{这个决策在哪个模块中体现？该模块的职责是什么？}
L3 代码层：{具体在哪个文件、哪段代码？}
```

## Git 历史分析策略

Git 提交历史是还原"决策过程"的宝贵资源，是 L3 微观分析的重要数据源。

**提交类型分析矩阵**：

| 提交类型 | 分析价值 | 提取方法 | 关联层 |
|----------|----------|----------|--------|
| `feat:` 新功能 | 架构演进、功能拆分方式 | `git log --oneline --grep="feat"` | L1→L2 |
| `fix:` 修复 | 排错过程、常见坑点 | `git log --oneline --grep="fix"` + `git show <commit>` | L3→L2→L1 |
| `refactor:` 重构 | 设计演进、代码质量改善策略 | `git log --oneline --grep="refactor"` | L2→L1 |
| `docs:` 文档 | 决策记录、设计说明 | 检查 `docs/` 目录和 README 更新历史 | L0→L1 |
| Merge/Rebase | 协作模式、分支策略 | `git log --merges --oneline` | L0 |

**`fix:` 提交深挖流程**（排错知识的金矿）：

```
1. git log --oneline --grep="fix"  → 获取所有修复提交列表
2. 按改动行数降序排序，取前 5 个提交深挖（超出部分记入备选列表）
3. 对每个选中的 fix 提交：
   a. git show <commit-hash>       → 查看具体改了什么
   b. 定位改动所在模块（L2关联）
   c. 分析：什么问题 → 怎么发现 → 怎么修复 → 怎么预防
   d. 追溯：这个 bug 反映了架构层面的什么问题？（L1关联）
4. 多个相关 fix 串连分析 → 识别系统性问题 vs 偶发问题
```

> **重点**：每个 bugfix 都代表一个真实踩过的坑。但单个 fix 只能告诉你"改了什么"，必须通过跨层关联追踪才能理解"为什么会出现这个问题"。

## 知识密度过滤

**目标**：在 L2-L3 分析中，快速判断哪些代码值得精读、哪些可以跳过，避免在低价值代码上浪费时间。

| 密度 | 代码类型 | 分析力度 | 判定依据 |
|------|----------|----------|----------|
| 🔴 高密度 | 核心业务逻辑、数据模型定义、集成点、自定义抽象、安全关键代码 | 逐行精读 | 包含领域知识或关键技术决策 |
| 🟡 中密度 | API handler、中间件、配置管理、错误处理基础设施 | 扫读 + 抽查 | 可能有设计模式或容错策略 |
| 🟢 低密度 | CRUD 样板、工具函数、类型定义、常量定义 | 跳过或快扫 | 知识密度低，除非有特殊技巧 |

**过滤规则**（以下内容直接跳过，不分析）：

- 模板生成代码（如 `create-react-app` / `django-admin startproject` 生成的样板文件）→ 只保留用户自定义的部分
- 纯依赖更新（`bump version` 类提交）→ 不含技术决策
- 自动生成的文件（如 `package-lock.json` / `go.sum` / `*.min.js`）→ 不分析
- 第三方库代码（`vendor/` / `node_modules/` / `third_party/`）→ 不分析
- 注释不足且逻辑简单的 CRUD 代码 → 仅当包含非标准查询优化、事务控制或权限逻辑时才分析

### 模式一：信号提取 — 从仓库代码中提炼关键信息

**目标**：基于分层递进拆解法（L0-L3）的分析结果，将发现转化为结构化的知识信号。

**提取维度**（五个方向，对应不同层级的分析产出）：

| 维度 | 提取什么 | 主要来源层级 | 信号特征 |
|------|----------|-------------|----------|
| 架构决策 | 技术选型、项目结构、设计模式、权衡取舍 | L0 + L1 | 画像卡中的选型、骨架图中的分层模式、依赖图中的拓扑 |
| 代码实现 | 关键模式、API 设计、状态管理、数据建模 | L2 + L3 | 模块深潜的"核心逻辑"、微观分析的"设计模式"维度 |
| 排错过程 | 错误类型、诊断路径、修复策略、预防手段 | L3 + Git 历史 | `fix:` 提交分析、错误处理策略、防御性编程模式 |
| 部署运维 | 环境配置、CI/CD、容器化、监控 | L0 + 配置文件 | Dockerfile、CI/CD 配置、部署脚本、环境变量管理 |
| 方法论 | 问题拆解方式、迭代策略、代码组织思想 | L1 + Git 历史 | 目录拆分方式、Git 提交节奏、渐进式重构痕迹 |

**对每个知识点，记录以下结构**：

```
【上下文】项目是什么？这个代码/配置在什么模块中？
【问题/决策】需要解决什么问题？做了什么技术决策？
【代码证据】具体在哪个文件、哪段代码体现了这个决策？（标注文件路径和关键代码）
【底层原理】为什么这个做法有效？背后的技术原理是什么？
【替代方案】还能怎么做？为什么选了当前方案？（从代码结构推断，或从 Git 历史中的废弃分支/重构痕迹发现）
【可迁移教训】换一个项目，这个经验还适用吗？适用条件是什么？
【跨层关联】L0→L1→L2→L3 的关联路径（见跨层关联追踪规则）
【信号强度】💎强信号 / 🔶中信号 / ⚪弱信号（见决策信号识别框架）
```

**用户确认环节**：

对于每个提取的知识点，如果技术决策的理由是**从代码结构推断**出来的（而非文档或注释中明确说明的），必须标注 `[待确认]` 并向用户提问：

> "我注意到这个项目用了 Redis 做缓存（`src/cache/redis_client.py`）。代码中没有注释说明原因，我推断是因为需要高频读取且数据结构简单。**[待确认]** 这个推断对吗？你当时是怎么考虑的？"

### 模式二：面试题生成 — 将知识转化为面试场景题

**目标**：基于模式一提取的知识点，生成 10 类面试题。每类生成数量规则：知识点 ≥ 3 个时每类 1 道，知识点 ≥ 8 个时每类 2 道，知识点 ≥ 15 个时每类 3 道。

**十类面试题**：

| 编号 | 类型 | 说明 | 示例 |
|------|------|------|------|
| 1 | 场景设计题 | 给定业务场景，要求设计技术方案 | "你的项目需要支持实时协作编辑，如何设计冲突解决机制？" |
| 2 | Bug 排查题 | 给定错误现象，要求分析根因并给出排错路径 | "线上服务返回 502，但容器日志显示正常，你从哪几个方向排查？" |
| 3 | 深挖原理题 | 追问技术选型的底层原因和设计思想 | "为什么选 PostgreSQL 而不是 MongoDB？它的 MVCC 机制是怎么工作的？" |
| 4 | 代码审查题 | 给出仓库中的一段代码，要求发现问题并提出优化 | "这段并发代码有竞态条件，你能指出来并修复吗？" |
| 5 | 项目表达题 | 要求清晰表达项目的背景、难点和成果 | "请用 3 分钟介绍你的项目，说清楚架构亮点和你解决的最难的问题" |
| 6 | 系统设计题 | 在现有项目基础上做规模扩展设计 | "如果用户量从 100 涨到 10 万，你的数据库架构需要怎么改？" |
| 7 | 运维排障题 | 模拟线上故障场景，考察排查能力 | "凌晨 3 点收到告警，服务 OOM 了，你的排查步骤是什么？" |
| 8 | 方案对比题 | 对比两种技术方案的优劣和适用场景 | "JWT vs Session，你在项目中选了哪个？为什么？什么情况下该选另一个？" |
| 9 | 复盘反思题 | 引导回顾整个项目，提炼改进方向 | "如果重新做这个项目，你会改变哪三个决定？为什么？" |
| 10 | 测试质量题 | 针对核心功能设计测试用例 | "你的用户认证模块，请设计 5 个关键测试用例，覆盖正常流程和边界情况" |

> **代码审查题特殊说明**：此题型直接从仓库中选取真实代码片段作为审查对象，是本 Skill 最具特色的题型。选取原则：选择有改进空间但非致命错误的代码，聚焦可优化的设计模式、性能问题或可维护性问题。

**每道题的输出格式**：

```
### [类型] 题目名称

**难度**：基础 / 进阶 / 高级
**标签**：#架构 #调试 #部署 ...
**来源**：基于 [项目名] 的 [模块/文件路径] 提取

#### 场景描述
（用 2-3 句话描述具体场景，让问题有代入感）

#### 问题
（明确的面试问题）

#### 参考思路
（不是标准答案，而是"应该怎么思考这个问题"的步骤）
1. 首先分析...
2. 然后考虑...
3. 最后...

#### 参考答案要点
（关键知识点，面试时应该提到的核心内容）

#### 反事实推理
（如果条件变化，答案会怎样？）
- 如果把 X 换成 Y，方案需要怎么调整？
- 如果规模扩大 100 倍，瓶颈会出现在哪里？

#### 深挖追问
（面试官可能的追问，帮助用户准备更深层的回答）
- 你提到用 X，那 X 的底层原理是什么？
- 这个方案有什么缺点？你怎么缓解的？
```

**反事实推理 — 强制要求**：

每道题**必须**包含"反事实推理"部分。这是区分"背答案"和"真理解"的关键。通过改变约束条件（规模、技术栈、时间、团队规模等），考察用户是否真正理解了方案的本质。

**用户复述环节 — 强制要求**：

每道题生成后，必须要求用户：

> "请你现在用自己的话，不看参考答案，口述一遍回答思路。如果卡住了，标记卡住的位置，这说明那个点你还没有真正掌握。"

**掌握度自评（三级制）**：用户复述后需给出自评分数：

| 评分 | 含义 | 下次复习间隔 |
|------|------|-------------|
| 0 — 完全卡住 | 无法回忆核心思路，需要重新学习 | 当天内复习 |
| 1 — 部分回忆 | 能说对大致方向，但关键细节遗漏或混淆 | 1 天后复习 |
| 2 — 流畅复述 | 能用自己的话完整讲清思路和原理 | 3 天后复习 |

**卡住位置诊断**：当用户标记"卡住了"时，要求进一步标注卡住的**性质**：
- `[概念不清]`：不知道这个概念是什么，需要从定义开始补
- `[逻辑链断裂]`：知道各个概念，但说不清它们之间的因果关系
- `[细节遗忘]`：理解整体思路，但忘了具体 API/配置/参数名

诊断结果用于后续针对性复习——"概念不清"生成前置知识学习建议，"细节遗忘"只做快速回顾，"逻辑链断裂"生成该逻辑链的专项练习。

**渐进式提醒机制**：

| 连续跳过数 | 行为 |
|-----------|------|
| 第 1-2 次 | 正常标记 `[未复述]`，继续下一题 |
| 第 3-5 次 | 主动提醒："你已经跳过 3 道题了，要不要回头挑一道最简单的试试？只需要 2 分钟。" |
| 第 6-9 次 | 加强提醒："连续跳过 6 道题——这些题是基于你的项目生成的，不练的话和你的项目经验就脱节了。建议至少复述 1 道再继续。" |
| 达到 10 次 | 硬性暂停："本会话已跳过 10 道题。剩下的题目将保存到知识库中标记为 `[未复述]`，建议你现在选一道复述，或结束本次复盘。" |

如果用户拒绝复述或表示"先跳过"，将该题标记为 `[未复述]`，但不记录为已完成。

> **防御机制 — 复述强制**：没有经过用户复述的知识点，在最终知识库中标记为"未内化"，在复习提醒中优先出现。超过 10 道未复述题目后，必须复述或结束当前复盘会话。

### 复习调度引擎（间隔复习系统）

基于简化 SM-2 算法，为每条面试题和知识条目自动计算下次复习时间，确保知识从"短时记忆"转化为"长时记忆"。

**算法规则**：

| 复述评分 | 间隔变化 | 说明 |
|----------|----------|------|
| 0 — 完全卡住 | 重置为 1 天 | 需要重新建立记忆，间隔从头开始 |
| 1 — 部分回忆 | 间隔 × 0.5（不低于 1 天） | 记忆不牢固，缩短复习间隔 |
| 2 — 流畅复述 | 间隔 × 2（上限 120 天） | 记忆稳固，延长复习间隔 |

**间隔序列**：1天 → 3天 → 7天 → 14天 → 30天 → 60天 → 120天

**复习调度表（review-schedule.md）格式**：

```markdown
# 复习调度表

> 最后更新：{日期}
> 当前待复习：{N} 项
> 本周已完成复习：{M} 项

## 🔴 今日到期（{n} 项）
| 编号 | 题目/条目 | 类型 | 上次评分 | 当前间隔 | 来源项目 |
|------|----------|------|----------|----------|----------|
| Q-003 | Docker 容器启动排查 | Bug排查 | 1 | 3天 | Flask应用容器化 |

## 🟡 本周内到期（{n} 项）
```

### 知识衰减与归档机制

知识条目有生命周期。随着技术栈升级和经验增长，部分条目会过时。必须定期清理，避免知识库变成"过期信息的垃圾场"。

**条目元数据**（每条知识条目必须记录）：

```markdown
- **创建日期**：2026-06-24
- **来源仓库**：{仓库名/路径}
- **技术栈版本**：Python 3.11 / React 18 / Docker 24
- **归档状态**：活跃 / 已过时 / 已替代 / 仍有效
- **最后审查日期**：未审查 / 2026-09-24
```

**审查触发条件**：

| 条件 | 行为 |
|------|------|
| 条目创建超过 90 天 | 提醒用户审查是否仍有效 |
| 条目创建超过 180 天 | 加强提醒，建议强制审查 |
| 条目创建超过 365 天 | 自动标记为 `[待年审]`，需用户在下次会话中逐条确认 |
| 源仓库有重大更新（新增 >20 次提交或架构级重构） | 提醒用户重新扫描相关模块，检查条目是否需要更新 |
| 用户主动请求 | 立即启动指定项目/时间段条目的审查 |

**归档标记**：

| 标记 | 含义 | 后续处理 |
|------|------|----------|
| `[活跃]` | 仍在学习/复习中 | 正常参与复习调度 |
| `[已过时]` | 技术已过时，不再适用 | 移入 `archive/`，不参与复习 |
| `[已替代]` | 被更好的方案取代 | 移入 `archive/`，保留作为对比参考 |
| `[仍有效]` | 超过 90 天但依然正确 | 更新审查日期，继续活跃 |

**归档文件结构**：

```
knowledge/archive/
├── archived-qa.md           # 已过时的面试题
├── archived-pitfalls.md     # 已过时的避坑条目（技术已不存在等）
└── archive-log.md           # 归档记录（时间、原因、操作人）
```

**季度审查流程**：

每季度首次使用 Skill 时触发：

1. 列出所有超过 90 天未审查的活跃条目
2. 逐条询问：`[仍有效]` / `[已过时]` / `[已替代]` / `[稍后审查]`
3. 将标记为过时/已替代的条目移入 `archive/`
4. 更新 `knowledge-index.md` 中的统计数字

## 防御机制汇总

本 Skill 内置以下防御机制，确保输出质量：

| 机制 | 触发条件 | 行为 |
|------|----------|------|
| **用户确认** | AI 从代码结构推断的决策理由 | 标注 `[待确认]`，反问用户确认 |
| **范围限制** | 项目源文件超过 200 个 | 建议分段复盘，每次只处理一个维度 |
| **分层强制** | 进入模式一之前 | 必须先完成 L0 画像 + L1 骨架分析，不得跳过直接进 L3 |
| **复述强制** | 每道题生成后 | 要求用户口述回答，自评掌握度（0/1/2），未复述标记为"未内化" |
| **渐进式提醒** | 连续跳过 ≥3 道复述题 | 主动降速提醒，超过 10 道硬性暂停 |
| **信号过滤** | 提取知识点时 | 丢弃模板代码、自动生成文件、第三方库代码、纯样板逻辑 |
| **信号强度判定** | 提取每个知识点时 | 必须标注信号强度（💎强/🔶中/⚪弱），弱信号不提取为正式知识点 |
| **跨层关联强制** | 每个知识点必须填写 | 必须记录 L0→L1→L2→L3 的关联路径，孤立发现不得作为正式知识点 |
| **深度标注** | 知识点深度不足时 | 标注 `[待深挖]`，提醒用户进一步学习 |
| **去重合并** | 增量更新知识库时 | 检测相似条目，合并而非重复添加 |
| **过期审查** | 知识条目超过 90 天 | 提醒用户审查有效性，标记为过时/替代/仍有效，过时条目移入 archive/ |
| **冷启动引导** | 用户首次使用且无仓库 | 提供最小启动步骤，不硬凑知识点 |

## 边界情况处理

**项目过小**：如果项目只有少量文件（少于 5 个源文件），L0 画像即可快速完成，L1-L3 合并为一次分析（跳过分层传递，直接从 L0 画像跳到 L3 代码精读）。聚焦提取最核心的架构决策和实现模式，诚实告知"本项目知识点有限"。

**项目过大**：如果项目源文件超过 200 个，必须按维度拆分复盘。L0 画像仍需完整执行（5 分钟即可完成），L1 骨架图聚焦当前复盘维度，L2 只深潜该维度相关模块。按以下固定顺序分多次复盘：架构 → 核心代码 → 排错历史 → 部署配置。

**L0 画像无法判断架构模式**：如果项目目录结构非常规整或过于混乱，L1 无法明确识别架构模式，诚实标注"架构模式不明确"，列出观察到的结构特征请用户确认。不要强行套用一个不匹配的架构标签。

**无明显学习点**：如果 L0-L1 分析后发现项目只是脚手架模板（如 `create-react-app` 初始状态），没有自定义的业务逻辑和技术决策，诚实告知用户"本项目学习点有限——大多是脚手架生成的模板代码"，建议用户选择有实际开发内容的项目进行复盘。不要硬凑知识点。

**无 Git 历史**：如果项目没有版本管理（没有 `.git` 目录），跳过 Git 历史分析，L3 微观分析仅依赖代码本身。主动告知用户"未检测到 Git 历史，排错维度的提取将依赖代码中的错误处理模式而非提交历史，提取效果可能受限"。

**多技术栈混合**：L0 画像时会识别出多个技术栈。按技术栈拆分为独立的知识条目，每个条目聚焦单一技术点。在索引中标注跨技术栈的关联。

**用户是初学者**：如果 L2-L3 提取的知识点超出初学者理解范围，在输出中增加"前置知识"说明，帮助用户建立学习路径。

**Monorepo / 多模块项目**：L0 画像时识别 Monorepo 结构。将每个子项目/模块视为独立的复盘对象，分别走 L1-L3 流程。在知识库索引中标注模块间的关联和共享依赖。
